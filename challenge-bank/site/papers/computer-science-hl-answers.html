1. CS-B2.3-001 16 marks

(a) Tracing the loop for readings = [70, 72, 71, 90, 89, 88, 87] with tol = 5:

| i | readings[i] | comparisons in the while | result |
|---|---|---|---|
| 0 | 70 | j = 0, loop does not run | 0 |
| 1 | 72 | $\lvert 72-70 \rvert = 2 \le 5 \rightarrow 1$ | 1 |
| 2 | 71 | $\lvert 71-72 \rvert = 1$, then $\lvert 71-70 \rvert = 1$ | 2 |
| 3 | 90 | $\lvert 90-71 \rvert = 19 > 5$ | 0 |
| 4 | 89 | $\lvert 89-90 \rvert = 1$, then $\lvert 89-71 \rvert = 18 > 5$ | 1 |
| 5 | 88 | $1$, then $2$, then $\lvert 88-71 \rvert = 17 > 5$ | 2 |
| 6 | 87 | $1$, then $2$, then $3$, then $\lvert 87-71 \rvert = 16 > 5$ | 3 |

The function returns [0, 1, 2, 0, 1, 2, 3]. (M1) for tracing the loop as a walk backwards while consecutive differences stay within the tolerance, (A1) for the correct values, (A1) for the list as a whole, including the reset to 0 at index 3 and the growing run at the end.

(b) The claim is unsound because the number of steps the inner loop performs is not a constant — it is the length of the steady run, which is a property of the *data*, not of the code. (M1) The claim assumes that consecutive readings almost always differ by more than the tolerance, so that the loop exits after one or two steps. (A1) That assumption is false for this application: heart rate sampled once a second during steady exercise changes by far less than 5 beats per minute between consecutive samples, so long runs are the normal case and the loop walks back a long way. (A1) The greatest number of steps occurs when every consecutive difference is within tolerance — a constant series, or a slow monotonic drift. For each $i$ the loop then runs all the way back to index 0, giving $0+1+2+\dots+(n-1) = \frac{n(n-1)}{2}$ steps, which is quadratic rather than linear. (A1)

(c)

def steady_runs(readings, tol=5):
    n = len(readings)
    runs = [0] * n
    for i in range(1, n):
        step = readings[i] - readings[i - 1]
        if -tol <= step <= tol:
            runs[i] = runs[i - 1] + 1
    return runs

(M1) for a single pass that keeps no inner loop. (A1) for the observation that makes it work: the steady run ending at i is either empty or it is the run ending at i - 1 extended by exactly one reading, so the answer for i can be read off the answer for i - 1. (A1) for runs[i] = runs[i - 1] + 1 and (A1) for initialising every entry to 0, which is what makes the run reset after a step larger than the tolerance. (A1) for using no library module and no abs, expressing the tolerance as the two-sided test -tol <= step <= tol.

The work done is $n-1$ comparisons and one assignment per reading, so the time is $O(n)$ and the extra memory is $O(n)$ for the output. A Java version of this paper asks for the same algorithm; the translation is a for loop over the array indices and the identical recurrence, so the language is irrelevant to the reasoning.

(d) The proposal should be rejected, for three reasons.

First, it does not change the complexity. The inner loop can still run up to 1,000 steps for every reading, so the worst case is still proportional to $1000n$; capping the loop divides the running time by a constant, and a constant factor is not a change of order. (M1) With 86,400 readings a day the uncapped worst case is $86{,}400 \times 86{,}399 / 2 = 3{,}732{,}436{,}800$ inner steps, the capped version still performs up to $86{,}400 \times 1000 = 86{,}400{,}000$, and the linear version performs 86,399. (A1)

Second, and more seriously, the cap makes the result *wrong* precisely where the app matters. A steady run of 1,500 readings would be reported as 1,000, and a run of 4,000 as 1,000; the error is silent, it is always an under-report, and it is concentrated on the longest runs — which are exactly the steady states the app exists to find. (A1)

Third, the trade is unnecessary, because part (c) already gives an exact linear algorithm. Capping the loop trades a correctness guarantee for a constant factor when a change of order was available at the same cost. (A1)

Markscheme notes

(a) Accept any trace, as a table or as prose. The essential marks are the mechanism (walk backwards while *each consecutive pair* is within tolerance) and the result. A candidate who compares every earlier reading against the current reading rather than against its own predecessor has misread the function and forfeits the trace marks — this is the single most common error.

(b) The two discriminating marks are the unstated assumption (that consecutive readings usually differ by more than the tolerance) and the worst-case count $n(n-1)/2$. A candidate who writes "it is actually O(n squared)" without naming the assumption earns one mark only. Accept a description of the worst case as "a constant series", "a steady recording" or "a slow drift"; require the recognition that the loop runs to index 0 each time.

(c) Accept any single-pass algorithm that returns the same list, including one that builds the list by appending rather than pre-allocating it. Do not award the linear mark to a candidate who keeps a nested loop, even a faster one — the question is about the order of growth. A candidate who uses abs despite the prohibition should be told the constraint was stated; the reasoning marks may still be awarded. A candidate who uses the csv-style two-pointer scan but does not derive the recurrence should be capped at two marks.

(d) The evaluation must distinguish a constant-factor improvement from a change of order. A candidate who says "1,000 is small enough" has missed that the cap silently corrupts the longest runs, and that those runs are the app's output. Award the final mark only when the answer connects the cap to a correctness loss rather than to performance alone.

2. CS-B3.2-001 16 marks

(a) For SeatPlan(20, 12) the attribute annual_fee holds 108. (A1) It is not 2160 because of the order in which the two constructors run. The first statement of SeatPlan.__init__ is super().__init__(months), and inside Plan.__init__ the assignment self.annual_fee = self.monthly_fee() * months calls self.monthly_fee(). (M1) Because monthly_fee is overridden, that call dispatches to SeatPlan.monthly_fee, which reads self.seats. At that moment the instance has only months in its attribute dictionary - the statement self.seats = seats has not run yet - so the lookup falls back to the class attribute seats = 1. The fee is therefore computed for a one-seat plan: $1 \times 9 = 9$ per month and $9 \times 12 = 108$ per year. (A1) Only after the superclass constructor returns is the instance attribute set to 20, and by then annual_fee has already been stored and is never recomputed; a later call to monthly_fee() correctly returns $20 \times 9 = 180$, so the live query and the cached value disagree.

(b) The defect is not that a constructor calls a method. It is that a constructor calls a method on an object that is only partly built, so the method can observe a field that does not exist yet. Composition removes the half-built object by making the pricing rule a separate, fully constructed collaborator:

class SeatPricing:
    PER_SEAT = 9
    def __init__(self, seats):
        self.seats = seats
    def monthly_fee(self):
        return self.seats * self.PER_SEAT

class Plan:
def __init__(self, months, pricing):
self.months = months
self.pricing = pricing
self.annual_fee = pricing.monthly_fee() * months

p = Plan(12, SeatPricing(20))
print(p.annual_fee) # 2160
```

(M1) for giving Plan a pricing collaborator instead of a subclass that overrides a price method. (A1) for constructing that collaborator completely before the plan uses it, so no method ever reads a field that has not been set. (A1) for computing the annual fee from the collaborator's result. (A1) for the correct value, $180 \times 12 = 2160$. (A1) for noting that Plan.__init__ still calls a method, but on a different object that is already finished, which is why the same line is now safe.

Two inheritance-preserving fixes also work and are acceptable. Assigning the subclass field before the superclass constructor runs:

class SeatPlan(Plan):
    def __init__(self, seats, months):
        self.seats = seats        # set first
        super().__init__(months)  # monthly_fee() now sees 20

and passing the already-computed fee up to the base constructor, so the base never calls an overridable method at all:

class Plan:
    def __init__(self, months, monthly_fee):
        self.months = months
        self.annual_fee = monthly_fee * months

All three produce annual_fee == 2160. (A1)

(c) During construction self.seats always falls back to the class attribute 1, so every SeatPlan caches $9 \times 12 = 108$ per year, whatever its seat count. (M1) At an average of 20 seats the correct fee is $20 \times 9 = 180$ per month, which is $180 \times 12 = 2160$ per year. (A1) The undercharge is therefore $2160 - 108 = 2052$ per customer per year. (A1) Across 900 customers the shortfall is $900 \times 2052 = 1{,}846{,}800$, and all 900 are billed incorrectly: a customer is billed correctly only if it happens to have exactly one seat, which the 20-seat average rules out. The cached fee is one twentieth of the true fee at 20 seats, which is why 108 looks like a plausible annual price for a small team rather than an obvious error. (A1)

(d) Both remedies remove the bug, so the choice is about the next change rather than this one. Patching the hierarchy - assign seats before super().__init__, or pass the fee up - is a one- or two-line change with no runtime cost, but it leaves the base constructor calling an overridable method, so the trap stays armed for the next subclass whose fields are set after super(). (M1) The composition design removes the trap: Plan depends on a SeatPricing object, so a subclass cannot observe an unset field. Its cost is one small object per plan - 900 SeatPricing objects of 48 bytes each, about 309,600 bytes once their instance dictionaries are counted, or roughly 0.31 MB - against a shortfall of 1,846,800. (A1) That is a ratio of about six to one between the money and the memory, so the memory argument is irrelevant at this scale. (A1) The decisive argument is growth: the catalogue will combine seats, usage and region, and inheritance multiplies subclasses (three independent pricing features give up to $2^3 = 8$ subclasses, and each new feature doubles that), while composition adds one collaborator per feature. Recommend adopting composition for the extended catalogue. (A1)

Markscheme notes

(a) The mark is for the mechanism, not the number. The candidate must say that super().__init__ runs before self.seats = seats, that the call to monthly_fee() inside the base constructor dispatches to the override, and that the attribute lookup then finds the class attribute seats = 1. A candidate who writes only that the constructor uses the wrong seat count, without the order of the statements, earns at most one mark. Accept a trace table. Do not accept the claim that the class attribute is overwritten: it is not; the instance attribute is created later and shadows it only from that point on.

(b) Accept any design that removes the read of a not-yet-assigned field, including composition, assigning the field before super().__init__, or passing the computed fee into the base constructor; code in Java or another language is acceptable if the syllabus version being sat requires it. The value 2160 must appear. A candidate who keeps the original hierarchy and merely adds a recompute() call after construction has treated the symptom; award at most two marks unless they also explain why the base constructor still calls an overridable method.

(c) Follow through on any consistent seat average; the marks are for the method (a cached 108 against a correct 180 per month, times 12) and for the totals 2052 and 1,846,800. A candidate who forgets that the cached fee is 108 for every plan and uses 20 seats in both terms obtains a shortfall of zero; this forfeits the first mark. Accept all 900, or every customer with more than one seat, for the count, provided the candidate notes the one-seat exception.

(d) This is an evaluate question, so a recommendation is required; a candidate who describes both fixes without choosing earns at most two of the four marks. The memory comparison must be present for the third mark and must be tied to the 1,846,800 figure. The final mark is for the growth argument - combinatorial subclass explosion under inheritance against one collaborator per feature under composition. Do not accept composition is always better without the growth reasoning, and do not accept keep inheritance because it is shorter without acknowledging the fragile base class.

3. CS-B4.1-001 16 marks

(a) A queue is suitable because sightings must be removed in the same order in which they arrive: FIFO matches exactly the behaviour of a buffer that is filled by the plate reader and drained by the upload process, whereas a stack would upload the most recent sighting first and destroy the chronological order. (A1)(A1)

The buffer is drained completely every 15 minutes and then refilled, so with a non-circular (linear) queue the front and rear pointers march steadily towards the end of the array; the array appears full even when the queue is nearly empty, and the pointers must be reset or the contents shifted. (M1) In a circular queue the vacated positions at the front are reused as the rear wraps around, so no shifting is needed and the fixed memory allocated to the buffer is used repeatedly — important on an embedded gantry controller with limited RAM. (A1)

(b) Design 1: $O(n)$ — in the worst case (a plate that is not present, or the last element) every one of the $n$ entries must be examined. (A1)

Design 2: $O(\log n)$ for a balanced tree — each comparison halves the remaining search space, so the number of comparisons grows as $\log_{2}n$. (A1)

At 40 000 plates, $\log_{2}(40\,000)\approx15.3$, so Design 2 needs about 15 comparisons per test against up to 40 000 for Design 1 — roughly a factor of 2 600. (M1) Across 40 000 tests per day this is the difference between about $1.6\times10^{9}$ and about $6\times10^{5}$ comparisons per day, so Design 1 is not viable at this volume; Design 2 is clearly preferable. (A1)

(c) Two pointers walk the two batches together, always taking the smaller of the two current timestamps:

MERGE(A, B)                       // A has p items, B has q items, each sorted by timestamp
    i = 0
    j = 0
    C = empty list
    while i < p and j < q         // both batches still have items
        if A[i].timestamp <= B[j].timestamp
            append A[i] to C
            i = i + 1
        else
            append B[j] to C
            j = j + 1
        end if
    end while
    while i < p                   // copy any remainder of A
        append A[i] to C
        i = i + 1
    end while
    while j < q                   // copy any remainder of B
        append B[j] to C
        j = j + 1
    end while
    return C
end MERGE

Award up to (M1) for the two-pointer idea, (A1) for comparing the two current timestamps and appending the smaller, (M1) for terminating when one batch is exhausted, (A1) for correctly copying the remainder of the other batch, and (A1) for stable handling of equal timestamps (using <= rather than <).

Each item is examined and appended exactly once, so the time complexity is $O(p+q)$; the space complexity is also $O(p+q)$ for the merged list. No sorting is required, because both inputs are already sorted.

(d) Inserting keys that are already in order makes every new key the rightmost (or leftmost) node, so the tree never branches: it degenerates into a structure with one node per level — effectively a linked list of height $n$. (A1) The search cost then becomes $O(n)$ rather than $O(\log n)$, so Design 2 loses the entire advantage identified in (b) precisely when the data are easiest to predict. (A1)

One fix: build the tree from the sorted keys by choosing the median as the root and recursing on each half, which produces a balanced tree of height $\lceil\log_{2}n\rceil$. Alternative acceptable fixes: use a self-balancing tree (AVL or red-black) that rebalances on insertion, or shuffle the insertion order. (A1)

Markscheme notes

(a) The reason must mention first-in-first-out / preserving arrival order; 'a queue stores things in order' is too vague for the second mark. For the circular-queue mark, credit reusing vacated space or avoiding shifting; do not credit 'it is faster' on its own.

(b) Credit $O(\log n)$ only if the candidate has reasoned about halving; a bare 'binary search tree is $O(\log n)$' with no justification earns the complexity mark but not the evaluation mark. Candidates who compute the ratio $n/\log_{2}n$ should be credited even if the arithmetic is imperfect.

(c) Accept structured English of equivalent precision, and accept a recursive solution that compares the two head elements and recurses on the remainder (complexity $O(p+q)$, with $O(p+q)$ recursion depth — note this as a weakness if the candidate does not). Do not penalise 1-based indexing. Candidates who sort the concatenated list instead earn at most (M1) for producing a correct result at higher cost ($O((p+q)\log(p+q))$).

(d) The consequence must be stated in terms of both shape (height $\approx n$, degenerate / list-like) and performance (search $O(n)$). Credit any balancing strategy; self-balancing trees go beyond the syllabus but should be credited as extension knowledge.

4. CS-A1.1-001 16 marks

(a) Award up to four points from:

  • The program counter / control unit holds the address of the next instruction and copies it into the memory address register; the instruction is fetched from memory into the memory data register and then into the instruction register. (A1)
  • The control unit decodes the instruction — determining the opcode and the operands — and sends control signals along the control bus to coordinate the other components. (A1)
  • The ALU performs the actual operation (arithmetic such as adding a sensor offset, or a logical comparison such as testing whether a distance is below a threshold) on data held in registers, setting status/flag bits as a result. (A1)
  • Registers hold the instruction, the operands and the intermediate results, giving much faster access than main memory; the result is written back to a register or to memory and the cycle repeats. (A1)

(b) Award two differences, each with a reason:

| | CPU | GPU | Why it matters here |
|---|---|---|---|
| Core design | Few cores, each large, complex and optimised for sequential tasks with heavy branching | Many hundreds or thousands of small, simple cores optimised for throughput | Obstacle detection applies the *same* operation to every pixel; thousands of cores work on different pixels simultaneously |
| Control vs compute | Much of the silicon is devoted to control logic, branch prediction and large caches | Far more of the silicon is devoted to arithmetic units | Image processing is data-parallel with almost no branching, so spending silicon on control logic is wasteful |

Other acceptable differences: SIMD/single-instruction-multiple-data execution; the GPU's higher memory bandwidth; the CPU's higher clock speed and lower latency per task. (A1)(A1)(A1)(A1)

(c) (i) Bits per frame $=1280\times720\times24=22\,118\,400$ bits (A1)

$$=\frac{22\,118\,400}{8}=2\,764\,800\ \text{bytes}\approx2.76\ \text{MB per frame}$$ (A1)

Data rate $=2.7648\times30=82.9\ \mathrm{MB\,s^{-1}}$ (A1)

(ii) Compressed rate $=\dfrac{82.9}{40}=2.07\ \mathrm{MB\,s^{-1}}$; for 90 s: $2.07\times90=187\ \mathrm{MB}$ (A1)

(Allow 186–188 MB. If 1 MB is taken as $2^{20}$ bytes throughout, the answers are 79.1 MB/s and 178 MB — credit both conventions if used consistently.)

(d) Indicative content:

  • Compiled: translated once into machine code before deployment; execution is fast and predictable because there is no translation at run time; the executable can be optimised for the specific target processor; the source code is not distributed, which protects intellectual property. (A1)(A1)
  • Interpreted: translated line by line at run time; slower (typically by an order of magnitude) and with less predictable timing; but easier to test and modify, and the same source runs on any hardware with a suitable interpreter. (A1)
  • Evaluation: the drone has fixed, known hardware and a hard real-time constraint of 20 ms, and the code will not be modified in flight. Compilation is therefore clearly preferable: the worst-case response time is shorter and, critically, more *predictable* — an interpreter introduces run-time translation delays that could cause a missed deadline and a collision. (A1)

Accept a contrary conclusion only if justified by a specific constraint (for example, if the software had to be updated in flight).

A third option students sometimes offer is just-in-time (JIT) compilation. It should not earn the evaluation mark on its own: a JIT compiler still translates each method at run time the first time it is executed, so the worst-case timing inside a 20 ms control window is not bounded by the source alone, and a routine that runs once per flight never benefits from the cached native code. It earns the same (A1) as any other answer only if the candidate states that the deadline is set by the worst case, and that compilation removes translation from the flight path altogether.

(a) Credit a clear description even if the register names differ (MAR/MDR/PC/IR/CIR/accumulator are all acceptable). (b) Each difference must be paired with a reason relating to the *task* (image processing / parallelism). A generic 'GPUs are faster' earns nothing. Credit any two well-explained differences.

(c) Award (A1) for the bits-per-frame figure, (A1) for the byte conversion, (A1) for the per-second rate, (A1) for applying the 40:1 ratio and the 90 s. Follow through on an arithmetic slip.

(d) This is an evaluate question, so a conclusion is required and must follow from the reasoning. Credit the comparison marks for either option, but the final (A1) requires a justified recommendation tied to a stated constraint (real-time deadline, fixed hardware, or IP protection).

Additional guidance. In (b) credit the SIMD framing ('one instruction applied to many pixels at once'), provided the consequence is stated. In (c) apply the candidate's figure from (i) consistently in (ii) and award the method marks even if that figure is wrong; mixing decimal and binary megabytes forfeits the final (A1). In (d) a hybrid answer — compile the control loop, interpret the mission scripts — earns full credit if both options are assessed against the 20 ms deadline.

5. CS-A2.3-001 16 marks

(a) Data: $1.2\ \mathrm{GB}=1.2\times10^{9}\ \text{bytes}=9.6\times10^{9}$ bits. (A1)

Usable bandwidth $=100\times10^{6}\times0.92=92\times10^{6}$ bits per second. (A1)

$$\text{time}=\frac{9.6\times10^{9}}{92\times10^{6}}=104\ \mathrm{s}$$ (A1)

At 1 Gbps: usable $=1000\times10^{6}\times0.92=920\times10^{6}$ bps, so

$$\text{time}=\frac{9.6\times10^{9}}{920\times10^{6}}=10.4\ \mathrm{s}$$ (A1)

Evaluation: the existing link takes about 104 s, roughly seven times the 15 s standard — the requirement is not met and cannot be met by any reasonable tuning. (A1) Upgrading to 1 Gbps gives 10.4 s, which meets the standard but with only about 4.6 s of margin. Since the link is shared with email, VoIP and sensor traffic (see part b), that margin could be eroded at busy times, so a 1 Gbps upgrade is justified but may not on its own be sufficient; the hospital should also consider prioritising (QoS) or transferring studies outside peak hours. (A1)

(b) In a packet-switched network the data is broken into packets, each carrying a destination address and a sequence number. (A1) Packets from different applications are interleaved on the same link, so the link is never idle waiting for one transfer to finish; routers forward each packet independently, possibly by different routes, and the receiving device reassembles them using the sequence numbers. (A1)(A1)

Consequence: the transfer time becomes variable rather than fixed — competing traffic reduces the share of bandwidth available to the image transfer, and because packets may take different routes they can arrive out of order or with varying delay (jitter), so the effective throughput fluctuates and the 104 s figure in (a) is a best case, not a guarantee. (A1)

(c) Segmentation divides one physical network into separate logical networks so that traffic in one segment cannot reach another. (A1) Its purpose here is to contain risk: a compromised guest device or an insecure building sensor cannot reach the clinical network holding patient records, and broadcast traffic is confined. (A1)

A firewall sits between segments and enforces the separation by applying rules — it inspects each packet's source, destination, port and protocol, permits traffic that matches an allowed rule (for example, a clinical workstation on VLAN 10 reaching the image server on TCP port 443) and drops or logs everything else by default. (A1)

(d) Symmetric encryption uses the *same* key to encrypt and decrypt. It is fast and suitable for bulk data, but the key must be shared securely in advance — if it is intercepted, all communication is compromised. (A1)

Asymmetric encryption uses a mathematically related *key pair*: a public key for encrypting and a private key (kept secret) for decrypting. No shared secret needs to be exchanged, but it is far slower, so in practice it is used to exchange a symmetric *session* key, which then encrypts the data. (A1)

A digital certificate solves the remaining problem — how the client knows the public key really belongs to the hospital server and not to an impostor. A trusted certificate authority signs a document binding the server's identity to its public key; the client verifies the signature against the CA's own certificate, and only then uses the public key. (A1)

A self-signed certificate does not solve the problem it appears to. It binds the server's identity to its own key, but the signature is made by the very key being vouched for, so a client that accepts it has no independent evidence of who is at the other end and is open to a man-in-the-middle presenting its own self-signed certificate. Certificates also expire and can be revoked: a client that checks the signature but never checks the validity dates or the revocation information will keep trusting a certificate whose private key has already been compromised.

Markscheme notes

(a) Award (A1) for the byte-to-bit conversion, (A1) for applying the 8% overhead, (A1) for 104 s, (A1) for 10.4 s. The last two marks are evaluative: one for stating clearly that 100 Mbps fails the standard, one for a judgement that recognises 10.4 s meets it *but with limited margin* — a bare 'yes, upgrade' earns only one of the two.

(b) Three of the four marks are for the mechanism (packetising, interleaving/sharing, independent routing and reassembly); the fourth is for a consequence. Accept latency, jitter, out-of-order arrival, variable throughput or the need for retransmission. Do not credit 'it is more efficient' on its own.

(c) One mark for what segmentation is, one for why (containment of risk/broadcast), one for the firewall's rule-based enforcement. Naming 'VLAN' without explaining the separation earns nothing.

(d) Each of the three marks is a separate idea: the shared-key/public-key distinction, the performance consequence (hybrid use), and the certificate's role in binding identity to a public key. Candidates who say 'a certificate encrypts the data' have misunderstood and forfeit the last mark.

Additional guidance. In (a) accept 'about 100 s' for 104 s, and follow through on the candidate's own bit conversion: both evaluation marks are awarded on their figures provided the 15 s comparison is explicit. In (b) credit 'packets can be routed around a failed link' as a consequence of independent routing.

6. CS-A3.2-001 16 marks

(a) Award two from:

  • Update (modification) anomaly. 'Midnight Chorus' and its venue 'East Stage' are repeated in rows 1001, 1002 and 1004. If the performance is moved to another venue, every one of those rows must be changed; if even one is missed, the database holds contradictory answers and a report cannot say where the performance is. (A1)(A1)
  • Insertion anomaly. A newly announced performance cannot be added to the database until someone books it, because the only place a performance name can exist is inside a booking row — and BookingID is the key, so there is no way to store a performance with no bookings. (A1)(A1)
  • Deletion anomaly. If customer L. Oyeka cancels booking 1003, that row is the only record of 'Brass Quartet' at the West Barn; deleting the booking destroys the performance record as well. (A1)(A1)
  • Redundancy / wasted storage. Customer name and email are repeated across every booking that customer makes, so A. Ferrer's details are stored twice and R. Duval's twice, and the repetition grows with the festival. (A1)(A1)

(Maximum 5 marks; at least one answer must name the anomaly type for the higher band.)

(b) A correct 3NF decomposition:

CUSTOMER(CustomerID PK, CustomerName, CustomerEmail)

PERFORMANCE(PerformanceID PK, PerformanceName, VenueName)

SEAT_PRICE(PerformanceID FK, SeatCategory PK *(composite with PerformanceID)*, PricePerTicket)

BOOKING(BookingID PK, CustomerID FK, PerformanceID FK, SeatCategory FK, Quantity)

Award (A1) for separating CUSTOMER, (A1) for separating PERFORMANCE, (A1) for recognising that PricePerTicket depends on the *performance and seat category* pair rather than on the booking (so it needs its own table), (A1) for correct primary keys, (A1) for correct foreign keys linking BOOKING to CUSTOMER and PERFORMANCE.

Why this is 3NF: in every table, each non-key attribute depends on the key, the whole key, and nothing but the key. In particular, PricePerTicket is no longer stored against BookingID (a transitive/partial dependency), and VenueName is no longer repeated per booking.

Note: the original table has no CustomerID or PerformanceID, so surrogate keys must be introduced — credit this explicitly if done.

(c) One correct solution:

SELECT c.CustomerName,
       p.PerformanceName,
       b.Quantity * s.PricePerTicket AS TotalCost
FROM BOOKING b
JOIN CUSTOMER    c ON b.CustomerID    = c.CustomerID
JOIN PERFORMANCE p ON b.PerformanceID = p.PerformanceID
JOIN SEAT_PRICE  s ON b.PerformanceID = s.PerformanceID
                  AND b.SeatCategory  = s.SeatCategory

*Check: $1101\,1010\,1000$ is $3496$ unsigned, and $3496-4096=-600$. Correct.*

*Representable: $-600$ lies inside the 12-bit signed range $-2048$ to $+2047$, so no clamping is needed.*

(b) A 12-bit two's complement register holds values from $-2048$ to $+2047$. Each individual reading is comfortably inside this range because the largest magnitude the sensor can report is about $128$ degrees Celsius. (M1)

Overflow is a property of the accumulator, not of the sensor. Two readings of $+2047$ already sum to $4094$, which is more than the largest 12-bit signed value, so the sum wraps and a positive result can appear negative. In practice the readings are far smaller than the maximum, but the accumulator has no way of knowing that: it is only 12 bits wide, so any pair of readings above about $1023$ will overflow it. (M1)(A1)

Sixteen readings can each be as large as $2047$, so the largest possible sum is $16\times 2047=32\,752$. (M1) A 15-bit two's complement register reaches only $+16\,383$, which is not enough; a 16-bit register reaches $+32\,767$, which is. The minimum width is therefore 16 bits. (A1)

In general an accumulator summing $k$ readings of width $w$ must satisfy $2^{W-1}-1\ge k(2^{w-1}-1)$; for $w=12$ and $k=16$ the smallest satisfying width is $W=16$, which is why the answer is 16 and not 15.

The Celsius conversion is therefore exact by construction, while the Fahrenheit error is one of representation rather than arithmetic: using more bits shrinks the rounding error but never removes it, because the expansion of $9/5$ does not terminate.

A journey is not like that: it happened, it was paid for, and it is the data the scheme reports on. The referential rule should therefore refuse to delete a bike while journeys still reference it (RESTRICT or NO ACTION), or, better, the bike should never be deleted at all: a Status column set to retired keeps the row, keeps the foreign key valid and keeps the history intact. A nullable foreign key with SET NULL is a weaker third option: it preserves the journey but loses the link to the bike, so the record can no longer say which bike was used. (A1) for a recommendation that is justified by the requirement to preserve history rather than by tidiness.

Markscheme notes

(a) Accept any correct definitions; do not accept "the first column". A candidate may argue for a composite key such as (MemberID, StartTime) — credit this if they then accept that TripID is the simpler unique key. The MemberID mark requires the *reason* (repetition, one row per journey), not merely the assertion that it is not unique.

(b) Follow through on all arithmetic. The 600 MB mark is for the method (bytes per row x rows) and the result; accept 572 MiB if the candidate states the binary convention. In the edits calculation, a candidate who uses 12,000,000 rows rather than ten rows per member has confused the two multiplicities and loses that (A1). The ChargeCents mark requires a *consequence* — cannot sum, cannot sort numerically, character ordering, the embedded comma — not just "it is stored as text".

(c) Accept any schema that stores member and bike facts once and links them by foreign keys; table and column names need not match. The foreign keys must be in TRIP and point at MEMBER and BIKE. A candidate who puts BikeID as a foreign key inside MEMBER, or who leaves MemberName in TRIP, has not removed the redundancy and loses the relevant mark. Accept a statement of referential integrity in words instead of SQL.

(d) This is an evaluate question, so a recommendation is required. A candidate who writes "cascade is bad practice" without the 240,000 figure earns at most the (M1). Accept RESTRICT, NO ACTION, a soft-delete Status column, or a nullable key with SET NULL *provided* the candidate acknowledges that SET NULL loses the link to the bike. Do not accept "take a backup first" — it does not change the integrity rule and the backup is itself a copy of data the rule would delete. Award the final (A1) only when the recommendation follows from the requirement to preserve history.

13. CS-B2.1-001 16 marks

(a) A floating-point number stores a value as a sign, a mantissa and a binary exponent. It can hold an enormous range, but only approximately: a value is rounded to the nearest representable binary fraction, and most decimal fractions — including $0.10$ — have no exact binary representation. (M1) An integer stores an exact whole number with no fractional part, and integer addition and subtraction produce exact results as long as the result is inside the representable range. (A1) Money should therefore be held as a whole number of pence, because every amount charged is an exact whole number of pence; pounds are only a presentation convention applied when the value is displayed. (A1)

(b)

def settle(balance_pence, minutes, points):
    charge = minutes * 2          # 2 pence per minute, exact
    discount = points             # 1 penny per point
    if discount > charge:
        discount = charge         # the amount due is never negative
    due = charge - discount
    if balance_pence < due:
        return None               # insufficient: the barrier stays down
    return balance_pence - due    # exact remaining balance, 0 when equal

(M1) for computing the charge as an integer product rather than a floating-point rate. (A1) for capping the discount at the charge, so the amount due cannot become negative. (A1) for the balance test. (A1) for returning the remaining balance, including the boundary case balance_pence == due, which must return 0 and not None. (A1) for using only integer arithmetic throughout.

A Java version of this paper asks for the same algorithm. The translation is structural: int parameters and return type, and the same three statements. Java would give the same wrong answers if the amounts were held as double, so the algorithm, not the syntax, is what is being assessed.

(c) The literal 0.10 is not exactly one tenth. The nearest 64-bit floating-point value is slightly larger than $0.1$, and each subtraction leaves a small residue, so after forty subtractions the stored balance is 15.999999999999945 rather than 16.00. (M1)(A1) The comparison balance >= 16.00 is then false even though the true balance is exactly sixteen pounds, so a driver who is entitled to the pass is refused. (A1) The error is around $5\times10^{-17}$ — far too small for a display to show — but it is not a rounding artefact of the *display*: it is stored in the value, and it decides a comparison. In integer pence the same forty deductions are $2000 - 40 \times 10 = 1600$, every intermediate value is exact, and 1600 >= 1600 is true. (A1)

Note how well the bug hides. The arithmetic expression 20.00 - 40 * 0.10 evaluates to exactly 16.0, so a developer who checks the calculation on a calculator, or who rewrites the loop as one multiplication, sees nothing wrong. Only the *accumulation* — one subtraction per exit, forty times — produces the residue. That is why the fault survives the obvious test.

(d) Holding amounts in integer pence is justified by exactness, and the exactness has a measurable cost when it is absent. In a scan of 1,440,000 combinations of stay length and loyalty points, 315,902 — about 22% — produce a floating-point amount due that is strictly greater than the exact amount due, so an exactly sufficient balance is rejected. (M1)(A1) The car park handles 250,000 exits a day. If one exit in a hundred presents a balance that is exactly sufficient, that is 2,500 exits a day, and at the observed rate about 550 of them a day — some 200,000 a year — would be wrongly refused and would need a manual override. (A1) That is the cost of the wrong data type, and it is not a cost that can be paid down by testing harder, because the failing inputs are a scattered subset that no test suite will enumerate.

One change is needed where the value crosses the boundary of the program. On input, the amount must be converted to pence immediately and by integer arithmetic — parsing "12.30" as 1230, never as float("12.30") * 100, which reintroduces the error. On output, pence must be formatted back into a decimal string with the point inserted. Inside the program, every amount is an integer. (A1)

(a) Accept any answer that distinguishes exactness from range; the essential contrast is that an integer is exact within its range while a binary floating-point value is a rounded approximation. Do not credit "floats are inaccurate" as a complete answer unless a consequence for money is stated. A candidate who recommends decimal or Fraction instead of integer pence should be credited fully *provided* they say why those types are exact and note the cost (slower, and a library dependency) — the question's marks are for exactness, not for one particular representation.

(b) Code in a language other than Python should be accepted if the syllabus version being sat requires it. (c) The two marks for the diagnosis require the mechanism (a decimal fraction has no exact binary representation, so repeated subtraction accumulates a residue) and the observed value. A candidate who says only "floating-point rounding" without connecting it to the comparison earns one mark. 14. CS-B2.5-001 16 marks

(a) The file is 40 GB and the machine has 8 GB of RAM, so stream.read() tries to build a string five times larger than the memory available; the process would be killed before any summary was produced, and the failure would happen after the whole file had been transferred. (M1) The stream also cannot be rewound: it arrives compressed over a socket and the raw file is never written to disk, so the program cannot read part of it, release the memory and then return to the beginning. (A1) A streaming implementation reads one record at a time and keeps only the running state it needs — for each station a count, a minimum, a maximum and a running total — so its memory use is proportional to the number of stations, not to the size of the file, and 500 stations need only a few tens of kilobytes. (A1)

(b) There are two faults, and neither is visible on a small test file.

The first is data.split("\n"). It splits the entire 40 GB string and, because a text file normally ends with a newline character, it produces a final empty element. That empty element is counted as a malformed record, so the reported error count is wrong by one before any real error is found. (M1)(A1) Iterating the file object directly avoids this, because a text stream yields one line per record and never yields a phantom line at the end.

The second is line.split(","), which splits on every comma, including a comma that is inside a quoted field. A record such as ST04,"North, West",4.0,60 contains four fields, but split(",") returns five pieces, so a perfectly valid record is rejected and the field boundaries of the following fields are wrong. (M1)(A1) A correct parser scans the line character by character, keeps a flag for whether it is inside a quoted field, treats a doubled quote as a literal quote character, and splits only on commas seen outside quotes.

(c)

def ingest(stream, max_errors):
    summary = {}
    errors = []
    total_errors = 0

for lineno, raw in enumerate(stream, start=1):
line = raw.rstrip("\r\n")
if line == "":
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "empty line"))
continue

fields = split_csv(line)
if len(fields) != 4:
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "field count %d" % len(fields)))
continue

station, timestamp, temp, humidity = fields
try:
t = float(temp)
except ValueError:
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "non-numeric temperature"))
continue

if station in summary:
count, low, high, total = summary[station]
summary[station] = (count + 1, min(low, t), max(high, t), total + t)
else:
summary[station] = (1, t, t, t)

return summary, errors, total_errors

def split_csv(line):
fields, current, in_quotes = [], [], False
i = 0
while i < len(line):
ch = line[i]
if ch == '"':
if in_quotes and i + 1 < len(line) and line[i + 1] == '"':
current.append('"')
i += 2
continue
in_quotes = not in_quotes
elif ch == "," and not in_quotes:
fields.append("".join(current))
current = []
else:
current.append(ch)
i += 1
fields.append("".join(current))
return fields

(M1) for consuming the stream exactly once, with enumerate supplying the line number, and never calling read() or seek(). (A1) for holding only bounded state per station — a count, a minimum, a maximum and a running total — so memory is proportional to the number of stations. (A1) for capping errors at max_errors while total_errors still counts every malformed record, so the exact scale of the corruption is preserved. (A1) for the quoted-field parser, which is what makes the field count correct for records such as ST04,"North, West",4.0,60. (A1) for validating the numeric field and continuing rather than crashing, so that one bad record does not abandon the remaining 400,000,000.

The time is $O(n)$ in the number of records and the memory is $O(S)$ for $S$ stations plus at most max_errors small tuples. A Java version of this paper asks for the same algorithm: a BufferedReader read line by line, a HashMap of running statistics, and the identical two-state parser.

(d) The requirement and the cap are in direct conflict. The provider must receive the line number of *every* malformed record, and a corrupt upload can contain millions of them, so an in-memory list capped at max_errors will be full almost immediately and the line numbers beyond the cap are lost. (M1) The cap does bound memory — max_errors tuples of an integer and a short string is a few tens of kilobytes, which is safe on an 8 GB machine — so the design trades completeness for a memory guarantee. (A1)

That trade is unnecessary, because the error report does not have to live in memory. Each malformed record can be written to a second output stream as it is found: memory stays bounded at one record, and the provider receives every line number. (A1) The costs are a second output to manage and the throughput the writes consume, but the error file is normally tiny — it is only large when the upload is genuinely corrupt, which is exactly when the provider needs it in full. The running total_errors count should be kept regardless, so that the summary can state the scale of the corruption even if the provider's tooling truncates the error file.

The recommendation is therefore to stream the errors out, and to fall back to a capped in-memory list only when no second output is available. In that fallback the report must say so: it must state that line numbers beyond the cap are missing while the total count remains exact, so that the provider knows how much of the report is absent rather than believing the report is complete. (A1)

Markscheme notes

(a) Require either the arithmetic (40 GB against 8 GB, a factor of five) or an equivalent statement of impossibility. A candidate who proposes adding RAM or using a bigger machine has not engaged with the design and should be redirected; credit is not awarded for hardware. "Streaming" must be described as reading one record at a time with bounded state, not merely as "using a loop".

(b) Each fault needs its mechanism. For the trailing-newline fault, accept a description of the phantom final empty element; a candidate who says only "split is wrong" earns nothing. For the quoting fault, accept a prose description or code. A candidate who says "use the csv module" earns the description mark only if they also say what a CSV parser must do about quoted delimiters.

(c) The marks are for structure, not for library knowledge. Accept any single-pass function returning equivalent summary, error and count objects; a dictionary of tuples, a dictionary of lists, or a small class are all acceptable. Do not award the capped-list mark to a candidate who stores every malformed line, and do not award the parser mark to a candidate who still calls split(",") on a raw line. try/except, an explicit numeric test, or a regular expression are all acceptable for the validation mark. A candidate who reads the stream twice loses the single-pass mark even if the results are correct.

(d) The evaluation must name the conflict and then choose. A candidate who says "increase max_errors" has not engaged with the memory bound and should be capped at one mark. The strongest answers propose the second output stream; a candidate who defends the cap can still earn two marks if the loss of line numbers is stated explicitly and the exact count is retained. Do not accept "store the errors in a database" as a free answer — it is a second output stream in disguise, and it should be credited only if the candidate says that the writes are streamed rather than batched.
