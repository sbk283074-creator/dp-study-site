A bike-hire class with one underlined attribute

A city bike-hire scheme is modelled by a single class, Bike. Its UML class diagram is shown in the figure. In UML an attribute or method whose name is underlined is a static member, which Java calls a class variable or class method.

A program creates three Bike objects with the identifiers B-01, B-02 and B-03. Over one day the first bike is hired twice, the second bike is hired once, and the third bike is not hired at all. The attribute hireCount records how many times a bike has been hired, and the attribute fleetSize records how many Bike objects exist. The class diagram shows which of the two is static.

Question

Evaluate the design of the class. Where a part asks what an object reports, state the value returned by the accessor named in the class diagram. Assume the three objects are created before any of them is hired.

  1. [3 marks](a)

    State the value that getHireCount() reports for each of the three objects at the end of the day, and the value that getFleetSize() reports.

    (State)
  2. [5 marks](b)

    Determine the number of copies of each attribute that exist in memory once the three objects have been created, and explain how the underline in the class diagram tells you which attributes are shared.

    (Determine)
  3. [4 marks](c)

    Explain why an object diagram cannot show the difference between a static attribute and an instance attribute, and state which diagram can.

    (Explain)
  4. [4 marks](d)

    The designer proposes to make hireCount static as well, so that the class keeps a single running total. Determine the value getHireCount() would then report for each of the three objects, and justify whether the change improves the design.

    (Justify)

Reveal the answer

Part (a). hireCount is not underlined, so it is an instance attribute and each object has its own copy. getHireCount() reports 2 for B-01, 1 for B-02 and 0 for B-03. (M1)(A1)

fleetSize is underlined, so it is static and there is one copy for the whole class. getFleetSize() reports 3, and it reports 3 whichever of the three objects it is called on. (A1)

Part (b). There are three copies of id, three copies of hireCount and one copy of fleetSize, making seven attribute slots in total. (M1)(A1)(A1)

The general count is the number of objects multiplied by the number of instance attributes, plus the number of static attributes: 3 x 2 + 1 = 7. (A1)

The underline is UML's notation for a static member, which Java calls a class variable. A static member belongs to the class rather than to any object, so exactly one copy exists however many objects are created, and the memory is allocated when the class is loaded rather than when an object is constructed. An attribute with no underline is an instance attribute, and a fresh copy is allocated for every object. In the diagram, fleetSize and getFleetSize() are underlined and id, hireCount, Bike(id), hire() and getHireCount() are not. (A1)

Part (c). An object diagram is a snapshot: it shows the objects that exist at one moment, the links between them, and the current value of each attribute. Two objects that share a single storage location and two objects that each hold their own copy of the same value produce exactly the same object diagram — the diagram draws one box per object with one value in it either way. (M1)(A1)

Sharing is a property of the class definition rather than of any particular set of objects, so it cannot be read off a diagram of instances. (A1)

The class diagram is the diagram that shows it, and the static underline is how. (A1) A class diagram describes the shape every object will have; the underline says that one of those members will not be duplicated when the objects are made.

Part (d). A static hireCount is a single counter belonging to the class. Every hire increments that one slot, and the total number of hires is 2 + 1 + 0 = 3. So all three objects report 3. (M1)(A1)

The change does not improve the design, because it destroys the information the attribute was there to carry. Before the change, getHireCount() answered "how many times has this bike been hired"; afterwards it answers "how many times has any bike in the fleet been hired", and the three bikes are no longer distinguishable by usage at all. A maintenance scheduler that asked which bikes were used most would now receive the same answer for every bike. (A1)

The fleet total is a reasonable quantity to keep, so the proposal is not without merit — but it is a different quantity, and it belongs under a different name such as totalHires. Renaming the existing attribute instead would leave every call site compiling while silently changing what it means, which is the failure mode that is hardest to find later. (A1)

Markscheme notes

(a) M1 for recognising that hireCount is an instance attribute, A1 for the three values 2, 1 and 0 in the right order. A1 for fleetSize reporting 3 and for noting that it reports 3 from any object. Do not award the final A1 for an answer that gives 3 as the value of hireCount for any object.

(b) M1 for the idea of counting copies rather than values. A1 for three copies of id, A1 for three copies of hireCount, A1 for one copy of fleetSize. A1 for the underline meaning static, or class variable, or one copy shared by the class. Accept 7 as the total with or without the general formula, provided the three parts are distinguished; a bare answer of 7 with no breakdown earns the M1 only.

(c) M1 for the snapshot idea, A1 for the observation that sharing and duplicating draw the same picture. A1 for the reason: sharing belongs to the class, not the objects. A1 for naming the class diagram. A candidate who answers "a class diagram" without saying why the object diagram fails earns the last A1 only.

(d) M1 for recognising that a static counter is one slot for the class, A1 for 3. A1 for the information-loss argument. A1 for distinguishing the fleet total from the per-bike count, or for requiring a different name. Accept a candidate who argues the change is acceptable provided they state that a different attribute is needed as well; do not accept a bare "it is better because it saves memory".

Why this question is hard

The item is built on the one distinction in introductory object orientation that a diagram cannot show from the objects themselves. Static and instance members look identical once the objects exist: an object diagram of three bikes each holding a hireCount of 0 is the same picture whether the counter is duplicated or shared. The information that separates them lives in the class definition, and the item makes the candidate say where.

The numeric trap is small and precise. A candidate who misses the underline will report that all three objects share a single hireCount, and the total of hires is 3, so they will answer 3, 3, 3 — which is exactly the right answer to part (d). The same wrong reading of the diagram produces the correct answer to the wrong question, and there is nothing in part (a) that flags it. Part (d) then asks the candidate to evaluate that arrangement deliberately, which means a candidate who was already answering 3, 3, 3 must now notice that they never made a decision at all.

Part (b) rewards a habit rather than a fact. Counting copies of each attribute, rather than values, is the operation that makes the static distinction visible, and it is the operation most candidates do not perform unless asked. The general form — objects times instance attributes, plus static attributes — is what turns a count into an understanding.

Part (d) is where the item is hardest, because the proposal is defensible and the candidate has to say why it is nonetheless wrong. A single running total is a real and useful quantity; what makes the change wrong is that it silently redefines an attribute that callers already use, so the design gets worse while the code keeps compiling. Naming the distinction — a new attribute under a new name, rather than a changed meaning under the old one — is the answer the item is looking for, and it is a judgement about design rather than a calculation.
