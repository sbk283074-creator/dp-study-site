A forty-gigabyte file that will not fit in memory twice

Computer science HL · CS-B2.5-001

B2.5 File processing (reading and writing files, line-by-line and whole-file processing, parsing records, detecting malformed data, memory and error handling)P2 · Section B16 marksdifficulty 4technology: not allowedpythonExplainConstructEvaluate

Northwind Climate Archive ingestion

A weather service ingests a daily archive from a national network of 500 stations. The archive is a single text file of 40 GB. Each record is one line of about 100 bytes holding four comma-separated fields: station code, timestamp, temperature and humidity.

The file arrives as a compressed stream over a socket. The stream cannot be rewound and the raw file is never written to disk, because the service has no room for it. The machine that runs the ingestion has 8 GB of RAM.

The service must produce, for each station, the number of valid readings, the minimum and maximum temperature and the mean temperature. It must also report every malformed record to the provider so that the archive can be corrected, and the provider needs the line number of each bad record. The provider has warned that a corrupt upload can contain millions of malformed lines.

def ingest(stream):
    data = stream.read()                      # 40 GB, held in memory
    errors = []
    summary = {}
    for lineno, line in enumerate(data.split("\n"), start=1):
        fields = line.split(",")
        if len(fields) != 4:
            errors.append((lineno, line))     # keeps every bad line
            continue
        station, timestamp, temp, humidity = fields
        ...
    return summary, errors

Question

The ingestion runs once a night on a single machine, must not exhaust memory, and must finish before the next upload arrives.

  1. [3 marks](a)

    Explain why stream.read() cannot be used here, referring to the size of the file and the memory available, and state what a streaming implementation does instead.

    (Explain)
  2. [4 marks](b)

    Explain why data.split("\n") followed by line.split(",") produces errors that the developer would not see when testing on a small file. Describe how a record containing a comma inside a quoted field must be parsed.

    (Explain)
  3. [5 marks](c)

    Construct a Python function ingest(stream, max_errors) that consumes the stream exactly once and returns a summary, an error report and an error count. stream is a file-like object that supports iteration and cannot be rewound. The summary must give, for each station, the count, minimum, maximum and sum of temperatures. The error report must hold the line number and a reason for at most max_errors malformed records, and the count must be the exact total of malformed records. You may not import any module, and you may not call stream.read() or stream.seek(). A Java version of this paper requires the same algorithm.

    (Construct)
  4. [4 marks](d)

    Evaluate the decision to keep only the first max_errors malformed records while still counting all of them, against the provider's requirement to receive the line number of every malformed record. State what is given up and recommend a design.

    (Evaluate)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) The file is 40 GB and the machine has 8 GB of RAM, so stream.read() tries to build a string five times larger than the memory available; the process would be killed before any summary was produced, and the failure would happen after the whole file had been transferred. (M1) The stream also cannot be rewound: it arrives compressed over a socket and the raw file is never written to disk, so the program cannot read part of it, release the memory and then return to the beginning. (A1) A streaming implementation reads one record at a time and keeps only the running state it needs — for each station a count, a minimum, a maximum and a running total — so its memory use is proportional to the number of stations, not to the size of the file, and 500 stations need only a few tens of kilobytes. (A1)

(b) There are two faults, and neither is visible on a small test file.

The first is data.split("\n"). It splits the entire 40 GB string and, because a text file normally ends with a newline character, it produces a final empty element. That empty element is counted as a malformed record, so the reported error count is wrong by one before any real error is found. (M1)(A1) Iterating the file object directly avoids this, because a text stream yields one line per record and never yields a phantom line at the end.

The second is line.split(","), which splits on every comma, including a comma that is inside a quoted field. A record such as ST04,"North, West",4.0,60 contains four fields, but split(",") returns five pieces, so a perfectly valid record is rejected and the field boundaries of the following fields are wrong. (M1)(A1) A correct parser scans the line character by character, keeps a flag for whether it is inside a quoted field, treats a doubled quote as a literal quote character, and splits only on commas seen outside quotes.

(c)

def ingest(stream, max_errors):
    summary = {}
    errors = []
    total_errors = 0

for lineno, raw in enumerate(stream, start=1):
line = raw.rstrip("\r\n")
if line == "":
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "empty line"))
continue

fields = split_csv(line)
if len(fields) != 4:
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "field count %d" % len(fields)))
continue

station, timestamp, temp, humidity = fields
try:
t = float(temp)
except ValueError:
total_errors += 1
if len(errors) < max_errors:
errors.append((lineno, "non-numeric temperature"))
continue

if station in summary:
count, low, high, total = summary[station]
summary[station] = (count + 1, min(low, t), max(high, t), total + t)
else:
summary[station] = (1, t, t, t)

return summary, errors, total_errors

def split_csv(line):
fields, current, in_quotes = [], [], False
i = 0
while i < len(line):
ch = line[i]
if ch == '"':
if in_quotes and i + 1 < len(line) and line[i + 1] == '"':
current.append('"')
i += 2
continue
in_quotes = not in_quotes
elif ch == "," and not in_quotes:
fields.append("".join(current))
current = []
else:
current.append(ch)
i += 1
fields.append("".join(current))
return fields

(M1) for consuming the stream exactly once, with enumerate supplying the line number, and never calling read() or seek(). (A1) for holding only bounded state per station — a count, a minimum, a maximum and a running total — so memory is proportional to the number of stations. (A1) for capping errors at max_errors while total_errors still counts every malformed record, so the exact scale of the corruption is preserved. (A1) for the quoted-field parser, which is what makes the field count correct for records such as ST04,"North, West",4.0,60. (A1) for validating the numeric field and continuing rather than crashing, so that one bad record does not abandon the remaining 400,000,000.

The time is $O(n)$ in the number of records and the memory is $O(S)$ for $S$ stations plus at most max_errors small tuples. A Java version of this paper asks for the same algorithm: a BufferedReader read line by line, a HashMap of running statistics, and the identical two-state parser.

(d) The requirement and the cap are in direct conflict. The provider must receive the line number of *every* malformed record, and a corrupt upload can contain millions of them, so an in-memory list capped at max_errors will be full almost immediately and the line numbers beyond the cap are lost. (M1) The cap does bound memory — max_errors tuples of an integer and a short string is a few tens of kilobytes, which is safe on an 8 GB machine — so the design trades completeness for a memory guarantee. (A1)

That trade is unnecessary, because the error report does not have to live in memory. Each malformed record can be written to a second output stream as it is found: memory stays bounded at one record, and the provider receives every line number. (A1) The costs are a second output to manage and the throughput the writes consume, but the error file is normally tiny — it is only large when the upload is genuinely corrupt, which is exactly when the provider needs it in full. The running total_errors count should be kept regardless, so that the summary can state the scale of the corruption even if the provider's tooling truncates the error file.

The recommendation is therefore to stream the errors out, and to fall back to a capped in-memory list only when no second output is available. In that fallback the report must say so: it must state that line numbers beyond the cap are missing while the total count remains exact, so that the provider knows how much of the report is absent rather than believing the report is complete. (A1)

Markscheme notes

(a) Require either the arithmetic (40 GB against 8 GB, a factor of five) or an equivalent statement of impossibility. A candidate who proposes adding RAM or using a bigger machine has not engaged with the design and should be redirected; credit is not awarded for hardware. "Streaming" must be described as reading one record at a time with bounded state, not merely as "using a loop".

(b) Each fault needs its mechanism. For the trailing-newline fault, accept a description of the phantom final empty element; a candidate who says only "split is wrong" earns nothing. For the quoting fault, accept a prose description or code. A candidate who says "use the csv module" earns the description mark only if they also say what a CSV parser must do about quoted delimiters.

(c) The marks are for structure, not for library knowledge. Accept any single-pass function returning equivalent summary, error and count objects; a dictionary of tuples, a dictionary of lists, or a small class are all acceptable. Do not award the capped-list mark to a candidate who stores every malformed line, and do not award the parser mark to a candidate who still calls split(",") on a raw line. try/except, an explicit numeric test, or a regular expression are all acceptable for the validation mark. A candidate who reads the stream twice loses the single-pass mark even if the results are correct.

(d) The evaluation must name the conflict and then choose. A candidate who says "increase max_errors" has not engaged with the memory bound and should be capped at one mark. The strongest answers propose the second output stream; a candidate who defends the cap can still earn two marks if the loss of line numbers is stated explicitly and the exact count is retained. Do not accept "store the errors in a database" as a free answer — it is a second output stream in disguise, and it should be credited only if the candidate says that the writes are streamed rather than batched.

Why this question is hard

Three requirements appear to conflict: process the file in one pass, keep memory bounded, and report every malformed record. The obvious way to satisfy any two of them is to break the third, and most students will break the third — they will cap the error list and accept that some line numbers are lost. The insight the question is testing is that the conflict is not real: it exists only because the error report was assumed to be an in-memory object. Move it to a different sink and all three requirements hold at once. That is a design move, not a coding trick, and it is the reason the final part carries the marks.

The memory arithmetic is the part that must be done rather than estimated. Forty gigabytes against eight gigabytes is a factor of five, and that is *before* the overhead of a Python string object; a list of 400,000,000 line objects would need several times the raw file size. A student who says "the file is large" has not established that the naive approach is impossible, and the difference between "slow" and "impossible" matters, because a slow program can be left to run and an impossible one cannot.

The two parsing faults are the classic reasons that file-processing code passes its tests and fails in production. A small test file written by hand often has no trailing newline and no quoted commas; a real 40 GB export has both. split("\n") on a file that ends with a newline produces a phantom empty record, which inflates the error count by one and, worse, trains the developer to ignore the error report. And splitting on commas is only correct for files whose fields never contain commas — which is a property of the data, not a guarantee, and CSV quoting exists precisely because that property fails. Both faults are invisible on the obvious test and both are trivially avoided by the right primitive: iterate the file object, and parse fields with a state machine that knows about quotes.

The final wrong turn is worth naming because it is the most reasonable-looking. A student who caps the error list has correctly identified that memory must be bounded and has made a defensible engineering trade. What they have missed is that the requirement they sacrificed was the one the *user* cared about, and that it could be satisfied at almost no cost. Recognising which constraint is genuinely binding — and which one is an artefact of an implementation choice — is the transferable skill.
