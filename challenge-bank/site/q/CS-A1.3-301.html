A1.3 A process whose working set exceeds the available frames, where the cost of traversing a large array depends on the access order by a factor equal to the number of elements that fit in one page

Computer science HL · CS-A1.3-301

With B2.2 Data structures: the layout of a two-dimensional array in memoryP1 · Section B15 marksdifficulty 4technology: permittedCalculateCalculateDetermineCalculate

Question

A server has $4\ {\rm GiB}$ of physical memory, of which the operating system and other resident processes occupy $2\ {\rm GiB}$, leaving $2\ {\rm GiB}$ of frames available to a numerical application. Memory is paged with a page size of $4\ {\rm KiB}$ $(4096\ {\rm bytes})$; a memory access that hits takes $t_{m} = 80\ {\rm ns}$, and a page fault costs $t_{d} = 8\ {\rm ms}$ because the page must be fetched from a solid-state device. The effective access time is
$$t_{\rm eff} = (1 - p)\,t_{m} + p\,t_{d},$$
where $p$ is the probability that a given access faults.
The application must traverse a square array of double-precision numbers, each occupying $8$ bytes, stored in row-major order, with $32\,768$ rows and $32\,768$ columns. Its declared working set is therefore the whole array. Two traversals are considered: one that visits the elements in row-major order and one that visits them in column-major order.

  1. [2 marks](a)

    Calculate the number of frames available to the application and the number of frames the array requires, and state whether the working set fits.

    (Calculate)
  2. [3 marks](b)

    Calculate the page-fault probability $p$ at which the effective access time is double the fault-free time, and comment on the magnitude of that probability.

    (Calculate)
  3. [4 marks](c)

    Determine the number of page faults generated by each traversal, assuming in the row-major case that each page is read once and in the column-major case that every element access faults. Determine the ratio of the two, and explain where that ratio comes from.

    (Determine)
  4. [3 marks](d)

    Calculate the time taken by each traversal at $8\ {\rm ms}$ per fault, giving your answers in hours for the row-major case and in days for the column-major case.

    (Calculate)
  5. [3 marks](e)

    A colleague proposes moving to huge pages of $2\ {\rm MiB}$ $(2\,097\,152\ {\rm bytes})$. Explain, with numbers, what this does for each of the two traversals, and explain why the same change has two such different effects.

    (Explain)

Reveal the answer

(a) The available memory is $2\ {\rm GiB} = 2 \times 1024^{3} = 2\,147\,483\,648$ bytes, giving

$$\frac{2\,147\,483\,648}{4096} = 524\,288\ \text{frames} \;\text{(A1)}$$

The array occupies $32\,768 \times 32\,768 \times 8 = 8\,589\,934\,592$ bytes $= 8\ {\rm GiB}$, so it needs

$$\frac{8\,589\,934\,592}{4096} = 2\,097\,152\ \text{frames} \;\text{(A1)}$$

four times what is available, so the working set does not fit and the process must fault under any policy.

(b) Setting $t_{\rm eff} = 2t_{m} = 160\ {\rm ns}$:

$$160 = 80(1-p) + p(8\times10^{6}) \quad\Longrightarrow\quad 80 = p(8\times10^{6} - 80) \quad\Longrightarrow\quad p \approx 1.0 \times 10^{-5} \;\text{(M1)(A1)}$$

A fault probability of one in a hundred thousand — a tenth of a basis point — is enough to double the time of every memory access, because a fault costs about $10^{5}$ times as much as a hit (A1). This is why paging systems are designed so that the fault rate stays several orders of magnitude below that; once it rises to even one per cent, the effective access time is roughly a thousand times the nominal one.

(c) The array holds $4096/8 = 512$ doubles per page (M1).

*Row-major.* Consecutive elements of a row are consecutive in memory, so a full traversal reads each page once and never revisits it. The number of faults is the number of pages:

$$\frac{8\,589\,934\,592}{4096} = 2\,097\,152 \;\text{(A1)}$$

*Column-major.* Consecutive elements of a column are $32\,768 \times 8 = 262\,144$ bytes apart, which is $64$ pages apart, so each access lands on a different page and the traversal revisits every page $512$ times over the course of a column pass. Since the whole array needs $2\,097\,152$ frames and only $524\,288$ are available, pages are evicted long before they are revisited, so essentially every access faults. The number of faults is therefore approximately the number of elements:

$$32\,768 \times 32\,768 = 1\,073\,741\,824 \;\text{(A1)}$$

The ratio is

$$\frac{1\,073\,741\,824}{2\,097\,152} = 512 \;\text{(A1)}$$

exactly the number of doubles that fit in one page. That is not a coincidence: in row-major order one fault serves $512$ consecutive element accesses, while in column-major order one fault serves one, so the ratio is precisely the number of elements per page.

(d) Row-major:

$$2\,097\,152 \times 8 \times 10^{-3} = 16\,777\ {\rm s} = 4.66\ {\rm hours} \;\text{(M1)(A1)}$$

Column-major:

$$1\,073\,741\,824 \times 8 \times 10^{-3} = 8.59 \times 10^{6}\ {\rm s} \approx 99\ {\rm days} \;\text{(A1)}$$

The same computation, on the same data, differing by a factor of $512$ purely because of the order in which the elements are visited.

(e) With $2\ {\rm MiB}$ pages the array occupies $8\,589\,934\,592 / 2\,097\,152 = 4096$ huge pages (M1). For the row-major traversal this reduces the fault count from $2\,097\,152$ to $4096$, a factor of $512$, and the time from $4.66$ hours to $4096 \times 0.008 = 32.8$ seconds (A1). For the column-major traversal it changes nothing: the number of distinct pages is still far more than the available frames can hold, and the access pattern still touches a different page on every single element, so the fault count remains of the order of $10^{9}$ and the traversal still takes about three months (A1). The change has two different effects because the two traversals are limited by different things. The row-major case is limited by the *number* of fault events, and larger pages reduce that number proportionally. The column-major case is limited by the *locality* of the access pattern, and no page size can create locality where the program does not have it: with $512$ doubles per page the row-major case amortises one fault over $512$ accesses, and the column-major case amortises it over one, whatever the page is called.

Markscheme notes

(a) (A1) for each of the two frame counts and (A1) for the conclusion. Accept the counts in gibibytes rather than bytes provided the conversion to frames is shown. Candidates who use $10^{9}$ rather than $1024^{3}$ for a gibibyte should be followed through rather than penalised, but should be told the convention.

(b) (M1) for setting $t_{\rm eff} = 2t_m$ and rearranging, (A1) for $1.0 \times 10^{-5}$, (A1) for a comment that connects the smallness of the probability to the size of the ratio $t_d/t_m$. Accept an answer of $10^{-5}$ given without the subtraction of $80$ from $8 \times 10^{6}$. A candidate who states merely 'a very small probability' without quantifying it loses the final mark.

(c) (M1) for computing 512 doubles per page, (A1) for $2\,097\,152$ faults, (A1) for $1\,073\,741\,824$ faults, (A1) for the ratio 512 with the explanation that it equals the number of elements per page. The explanation carries a mark in its own right: a candidate who produces the two counts and divides them without saying why the quotient is 512 gets three of the four. Credit candidates who note that the column-major figure is an upper bound, since the very first pass through a column may find some pages still resident.

(d) (M1) for multiplying a fault count by the fault cost, (A1) for 4.66 hours, (A1) for about 99 days. Accept 4.7 hours and 100 days. Note that the conversion to hours and days is asked for and should be shown; a raw seconds figure alone loses the accuracy marks.

(e) (M1) for computing 4096 huge pages, (A1) for the row-major improvement to about 33 seconds, (A1) for the column-major case being unchanged, together with the distinction between a limit on the number of fault events and a limit on locality. The distinction is the mark: a candidate who says simply 'huge pages make it faster' without separating the two traversals earns at most one. Credit candidates who observe that huge pages also increase internal fragmentation and are therefore not free, even where they help.

Why this question is hard

The numbers here are large enough to be genuinely alarming, which is the point: a 512-fold difference in running time produced by the order of two nested loops, with no change to the data, the algorithm's output, or the hardware. Four and a half hours against three months.

It is worth being precise about the two conditions, because the item is built on their conjunction and candidates regularly attribute the disaster to only one. If the array fitted in memory, the column-major traversal would still touch memory in a poor order, but it would cost a modest multiple rather than a catastrophe, because nothing would ever be evicted. If the array did not fit but the traversal were row-major, the cost would be one fault per page, which is the minimum possible for streaming through data larger than memory. It takes both — an oversized working set *and* an access pattern with no locality — to reach a fault per element.

That conjunction is exactly why part (e) is interesting. Huge pages reduce the number of pages by a factor of 512, and for a streaming traversal that translates directly into 512 times fewer faults: 4.66 hours becomes 33 seconds. For the strided traversal it is worth nothing at all, because the number of distinct pages was never the binding constraint — the absence of locality was. The same change, applied to the same array, on the same machine, is either a 500-fold win or nothing.

Part (b) deserves a moment on its own, because the number is so small that it looks wrong. A fault probability of one in a hundred thousand doubles the effective access time. The reason is the ratio $t_d/t_m$, which is about $10^{5}$: a fault costs five orders of magnitude more than a hit, so a fault rate of one in ten to the five contributes as much delay as all the hits combined. This is the arithmetic behind the folklore that paging either works or does not — there is no regime in which it degrades gracefully.

The practical lesson generalises past arrays. Any data structure whose traversal order does not match its memory layout pays a fixed penalty per element, and the penalty is the ratio of elements per page. Row-major arrays traversed by column, linked lists where arrays would do, hash tables with poor locality, structures of arrays split into arrays of structures: the underlying arithmetic is the same, and it is the number of useful accesses served per fault.

Challenge lever
Two things have to be true at once for the array traversal to be catastrophic, and separately each is survivable. The working set must exceed the available frames, otherwise everything stays resident and the access order costs nothing; and the access order must be column-major, otherwise the traversal streams through memory and each page is touched once. Neither condition is the cause on its own — it is their conjunction, which is why a fix aimed at one of them, such as moving to huge pages, repairs the sequential case by a factor of five hundred and does nothing at all for the strided one.
