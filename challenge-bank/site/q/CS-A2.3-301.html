A2.3 Why lowering a DNS time-to-live barely changes the latency a busy site's users see, while the same value governs the latency of a quiet one completely

Computer science HL · CS-A2.3-301

Theme A: Concepts of computer scienceA2.3 Data transmissions: the domain name system, caching, and the latency a resolution adds to a request. With A2.1 Network fundamentals: the role of a resolving name serverP1 · Section B16 marksdifficulty 4technology: permittedCalculateCalculateDetermineExplain

Question

A web page references resources from $D = 6$ distinct host names. Each name must be resolved before the resource can be fetched. The organisation runs its own resolving name server, which serves a cached record in $t_{\rm hit} = 2\ {\rm ms}$ and, on a miss, performs a full recursive resolution taking $t_{\rm rec} = 180\ {\rm ms}$. Every record carries the same time-to-live $T$, measured in seconds, and a cached record expires $T$ seconds after it was obtained; the first request arriving after an expiry is the one that pays for the recursive resolution. Requests for the page arrive uniformly at a constant rate $R$ pages per second.
Two services use the same infrastructure. The public service receives $R = 2.0$ requests per second; an internal reporting service, using the same six host names, receives $R = 1.0$ request per minute. In both cases the current value is $T = 300\ {\rm s}$.

  1. [3 marks](a)

    For the public service, calculate the number of recursive resolutions the resolver performs per second, and hence the fraction of page loads that trigger at least one of them.

    (Calculate)
  2. [3 marks](b)

    Calculate the average time per page load spent on name resolution for the public service, and repeat the calculation for $T = 60\ {\rm s}$. State how much DNS traffic increases and how much the average resolution time increases.

    (Calculate)
  3. [3 marks](c)

    Determine the request rate below which the cache is effectively cold, in the sense that essentially every lookup misses, and hence determine the average resolution time per page load for the internal reporting service at $T = 300\ {\rm s}$.

    (Determine)
  4. [4 marks](d)

    Explain why the time-to-live is not the quantity that governs the resolution time a user experiences, identify the dimensionless ratio that does, and state what value of that ratio separates the two regimes. Explain also why the two services experience the same $T = 300\ {\rm s}$ so differently.

    (Explain)
  5. [3 marks](e)

    A colleague proposes lowering the time-to-live to $10\ {\rm s}$ 'so that records are always fresh'. Comment on this proposal with numbers, treating the public service and the internal service separately, and referring to a stated latency budget of $200\ {\rm ms}$ for resolution.

    (Comment)

Reveal the answer

(a) Each of the $D = 6$ records expires once every $T = 300$ s, so the resolver performs

$$\frac{D}{T} = \frac{6}{300} = 0.020 \ \text{resolutions per second }\;\text{(M1)(A1)}$$

in total. Pages arrive at $R = 2.0$ per second, so the fraction of page loads that trigger a recursive resolution is

$$\frac{D/T}{R} = \frac{0.020}{2.0} = 0.010 \;\text{(A1)}$$

about one page load in a hundred. (This assumes the fraction is below one; part (c) examines what happens when it is not.)

(b) Each page load performs $D = 6$ lookups. In the steady state, $0.010$ of them are misses at $180$ ms and effectively all the rest are hits at $2$ ms, so

$$t_{ m DNS} = 6 \times 2 + 0.010 \times (180 - 2) = 12 + 1.78 = 13.8\ {\rm ms} \;\text{(M1)(A1)}$$

With $T = 60$ s the expiry rate is $6/60 = 0.10$ per second and the miss fraction is $0.10/2.0 = 0.050$, giving

$$t_{ m DNS} = 12 + 0.050 \times 178 = 12 + 8.9 = 20.9\ {\rm ms} \;\text{(A1)}.$$

So the resolver's query traffic rises fivefold, from $0.020$ to $0.10$ recursive resolutions per second, while the average resolution time the user sees rises from $13.8$ ms to $20.9$ ms — about $7$ ms, which is well inside any plausible latency budget and barely measurable against the hundreds of milliseconds a page takes to load.

(c) The cache is effectively cold when the expiry rate reaches the arrival rate, that is when

$$\frac{D}{T} \ge R \quad\Longrightarrow\quad R \le \frac{6}{300} = 0.020\ \text{requests per second} = 1.2\ \text{per minute} \;\text{(M1)(A1)}$$

Below that rate, essentially every lookup misses, because the record has expired again before the next request arrives. The internal service receives $1.0$ request per minute $= 0.0167$ per second, which is below $0.020$, so all six of its lookups are misses and

$$t_{ m DNS} = 6 \times 180 = 1080\ {\rm ms} \;\text{(A1)}$$

more than a second of pure name resolution on every page load.

(d) The resolution time a user experiences is set by how often a lookup misses in the moment it is made, and that is governed by the ratio

$$\frac{D/T}{R} = \frac{D}{RT} \;\text{(M1)}$$

the number of records expiring per second divided by the number of requests arriving per second — equivalently, the number of requests that arrive during one lifetime of a record, inverted (A1). The value $1$ separates the regimes: below it the cache is warm and only that fraction of lookups miss; at or above it the cache is cold and every lookup misses, at which point $T$ has no further effect at all because there is nothing left to degrade (A1). The time-to-live alone cannot say which regime a service is in, because it carries no information about $R$: the same $T = 300$ s puts the public service at a ratio of $0.010$, comfortably warm, and the internal service at a ratio of $1.2$, fully cold — a hundredfold difference in resolution time produced by identical configuration (A1).

(e) For the public service, $T = 10$ s gives an expiry rate of $6/10 = 0.60$ per second, a miss fraction of $0.60/2.0 = 0.30$, and

$$t_{ m DNS} = 12 + 0.30 \times 178 = 12 + 53.4 = 65.4\ {\rm ms} \;\text{(A1)}$$

which is thirty times the recursive resolution traffic of the current setting ($0.60$ against $0.020$ per second) and is still within the $200$ ms budget, though it now consumes a third of it on a component that previously used under seven per cent. For the internal service the proposal changes nothing measurable: its ratio is already above $1$ at $T = 300$ s, so it is already paying $1080$ ms on every load, and lowering $T$ further cannot raise a fraction that is already saturated at unity — it only adds resolver load for no benefit (A1). The proposal is therefore poor value at both sites: it buys no freshness that anyone can perceive, since records change rarely, and it spends a large multiple of the query budget to do so. The change that would actually help the internal service is one that raises the ratio above unity by a different route: a longer time-to-live, a scheduled prefetch that refreshes records before expiry, or a local resolver on the reporting host itself (A1).

Markscheme notes

(a) (M1) for computing the expiry rate $D/T$, (A1) for $0.020$ per second, (A1) for the fraction $0.010$. Accept the fraction expressed as a percentage or as 'one request in a hundred'. A candidate who works out $T/D = 50$ s between resolutions and then relates it to the arrival interval of $0.5$ s is taking an equivalent route and earns full marks.

(b) (M1) for a correct weighted average of hit and miss costs, (A1) for $13.8$ ms, (A1) for $20.9$ ms. Accept a candidate who computes two separate totals and subtracts, provided both are shown. The comparison asked for — fivefold traffic, about seven milliseconds — should be credited if stated qualitatively but correctly; the numbers themselves carry the marks here. Forfeits: treating all six lookups as misses whenever a miss occurs, which double-counts and gives $13.8$ ms where the correct figure is lower.

(c) (M1) for setting the expiry rate equal to the arrival rate, (A1) for $0.020$ per second or $1.2$ per minute, (A1) for $1080$ ms. The essential step is recognising that the internal service sits below the threshold; a candidate who computes the threshold correctly but then applies the warm-cache formula to the internal service anyway loses the final mark, because the fraction would come out above one, which is the signal that the model has broken down.

(d) (M1) for forming the ratio $D/(RT)$, (A1) for identifying it as expiries per request or the reciprocal of requests per record lifetime, (A1) for the value $1$ as the boundary and for the observation that beyond it $T$ has no further effect, (A1) for the explicit comparison of the two services under identical configuration. Four fields; credit four. Candidates are not required to use the word 'dimensionless', but should say enough to show they understand it is a comparison of two rates rather than a property of either alone.

(e) (A1) for the public-service figure of $65.4$ ms with the traffic multiple, (A1) for the internal-service conclusion that nothing changes, (A1) for a constructive alternative that would actually help. The last mark requires a mechanism, not a sentence: 'monitor it' or 'review the TTL policy' earns nothing, while a longer time-to-live, a prefetch, or a host-local resolver each earns it. Note that candidates who point out that a 30-fold traffic increase also raises the load on upstream servers should be credited for the observation even if it is not asked for.

Why this question is hard

The reason this trips people up is that a time-to-live is a duration and a latency is a duration, so it feels natural to expect one to set the other. It does not. What determines whether a given user's lookup hits the cache is whether anybody else arrived recently enough to have warmed it, and that is a statement about arrivals per unit time — a rate — compared against the expiry rate. Two rates, one ratio.

Writing the ratio explicitly is the whole move. Expiries per second is $D/T$; requests per second is $R$; the fraction of lookups that miss is their ratio, capped at one. Everything else in the item follows from that one expression, including the two facts that make it interesting: the cap at one, which is why there is a threshold at all, and the fact that $R$ appears in it, which is why the same configuration behaves differently for two services.

The numbers were chosen so the two services sit on opposite sides of the threshold with nothing in between. At $R = 2.0$ per second the ratio is $0.010$ and the resolution cost is $13.8$ ms, essentially all of it the six cheap hits. At $R = 1/60$ per second the ratio is $1.2$, the cache is cold, and the cost is $1080$ ms. Same $T$, same $D$, same resolver, seventy-eight times worse. Nothing about the configuration changed; only the traffic did.

The cap at unity is the part worth carrying away, because it is the source of the asymmetry in part (e). Above the threshold, changing $T$ does nothing at all — the service is already paying the maximum and there is no headroom to lose. Below it, changing $T$ scales the miss fraction linearly but only shifts a small component of a mostly-hit workload. So lowering a time-to-live is either useless or mildly expensive, and raising it is either transformative or mildly beneficial, and which you get is decided entirely by the traffic. That is a genuinely useful thing to know before touching a DNS setting.

One more lesson hides in part (b), which is about the difference between cost and cost-per-user. The resolver's query traffic went up fivefold, which sounds alarming, while the user-visible latency went up by seven milliseconds, which is not. Both are true. A change can be expensive for infrastructure and invisible to users, and deciding which of those matters is a judgement the numbers cannot make for you.

Challenge lever
The time-to-live is the obvious dial and it is the wrong one. What sets how often a user waits for a full recursive resolution is not how long records live but how many requests arrive during one lifetime: the ratio of records expiring per second to requests arriving per second. Once the request rate exceeds the expiry rate, the cache is warm almost all the time and the contribution of resolution to page load is dominated by cheap hits, so a fivefold change in TTL moves the average by a few milliseconds. At a request rate below the expiry rate, every single request waits for a full resolution and the same TTL produces a latency a hundred times worse.
