B2.2 Two hash tables of different sizes holding the same six keys: the load factor is not what decides the number of collisions

Computer science HL · CS-B2.2-401

Theme B: Computational thinking and problem-solvingB2.2 Data structures (hash tables, collisions and the cost of the operations they support), with B2.4 Programming algorithms (B2.4.1 the complexity of an algorithm)P16 marksdifficulty 5technology: not allowedCalculateExplainDetermine

Question

A program stores six records in a hash table. Each record is 16 bytes long and they lie consecutively in a memory image, so the six keys passed to the hash function are the byte offsets 4096, 4112, 4128, 4144, 4160 and 4176.

The hash function is h(k) = k mod m, where m is the size of the table and the result is the slot number. Collisions are resolved by chaining, so every slot holds a list of the keys that hash to it and a lookup walks that list. The figure shows the same six keys in two tables, one of size 16 and one of size 17. The load factor of a table is the number of stored keys divided by the number of slots.

A colleague proposes to enlarge the table from 17 slots to 20 slots in order to reduce the number of collisions.

(a) Calculate the load factor of each of the two tables shown, and state the number of slots occupied in each.

(b) Explain why the table of size 16 stores all six keys in one slot although its load factor is the lower of the two, and state which quantity decides how the keys are distributed.

(c) Determine the number of slots occupied for table sizes 8, 16, 17 and 20, and hence determine the smallest table size of 20 or less that stores all six keys in distinct slots.

Reveal the answer

(a) The table of size 16 holds six keys in sixteen slots, so its load factor is 6 / 16 = 0.375 (A1). The table of size 17 holds the same six keys in seventeen slots, so its load factor is 6 / 17 = 0.353 to three decimal places, which is lower. The table of size 16 occupies one slot, because every key hashes to slot 0: 4096 is a multiple of 16, and every other key is 4096 plus a multiple of 16, so every key leaves the same remainder, zero. The table of size 17 occupies six slots, holding 4096 in slot 16, 4112 in slot 15, 4128 in slot 14, 4144 in slot 13, 4160 in slot 12 and 4176 in slot 11 (A1).

(b) The load factor measures how full a table is, not how the keys are arranged within it, and those are different questions. Here all six keys are congruent modulo 16 because the gap between consecutive keys is 16 and 16 divides 16 exactly, so the remainder is the same for every one of them and the chain has length six whatever the load factor says (M1). In the table of size 17 the same gap of 16 shares no common factor with 17, which is prime, so adding 16 repeatedly cycles through six different remainders before repeating. The quantity that decides the distribution is the relationship between the stride, 16, and the table size: the keys collide when the stride and the size have a common factor, and in the extreme case of the size dividing the stride exactly, every key lands in the same slot (A1). A table of size 8 or 16 divides the stride and collapses completely, while a table of size 17 is coprime to it and separates the keys perfectly.

(c) For a table of size 8 every offset is a multiple of 8, so all six keys hash to slot 0 and one slot is occupied. For size 16 the same collapse gives one slot. For size 17 the six remainders are 16, 15, 14, 13, 12 and 11, all different, so six slots are occupied (A1). For size 20 the key 4096 gives remainder 16 and the key 4176 gives remainder 16 as well, because 4176 = 4096 + 80 and 80 is a multiple of 20; the six remainders are 16, 12, 8, 4, 0 and 16, so five slots are occupied. The smallest size of 20 or less that separates all six keys is 7: the remainders there are 1, 5, 4, 3, 2 and 6, six distinct values, and no size below 7 can separate six keys because it does not have six slots (A1). The proposal to enlarge the table from 17 slots to 20 slots would therefore make matters worse rather than better, reducing the number of occupied slots from six to five and lengthening the chain in slot 16 to two keys.

Markscheme notes

(a) (A1) for 0.375 and 0.353, with the lower value explicitly attached to the table of size 17; (A1) for one slot and six slots. The slot numbers 16 down to 11 are not required, but a candidate who lists them has demonstrated the arithmetic and should be credited.

(b) (M1) for the observation that the gap between consecutive keys is a multiple of the table size in the first case and shares no factor with it in the second; (A1) for naming the relationship between the stride and the table size, or the greatest common factor of the two, as the deciding quantity. Do not accept 'the table is too small' or a restatement of the load factor as the explanation: the whole point of the part is that a smaller load factor did not help. Accept a candidate who phrases the condition as the six keys being congruent modulo the table size.

(c) (A1) for the four counts 1, 1, 6 and 5, correctly attached to 8, 16, 17 and 20; (A1) for 7. A candidate who gives 7 with the reason that no smaller size has six slots earns the mark; a candidate who gives 7 from a list without justification does not. Accept 17 as an answer to 'smallest size above 16', but the question asks for the smallest overall and 7 is the answer.

Why this question is hard

The two panels in the figure are arranged so that the smaller table is the better one and the difference is not small. Six keys in one chain against six keys in six chains is a factor of six in the average lookup cost, and the tables it is choosing between have load factors of 0.375 and 0.353, a difference of about six per cent. Anyone who ranks the two by load factor gets the order exactly wrong, and does so with a number that is an accepted measure and is not being misused: the load factor is genuinely 0.375, and it genuinely is lower than 0.353. The error is not arithmetic, it is choosing a measure that does not answer the question.

What does answer the question is the arithmetic of the stride. The keys are not arbitrary; they are consecutive 16-byte records, which is what a real allocator produces, and every key therefore differs from the first by a multiple of 16. The remainder after division by a table size m is the same for all six keys exactly when m divides every one of the five gaps, that is when m divides 16. Sizes 1, 2, 4, 8 and 16 destroy the table; every other size gives some spreading, and a size coprime to 16 gives complete spreading, because then the five additions of 16 generate five distinct non-zero residues. Seventeen is prime and coprime to 16, which is why it is perfect; fourteen is not coprime either, but because 16 has only one factor of 2 above 8 the multiples 16, 32, 48, 64 and 80 reduced modulo 14 give 2, 4, 6, 8 and 10, which are still six distinct offsets, so it works as well.

The general lesson is that a hash function built from the identity of a key and a modulus is only as good as the relationship between the data and the modulus, and that a prime table size is the standard defence precisely because it removes the possibility of a common factor. It is worth noticing that the colleague in the question makes a mistake that looks like prudence. Enlarging a table is the ordinary response to collisions, it costs memory, and here it reduces the number of occupied slots while increasing the longest chain. Raising a resource is not the same as fixing a distribution.

Challenge lever
The load factor is the first number anybody computes about a hash table and it is reported on every data-structures slide, so it is reached for automatically. Here it is a decoy of a precise kind: the table of size 16 has the lower load factor, 0.375 against 0.353, and is catastrophically worse, because the six keys are byte offsets separated by a stride of 16 and every one of them is therefore a multiple of 16. The quantity that decides the outcome is the relation between the stride and the table size, and the relation is that the six keys occupy distinct slots exactly when no multiple of the stride up to five times it is divisible by the size. A candidate who answers from the load factor gets the ranking of the two tables exactly backwards, and the reversal is not marginal: one table holds all six keys in a single chain and the other spreads them perfectly, at almost the same load factor. The second half of the item makes the point structural rather than anecdotal by asking for the smallest size that separates all six keys, which cannot be reached by estimating and has to be found by working through the sizes.

Adaptation
The source presents the load factor as the quantity to keep below a threshold and illustrates collisions with arbitrary integer keys. Here the six keys are the byte offsets of consecutive fixed-length records, which is what makes the stride a multiple of the table size rather than a coincidence, and the question is built so that the table with the lower load factor is the worse of the two. The candidate is asked to explain the reversal, to name the quantity that actually decides the distribution, and to find the smallest table size that separates all six keys, which requires searching a range of sizes rather than applying a rule of thumb. The colleague's proposal to enlarge the table from 17 to 20 slots is added because it is worse than the original, which the source material provides no reason to check.
Verification
The six keys 4096 + 16k for k = 0 to 5 were reduced modulo every table size from 1 to 40 and the number of distinct remainders recorded. Sizes 8 and 16 give one distinct remainder, matching the collapse shown in the figure; sizes 7, 9, 11, 13, 14, 15, 17, 18 and 19 give six. Size 20 gives five, because 4096 and 4176 are congruent modulo 20. The smallest size giving six distinct remainders is 7. The load factors were computed as 6/16 = 0.375 and 6/17 = 0.35294 and confirmed to be in the order stated, so that the worse table has the lower load factor.
