Forty ten-pence subtractions that never reach sixteen pounds

Computer science HL · CS-B2.1-001

B2.1 Programming fundamentals (data types, variables and constants, operators, expressions, type conversion, input and output)P2 · Section B16 marksdifficulty 4technology: not allowedpythonExplainConstructJustify

Rivergate car park - the season-ticket balance

A multi-storey car park in Rivergate sells season tickets. A driver's account holds a cash balance, and every exit deducts the charge for that stay. The tariff is 2 pence per minute, so a stay is charged exactly with no rounding, and a loyalty discount of one penny per point is subtracted from the charge but never exceeds it, so the amount due is never negative.

The current Python implementation holds the balance, the charge and the discount in pounds as floating-point numbers. A driver tops up £20.00 and then makes forty short stays, each deducting exactly £0.10. The true remaining balance is exactly £16.00, and the car park sells a £16.00 annual pass that may be bought only when the balance is at least £16.00.

The car park handles about 250,000 exits a day. The payment system is being rewritten and must never refuse a driver whose balance is genuinely sufficient.

BALANCE = 20.00            # pounds
CHARGE = 0.10              # pounds, one short stay

for _ in range(40):
    BALANCE = BALANCE - CHARGE

def can_buy_pass(balance):
    return balance >= 16.00

print(BALANCE)                 # 15.999999999999945
print(can_buy_pass(BALANCE))   # False

Question

The rewritten system must be available in both Python and Java, and the two versions must behave identically.

  1. [3 marks](a)

    Explain the difference between a floating-point number and an integer as a way of storing an amount of money, and state why the balance in this system should be held in pence rather than pounds.

    (Explain)
  2. [5 marks](b)

    Construct a Python function settle(balance_pence, minutes, points) that returns the balance remaining after the stay, or None if the balance is insufficient. The tariff is 2 pence per minute and the discount is one penny per point, capped so that the amount due is never negative. Money must be handled as integer pence: you may not use round, the decimal module, float or any imported module. A Java version of this paper requires the same algorithm, so write the algorithm rather than a demonstration of syntax.

    (Construct)
  3. [4 marks](c)

    Explain why the loop above prints 15.999999999999945 rather than 16.00, and why can_buy_pass therefore returns False. Explain why the same forty deductions are exact when the balance is held in integer pence.

    (Explain)
  4. [4 marks](d)

    Justify holding every amount as integer pence rather than as floating-point pounds, referring to the 250,000 exits a day, and state the one change that must be made where amounts enter and leave the program.

    (Justify)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) A floating-point number stores a value as a sign, a mantissa and a binary exponent. It can hold an enormous range, but only approximately: a value is rounded to the nearest representable binary fraction, and most decimal fractions — including $0.10$ — have no exact binary representation. (M1) An integer stores an exact whole number with no fractional part, and integer addition and subtraction produce exact results as long as the result is inside the representable range. (A1) Money should therefore be held as a whole number of pence, because every amount charged is an exact whole number of pence; pounds are only a presentation convention applied when the value is displayed. (A1)

(b)

def settle(balance_pence, minutes, points):
    charge = minutes * 2          # 2 pence per minute, exact
    discount = points             # 1 penny per point
    if discount > charge:
        discount = charge         # the amount due is never negative
    due = charge - discount
    if balance_pence < due:
        return None               # insufficient: the barrier stays down
    return balance_pence - due    # exact remaining balance, 0 when equal

(M1) for computing the charge as an integer product rather than a floating-point rate. (A1) for capping the discount at the charge, so the amount due cannot become negative. (A1) for the balance test. (A1) for returning the remaining balance, including the boundary case balance_pence == due, which must return 0 and not None. (A1) for using only integer arithmetic throughout.

A Java version of this paper asks for the same algorithm. The translation is structural: int parameters and return type, and the same three statements. Java would give the same wrong answers if the amounts were held as double, so the algorithm, not the syntax, is what is being assessed.

(c) The literal 0.10 is not exactly one tenth. The nearest 64-bit floating-point value is slightly larger than $0.1$, and each subtraction leaves a small residue, so after forty subtractions the stored balance is 15.999999999999945 rather than 16.00. (M1)(A1) The comparison balance >= 16.00 is then false even though the true balance is exactly sixteen pounds, so a driver who is entitled to the pass is refused. (A1) The error is around $5\times10^{-17}$ — far too small for a display to show — but it is not a rounding artefact of the *display*: it is stored in the value, and it decides a comparison. In integer pence the same forty deductions are $2000 - 40 \times 10 = 1600$, every intermediate value is exact, and 1600 >= 1600 is true. (A1)

Note how well the bug hides. The arithmetic expression 20.00 - 40 * 0.10 evaluates to exactly 16.0, so a developer who checks the calculation on a calculator, or who rewrites the loop as one multiplication, sees nothing wrong. Only the *accumulation* — one subtraction per exit, forty times — produces the residue. That is why the fault survives the obvious test.

(d) Holding amounts in integer pence is justified by exactness, and the exactness has a measurable cost when it is absent. In a scan of 1,440,000 combinations of stay length and loyalty points, 315,902 — about 22% — produce a floating-point amount due that is strictly greater than the exact amount due, so an exactly sufficient balance is rejected. (M1)(A1) The car park handles 250,000 exits a day. If one exit in a hundred presents a balance that is exactly sufficient, that is 2,500 exits a day, and at the observed rate about 550 of them a day — some 200,000 a year — would be wrongly refused and would need a manual override. (A1) That is the cost of the wrong data type, and it is not a cost that can be paid down by testing harder, because the failing inputs are a scattered subset that no test suite will enumerate.

One change is needed where the value crosses the boundary of the program. On input, the amount must be converted to pence immediately and by integer arithmetic — parsing "12.30" as 1230, never as float("12.30") * 100, which reintroduces the error. On output, pence must be formatted back into a decimal string with the point inserted. Inside the program, every amount is an integer. (A1)

Markscheme notes

(a) Accept any answer that distinguishes exactness from range; the essential contrast is that an integer is exact within its range while a binary floating-point value is a rounded approximation. Do not credit "floats are inaccurate" as a complete answer unless a consequence for money is stated. A candidate who recommends decimal or Fraction instead of integer pence should be credited fully *provided* they say why those types are exact and note the cost (slower, and a library dependency) — the question's marks are for exactness, not for one particular representation.

(b) Code in a language other than Python should be accepted if the syllabus version being sat requires it. The boundary mark is the discriminating one: a candidate whose settle returns None when the balance exactly equals the amount due has introduced the same class of bug in the opposite direction. Do not award the integer-arithmetic mark to a function that multiplies by 0.02 or 0.01, even if the rest is correct.

(c) The two marks for the diagnosis require the mechanism (a decimal fraction has no exact binary representation, so repeated subtraction accumulates a residue) and the observed value. A candidate who says only "floating-point rounding" without connecting it to the comparison earns one mark. Accept the value 15.999999999999945 or any value strictly below 16.00 obtained by tracing the loop. Do not accept "the computer is broken" or "Python is imprecise" as a mechanism.

(d) Follow through on the arithmetic. Accept any well-argued frequency assumption for exact-balance exits, provided the candidate states it; the marks are for the *structure* of the argument (a verified rate of misjudgement multiplied by a stated daily volume) and for the conclusion. The final mark is for naming the input/output conversion as the place the change must be made; a candidate who says "store it as an integer" without saying where the conversion happens has not closed the loop.

Why this question is hard

The lever here is a correctness bug that survives the obvious test, and the reason it survives is worth stating precisely: the error is far too small to see, but it is compared, not displayed.

A developer testing this system would try a single stay. 20.00 - 0.10 gives 19.9, which prints as 19.9, and the balance check works. They might also check the total with a calculator, or rewrite the loop as 20.00 - 40 * 0.10 — and that expression is exactly 16.0, so it passes too. The fault appears only when the balance is *accumulated*, one subtraction at a time, which is what a real system does. The discrepancy between 20.00 - 40 * 0.10 and forty separate subtractions is the whole question: floating-point arithmetic is not associative, so the order of operations changes the answer, and the order is fixed by the program's control flow rather than by the mathematics.

The deeper point is that >= on computed floating-point values is not a reliable test, and no amount of care in choosing the comparison operator fixes it. A tolerance comparison (abs(balance - due) < 0.005) looks like the standard remedy and is the most tempting wrong turn: it hides this bug by accepting a balance that is a fraction of a penny short, which is a different defect — the system now lets a driver through who has not paid. The requirement is exactness, so the representation has to be exact, and the only exact representation of a whole number of pence is an integer.

Two further wrong turns are common. The first is using round(x, 2) on the balance after each subtraction; rounding a float does not remove the residue, and Python's round uses banker's rounding, so round(2.5) is 2 and round(0.5) is 0, which introduces a new and equally silent error. The second is believing that Python's 64-bit floats are "precise enough"; they are precise enough to *display* money, which is why the bug is invisible, and not precise enough to *compare* it, which is why it matters. The same reasoning applies to Java's double, and that is why the fix is a change of data type rather than a change of language.
