A singleton holding a mutable setting

A web application runs 12 user sessions at the same time. Each session needs to know which measurement units to display, and the user can change the units at any moment.

The units are held in a class called Settings, which is written as a singleton: a private static attribute holds the one instance, a static method getInstance() returns it, and an instance attribute units holds the current unit name. Every session obtains the settings object through getInstance() and reads and writes units on it. Because there is only ever one Settings object, every session is reading and writing the same field.

In one hour the units field is changed 34 times across the 12 sessions.

Question

Evaluate the singleton as a home for the units field. Assume the 12 sessions overlap in time, that any of them may change the units at any moment, and that a session reads the units immediately before it formats a measurement.

  1. [3 marks](a)

    State what a session reads when it asks the settings object for the units, if a different session changed the units a fraction of a second earlier.

    (State)
  2. [4 marks](b)

    Determine the number of session-and-change pairs in which a session observes a change it did not make, and express that number as a percentage of all session-and-change pairs.

    (Determine)
  3. [5 marks](c)

    Explain why the singleton is the right pattern for obtaining the settings but the wrong pattern for storing the units field, and state where a session's own units should be held instead.

    (Explain)
  4. [4 marks](d)

    A colleague proposes keeping the singleton and adding a sessionId attribute, so that setUnits can ignore changes made by other sessions. Justify whether that repairs the design.

    (Justify)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

Part (a). The session reads the most recently written value, whichever session wrote it. There is one storage location, so the last write wins, and the session has no way to tell whether the value it received is the one it set. (M1)(A1)(A1)

Part (b). Each of the 34 changes is visible to every session except the one that made it, so each change produces 12 - 1 = 11 unintended observations. The number of such session-and-change pairs is therefore 34 x 11 = 374. (M1)(A1)

The total number of session-and-change pairs is 34 x 12 = 408. (A1)

So 374 / 408 = 0.91666..., which is 91.7% to one decimal place. (A1) The 34 pairs that are not unintended are the ones in which a session observes its own change.

Part (c). The singleton is the right pattern for obtaining the settings. The units are a property of the application rather than of a session, so the value has to be reachable from anywhere in the code; constructing a fresh Settings per session would give each session a different starting value; and a single access point means the configuration is loaded once rather than repeatedly. getInstance() supplies all three without exposing a global variable. (M1)(A1)(A1)

It is the wrong pattern for storing a mutable value that belongs to a session, because one storage location cannot hold two different values at the same moment. Two sessions that want different units are not in conflict about the object — they are in conflict about the field, and no care taken at the access point can resolve that. (A1)

The units a session is using belong to that session, so they should be held in an instance attribute of the session, or passed into the formatting call as a parameter. The singleton can still hold the default units, which is a value about the application rather than about any session. (A1)

Part (d). Adding sessionId does not repair the design. It lets setUnits refuse a write that came from another session, so a session's own writes are protected from being overwritten by its neighbours. (M1)(A1)

But the field is still a single storage location. The sessionId records whose value is currently stored; it does not let two sessions each have one. If session 1 sets the units to metres and session 2 then sets them to feet, the field holds one of those two values and the other session has lost its setting. Refusing the second write does not preserve session 1's value *for* session 2 — it merely prevents session 2 from setting anything at all, so the second session is now unable to choose its units rather than able to choose them independently. (A1)

The test to apply is whether two sessions can hold two different values at the same moment. A single field cannot, whatever guard is placed on the setter, because the guard changes who is allowed to write and not how many values exist. Repairing the design means one value per session, which means moving the field out of the singleton; the singleton can keep the default and the access point. (A1)

Markscheme notes

(a) M1 for the last-write-wins idea, A1 for naming the most recent value, A1 for noting that the reading session cannot tell whose value it received. A candidate who answers "its own value" has missed the sharing and scores nothing in this part.

(b) M1 for 12 - 1 = 11 sessions per change, A1 for 374. A1 for 408 as the total. A1 for 91.7%. Accept 91.67% or 0.917. A candidate who computes 34 x 12 = 408 as the unintended count has confused the total with the subset and should lose the first A1.

(c) M1 for the access-point argument, A1 for reachability from anywhere in the code, A1 for a single shared initial value or a single load. A1 for the observation that one storage location cannot hold two values at once. A1 for moving the units into the session or passing them per call. Do not award the final A1 for a restatement of the problem in part (a); the mark is for naming where the value should live.

(d) M1 for stating what the guard does, A1 for recognising that it protects a session's own writes. A1 for the observation that the field remains one location. A1 for the conclusion that the second session is blocked rather than served, or for the two-values-at-once test. A candidate who concludes that the proposal repairs the design because writes are now checked scores at most two marks.

Why this question is hard

The singleton is the pattern most often taught as a recipe and least often taught with its limits, and this item separates the two uses that the recipe runs together. The pattern exists to guarantee that one object of a class exists and to give it a known access point. Neither of those guarantees says anything about whether the object's *fields* are safe to share, and the item is built on that gap.

The trap is that the code is a textbook singleton. A candidate who knows the pattern will recognise it, will see getInstance() implemented correctly with a private static instance and a static accessor, and will have no reason to suspect it. The defect is not in the implementation of the pattern but in what has been put inside the object, and nothing about the pattern's shape draws attention to it.

The counting in part (b) is designed so that the wrong model produces a plausible number. A candidate who counts each change once will report 34 unintended observations, which is the number of changes, not the number of sessions that saw them. A candidate who counts every pair will report 408. Only the model in which each change is seen by every session except its author gives 374, and 374/408 = 91.7% is the figure that makes the problem's scale visible: nine out of ten observations in this system are of a value the session did not choose.

Part (c) is the conceptual centre and it asks for a separation that the pattern's own name conceals. The same object can be the right home for a default and the wrong home for a session's setting, and a candidate who can say which is which has understood scope rather than syntax.

Part (d) is the hardest part because the proposed fix is thoughtful. Guarding the setter with a session identifier is exactly the kind of repair a competent engineer reaches for, and it does improve the behaviour: a session's writes are no longer clobbered by its neighbours. What it cannot do is change the number of values the field can hold, which is one. The item's test — can two sessions hold two different values at the same moment — is deliberately a question about storage rather than about permissions, because that is the distinction the fix obscures. A session that is forbidden to set its units has not been given its own units; it has been given the other session's units and told not to argue.
