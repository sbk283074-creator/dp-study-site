A3 Databases

Computer science HL · CS-A3.2-001

A3.2 Database design (schemas, ERDs, normalisation), A3.3 Database programming (SQL joins, views HL only)P1 · Section A16 marksdifficulty 4sqlExplainConstructState

Stimulus

A small music festival stores all of its booking data in a single table:

PERFORMANCE_BOOKING

| BookingID | CustomerName | CustomerEmail | PerformanceName | VenueName | SeatCategory | PricePerTicket | Quantity |
|---|---|---|---|---|---|---|---|
| 1001 | A. Ferrer | a.ferrer@mail | Midnight Chorus | East Stage | Premium | 85.00 | 2 |
| 1002 | A. Ferrer | a.ferrer@mail | Midnight Chorus | East Stage | Standard | 45.00 | 4 |
| 1003 | L. Oyeka | l.oyeka@mail | Brass Quartet | West Barn | Standard | 40.00 | 2 |
| 1004 | R. Duval | r.duval@mail | Midnight Chorus | East Stage | Premium | 85.00 | 1 |
| 1005 | R. Duval | r.duval@mail | Brass Quartet | West Barn | Standard | 40.00 | 3 |

BookingID is unique. A customer may make several bookings, and a performance runs in exactly one venue.

Question

The festival is expanding and the table is causing problems.

  1. [5 marks](a)

    Explain two specific problems with this design, using the data above to illustrate each. For each, name the type of anomaly it represents.

    (Explain)
  2. [5 marks](b)

    Construct a set of tables in third normal form (3NF) to replace PERFORMANCE_BOOKING. State the primary key of each table and show the foreign-key links between them.

    (Construct)
  3. [4 marks](c)

    Using your 3NF design, write an SQL query that lists the customer name, the performance name and the total cost of each booking (quantity × price), for bookings of more than two tickets, ordered by total cost from highest to lowest.

    (Construct)
  4. [2 marks](d)

    Box-office staff need to see booking details but must not see customer email addresses or prices. Explain how a database view solves this. (HL only)

    (Explain)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) Award two from:

  • Update (modification) anomaly. 'Midnight Chorus' and its venue 'East Stage' are repeated in rows 1001, 1002 and 1004. If the performance is moved to another venue, every one of those rows must be changed; if even one is missed, the database holds contradictory answers and a report cannot say where the performance is. (A1)(A1)
  • Insertion anomaly. A newly announced performance cannot be added to the database until someone books it, because the only place a performance name can exist is inside a booking row — and BookingID is the key, so there is no way to store a performance with no bookings. (A1)(A1)
  • Deletion anomaly. If customer L. Oyeka cancels booking 1003, that row is the only record of 'Brass Quartet' at the West Barn; deleting the booking destroys the performance record as well. (A1)(A1)
  • Redundancy / wasted storage. Customer name and email are repeated across every booking that customer makes, so A. Ferrer's details are stored twice and R. Duval's twice, and the repetition grows with the festival. (A1)(A1)

(Maximum 5 marks; at least one answer must name the anomaly type for the higher band.)

(b) A correct 3NF decomposition:

CUSTOMER(CustomerID PK, CustomerName, CustomerEmail)

PERFORMANCE(PerformanceID PK, PerformanceName, VenueName)

SEAT_PRICE(PerformanceID FK, SeatCategory PK *(composite with PerformanceID)*, PricePerTicket)

BOOKING(BookingID PK, CustomerID FK, PerformanceID FK, SeatCategory FK, Quantity)

Award (A1) for separating CUSTOMER, (A1) for separating PERFORMANCE, (A1) for recognising that PricePerTicket depends on the *performance and seat category* pair rather than on the booking (so it needs its own table), (A1) for correct primary keys, (A1) for correct foreign keys linking BOOKING to CUSTOMER and PERFORMANCE.

Why this is 3NF: in every table, each non-key attribute depends on the key, the whole key, and nothing but the key. In particular, PricePerTicket is no longer stored against BookingID (a transitive/partial dependency), and VenueName is no longer repeated per booking.

Note: the original table has no CustomerID or PerformanceID, so surrogate keys must be introduced — credit this explicitly if done.

(c) One correct solution:

SELECT c.CustomerName,
       p.PerformanceName,
       b.Quantity * s.PricePerTicket AS TotalCost
FROM BOOKING b
JOIN CUSTOMER    c ON b.CustomerID    = c.CustomerID
JOIN PERFORMANCE p ON b.PerformanceID = p.PerformanceID
JOIN SEAT_PRICE  s ON b.PerformanceID = s.PerformanceID
                  AND b.SeatCategory  = s.SeatCategory
WHERE b.Quantity > 2
ORDER BY TotalCost DESC;

Award (A1) for joining the three or four tables correctly, (A1) for the composite join to SEAT_PRICE (both PerformanceID *and* SeatCategory — joining on SeatCategory alone is the common error and returns wrong prices), (A1) for the computed total and the WHERE b.Quantity > 2 filter, (A1) for ORDER BY TotalCost DESC.

(d) A view is a stored, named query that behaves like a virtual table. (A1) The administrator creates a view exposing only BookingID, CustomerName, PerformanceName, SeatCategory and Quantity, grants box-office staff SELECT on that view, and grants them no privileges at all on the underlying tables. Staff then query the view and cannot reach the excluded columns or the base tables, so security is enforced by the database itself rather than by trusting an application or a member of staff. (A1)

Markscheme notes

(a) Two problems, each illustrated from the data, each named. A problem described without reference to the data is capped at one mark per problem; a problem described without naming the anomaly type is likewise capped. Do not credit 'it is not normalised' as an explanation.

(b) Accept any correct 3NF decomposition, including one that keeps PricePerTicket in BOOKING *if* the candidate has defined the price as a property of the individual transaction (e.g. historic pricing) and says so — but push for the four-table version, since price is a property of the (performance, category) pair. The composite join in (c) is what discriminates.

(c) Credit equivalent SQL: implicit joins in the WHERE clause, INNER JOIN spelled out, or an alias for the computed column. Minor syntax slips (missing semicolon, AS omitted) should not be penalised. Do not credit a query that omits the SEAT_PRICE join and uses a literal price.

(d) One mark for what a view is, one for the security mechanism (granting privileges on the view and withholding them from the base tables). Candidates who say 'a view hides the data' without explaining the grant mechanism earn only the first.

Why this question is hard

Normalisation is one of the topics students can define flawlessly and apply badly. This question is built so that definitions are not enough.

In (a) the anomalies have to be *demonstrated* on the five rows given. 'Repetition causes problems' is not an answer; 'Midnight Chorus is stored three times, so moving it to a different venue means editing three rows, and missing one leaves the database contradicting itself' is. Naming it as an update anomaly is what lifts the answer into the top band.

Part (b) is where the design decisions live, and there are two of them:

1. Customer and performance must be split out — that part is routine.
2. Price is the interesting one. PricePerTicket looks like it belongs to the booking, but it is a property of the (performance, seat category) *pair*: Premium seats for Midnight Chorus cost 85.00 in rows 1001 and 1004, identical because they are the same pair, not because they are the same booking. Leaving price in BOOKING leaves a transitive dependency and the table is not in 3NF. Most candidates miss this.

Part (c) then punishes the mistake automatically: if SEAT_PRICE was not separated out, the query cannot be written correctly, and if it was, the join must be on both PerformanceID and SeatCategory. Joining on SeatCategory alone silently returns several prices per row and a wrong total — the kind of error that produces a plausible-looking report and no error message.

Classic wrong turns: introducing CustomerID but then never using it as a foreign key; writing SELECT with no JOIN conditions (a Cartesian product); and describing a view as a copy of the data (it is not — it is a stored query, and it reflects changes to the base tables immediately).
