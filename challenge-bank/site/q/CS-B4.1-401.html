A logger that keeps its readings in a singly linked list

A data logger keeps its most recent readings in a singly linked list. Each node holds one reading in a field called data and one pointer in a field called next that points at the following node. The last node's next pointer is None, and the whole list is reached through a single variable head that points at the first node. No node holds a pointer to the node before it.

After four readings have been logged the list is A -> B -> C -> D, where A is the node that head points at and D is the last node.

A method remove(node) is added to the class. It is called with a reference to the node that should be deleted and with nothing else: it is not given head, and it is not told where the node sits in the list.

Question

Evaluate the design of remove(node). Assume the list is never empty when remove is called, and that no other part of the program holds a reference to the node that is deleted.

  1. [4 marks](a)

    Explain why remove(node) cannot delete node by changing the pointer that currently reaches it.

    (Explain)
  2. [4 marks](b)

    Describe the technique that remove(node) can use instead, stating what it must do to the node's data field and what it must do to its next field.

    (Describe)
  3. [5 marks](c)

    Determine which of the four nodes A, B, C and D a correctly written remove(node) can delete in a list of four nodes, and explain what goes wrong for the node it cannot delete.

    (Determine)
  4. [3 marks](d)

    State the single change to the node's structure that would make every node deletable in a constant number of steps, and state what that change costs.

    (State)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

Part (a). In a singly linked list the only pointer that reaches node is the next pointer of the node before it. Deleting node means changing that predecessor's next pointer so that it skips over node and points at node.next. (M1)

The method receives a reference to node itself. From node there is no pointer backwards, so the predecessor cannot be reached from the argument. The only route to the predecessor is to start at head and walk forward until some node's next pointer is node — which costs a traversal of the whole list up to that point, and which would make the reference that was passed in pointless, since the same walk would have found the node by value. (A1)

So the method holds the object that must disappear, while the thing that must change is a field of a different object it has no way to name. (A1)(A1)

Part (b). The technique is to overwrite the node with its successor and then unlink the successor, in two assignments:

node.data = node.next.data
node.next = node.next.next

The first line copies the successor's reading into the node the caller is holding, so that node's value becomes the successor's value. (M1) The second line makes the node point past its successor, so the successor is no longer reachable from anywhere in the list. (A1) The caller's reference stays valid, the list is one node shorter, and the node that is actually released is the successor rather than the node the caller named. (A1)

It is worth being explicit that the *object* the caller holds survives while the *value* it was created with does not. Any other part of the program that kept a reference to the successor is now holding a node that is no longer in the list, and any part that looks for the deleted value will find it in the node it did not nominate. (A1)

Part (c). It works for A, B and C.

For A: A.data becomes B's reading and A.next becomes C, so the list reads (B) -> C -> D. For B: B.data becomes C's reading and B.next becomes D, giving A -> (C) -> D. For C: C.data becomes D's reading and C.next becomes D.next, which is None, giving A -> B -> (D). (M1)(A1)(A1)

It fails for D. D is the last node, so D.next is None, and the first assignment evaluates None.data. In Python that raises AttributeError; in a language without exceptions it would follow a null pointer and the program would be undefined from that point on. (A1)

So three of the four nodes can be deleted and the one that cannot is the one whose successor does not exist. (A1) The failure is not a corner case in the arithmetic sense — it is the ordinary case of deleting the last item, which any logger will reach as soon as it trims its oldest reading. Note also that in a circular list no node has next equal to None, so the technique would appear to work on all four nodes; for the last node it would overwrite the head's data, corrupting the list silently instead of failing loudly, which is worse.

Part (d). Give each node a second pointer to the node before it, making the list doubly linked. (M1) Then the node can be unlinked directly by joining its two neighbours to each other, which is a constant number of pointer assignments for every node including the last one. (A1)

The cost is one extra reference per node. Four nodes need four extra references, so the node structure doubles in size for a list that holds one reading per node. (A1)

Markscheme notes

(a) M1 for identifying that the predecessor's next pointer is the one that must change. A1 for the observation that no backward pointer exists from the argument. A1 for the consequence: the predecessor cannot be named from node. A1 for noting that reaching it requires a traversal from head, which defeats the purpose of the argument. Accept any phrasing that distinguishes the object held from the field that must change.

(b) M1 for the copy-the-successor idea in any form. A1 for the data assignment, A1 for the next assignment. A1 for stating that the successor is the node actually released, or that the caller's reference remains valid. A candidate who describes traversing to the predecessor scores nothing here even if the traversal is correct, because part (a) established that the reference makes it unnecessary.

(c) M1 for the correct list after one removal, A1 for the list after a second, A1 for the third. A1 for identifying D as the failure. A1 for the reason: D.next is None, so the copy dereferences None. Do not award the final A1 for "the last node always fails" without the null dereference; the mark is for the mechanism. Accept a discussion of the circular case in place of the null-dereference explanation only if the null case is also stated.

(c) alternative. A candidate who answers "all four, because you can also check whether the node is the last one and traverse from head in that case" should be given full marks for the determination *and* the explanation, since the traversal is correct for that one node; award the marks and note that the constant-time claim of part (d) is what the traversal fails.

(d) M1 for the previous pointer. A1 for the constant-time unlink. A1 for the cost, expressed as one extra reference per node. Accept "a doubly linked list" as naming the change.

Why this question is hard

This item takes a task that sounds routine — delete a node you have been handed — and makes it impossible as stated, for a reason that is invisible in the wording of the task. The candidate is given the object that must disappear; the object that must change is a different one. Nothing in the signature says so, and the failure only appears when the candidate tries to write the assignment.

The trap is that the natural implementation is not merely inefficient, it cannot be written at all. A candidate who has met linked lists will produce "find the node before this one and point it past this one", which is a correct description of deletion and cannot be executed with the argument supplied. The instruction that the method is given nothing else is doing the work: without it, the candidate can quietly assume head is available and never notice the problem.

The workable technique is genuinely surprising, and it is worth noticing how much it gives up. It does not delete the node the caller named; it deletes the node after it and then disguises the survivor. That means the identity of the node object is preserved while its contents are replaced, which is exactly backwards from what a caller expects, and it is the reason the technique is a trap in production code even though it is correct as an algorithm.

Part (c) turns the technique against itself. The trick works on three nodes of four and fails on the last, and the last is not a rare case — it is what happens the first time the logger trims its oldest reading. The failure is a null dereference, which in an exception-free language is silent corruption rather than an error. The circular list makes it worse rather than better: no node has a null next pointer, so the technique never raises, and instead overwrites the head's data. Part (d) is short by design — the answer is one pointer, and the item is testing whether the candidate can name the structural cause rather than patch the symptom.
