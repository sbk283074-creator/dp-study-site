A flat-file timetable that deletes its own history

Computer science HL · CS-A3.1-001

A3.1 Database fundamentals (data types, primary keys and foreign keys, referential integrity, flat-file and relational databases, the role of the DBMS)P1 · Section A16 marksdifficulty 4technology: not allowedExplainCalculateEvaluate

Veloway bike share - the TRIPS spreadsheet

Veloway runs a city bike-share scheme. Its entire operation is held in one spreadsheet table called TRIPS, which has one row for each completed journey. The scheme has 1,200,000 registered members and 15,000 bikes, and it records about 12,000,000 journeys in a year.

Every row of TRIPS repeats the member's name, phone number and email address, which together occupy about 50 bytes. The amount charged for a journey is held in a column called ChargeCents, declared as text, so a charge of one thousand and fifty pence is stored as the characters "1,050".

The operator intends to replace the spreadsheet with a relational database that has a MEMBER table, a BIKE table and a TRIP table. A developer has suggested that the bike column in TRIP should carry a referential rule that deletes a bike's journey rows automatically when the bike is removed from BIKE, because retired bikes would otherwise leave rows behind. About 2% of the fleet is retired each year.

Question

The scheme is expanding to five more cities and the spreadsheet is becoming unworkable. The operator has asked you to review the design before the data is migrated to a relational database management system.

  1. [3 marks](a)

    Explain the difference between a primary key and a foreign key, and identify the primary key of the table above. Explain why MemberID cannot serve as the primary key of this table.

    (Explain)
  2. [5 marks](b)

    Calculate the volume of duplicated member-contact data held in one year of rows, and the number of rows that must be edited when 10% of members change their phone number, given that a member makes an average of ten journeys a year. Explain one way in which storing ChargeCents as text prevents a report from working correctly.

    (Calculate)
  3. [4 marks](c)

    Explain how replacing the single table with MEMBER, BIKE and TRIP tables removes the two problems you calculated in part (b). Name the primary key and the foreign keys of each table, and state one referential-integrity rule the DBMS should enforce.

    (Explain)
  4. [4 marks](d)

    The developer proposes that deleting a bike from BIKE should automatically delete that bike's rows from TRIP. Evaluate this proposal using the figures above, and recommend what the referential rule should be instead.

    (Evaluate)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) A primary key is the column, or the smallest set of columns, whose value uniquely identifies one row of a table; it must be unique and it cannot be null. (M1) A foreign key is a column in one table whose values must match the primary key of another table, and it is how a relationship between two tables is recorded. (A1) In TRIPS the primary key is TripID, because one row is one completed journey. MemberID cannot be the primary key because one member makes many journeys: 12,000,000 journeys are made by 1,200,000 members, an average of ten rows per member, so MemberID is repeated and does not identify a single row. (A1)

(b) Each row repeats the member's name, phone number and email address, which occupy about 50 bytes, and there are 12,000,000 rows in a year. (M1) The duplicated volume is

$$12{,}000{,}000 \times 50 = 600{,}000{,}000\ \text{bytes} = 600\ \text{MB per year}$$

and because the redundancy is stored once per journey it grows by 600 MB every year, reaching about 3 GB after five years. (A1) In a relational design the same 50 bytes are stored once per member, so the redundancy disappears.

Ten per cent of 1,200,000 members is 120,000 members. (M1) Because each of them makes about ten journeys a year, those members appear in $120{,}000 \times 10 = 1{,}200{,}000$ rows, so a change of phone number needs 1,200,000 edits in the spreadsheet against 120,000 — one per member — in the relational design. (A1)

ChargeCents is declared as text, so the DBMS treats "1,050" as four characters rather than as a number. (A1) It cannot be summed to give total revenue, it cannot be compared numerically, and it sorts by character order, so "1,050" is placed before "525"; any report must parse every one of the 12,000,000 values before it can add them.

(c) A relational design stores each fact once and links the tables by key:

  • MEMBER(MemberID PK, MemberName, MemberPhone, MemberEmail)
  • BIKE(BikeID PK, BikeModel, CommissionedDate)
  • TRIP(TripID PK, MemberID FK, BikeID FK, StartDock, EndDock, DurationMinutes, ChargeCents)

(A1) for splitting MEMBER and BIKE out of TRIPS; (A1) for placing the two foreign keys in TRIP and pointing them at the correct primary keys. Changing a phone number is now one row in MEMBER, not 1,200,000 rows, and the 50 bytes of contact data are held 1,200,000 times rather than 12,000,000 times, which removes both problems from part (b). (A1) The DBMS should enforce referential integrity: every value of TRIP.MemberID must exist in MEMBER, and every value of TRIP.BikeID must exist in BIKE, so a journey cannot be recorded against a member or a bike that does not exist. (A1)

(d) The proposal is technically correct and wrong for this requirement. If deleting a row from BIKE cascades to TRIP, then retiring a bike destroys its journeys:

  • 2% of the 15,000 bikes is 300 bikes retired each year. (M1)
  • Each bike averages $12{,}000{,}000 / 15{,}000 = 800$ journeys a year. (A1)
  • So $300 \times 800 = 240{,}000$ journey records would be silently deleted every year. (A1)

Nothing would raise an error. Ridership totals, revenue history and the city-to-city comparisons the operator is about to need would simply lose 240,000 true facts a year, and no later query could recover them, because the facts would no longer exist. The proposal confuses two different things. Cascading deletes are appropriate for rows that have no meaning without their parent — a saved payment method, for example, is meaningless once the member is gone. A journey is not like that: it happened, it was paid for, and it is the data the scheme reports on. The referential rule should therefore refuse to delete a bike while journeys still reference it (RESTRICT or NO ACTION), or, better, the bike should never be deleted at all: a Status column set to retired keeps the row, keeps the foreign key valid and keeps the history intact. A nullable foreign key with SET NULL is a weaker third option: it preserves the journey but loses the link to the bike, so the record can no longer say which bike was used. (A1) for a recommendation that is justified by the requirement to preserve history rather than by tidiness.

Markscheme notes

(a) Accept any correct definitions; do not accept "the first column". A candidate may argue for a composite key such as (MemberID, StartTime) — credit this if they then accept that TripID is the simpler unique key. The MemberID mark requires the *reason* (repetition, one row per journey), not merely the assertion that it is not unique.

(b) Follow through on all arithmetic. The 600 MB mark is for the method (bytes per row x rows) and the result; accept 572 MiB if the candidate states the binary convention. In the edits calculation, a candidate who uses 12,000,000 rows rather than ten rows per member has confused the two multiplicities and loses that (A1). The ChargeCents mark requires a *consequence* — cannot sum, cannot sort numerically, character ordering, the embedded comma — not just "it is stored as text".

(c) Accept any schema that stores member and bike facts once and links them by foreign keys; table and column names need not match. The foreign keys must be in TRIP and point at MEMBER and BIKE. A candidate who puts BikeID as a foreign key inside MEMBER, or who leaves MemberName in TRIP, has not removed the redundancy and loses the relevant mark. Accept a statement of referential integrity in words instead of SQL.

(d) This is an evaluate question, so a recommendation is required. A candidate who writes "cascade is bad practice" without the 240,000 figure earns at most the (M1). Accept RESTRICT, NO ACTION, a soft-delete Status column, or a nullable key with SET NULL *provided* the candidate acknowledges that SET NULL loses the link to the bike. Do not accept "take a backup first" — it does not change the integrity rule and the backup is itself a copy of data the rule would delete. Award the final (A1) only when the recommendation follows from the requirement to preserve history.

Why this question is hard

The question is built so that the cost of a design decision can be counted, and so that the decision that looks tidiest is the destructive one.

The flat file's real problem is not that it is a spreadsheet. It is that facts about members and bikes are stored *inside* journey rows, so their multiplicity becomes the journey count. Every number in part (b) follows from that single structural fact: 50 bytes multiplied by 12,000,000, and 1,200,000 edits instead of 120,000 for the same administrative event. A student who thinks the problem is "the file is big" has not found the mechanism, and their answer to part (c) will be a list of table names rather than an explanation of why the multiplicity changed.

Part (d) is where the trap is. Cascading deletes are widely taught as good practice because they prevent orphan rows, and a student who has learned that rule will recommend the cascade without hesitating. But preventing an orphan has two implementations with opposite consequences: RESTRICT refuses the delete and keeps the child; CASCADE allows the delete and destroys the child. Cascade is right only when the child row has no independent meaning. A journey has independent meaning — it is the thing the scheme measures — so the "clean" option is the one that quietly deletes 240,000 records a year. That is the sense in which the obvious answer is wrong.

Two further wrong turns are common. The first is treating 600 MB as too small to matter; the argument is not the bytes but the unbounded growth and the 1,200,000-row update multiplicity. The second is treating ChargeCents as text as a cosmetic issue, because in a spreadsheet the value is right-aligned and looks like a number. It only fails when a query tries to aggregate it — which is exactly when the report is due. Data types are not decoration; they determine which questions the database can answer at all.
