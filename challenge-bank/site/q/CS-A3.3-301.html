Two transfers that interleave so that the second reads the balance before the first commits, and the committed value is short by exactly the first transfer

Computer science HL · CS-A3.3-301

Theme A: Concepts of computer scienceA3.3 Database programming (A3.3.6 describe how transactions maintain data integrity in a database, including the role of atomicity, consistency, isolation and durability to ensure reliable processing of transactions, and the transaction control language commands BEGIN TRANSACTION, COMMIT and ROLLBACK)P1 · Section A13 marksdifficulty 5technology: not applicableDetermineStateExplainEvaluate

Question

A savings account holds a balance of 500. Two transfers into the account are submitted at almost the same moment: one adds 100 and one adds 50. Each transfer is written as a transaction that reads the balance, computes the new balance from the value it read, writes that value back, and commits. The application does not use a lock, and the database engine is running at an isolation level that permits the two transactions to interleave.

The figure shows what the engine actually did, as an ordered list of operations. Each operation is labelled with the transaction that issued it and the moment it was issued. Nothing in the figure has been simplified: this is the whole of both transactions, and both of them commit.

  1. [3 marks](a)

    Using the timeline, state the balance that each of the two transactions reads and the balance that each of them writes. Determine the balance that is left in the account once both transactions have committed, and state which of the two COMMIT statements fixes that value.

    (Determine)
  2. [4 marks](b)

    Determine the balance that would remain if the two transfers had run one after the other, and show that both possible orders give the same result. State the amount by which the interleaved execution has lost. Name the ACID property whose role this interleaving has defeated, and name one of the other three properties that this same interleaving has not defeated, justifying each of your two answers.

    (Determine)
  3. [6 marks](c)

    A developer proposes to change nothing in the application, to rely on ROLLBACK to undo any damage, and to allow both transactions to run for longer so that they overlap more often. Evaluate that proposal. Your answer should state what ROLLBACK can and cannot recover in this timeline, identify the smallest change to the timeline that removes the loss, and reach a judgement on whether this anomaly can be prevented using transaction control commands alone.

    (Evaluate)

Reveal the answer

(a) The first SELECT is issued by the first transaction at t1 and returns 500. The second SELECT is issued by the second transaction at t3 and also returns 500, because the first transaction has not yet written anything at that moment (A1). The first transaction writes $500 + 100 = 600$ at t4, and the second writes $500 + 50 = 550$ at t6 (A1). The last COMMIT is the second transaction's, at t7, and it fixes the stored balance at 550 (A1). The first transaction's 600 is not in the database any more: the second transaction wrote over it.

(b) Run in either serial order, the arithmetic gives the same answer. First then second: the first reads 500 and writes 600, then the second reads 600 and writes $600 + 50 = 650$. Second then first: the second reads 500 and writes 550, then the first reads 550 and writes $550 + 100 = 650$ (M1). Both orders give 650, which is what makes 650 the correct result rather than merely one possible result (A1).

The interleaved execution has left 550, so the loss is $650 - 550 = 100$ (A1). That is exactly the amount the first transaction added, which is what a lost update looks like: one transaction's write is entirely overwritten by another's, and the update that is lost is the earlier one.

The property whose role has been defeated is isolation (A1). Isolation is what guarantees that the result of running transactions concurrently is the same as the result of running them in some serial order, and here the concurrent result of 550 matches neither serial order.

Atomicity has not been defeated. Each transaction did what atomicity requires: the first transaction's read and write both took effect and it committed as a unit, and the second's did the same. Atomicity is about a transaction not being half-applied, and neither transaction was half-applied; the first was applied in full and then overwritten in full by a later transaction, which is an ordering fault and not a failure of atomicity. Durability has not been defeated either: both COMMIT statements were honoured and both transactions' effects were persisted, and the persisted value is wrong for a reason that has nothing to do with losing committed data. Either answer earns the mark, provided the candidate distinguishes it from isolation.

(c) ROLLBACK undoes the writes of the transaction that issues it, and only while that transaction has not yet committed. In this timeline there is nothing left for it to undo (A1). By t7 both transactions have committed, so neither can be rolled back: a rollback of the first transaction is refused because it has already committed, and a rollback of the second would remove the 550 and leave the account at 500, which is worse, not better. The value the first transaction computed, 600, was overwritten inside the second transaction's write and is no longer held anywhere the database can reach. ROLLBACK recovers a transaction that has failed; it cannot recover a value that a later committed transaction has already replaced.

Making the transactions run for longer, so that they overlap more often, makes the anomaly more likely rather than less. The loss happened because the second transaction's read fell between the first transaction's read and its COMMIT. Widening the interval between a transaction's read and its commit widens exactly the window in which another transaction can read the old value, so the proposal increases the frequency of the fault it is offered as a defence against (A1).

The smallest change to the timeline is to move the second transaction's read so that it happens after the first transaction's COMMIT, that is from t3 to after t5 (A1). If the second transaction reads after t5 it reads 600, and it then writes $600 + 50 = 650$, which is the correct result. Nothing else needs to change: both transactions keep their structure, both still commit, and no statement is rewritten. The change is a change of ordering, and it corresponds to a real mechanism, which is to make the second transaction wait until the first has finished, whether by taking a lock on the row before reading it or by raising the isolation level so that the engine takes one on the transaction's behalf (A1).

The judgement is that this anomaly cannot be prevented using transaction control commands alone (A1). The commands the guide lists are BEGIN TRANSACTION, COMMIT and ROLLBACK, and between them they let a candidate start a transaction, finish it successfully, or abandon it. None of them constrains when another transaction may read. The fault is in the interleaving, and the interleaving is controlled by locking and by the isolation level, which are properties of how the transaction is declared and of how the engine schedules it rather than commands that a developer issues. A candidate who answers that ROLLBACK can be used to detect and retry the second transaction should be credited for the retry idea, but must also be asked to say what triggers the rollback, since nothing in this timeline fails and so nothing raises an error for the application to catch.

Markscheme notes

(a) 3 marks. One mark for both reads giving 500. One mark for the two written values, 600 and 550, each computed from the value that transaction actually read. One mark for the final committed balance of 550 and for attributing it to the second transaction's COMMIT. A candidate who answers 650 has added the transfers together without following the timeline; no marks for that part.

(b) 4 marks. One mark for showing both serial orders, 600 then 650 and 550 then 650, and stating that they agree. One mark for the loss of 100 and for identifying it as the first transaction's increment. One mark for isolation as the property defeated, with a reason that refers to the serial-order guarantee. One mark for naming atomicity or durability as preserved, with a reason. A candidate who names consistency as defeated should be credited only if the answer states the invariant that was broken, namely that the two transfers must both be reflected in the balance.

Do not accept 'atomicity is violated' for the final mark: both transactions committed as units, and the failure is in the ordering.

(c) 6 marks. One mark for stating that ROLLBACK cannot act here because both transactions have committed. One mark for stating that a rollback of the second transaction would make the balance worse rather than better. One mark for the observation that making the transactions overlap more often widens the read-to-commit window and increases the fault rate. One mark for the smallest change, which is to move the second read to after the first COMMIT, giving a write of 650. One mark for naming the mechanism, a row lock or a raised isolation level. One mark for the judgement that transaction control commands alone cannot prevent the anomaly, with the reason that none of BEGIN TRANSACTION, COMMIT and ROLLBACK constrains when another transaction may read.

A candidate who proposes a retry loop should keep the first four marks if the reordering is also given, but must be asked what would trigger the retry, since no statement in this timeline raises an error.

Why this question is hard

This is the classic lost update, and it is worth being precise about why it is hard. The two transactions are individually correct. Each reads the balance, each computes a new balance from what it read, each writes, each commits. There is no statement a reviewer could point at and call wrong. The defect is entirely in the ordering: the second transaction's read falls after the first transaction's read and before the first transaction's COMMIT, which is the one interval in which the value it reads is about to be superseded.

That is why the figure is given as an ordered list rather than as a description. The candidate cannot answer by pattern-matching the word 'transaction' to a list of ACID properties; the properties have to be used to predict an outcome, and then checked against the arithmetic. The item is a harder route to exactly the content the guide names, which is the role of isolation in maintaining integrity.

The loss is exactly 100, the first transaction's increment, and that is not a coincidence of the numbers chosen. When one transaction overwrites another's write with a value computed from a stale read, the surviving value is the later transaction's read plus the later transaction's increment, so the difference from the correct serial result is the earlier transaction's increment in full. A candidate who notices this has understood the mechanism rather than the example, and the answer says so.

Part (c) is written so that the two plausible remedies are both wrong. ROLLBACK cannot help because by the time anyone notices, both transactions have committed, and rolling back the second would discard a correct 50 to remove a wrong 100. Making the transactions longer makes the window wider and the fault commoner. What actually fixes it is a change of ordering, which is to say a lock or an isolation level, and the judgement the part asks for is that the transaction control commands the guide lists do not reach that far. That is a real and examinable point: BEGIN TRANSACTION, COMMIT and ROLLBACK delimit a transaction, and they do not schedule it.

The item deliberately avoids the terms 'dirty read' and 'non-repeatable read', which belong to a finer-grained taxonomy than the guide asks for. Everything the candidate needs is in the timeline and in the four properties named by A3.3.6.
