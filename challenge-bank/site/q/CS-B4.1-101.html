B4.1 Binary search trees: traversal, insertion, deletion and search cost

Computer science HL · CS-B4.1-101

Theme B: Computational thinking and problem-solvingB4.1 Fundamentals of ADTs (HL only), B2.2 Data structures (binary search trees: traversal, insertion, deletion, search cost)P216 marksdifficulty 4technology: not allowedStateDetermineDescribeCompare

Question

A public library is building a catalogue system. Each book is identified by a numerical accession number, and the catalogue must support three operations: finding the record for a given accession number, adding a new accession number, and printing the whole catalogue in ascending order of accession number. The system designer decides to hold the accession numbers in a binary search tree. The figure shows two binary search trees, A and B, that were built from the same five accession numbers, with the insertion order used for each tree given above it. The height of a tree is taken to be the number of nodes on the longest path from the root to a leaf. Answer all parts with reference to the figure, and justify each answer.

  1. [2 marks](a)

    State the in-order traversal of tree A, and explain why an in-order traversal of any binary search tree returns its keys in ascending order.

    (State)
  2. [3 marks](b)

    Determine where the accession number 40 would be inserted in tree A, and state the height of the tree after that insertion.

    (Determine)
  3. [4 marks](c)

    Describe the steps needed to delete a node that has two children from a binary search tree, and apply your description to the deletion of the node holding 45 from tree A.

    (Describe)
  4. [4 marks](d)

    The library's catalogue will eventually hold 200 000 accession numbers. Compare the greatest number of comparisons a search might need in a tree shaped like tree A with the greatest number it might need in a tree shaped like tree B, and comment on the practical significance of the difference.

    (Compare)
  5. [3 marks](e)

    A colleague suggests replacing the tree with a hash table, which would give constant-time lookup. Explain whether a hash table could satisfy all three of the operations the catalogue must support.

    (Explain)

Reveal the answer

(a) An in-order traversal visits the left subtree, then the node, then the right subtree, and applied to tree A it yields 20, 30, 35, 45, 50. (A1) The traversal is ascending because of the ordering property of a binary search tree: every key in the left subtree of a node is smaller than the node's key, and every key in the right subtree is larger. (M1) Visiting left, then node, then right therefore emits each key only after every smaller key in its subtree, and before every larger one, so the output is sorted whatever the shape of the tree.

(b) Insertion compares the new key with each node from the root downwards and moves left when the key is smaller and right when it is larger. Starting at 30, the key 40 is larger, so it goes right; at 45 it is smaller, so it goes left; at 35 it is larger, so it goes right, and the position is empty. (M1)(A1) The key 40 therefore becomes the right child of 35. (A1) That path visits four nodes, 30, 45, 35 and 40, so the height of the tree rises from 3 to 4.

(c) A node with two children cannot simply be removed, because the two subtrees would have to be reattached. The standard method is to replace the key being deleted with its in-order successor, which is the smallest key in its right subtree, and then delete that successor from the right subtree, where it is guaranteed to have at most one child. (M1)(A1) For tree A, the in-order successor of 45 is 50, since 50 is the only key in 45's right subtree and is therefore its smallest. (A1) The key at the node is overwritten with 50, and the original node holding 50, which is a leaf, is then removed. The resulting tree has root 30, left child 20, and right child 50 with left child 35, so its height is 3. (A1)

(d) In a tree shaped like A the height grows with the logarithm of the number of keys, because each comparison halves the range still to be searched. (M1) For 200 000 keys the height is about log2(200000), which is 17.6, so a search visits at most 18 nodes and needs at most 18 comparisons. (A1) In a tree shaped like B, each node has only one child, so the tree is a chain and a search may have to visit every node. (M1) For 200 000 keys that is 200 000 comparisons, which is roughly 11 000 times as many as the balanced shape needs. The practical significance is that the degenerate shape offers no improvement over scanning a list, so the choice of a tree delivers nothing unless the shape is controlled. (A1)

(e) A hash table computes the position of a key from the key itself, so lookup, insertion and deletion are all constant-time on average, and the three operations would be fast. (M1) However, the keys in a hash table are stored in an order determined by the hash function, not by the keys, so the third operation, printing the catalogue in ascending order of accession number, cannot be done without retrieving every key and sorting it, which costs O(n log n) each time. (A1) The hash table is therefore the better structure only if the ordered listing is not required, or if it is produced once and cached; as specified, it does not satisfy the third requirement. (A1)

Why this question is hard

The figure makes one point very clearly: two trees can hold the same data and behave completely differently. Tree A and tree B contain the same five accession numbers, and an in-order traversal of either returns 20, 30, 35, 45, 50. Nothing about the contents of the trees distinguishes them. What differs is their shape, and shape is what determines the cost of every operation performed on them.

The traversal part of the question is the part that shape cannot affect, and that is worth seeing. The ordering property guarantees that the left subtree of any node holds only smaller keys and the right subtree only larger ones, so visiting left, node, right emits the keys in ascending order regardless of how the tree is arranged. This is the property that makes a binary search tree useful for the library's third requirement, printing the catalogue in order, which is the requirement a hash table cannot meet.

Insertion follows one path from the root, turning left or right at each node, and the new key always becomes a leaf. In tree A the key 40 travels 30, then 45, then 35, and lands to the right of 35. The tree's height becomes 4, which is worth noting because insertion can change the height without changing the number of nodes on the old longest path.

Deletion is the operation that cannot be inferred from insertion. Removing a leaf is trivial, and removing a node with one child is easy, but a node with two children has two subtrees to preserve and only one slot to put them in. The standard solution is to overwrite the node's key with its in-order successor, the smallest key in its right subtree, and then delete that successor, which by construction has at most one child. Here the successor of 45 is 50, and after the operation the tree has 50 where 45 was, with 35 still as its left child.

The comparison in part (d) is the reason any of this matters. A balanced tree of 200 000 keys has height about 18, so a search visits at most 18 nodes. A tree shaped like a chain visits up to 200 000. Both are valid binary search trees, so the structure guarantees nothing on its own; the guarantee comes from controlling the shape. Part (e) closes the argument by asking whether a different structure would avoid the problem, and the answer is that a hash table solves the lookup problem while creating a new one, because it has no notion of order.
