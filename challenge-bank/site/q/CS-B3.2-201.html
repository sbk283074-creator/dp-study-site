B3.2 Two independent classification axes modelled with inheritance, where the obvious hierarchy multiplies out and the correct design uses composition to keep the two axes separate

Computer science HL · CS-B3.2-201

Theme B: Computational thinking and problem-solvingB3.2 Fundamentals of OOP for multiple classes (HL only), with B3.1 Fundamentals of OOP for a single class and B2.2 Data structuresP1 · Section B10 marksdifficulty 4technology: allowedIdentifyExplainDesignJustify

A media catalogue for a school library

A library system stores entries for its collection. Each entry has a format, which is one of four: Print, Audio, Video or Download. Each entry also has a genre, which is one of five: Fiction, Reference, Biography, Poetry or Periodical. Format and genre vary independently: the library holds every combination except Download with Periodical, which it has decided never to stock, so there are nineteen combinations in use out of a possible twenty. Every entry also has a title, an author or creator, a shelf location and a loan period.

Behaviour depends on both axes. A format dictates how a copy is lent (a print copy can be recalled, a download expires, an audio copy has a play count), and a genre dictates how the entry is catalogued and which subject headings apply. A later release will add a fifth format, Microform, and a sixth genre, Drama.

A junior developer has proposed a class hierarchy with one abstract class MediaEntry and a concrete subclass for each combination: PrintFiction, PrintReference, PrintBiography, and so on.

Question

The library must decide whether to accept the junior developer's hierarchy. Identify the two axes of classification and the data and operations that belong to each, explain how many concrete classes the proposal contains in use and in full, design an alternative structure that keeps the axes separate, and justify a situation in which the multiplicative hierarchy would nevertheless be the better choice.

  1. [3 marks](a)

    Identify the two axes of classification in this system and, for each, state one piece of data and one operation that depends on it rather than on the other axis.

    (Identify)
  2. [2 marks](b)

    Explain how many concrete classes the proposed hierarchy contains in use and how many it would contain if it covered every possible combination including the one the library has decided never to stock.

    (Explain)
  3. [3 marks](c)

    Design an alternative class structure that keeps the two axes separate, state how many classes it contains, and state what it costs to add the proposed fifth format.

    (Design)
  4. [2 marks](d)

    Justify a situation in which the junior developer's multiplicative hierarchy would be the better choice despite the larger class count.

    (Justify)

Total: 10 marks. Try the question before revealing anything below.

Reveal the answer

(a) The two axes are format ('Print', 'Audio', 'Video', 'Download') and genre ('Fiction', 'Reference', 'Biography', 'Poetry', 'Periodical') (A1).

A datum that depends on format rather than on genre: the media type stored with a copy, or a play count or an expiry date -- all of these are properties of how the thing is carried, and none of them changes when a biography is reclassified as reference (A1). An operation that depends on format: renew(), which behaves differently for a print copy that can be recalled and a download that expires. A datum that depends on genre: the list of subject headings, or the Dewey-class code. An operation that depends on genre: catalogue(), or suggestSimilar(), which works on subject matter and is indifferent to whether the item is a download or a video (A1).

The test in each case is whether a change on the *other* axis would force a change here. Reclassifying a novel as poetry changes the subject headings and changes nothing about how it is lent; converting the same title from print to audio changes how it is lent and changes nothing about its subject headings.

(b) In use the library holds every combination except 'Download' with 'Periodical', so the proposal needs
$$4 \times 5 - 1 = 19 \ \text{concrete classes} \;\; (A1).$$
It also needs at least one method to differ between them, or the subclasses are empty shells that exist only to carry a name.

Covering every combination gives
$$4 \times 5 = 20 \ \text{concrete classes} \;\; (A1),$$
one more than the number in use. The difference is worth noticing in the other direction: the proposal is already nineteen classes and the library intends to add a fifth format and a sixth genre, which takes the in-use count from nineteen to
$$5 \times 6 - 1 = 29,$$
an addition of ten classes for two changes to the specification.

(c) A design that keeps the axes apart uses two small hierarchies and lets each entry hold one of each:

  • a Format hierarchy with an abstract Format and four subclasses (Print, Audio, Video, Download), each implementing lend() and renew() (A1);
  • a Genre hierarchy with an abstract Genre and five subclasses (Fiction, Reference, Biography, Poetry, Periodical), each implementing headings() (A1);
  • a single MediaEntry class holding a title, a creator, a location, a loan period, one Format object and one Genre object, and delegating the format-specific and genre-specific operations to whichever objects it holds (A1).

The class count is $2$ abstract bases $+\ 4$ formats $+\ 5$ genres $+\ 1$ entry $= 12$ classes in total, of which the two abstract bases carry no instances and the concrete working classes number ten. The library's existing nineteen combinations are expressed as nineteen *objects* of MediaEntry, not as nineteen classes.

Adding Microform means writing one new subclass of Format and changing nothing else: the count of classes goes up by one, no MediaEntry code changes, and the combination of Microform with each of the five genres works immediately. Under the proposal the same change would add five classes, each of which would need its own lend() and renew() implementations even though they would be identical.

(d) The multiplicative hierarchy is the better choice when the two axes do not merely coexist but interact, that is when the behaviour of a combination is not the sum of what the two axes would do separately (A1).

A concrete case from this system: a DownloadPeriodical may be barred from the collection, and a PrintPeriodical must be lent with a shorter period than other print material. If a rule of that kind applies to one cell of the grid and to no other, then the cell has behaviour of its own, and the cleanest place for it is a subclass that exists to hold it. Composition would express the same thing with a conditional inside MediaEntry, and a conditional that tests the pair of axes is exactly a hard-coded combination in a different place (A1).

The general statement is worth giving: composition is preferred when the axes can be combined freely and their behaviour composes; inheritance is preferred when the combinations have their own behaviour. Here nineteen of the twenty cells behave as the composition of their row and column, so composition is right, and a candidate who says so and identifies the one cell that would justify the other design has understood the distinction rather than the rule of thumb.

Markscheme notes

(a) (A1) for naming both axes, (A1) for a format-dependent datum or operation, (A1) for a genre-dependent one. The two examples must be *different in kind* or the mark is not awarded twice for the same idea: a candidate who gives playCount for format and shelfLocation for genre scores the first two marks only if the shelf location is shown to be genre-independent, which it is not -- location is a property of neither axis and is a generic attribute. A candidate who gives headings() for genre and lend() for format scores all three.

(b) (A1) for nineteen, (A1) for twenty, with the reason for the difference stated or implied. A candidate who writes twenty twice has not read the exception and scores one mark.

(c) (A1) for the format hierarchy, (A1) for the genre hierarchy, (A1) for a single entry class that holds one of each. The class count is not itself marked in this part, but a candidate who produces two hierarchies and no entry class has not designed a structure that can hold the nineteen combinations and cannot score the third mark. Counting the classes as ten, twelve or "nine concrete plus one entry" is all accepted provided the arithmetic matches the structure described.

(d) (A1) for the general criterion -- the axes interact, or some cells have behaviour of their own -- (A1) for a specific example from this system. "When the combinations are genuinely different" without an example scores the first mark only.

Condonation: a candidate who uses an interface rather than an abstract class scores the same; so does one who makes Format and Genre enumerations with a strategy object per value, provided the two axes remain separate. Forfeits: proposing a single class with a format field and a genre field and a long if-else chain over both, which does express the two axes but puts all the behaviour in one class -- a candidate who explains that the behaviour is still separated by dispatching on the held objects scores full credit, and one who simply nests the conditionals does not.

Why this question is hard

The distinction this item is built on is old and it is still got wrong constantly: inheritance models *what something is*, and composition models *what something has*. The library entry is a print copy and it is a work of fiction, and both statements are true, and neither of them is more fundamental than the other. When a designer picks one of the two axes and hangs inheritance off it, they have quietly decided that the other axis will be handled by something else -- and if there is no plan for that, the other axis gets handled by a class per combination.

That is how the nineteen subclasses appear. Nobody chooses twenty classes for a two-dimensional problem; it happens because the first axis is modelled properly with four subclasses, and then the second axis has nowhere to live, and the path of least resistance is a subclass. The tell is that the subclasses come in groups of five or four with identical bodies, differing only in their name.

Composition removes the multiplication because the two axes become two *objects* held by one class, and objects compose where classes multiply. The entry delegates lend() to its format object and headings() to its genre object, and the number of classes stops depending on the product of the two list lengths. The numbers are small enough here to check by hand: nineteen against twelve, and the addition of a format costs one class against five. That comparison is the argument, and it is why the item asks for the counts rather than for a design principle.

Part (d) is where a candidate who has only memorised "prefer composition" is separated from one who has understood it. There is a real case for the multiplicative hierarchy, and it is not a rare one: when a specific cell of the grid has behaviour that neither axis explains, the cell is an entity and deserves a class. A download periodical that is barred from the collection is such a cell. The point is not that composition is always right; it is that composition is right when the grid's behaviour composes, and a designer who knows which of the two situations they are in has the whole of the answer.

Challenge lever
The naive hierarchy is not wrong, it is merely multiplicative: with four formats and five genres, a class per combination gives twenty subclasses, and adding one format costs five more. The design that keeps the axes separate gives nine classes and adding a format costs one. The judgement the item asks for is *when* the multiplicative hierarchy is nevertheless the right answer, and there is a real answer to that, which the last part requires.
