A rule-based packet filter in which one rule is unreachable because a broader rule with the same destination pattern is evaluated first

Computer science HL · CS-A2.4-301

Theme A: Concepts of computer scienceA2.4 Network security (A2.4.1 discuss the effectiveness of firewalls at protecting a network, including the function of firewalls in inspecting and filtering incoming and outgoing traffic based on whitelists, blacklists and rules, and the strengths and limitations of firewalls)P1 · Section A12 marksdifficulty 5technology: not applicableDetermineExplainEvaluateState

Question

A small research institute has three networks. Its staff work from the internet, its system administrators work from an administration subnet at 10.0.9.0/24, and its servers sit in a server subnet at 10.0.5.0/24. The boundary is a stateless packet filter that holds an ordered list of rules. The filter compares a flow against the rules from the top of the list downwards, and the first rule whose source, destination and port all match the flow decides the action; no later rule is consulted, whether the action was ALLOW or DENY. The last rule in the list is the catch-all.

The administrator has been asked to allow the system administrators to reach the servers over SSH from the administration subnet, while denying every other flow that enters the server subnet. The rules currently in the filter, and two flows that were captured at the boundary, are shown in the figure. The server subnet holds the host 10.0.5.20, which runs the public web service, and the host 10.0.5.31, which the administrators manage.

  1. [3 marks](a)

    Using the rule table, determine the action the filter takes for each of the two flows in the figure, and name the number of the rule that decides each one. For each flow, show why every rule above the deciding rule fails to match it.

    (Determine)
  2. [4 marks](b)

    Explain why rule 3 never decides the action for any flow at all, whatever its source address and whatever port it carries. Your answer must refer to the destination pattern in rule 3, to the destination pattern in the rule above it, and to the position of that rule in the list, and must state the property of the two patterns that makes the outcome unavoidable.

    (Explain)
  3. [5 marks](c)

    State the smallest change to the table that restores the administrator's intention, and evaluate one security consequence of making that change. Your answer should state how many hosts in the server subnet the restored rule would reach, explain what the rule grants to every device on the administration subnet, and state whether rule 4 should be kept.

    (Evaluate)

Total: 12 marks. Try the question before revealing anything below.

Reveal the answer

(a) Flow 1 runs from 203.0.113.7 to 10.0.5.20 on port 443. Rule 1 has a destination of exactly 10.0.5.20 and a port of 443, and its source is a wildcard, so it matches and the action is ALLOW (A1). Rule 2 is never consulted, because the filter stops at the first match and rule 1 sits above it.

Flow 2 runs from 10.0.9.14 to 10.0.5.31 on port 22. Rule 1 does not match it: the destination 10.0.5.31 is a different host from 10.0.5.20, and the port 22 is a different port from 443 (A1). Rule 2 has a destination of 10.0.5.0/24 and a port wildcard, so it matches any host in the server subnet on any port. The address 10.0.5.31 lies in 10.0.5.0/24, so rule 2 matches and the action is DENY (A1). Rule 3 is not consulted, even though its source, destination and port all describe flow 2 exactly.

(b) Rule 3 requires a destination in 10.0.5.0/24 and a port of 22, from a source in 10.0.9.0/24. Rule 2 requires a destination in 10.0.5.0/24, and its source and port are both wildcards (A1). Every flow that can match rule 3 therefore also matches rule 2: the set of destinations rule 3 accepts is the whole server subnet, and that is exactly the set of destinations rule 2 accepts, so rule 3 adds no destination that rule 2 does not already cover (A1).

Rule 2 also accepts every source and every port, so it cannot fail on a flow that rule 3 would have accepted. Since rule 2 sits above rule 3 in the list, the filter reaches rule 2 first for every such flow, matches it, and stops (A1). The property that makes this unavoidable is that rule 2's match set is a superset of rule 3's, and a superset earlier in a first-match list makes the rule below it unreachable. It is not a configuration error that a validation check would catch by looking at rule 3 alone: rule 3 is well formed, and it is only the pair of rules and their order that makes it dead (A1).

(c) The smallest change is to exchange the positions of rule 2 and rule 3, so that the SSH allowance is evaluated before the blanket denial (A1). After the exchange, flow 2 is matched by rule 3 and is ALLOWed, while flow 1 is still matched by rule 1 and unaffected, and a flow into the server subnet from anywhere other than the administration subnet still falls through to rule 2 and is denied (A1).

The security consequence is that the restored rule is written over a subnet, not over a host. Its destination is 10.0.5.0/24, which is 254 usable addresses, and its source is 10.0.9.0/24, which is another 254 (A1). The administrator wanted the system administrators to manage 10.0.5.31; the rule as written grants SSH access from every device on the administration subnet to every host in the server subnet, including the public web host at 10.0.5.20. One compromised workstation on the administration network therefore has an SSH path to the whole server estate, and the workstation does not need any privilege beyond an address in the subnet. Narrowing rule 3's destination to the hosts that actually need managing, or pairing it with multifactor authentication, would keep the intent while removing the reach (A1).

Rule 4 should be kept. It is the default deny, and it is the reason the table fails closed: anything that matches no earlier rule is dropped. Removing it would leave unmatched traffic with no decision, which in most implementations means it is permitted, so the table would move from denying by default to allowing by default and every flow the other rules do not name would be admitted. The correct reading of rule 4 is that it is not redundant with rule 2; rule 2 denies the server subnet, and rule 4 denies everything else, including flows to the rest of the estate (A1).

Markscheme notes

(a) 3 marks. One mark for flow 1 decided by rule 1 with the action ALLOW. One mark for flow 2 decided by rule 2 with the action DENY. One mark for showing that rule 1 fails on flow 2 because the destination host and the port both differ, and that rule 2 therefore matches before rule 3 is reached. A candidate who answers flow 2 with rule 3 has read the rule that mentions SSH and has not evaluated the list; no marks for that flow.

(b) 4 marks. One mark for stating that rule 3's destination set is the whole server subnet. One mark for stating that rule 2's destination set is the same whole subnet, so rule 3 adds nothing to it. One mark for stating that rule 2 is evaluated first and that the filter stops at the first match. One mark for naming the general property, that a rule whose match set contains another rule's match set makes the other rule unreachable when it is placed above it. A candidate who says only 'rule 3 is never reached because rule 2 catches everything first' earns two of the four marks; the other two require the pattern comparison and the general statement.

Accept 'shadowed', 'unreachable', 'dead rule' or an equivalent phrase for the final mark.

(c) 5 marks. One mark for the smallest change, which is to swap rules 2 and 3, or equivalently to move rule 3 above rule 2. One mark for confirming that the swap leaves flow 1 decided by rule 1 and still denies flows into the server subnet from elsewhere. One mark for the count of 254 usable hosts at each end of the restored rule. One mark for the consequence: the rule reaches the public web host as well as the managed host, and every device on the administration subnet inherits it, so one compromised workstation gains an SSH path to the whole server estate. One mark for stating that rule 4 should be kept and giving the reason, that it is the default deny and removing it would allow unmatched traffic.

A candidate who proposes adding a new rule above rule 2 that names only 10.0.5.31 has changed the intention, which was to allow the whole server subnet. Accept it only if the candidate states that it narrows the intention and explains why that is acceptable.

Accept 'moving rule 3 up' and 'swapping 2 and 3' as the same answer. Do not accept 'change rule 2 to allow SSH', which breaks the denial for every other source.

Why this question is hard

A stateless packet filter is an ordered list, and its semantics are first-match. Two consequences follow that are easy to state and easy to get wrong. The first is that the order carries meaning that no individual rule expresses: the same four rules in a different order are a different filter. The second is that a rule can be well formed, correct in its own fields, and still never decide anything, because a rule above it matches everything it would have matched. That condition is called shadowing, and it is the reason a firewall audit compares rules in pairs rather than reading them one at a time.

The shadowing here is exact rather than partial. Rule 3's destination is 10.0.5.0/24 and rule 2's destination is 10.0.5.0/24, so the two destination sets are not merely overlapping, they are identical; rule 2 is broader only in that its source and port are wildcards. A candidate can see this without enumerating addresses, and the verification does enumerate them, all 256 of them, to confirm that no host in the server subnet escapes rule 2's pattern.

The item is written so that the wrong answer is the one that looks most like diligence. A candidate who reads the table and looks for the rule about SSH finds rule 3, and rule 3 says exactly what the administrator intended. The mistake is not misreading the rule; it is treating a list as a set. The two flows in the figure are chosen so that the list and the set give different answers: flow 2 is precisely the flow rule 3 was written for, and the list denies it.

The final part makes the repair carry a cost, which is what turns the item from a puzzle into an evaluation. Restoring the intention is one line of reordering, and it simultaneously widens the reach of the allowance from one host to a subnet of 254, because the rule was always written over a subnet and the shadowing was hiding that. So the correct answer has to hold two things at once: the rule was dead, and reviving it grants more than the administrator thought it did. That is the sense in which rule-based filtering has limitations as well as strengths, which is the language the guide uses for this node.
