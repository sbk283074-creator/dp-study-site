A1 Computer fundamentals

Computer science HL · CS-A1.1-001

Theme A: Concepts of computer scienceA1.1 Computer hardware and operation, A1.1.8 compression, A1.4 Translation (HL only)P1 · Section A16 marksdifficulty 4DescribeExplainCalculateEvaluate

Stimulus

An autonomous inspection drone flies a fixed route inside a warehouse, checking stock on high shelves. It carries a forward-facing camera, a distance sensor array, and a flight controller that must respond to obstacles within 20 ms. Video is stored on the drone and analysed after the flight.

Question

The drone's on-board computer has a general-purpose CPU and a separate GPU.

  1. [4 marks](a)

    Describe how the control unit, the ALU and the registers interact during one fetch–decode–execute cycle.

    (Describe)
  2. [4 marks](b)

    The obstacle-detection workload runs on the GPU rather than the CPU. Explain two architectural differences between a CPU and a GPU and, for each, why it matters for this task. (HL only)

    (Explain)
  3. [4 marks](c)

    The camera produces $1280\times720$ pixel frames at 24 bits per pixel and 30 frames per second.

    (i) Calculate the uncompressed data rate in MB per second.

    (ii) A codec compresses the video by a factor of 40. Calculate the storage required for a 90-second flight.

    (Calculate)
  4. [4 marks](d)

    The flight-control software is written in a high-level language. Evaluate whether it should be compiled or interpreted for the deployed drone. (HL only)

    (Evaluate)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) Award up to four points from:

  • The program counter / control unit holds the address of the next instruction and copies it into the memory address register; the instruction is fetched from memory into the memory data register and then into the instruction register. (A1)
  • The control unit decodes the instruction — determining the opcode and the operands — and sends control signals along the control bus to coordinate the other components. (A1)
  • The ALU performs the actual operation (arithmetic such as adding a sensor offset, or a logical comparison such as testing whether a distance is below a threshold) on data held in registers, setting status/flag bits as a result. (A1)
  • Registers hold the instruction, the operands and the intermediate results, giving much faster access than main memory; the result is written back to a register or to memory and the cycle repeats. (A1)

(b) Award two differences, each with a reason:

| | CPU | GPU | Why it matters here |
|---|---|---|---|
| Core design | Few cores, each large, complex and optimised for sequential tasks with heavy branching | Many hundreds or thousands of small, simple cores optimised for throughput | Obstacle detection applies the *same* operation to every pixel; thousands of cores work on different pixels simultaneously |
| Control vs compute | Much of the silicon is devoted to control logic, branch prediction and large caches | Far more of the silicon is devoted to arithmetic units | Image processing is data-parallel with almost no branching, so spending silicon on control logic is wasteful |

Other acceptable differences: SIMD/single-instruction-multiple-data execution; the GPU's higher memory bandwidth; the CPU's higher clock speed and lower latency per task. (A1)(A1)(A1)(A1)

(c) (i) Bits per frame $=1280\times720\times24=22\,118\,400$ bits (A1)

$$=\frac{22\,118\,400}{8}=2\,764\,800\ \text{bytes}\approx2.76\ \text{MB per frame}$$ (A1)

Data rate $=2.7648\times30=82.9\ \mathrm{MB\,s^{-1}}$ (A1)

(ii) Compressed rate $=\dfrac{82.9}{40}=2.07\ \mathrm{MB\,s^{-1}}$; for 90 s: $2.07\times90=187\ \mathrm{MB}$ (A1)

(Allow 186–188 MB. If 1 MB is taken as $2^{20}$ bytes throughout, the answers are 79.1 MB/s and 178 MB — credit both conventions if used consistently.)

(d) Indicative content:

  • Compiled: translated once into machine code before deployment; execution is fast and predictable because there is no translation at run time; the executable can be optimised for the specific target processor; the source code is not distributed, which protects intellectual property. (A1)(A1)
  • Interpreted: translated line by line at run time; slower (typically by an order of magnitude) and with less predictable timing; but easier to test and modify, and the same source runs on any hardware with a suitable interpreter. (A1)
  • Evaluation: the drone has fixed, known hardware and a hard real-time constraint of 20 ms, and the code will not be modified in flight. Compilation is therefore clearly preferable: the worst-case response time is shorter and, critically, more *predictable* — an interpreter introduces run-time translation delays that could cause a missed deadline and a collision. (A1)

Accept a contrary conclusion only if justified by a specific constraint (for example, if the software had to be updated in flight).

A third option students sometimes offer is just-in-time (JIT) compilation. It should not earn the evaluation mark on its own: a JIT compiler still translates each method at run time the first time it is executed, so the worst-case timing inside a 20 ms control window is not bounded by the source alone, and a routine that runs once per flight never benefits from the cached native code. It earns the same (A1) as any other answer only if the candidate states that the deadline is set by the worst case, and that compilation removes translation from the flight path altogether.

Markscheme notes

(a) Credit a clear description even if the register names differ (MAR/MDR/PC/IR/CIR/accumulator are all acceptable). The four marks are for: fetch, decode, execute, and the role of registers/speed of access. A purely list-like answer naming components without describing interaction is capped at two marks.

(b) Each difference must be paired with a reason relating to the *task* (image processing / parallelism). A generic 'GPUs are faster' earns nothing. Credit any two well-explained differences.

(c) Award (A1) for the bits-per-frame figure, (A1) for the byte conversion, (A1) for the per-second rate, (A1) for applying the 40:1 ratio and the 90 s. Follow through on an arithmetic slip.

(d) This is an evaluate question, so a conclusion is required and must follow from the reasoning. Credit the comparison marks for either option, but the final (A1) requires a justified recommendation tied to a stated constraint (real-time deadline, fixed hardware, or IP protection).

Additional guidance. In (b) credit the SIMD framing ('one instruction applied to many pixels at once'), provided the consequence is stated. In (c) apply the candidate's figure from (i) consistently in (ii) and award the method marks even if that figure is wrong; mixing decimal and binary megabytes forfeits the final (A1). In (d) a hybrid answer — compile the control loop, interpret the mission scripts — earns full credit if both options are assessed against the 20 ms deadline.

Why this question is hard

Theme A questions are usually pure recall dressed up in a context, and this one is built to resist that. Three things make it harder than it looks:

  • In (a), 'describe the interaction' is not 'list the components'. The fetch–decode–execute cycle is a *sequence* with data moving between named registers, and answers that simply define the control unit, the ALU and the registers separately cannot access the top marks.
  • In (b) the mark scheme is explicitly looking for a difference and a consequence for this workload. 'A GPU has more cores' is a fact; 'obstacle detection applies one operation to every pixel, so thousands of cores each handle a different pixel at the same time' is an explanation.
  • Part (c) is the pivot. Without the number, part (d) is an opinion. With it, students can see that 82.9 MB/s of raw video cannot be stored or processed casually — the compression ratio is doing real work, and any architecture that has to move uncompressed frames around is in trouble.

The evaluation in (d) then has something to bite on. The 20 ms deadline is the decisive constraint: it is not that compilation is 'faster' in some abstract sense, it is that interpretation makes the *worst-case* timing unpredictable, and a hard real-time control loop is governed by its worst case, not its average case.

Classic wrong turns: describing the GPU as 'a faster CPU'; confusing compression ratio with compression *factor* (dividing by 40 when they should, or multiplying); and in (d), describing both options competently and then never choosing.

One further trap is worth naming, because part (c) carries a mark for it. The arithmetic there mixes bits and bytes: the colour depth is given in bits per pixel, so the frame rate produces a rate in bits per second, while the question asks for megabytes per second. Dividing by 8 is not a tidiness step that can be skipped, and a candidate who omits it obtains a rate eight times too large. That error is easy to miss, because the same factor of eight is then carried silently into the 90-second storage figure, where the answer still looks like a plausible number rather than a wrong one.
