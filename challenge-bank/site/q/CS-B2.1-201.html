A function that reads one number from a file

The figure shows a function read_reading(path), written in Python, that returns the single integer stored in a text file whose path it is given.

The variable handle is assigned None before the try region. If the file opens, its first line is read and converted to an integer, and that integer is returned. If the conversion fails the function prints "bad value" and returns -1. If the file cannot be opened the function prints "cannot open" and returns -2. Whichever of those happens, the finally region then runs handle.close().

Two facts about the language matter here. FileNotFoundError is a subclass of OSError, so a handler written for OSError also catches a missing file. And an exception raised inside a finally region replaces any value that the try or except regions were in the middle of returning.

Question

Trace the function for each of three files and decide what the caller receives in each case. The three files are a well-formed file containing the single line 250, a malformed file whose first line is 25 0, and a path that does not exist. Assume no other code changes the value of handle.

  1. [3 marks](a)

    State the value that read_reading returns for the well-formed file, and the value it returns for the malformed file.

    (State)
  2. [5 marks](b)

    Determine the value the caller receives for the path that does not exist. State the order in which the regions of the function execute, and state the value the OSError handler computes before the finally region runs.

    (Determine)
  3. [4 marks](c)

    Explain why the finally region changes the outcome on that path but leaves the outcome on the other two paths unchanged.

    (Explain)
  4. [4 marks](d)

    Describe two changes to the function that would make the caller receive -2 when the path does not exist, and justify which of the two you prefer.

    (Justify)

Reveal the answer

Part (a). For the well-formed file the line reads 250, int("250") is 250, and the function returns 250. (M1)(A1)

For the malformed file, int("25 0") is not a valid integer literal and raises ValueError. The ValueError handler runs, prints "bad value" and returns -1. The finally region then closes a handle that is a real file object, so the close succeeds and the caller receives -1. (A1)

Part (b). The regions execute in this order. First handle = None runs. Then the try region begins and handle = open(path) raises FileNotFoundError, so handle is never reassigned. Because FileNotFoundError is a subclass of OSError, the OSError handler runs: it prints "cannot open" and computes the value -2. Before that value can be returned, the finally region runs handle.close(). (M1)(A1)(A1)

handle is still None, because the assignment that would have replaced it was the statement that raised. So the finally region calls None.close(), which raises AttributeError. (M1)

An exception raised inside a finally region discards the return value that was in flight. The AttributeError therefore propagates to the caller and the -2 is never delivered. The caller receives an AttributeError, not -2. (A1)

Two details are worth recording. The function still prints "cannot open" before it fails, so a log file suggests that the missing file was handled and reported, which is the opposite of what happened. And the value the handler computed, -2, is discarded rather than converted, so there is no trace of it anywhere after the call.

Part (c). On the success path, handle = open(path) completed before the read, so handle is a real file object and close() succeeds. The return value 250 stands. (M1)(A1)

On the ValueError path, open(path) also completed. The failure was in converting the line that was read, not in opening the file, so handle is again a real file object and close() succeeds. The return value -1 stands. (A1)

Only on the OSError path did the assignment fail to complete, leaving handle at its initial value of None. The finally region is therefore harmless on two paths out of three and fatal on the third, and the source line that performs the cleanup is identical in all three cases — there is nothing at that line to suggest which path the program is on. (A1)

Part (d). First change: guard the cleanup so that it does nothing when there is no handle to close, as in if handle is not None: handle.close(). (M1)

Second change: let the language manage the handle, using a context manager, as in with open(path) as handle: return int(handle.readline()), with the except regions kept around the with statement. The initial assignment of None is then not needed at all. (A1)

I prefer the second. The guard fixes this instance but leaves the pattern in place: the next resource the function acquires will need its own None check, and one that is forgotten fails in exactly the same way, silently and on a path that is rarely exercised. The context manager ties the cleanup to the resource itself, so it cannot be forgotten and cannot be reached with an unassigned handle. Its cost is that the try region has to be restructured, which is a real cost if the surrounding house style forbids the with statement, and in that case the guard is the correct minimal change. (A1)

Markscheme notes

(a) M1 for the successful conversion, A1 for 250. A1 for -1 with the reason that int("25 0") raises ValueError. A candidate who answers -2 for the malformed file has confused the two handlers and scores nothing in this part.

(b) M1 for recognising that the missing file reaches the OSError handler because FileNotFoundError is a subclass of OSError. A1 for the execution order, A1 for the value -2 being computed. M1 for the observation that handle is still None at the finally region. A1 for the conclusion that the caller receives AttributeError and not -2. Accept "the -2 is discarded" or "the finally exception replaces the return" as the final A1. A candidate who states only that an AttributeError occurs, without saying what the caller would otherwise have received, earns the M1 but not the A1.

(c) M1 for the idea that handle is a real object on the success path, A1 for close() succeeding there. A1 for the corresponding point on the ValueError path, including the reason that the failure was in the conversion rather than in the open. A1 for stating that only the OSError path leaves handle as None. Do not award the last A1 for a restatement of part (b).

(d) M1 for a None guard, A1 for a context manager or for moving the close into each handler. A1 for a justification that names a property of the preferred fix rather than merely restating it. Accept either preference provided the reasoning refers to what the change does or does not prevent; a bare "it is cleaner" earns no mark. Do not award the final A1 to a candidate who proposes catching AttributeError, since that hides the defect rather than removing it.

Why this question is hard

This item turns on the fact that finally is not merely housekeeping. It is taught as the region that always runs, which is true, and the natural inference — that it therefore cannot change what the function does — is false. A region that always runs is exactly the region whose failure is guaranteed to matter, because it sits between every computed return value and the caller.

The trap is that the code is idiomatic. Initialising handle to None, opening inside the try, returning from the handler, and closing in finally is a shape candidates are taught to write, and it is correct on the two paths a student is most likely to test. The success path works. The malformed-file path works, and it is the more interesting of the two, because the file *did* open — the failure came later — so the close is legitimate. Only the third path, where the open itself fails, leaves handle unassigned, and that is the path a student is least likely to construct.

The item therefore rewards tracing rather than pattern-matching. A candidate who recognises the idiom and reports what it usually does will answer -2 and be wrong for a reason that has nothing to do with exceptions in the abstract: the answer turns on which of three paths leaves a variable unassigned.

There is a second layer that makes the failure hard to notice in practice, and it is why the item asks for the order of execution. The handler prints "cannot open" before it computes -2, and the print succeeds. So the program produces a diagnostic that says the missing file was handled, and then fails anyway. A developer reading the log sees the expected message and concludes the branch was exercised correctly. The value -2 is discarded without a trace, which is the worst combination: a misleading success message followed by an unrelated-looking error.

Part (d) asks for a repair rather than a diagnosis, and the two repairs are not equivalent. The guard is correct and local; the context manager removes the class of defect. Preferring the second is a judgement about which kind of fix a codebase wants, and the item accepts either answer provided the candidate says what the chosen fix does and does not prevent. Catching AttributeError is the answer that must be refused: it makes the symptom disappear while the caller still receives the wrong value.
