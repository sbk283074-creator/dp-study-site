B2.4 A recursive implementation of a linear recurrence whose call count is exactly twice the answer minus one, where memoisation changes the cost class and the recursion depth sets a separate, independent limit

Question

A service computes terms of a sequence defined by $F(1) = 1$, $F(2) = 1$ and $F(n) = F(n-1) + F(n-2)$ for $n \ge 3$. The implementation currently in production is the following, in a language whose default recursion limit is $1000$ nested calls and whose interpreter executes about $1.0 \times 10^{7}$ function calls per second:
``
FUNCTION term(n)
IF n <= 2 THEN
RETURN 1
ELSE
RETURN term(n - 1) + term(n - 2)
END IF
END FUNCTION
`
A second implementation stores each computed value in a dictionary the first time it is needed and reads it thereafter, so that each index is evaluated once. A third implementation uses a loop and holds only the two most recent values.
Throughout, a *call* means one invocation of term`, including the invocation that answers the original request. The phrase *recursion depth* means the number of invocations that are simultaneously on the call stack at the deepest point of the computation.

  1. [3 marks](a)

    Determine the number of calls made when term(6) is evaluated, by writing down the recurrence satisfied by the call count and evaluating it from the base cases upwards. State the recurrence you used.

    (Determine)
  2. [4 marks](b)

    Let $c(n)$ be the number of calls made in evaluating term(n), and let $F$ denote the sequence itself. Show that $c(n) = 2F(n) - 1$ satisfies the recurrence from part (a) together with its base cases, and hence determine the number of calls made when term(40) is evaluated. Estimate the time this takes at the stated execution rate.

    (Show that)
  3. [3 marks](c)

    The memoised implementation makes exactly $2n - 3$ calls for $n \ge 2$. Determine the number of calls it makes for $n = 40$, determine the factor by which this reduces the work against part (b), and determine the largest value of $n$ for which the unmemoised implementation finishes within one minute.

    (Determine)
  4. [3 marks](d)

    Explain why the memoised implementation still fails when asked for term(2000), even though it is efficient in the number of calls. State the depth of the call stack in each implementation as a function of $n$, and state which implementation is not subject to the failure and why.

    (Explain)
  5. [3 marks](e)

    The service must answer $1.0 \times 10^{4}$ requests per day for values of $n$ up to $1500$, each request arriving independently and needing one term. Justify, with quantitative reasoning, which of the three implementations should be deployed, and state one circumstance in which your recommendation would change.

    (Justify)

Reveal the answer

(a) Evaluating term(n) for n >= 3 invokes term(n - 1) and term(n - 2) as well as being an invocation itself, so the call count satisfies

$$c(n) = 1 + c(n-1) + c(n-2), \qquad c(1) = c(2) = 1 \;\text{(M1)(A1)}$$

the base cases holding because for n <= 2 the function returns immediately without recursing. Working upwards:

$c(3) = 1 + 1 + 1 = 3$, $c(4) = 1 + 3 + 1 = 5$, $c(5) = 1 + 5 + 3 = 9$, $c(6) = 1 + 9 + 5 = 15$ (A1).

So term(6) makes 15 calls to compute the value 8.

(b) Substituting $c(n) = 2F(n) - 1$ into the recurrence, the left-hand side is $2F(n) - 1$ and the right-hand side is

$$1 + \bigl(2F(n-1) - 1\bigr) + \bigl(2F(n-2) - 1\bigr) = 2\bigl(F(n-1) + F(n-2)\bigr) - 1 = 2F(n) - 1 \;\text{(M1)(A1)}$$

using the definition of $F$ itself. For the base cases, $c(1) = 2(1) - 1 = 1$ and $c(2) = 2(1) - 1 = 1$, both correct (A1). Since a first-order recurrence in two variables with two base conditions has a unique solution, the closed form is established. With $F(40) = 102\,334\,155$,

$$c(40) = 2(102\,334\,155) - 1 = 204\,668\,309 \;\text{(A1)}$$

about $2.0 \times 10^{8}$ calls. At $1.0 \times 10^{7}$ calls per second that is roughly $20$ seconds for one term (A1) — and the cost grows by a factor of about $1.618$ for each increment of $n$, so each extra unit of $n$ adds about $62\%$ to the running time.

(c) For $n = 40$ the memoised version makes $2(40) - 3 = 77$ calls (A1). The reduction factor is

$$\frac{204\,668\,309}{77} \approx 2.66 \times 10^{6} \;\text{(A1)}$$

so roughly two and a half million times less work, taking a few microseconds rather than twenty seconds. For the unmemoised version, one minute allows $6.0 \times 10^{7}$ calls, which requires $2F(n) - 1 \le 6.0 \times 10^{7}$, that is $F(n) \le 3.0 \times 10^{7}$. Since $F(41) = 165\,580\,141$ and $F(42) = 267\,914\,296$ are respectively above and below $3.0 \times 10^{7}$ after dividing by two, checking directly: $c(42) = 535\,828\,591$ calls, which takes $54$ seconds, while $c(43) = 866\,988\,873$ takes $87$ seconds. The largest value computable within a minute is therefore $n = 42$ (A1).

(d) The memoised version is efficient in *calls* but not in *depth*. Each evaluation of term(n) proceeds by calling term(n - 1), which calls term(n - 2), and so on down to the base case, so the deepest point of the computation has about $n - 1$ invocations simultaneously on the stack (M1). Memoisation prevents repeated evaluation of a value; it does not shorten the chain, because the first evaluation of each index still descends the whole way to the base case before anything is stored. At $n = 2000$ the depth is about $1999$, well past the default limit of $1000$, so the interpreter raises a stack-overflow error before the answer is produced (A1). The unmemoised version has the same depth and the same problem, besides being astronomically slow. The iterative version keeps no chain at all: it holds two variables and updates them $n - 2$ times, so its stack use is constant and its depth does not depend on $n$ (A1). It is the only one of the three that is not subject to this failure.

(e) The iterative implementation should be deployed (A1). The reasoning: at $n = 1500$ the naive version needs about $2F(1500) - 1$ calls, and since $F(n) \approx \varphi^{n}/\sqrt{5}$ with $\varphi = 1.618$, $\log_{10} F(1500) \approx 1500 \times 0.2090 - 0.349 = 313$, so on the order of $10^{313}$ calls — beyond any conceivable hardware, and it would also breach the stack limit. The memoised version makes only $2(1500) - 3 = 2997$ calls, which is trivial, but at $n = 1500$ its depth is about $1499$, still beyond the default limit of $1000$, so it would fail at run time for the upper part of the requested range (M1). The iterative version uses about $1500$ loop steps and constant memory per request; at $1.0 \times 10^{4}$ requests per day that is $1.5 \times 10^{7}$ steps per day, a fraction of a second of processor time in total, and it has no stack exposure at all (A1). The recommendation would change if the language runtime guaranteed tail-call elimination or if the recursion limit were raised well above $1500$ — in that case the memoised version, or a plain iterative version with the same cost, would be equally acceptable and the choice could be made on readability alone (A1).

Why this question is hard

There is a pleasing sting in the tail of this one: the number of calls the naive recursion makes is exactly $2F(n) - 1$, which is to say that computing a value costs you about twice that value in calls. The cost is not merely proportional to the answer, it is a fixed multiple of it, and since the answer grows exponentially the cost does too. That identity is worth deriving rather than quoting, and part (b) is built to make candidates do it: substitute the closed form into the recurrence and the definition of $F$ falls out of the other side.

The point of part (c) is that asymptotics alone do not tell you what you can actually run. Two and a half million times less work sounds like an abstraction until it is translated into 'twenty seconds down to a few microseconds', and the one-minute question forces the candidate to sit with the boundary rather than classify the growth. Landing on $n = 42$ requires evaluating both $n = 42$ and $n = 43$ and comparing, and the two answers straddle the budget by a comfortable margin, so guessing is visible.

Part (d) is the real test, and it is the reason the item is claimed at difficulty 5 rather than 4. Having just fixed the exponential blow-up, the natural conclusion is that the problem is solved. It is not, because two different resources are being consumed and only one was measured. Memoisation reduces the number of calls to linear, but the depth of the call stack is set by how the recursion descends, not by how many times it repeats, and that depth is about $n$ in both recursive versions. At $n = 2000$ the fast version fails for exactly the same reason the slow version would have if it had ever got there.

The practical conclusion, in part (e), is that the iterative version is not a micro-optimisation but the only one of the three that is correct over the required range. It also happens to be the cheapest in absolute terms: about $1.5 \times 10^{7}$ loop steps per day is nothing. A candidate who recommends memoisation because it is 'efficient' has optimised one axis and shipped a program that raises an exception on the largest inputs requested.

The general lesson generalises well beyond Fibonacci. Whenever a recursive solution is replaced by a faster recursive solution, the question 'how deep does it go' remains open, and it is usually the one that bites in production, because it manifests as a crash at a specific input size rather than as a gradual slowdown that someone would notice in testing.

Challenge lever
Two independent limits are in play and the item is built so that fixing the visible one exposes the hidden one. The visible limit is exponential: the naive recursion calls itself twice per level, so the number of invocations is exactly twice the value being computed minus one, and by nought point two of the way to two thousand that number exceeds ten to the four hundred and seventeen. The hidden limit is the depth of the call stack, which memoisation does nothing whatever about, so the 'fixed' algorithm is fast and still fails. Quantifying both, in the units a service actually cares about, is the whole question.
