The algorithm that wins on paper and loses on the machine

Computer science HL · CS-B2.4-001

Theme B: Computational thinking and problem-solvingB2.4 Programming algorithms (B2.4.1 the complexity of an algorithm, B2.4.2 searching and sorting algorithms, B2.4.3 the suitability of an algorithm for a given task)P115 marksdifficulty 5DetermineCalculateExplainEvaluate

Two ways to find one record

A library catalogue holds $n$ records sorted by accession number, stored contiguously in memory. Two search routines are available. Linear search examines records in order from the start of the list; in the worst case it makes $n$ comparisons. Binary search repeatedly compares against the middle of the remaining range; in the worst case it makes $\lfloor \log_{2} n \rfloor + 1$ comparisons. Profiling on this machine gives a realistic cost model rather than a comparison count: a linear-search comparison costs $3\ \mathrm{ns}$, because consecutive records are already in the cache, while a binary-search comparison costs $30\ \mathrm{ns}$, because each probe lands far from the last one and usually misses the cache. A binary search also pays a one-off $400\ \mathrm{ns}$ of setup before its first comparison.

Question

The table appears to settle the matter. This question asks whether it does.

  1. [3 marks](a)

    Determine the worst-case number of comparisons binary search makes for each value of $n$ in the table, showing how $\lfloor \log_{2} n \rfloor + 1$ gives the stated figures, and state the complexity class of each algorithm.

    (Determine)
  2. [5 marks](b)

    Using the cost model in the stimulus, calculate the worst-case time taken by each algorithm for each value of $n$ in the table. Hence determine the smallest value of $n$ for which binary search is the faster of the two, showing your method.

    (Calculate)
  3. [4 marks](c)

    Explain why the comparison counts in the table give the opposite ranking to the timings for small $n$, referring to the cost model and to the way each algorithm accesses memory.

    (Explain)
  4. [3 marks](d)

    Evaluate whether a programmer should implement a hybrid routine that uses linear search below the crossover value and binary search above it, giving one reason for and one reason against.

    (Evaluate)

Reveal the answer

(a) For $n = 16$, $\lfloor\log_{2} 16\rfloor + 1 = 4 + 1 = 5$; for $n = 256$, $8 + 1 = 9$; for $n = 65\,536$, $16 + 1 = 17$; for $n = 16\,777\,216$, $24 + 1 = 25$. (A1) for the method, (A1) for the four values. Linear search is $\mathrm{O}(n)$ and binary search is $\mathrm{O}(\log n)$. (A1)

(b) Linear search takes $3n$ nanoseconds. Binary search takes $400 + 30(\lfloor\log_{2} n\rfloor + 1)$ nanoseconds. (M1)

| $n$ | linear search | binary search |
|---|---|---|
| $16$ | $48\ \mathrm{ns}$ | $400 + 30(5) = 550\ \mathrm{ns}$ |
| $256$ | $768\ \mathrm{ns}$ | $400 + 30(9) = 670\ \mathrm{ns}$ |
| $65\,536$ | $196\,608\ \mathrm{ns}$ | $400 + 30(17) = 910\ \mathrm{ns}$ |
| $16\,777\,216$ | $50\,331\,648\ \mathrm{ns}$ | $400 + 30(25) = 1150\ \mathrm{ns}$ |

(A1) for each column. For the crossover, note that between $n = 128$ and $n = 255$ the binary-search comparison count is fixed at $8$, so the binary-search time is constant at $400 + 30(8) = 640\ \mathrm{ns}$ across that range. (M1) Solving $3n = 640$ gives $n = 213.3$, so (M1) at $n = 213$ linear search takes $639\ \mathrm{ns}$ and binary takes $640\ \mathrm{ns}$, and at $n = 214$ linear takes $642\ \mathrm{ns}$ and binary still takes $640\ \mathrm{ns}$. The smallest $n$ for which binary search is faster is therefore $n = 214$. (A1)

(c) The comparison count measures one cost, and it is not the cost that dominates for small $n$. Binary search has a fixed setup of $400\ \mathrm{ns}$, which at $n = 16$ is more than eight times the entire cost of the linear search, and each of its comparisons costs ten times as much because the probes jump around the array and usually miss the cache. (A1)(A1) Linear search walks along the array, so after the first access every subsequent record is already in a cache line that has been fetched, and each comparison costs $3\ \mathrm{ns}$. (A1) Complexity classes describe how the time grows as $n$ becomes large, and they deliberately discard constant factors; for $n$ below a few hundred the constants here decide the outcome, and the asymptotically worse algorithm wins. (A1)

(d) In favour: the hybrid takes the better of the two routines at every size, so it is never worse than either, and the crossover is a single comparison against a constant, which is almost free. (A1) Against: it is two code paths to write, test and maintain instead of one, and the crossover of $214$ is specific to this machine's cache behaviour and this record size — on different hardware the threshold moves, so the constant becomes a tuning parameter that someone has to keep valid. (A1) Whether it is worth it depends on how often the routine runs: in a loop executed millions of times the gain is real, and in a function called once per user action it is not worth the complexity. (A1)

Markscheme notes

(a) Accept the four values with or without the working; the complexity classes must be stated in big-O form. (b) Accept the table entries to two significant figures. For the crossover, credit any systematic method — tabulation, bisection or solving $3n = 640$ on the correct interval — and accept $214$; a candidate who solves $3n = 400 + 30(\log_{2} n + 1)$ treating the logarithm as continuous gets about $n = 200$ and should not be penalised provided the method is shown, since the floor function is what makes the true answer a little higher. (c) The explanation must refer to the fixed setup cost and to the per-comparison cost difference; a candidate who says only that binary search has overhead has not used the model. The cache explanation is the more valuable of the two and should be credited generously. (d) Credit a reason for and a reason against; a candidate who argues only one side cannot reach the top mark. The point that the threshold is machine-specific is the strongest objection and should be looked for. Do not accept 'binary search is O(log n) so it is always faster' as an answer to any part: the item exists to show that this is false, and a candidate who restates it has not engaged with the model at all.

Why this question is hard

Complexity analysis is taught because it survives changes of hardware, and this item exists to show what it costs to be that general. Big-O deliberately throws away constant factors and lower-order terms, and for large inputs that is exactly right: at $n = 16$ million, binary search is about forty thousand times faster and no constant could close the gap. At $n = 16$, binary search is more than eleven times slower, and the same analysis predicts nothing about that. The crossover sits at $214$, which is small enough that a working programmer will meet it.

The mechanism is worth being precise about, because 'overhead' is not an explanation. Binary search probes the middle of the array, then the middle of a half, then the middle of a quarter, and those addresses are far apart. Each probe is therefore very likely to miss every level of cache and cost a full memory access, which is why the model charges $30\ \mathrm{ns}$ per comparison against linear search's $3\ \mathrm{ns}$. Linear search reads consecutive records, so the first access pulls in a cache line containing the next several records and the following comparisons are almost free. The asymptotic advantage of binary search is real; the per-comparison advantage of linear search is also real; which one wins depends on how many comparisons there are, and that is a question with a numerical answer.

Part (d) resists the tidy conclusion. Having computed the crossover, the natural response is to implement the hybrid, and for a hot loop that is correct. But the threshold of $214$ is not a fact about searching — it is a fact about this cache, this record size and this clock speed, and it will be different on the next machine. Embedding it in source code turns a measured quantity into a magic number that nobody will re-measure. A candidate who sees that has understood something about software engineering that the complexity analysis was never going to teach them, which is the reason the item ends there rather than at the arithmetic.
