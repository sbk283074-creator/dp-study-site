A bounded buffer class where the bug is in the average

Computer science HL · CS-B3.1-001

B3.1 Fundamentals of OOP for a single class (B3.1.2 class design, B3.1.3 static and non-static members, B3.1.4 defining classes and instantiating objects, B3.1.5 encapsulation and information hiding)P2 · Section B16 marksdifficulty 4technology: not allowedpythonExplainConstruct

SensorReadings

A weather station holds the most recent readings from a thermometer in a fixed-size window so that a rolling average can be displayed. The class must never store more than CAPACITY readings: when it is full and a new reading arrives, the oldest reading is discarded to make room.

A first attempt at part of the class is shown below.

class SensorReadings:
def __init__(self, capacity):
self.values = []
self.capacity = capacity

def add(self, reading):
self.values.append(reading)

def mean(self):
total = 0
for v in self.values:
total += v
return total / self.capacity

The class works when tested with a single reading, and gives a value that looks reasonable for the first few readings after that.

Question

The window size is a property of the device, not of any individual object, and several SensorReadings objects may exist at once for different sensors.

  1. [3 marks](a)

    Explain why CAPACITY should be a class-level constant rather than an instance variable set by __init__, and state one invariant that the class must maintain.

    (Explain)
  2. [6 marks](b)

    Construct the completed class, including __init__, add, mean and __len__, so that it maintains the invariant you stated and never holds more than CAPACITY readings.

    (Construct)
  3. [4 marks](c)

    Explain the error in the draft mean method and the effect it has after three readings have been added to a buffer whose capacity is five, and state the corrected line.

    (Explain)
  4. [3 marks](d)

    Explain why a method that returns self.values directly breaks encapsulation, and describe one way of giving the caller the data without doing so.

    (Explain)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) The window size is a property of the device, is the same for every object created, and must not vary between objects; making it a class-level constant expresses that and prevents one instance from being given a different capacity from another. (M1) It also removes the risk that the value is reassigned after construction, which would make the buffer's behaviour depend on when a method was called. (A1)

An invariant the class must maintain: the number of readings held is never greater than CAPACITY, and the values held are always the most recent ones added, in order. (A1)

(b)

class SensorReadings:
    CAPACITY = 5

def __init__(self):
self._values = []

def add(self, reading):
if len(self._values) == self.CAPACITY:
self._values.pop(0)
self._values.append(reading)

def mean(self):
if not self._values:
return None
return sum(self._values) / len(self._values)

def __len__(self):
return len(self._values)
```

The critical construction is the eviction in add: the oldest reading is removed before the new one is appended, which is what keeps the length bounded. (M1)(A1) The guard inside mean handles the empty buffer, which would otherwise raise a division by zero; the guard must be present because the class is usable before any reading arrives. (M1)(A1)

Using len(self._values) rather than a stored count means the count cannot fall out of step with the list. (M1) The attributes are prefixed with a single underscore to signal that they are internal, and __len__ gives callers the size without exposing the list. (A1)

(c) The error is that mean divides the total by self.capacity, the maximum number of readings the buffer can hold, instead of by the number of readings it actually holds. (M1)

With a capacity of five and three readings added, say 10, 20 and 30, the total is 60 and the correct mean is $60/3=20$. The draft returns $60/5=12$. (M1)(A1) The error is therefore not a failure but an understatement: the displayed average is too low by a factor of 3/5, and because the divisor is fixed, the error shrinks as the buffer fills and disappears entirely once five readings have been added. That is why testing with a single reading and then a few more gives values that look plausible. (A1)

The corrected line is:

        return total / len(self.values)

The same correction is what makes the earlier version of mean safe against an empty buffer, since a division of zero by zero would otherwise raise an exception.

(d) Returning self.values hands the caller a reference to the internal list, not a copy. (M1) The caller can then append to it, sort it in place or clear it, and every one of those operations changes the state of the object without going through add, which is the only method that enforces the capacity limit. The invariant established in part (b) is then broken from outside the class, and the object can end up holding more readings than CAPACITY or in an order that no longer reflects when they arrived. (A1)

One way to avoid this is to return a copy of the list, for example return list(self._values), so that the caller's changes affect only their own copy. (A1) A generator that yields each reading in turn achieves the same protection while avoiding the cost of copying a large buffer.

Note that list(self._values) is a shallow copy: it protects the list itself, but if the readings were mutable objects rather than numbers the caller would still share the same objects and could mutate them in place. For numeric readings the distinction does not bite, which is why the question uses temperatures; a class holding mutable records would need a deep copy, or better, to hand back immutable values.

Markscheme notes

Part (a): the explanation must connect the class-level constant to the fact that the value is shared and fixed; an answer that only says 'it is a constant' with no reason earns one mark. Accept any genuine invariant, including the one given here, provided it constrains the state rather than describing a method. Part (b): code in a language other than the one indicated should be accepted if the syllabus version being sat requires it, but the eviction logic must be present and correct. Do not award the invariant-preservation marks to a candidate whose add simply appends, even if the rest of the class is correct, because the stated invariant is then violated. The empty-buffer guard is worth its marks even though it is one line; a candidate who omits it should be told that the class is usable before any reading arrives. Part (c): the mark is for identifying the divisor rather than for restating the method. Require the numerical example — a candidate who says 'it divides by the wrong thing' without showing the effect on a value earns the first mark only. Part (d): the explanation must refer to the caller modifying the internal state; 'it is not good practice' is not an answer. Any concrete remedy, such as returning a copy, returning a tuple, or yielding items from a generator, earns the last mark.

Why this question is hard

This question is built around a bug that a cursory test will not find. When only one reading has been added, the draft's mean divides by the capacity and returns a number that is wrong but not obviously so; as more readings arrive the divisor becomes closer to the truth, and once the buffer is full the bug disappears entirely. A student who tests with a full buffer will conclude that the class works. That is exactly the failure mode of real code that maintains a rolling statistic, and it is why the question asks for the effect after three readings out of five rather than at the end.

The design issue underneath is the difference between the capacity and the count. They are equal only when the buffer is full, and code that uses them interchangeably is correct in the case people test and wrong in the case that matters. Writing the class so that the count is always derived from the data, rather than stored separately, removes the possibility of the two drifting apart — a small decision with a large effect on how many bugs the class can have.

The encapsulation part is not a formality. Returning the internal list gives the caller a reference, and the caller can then violate the invariant that add was written to protect. This is the most common way that a class with a carefully written interface is broken from the outside, and the fix is not to document the danger but to remove it by returning a copy or yielding values. The same reasoning explains why the attributes are private: the capacity rule lives in add, and nothing should be able to bypass it.

Finally, making the capacity a class-level constant expresses something true about the problem — the window size belongs to the device, not to an individual window object — and it makes the invariant checkable, since a value that cannot be reassigned per object cannot be violated per object.
