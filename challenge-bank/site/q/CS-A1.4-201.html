A1.4 Compilation against interpretation on a stated cost model, where the one-off compilation cost is the whole of the decision and the per-run comparison points the wrong way

Computer science HL · CS-A1.4-201

A configuration language for a mail-order catalogue

A retailer maintains a small configuration language, catcfg, used to describe how a printed catalogue's pages are built from a product database. A script is about $12\,000$ tokens long, is stored as a text file, and is run once each weekday morning to generate that day's catalogue layout. When a price band changes, an editor edits the script by hand and the next morning's run uses the edited version. The engineering team is deciding between two ways of running it: an interpreter that reads the script and executes it directly on every run, and a compiler that translates the whole script into an intermediate form which is then executed. Measured on the retailer's server, the interpreter consumes $1.5\ \mu\mathrm{s}$ per token on each run, and the compiler consumes $60\ \mu\mathrm{s}$ per token once when it translates the script and $0.25\ \mu\mathrm{s}$ per token on each run of the translated form. For this question you may ignore the cost of starting either program and the cost of reading the file from disk.

Question

The engineering team has asked for a recommendation on how to run catcfg, grounded in the costs given in the stimulus. Identify which stage of translation detects each of the three faulty fragments, explain one advantage the compiled form has for this particular workflow, determine when the two approaches cost the same across a sequence of runs, and comment on whether that figure should decide the choice.

  1. [3 marks](a)

    Three faulty fragments of a catcfg script are given below. For each one, identify the stage of translation that detects it -- lexical analysis, syntax analysis or semantic analysis -- and justify your choice.
    (i) price + 1@5 (ii) if price > 100 then total = total + price with no closing keyword (iii) pagewidth = priceband * 2 where priceband is a text value and pagewidth is declared as an integer.

    (Identify)
  2. [2 marks](b)

    Explain one advantage that the compiled form has over the interpreted form for this particular workflow, referring to the number of times the script is run and to what changes between runs.

    (Explain)
  3. [4 marks](c)

    Determine the total time in milliseconds taken by each of the two approaches for a single run, and determine the number of executions at which the two totals become equal. Show your working.

    (Determine)
  4. [2 marks](d)

    Comment on whether the equality you found in part (c) should decide the choice, referring to what the workflow does between executions.

    (Comment)

Total: 11 marks. Try the question before revealing anything below.

Reveal the answer

(a)

(i) 1@5 is lexical: the tokeniser's rules define a number as a run of digits and @ is not a character that can appear in one, so the scanner fails to form a valid token before any grammar is considered (A1). The characters are individually fine; it is the sequence that no token can cover.

(ii) The missing closing keyword is syntax. Every token so far is valid -- if, an identifier, a relation, a number, the keyword then, an assignment -- and it is the arrangement of those tokens that the grammar rejects, because the rule for a conditional requires a terminator (A1). No meaning has been examined yet.

(iii) priceband * 2 with a text operand is semantic. The statement is grammatically well formed and every token is valid; what fails is the check that the types of the operands are compatible with the operator and with the declared type of the target (A1). This check needs the symbol table of declarations, which is why it cannot be done during scanning or parsing.

(b) The compiled form pays the translation cost once and then runs cheaply, and on this workflow the script is executed roughly $260$ times a year -- once each weekday -- against a small number of edits. The number of executions is large and the number of *different* versions is small, so the one-off cost is amortised over many runs (M1).

What changes between runs is normally nothing at all: the environmental data comes from the product database, not from the script. The edit that follows a price-band change is the exception, and it does invalidate the translated form; but even if the script were edited once a month, the translation would be repeated twelve times a year against two hundred and sixty executions (A1).

(c) One run of the interpreter:
$$12\,000\ \text{tokens} \times 1.5\ \mu\mathrm{s} = 18\,000\ \mu\mathrm{s} = 18\ \mathrm{ms} \;\; (A1).$$

One *first* run of the compiled route:
$$12\,000 \times 60\ \mu\mathrm{s} = 720\,000\ \mu\mathrm{s} = 720\ \mathrm{ms} \;\; (A1\text{ for the translation}) ,$$
and each subsequent run costs
$$12\,000 \times 0.25\ \mu\mathrm{s} = 3\,000\ \mu\mathrm{s} = 3\ \mathrm{ms} \;\; (A1).$$

Let $n$ be the number of executions. The interpreted total is $18n$ milliseconds and the compiled total is $720 + 3n$ milliseconds, both measured from the first run and including it. Setting them equal:
$$18n = 720 + 3n, \qquad 15n = 720, \qquad n = 48 \;\; (A1).$$
After $48$ executions both routes have consumed $864\ \mathrm{ms}$. Under the compiled route the script is executed about $260$ times a year, so the crossover is passed in the tenth week of the first year, and the compiled route is decisively cheaper thereafter: at $260$ executions the interpreted total is $4\,680\ \mathrm{ms}$ against $1\,500\ \mathrm{ms}$ for the compiled one, a saving of about $3.2$ seconds a year.

(d) The equality should not decide the choice on its own, because it is derived from a model whose central assumption is that the same script is executed many times unchanged (M1).

The workflow does edit the script: whenever a price band changes, the editor changes the file, and a compiler must then translate the whole thing again at a cost of $720\ \mathrm{ms}$. If the script were edited before every run, the compiled total for $n$ runs would be $n(720 + 3)$ milliseconds against $18n$ for the interpreter, and the compiler would never win. Between the two extremes the answer turns on the edit rate, which the stimulus does not fix. What can be said without that number is that the crossover of $48$ is the edit-free case and therefore the *most favourable* figure the compiler can claim; the real crossover is higher, by $48$ executions for every extra retranslation, and the decision should be taken on a measured edit rate rather than on the model alone (A1).

The model also ignores two things that favour the interpreter: the compiled intermediate form has to be stored and kept in step with its source, which is a real operational cost, and in this workflow the run takes place once a day, so a saving of sixteen milliseconds per run is not visible to anybody. If the only consideration were time, the case for compiling would rest on the tenth week of each year; if the consideration is engineering effort and the risk of a stale translated file, the interpreter may still be the better answer.

Markscheme notes

(a) (A1) for each of the three with a reason. The reason must refer to the stage's own job, not restate the error: "lexical because it is a character that cannot start a token" scores, "lexical because it is a typo" does not. A candidate who places (iii) at syntax has confused a grammar rule with a type rule and scores two of three.

(b) (M1) for using the ratio of executions to distinct versions, (A1) for connecting it to what changes between runs. A candidate who says "compiled code runs faster" without referring to the number of runs scores nothing: the mark is for the amortisation argument, which is the only thing that distinguishes the two approaches here.

(c) (A1) for $18\ \mathrm{ms}$, (A1) for $720\ \mathrm{ms}$ of translation, (A1) for $3\ \mathrm{ms}$ per subsequent run, (A1) for $n = 48$ with the working. A candidate who writes $18n = 720 + 3(n-1)$ obtains $n = 47.8$ and should be given the final mark if they state that $48$ executions is the first at which the compiled total is lower; the difference is whether the first run is counted in both totals, which it should be. A candidate who answers with the per-run ratio ("six times faster") forfeits the last mark; that is exactly the comparison the item is testing.

(d) (M1) for identifying the assumption of an unchanged script, (A1) for a consequence that changes the decision -- a higher crossover, or a crossover that does not exist if the edit rate is high enough. A candidate who says only "the script is edited sometimes" scores the first mark and not the second, because the mark requires the effect of the edit to be traced into the arithmetic.

Condonation: speeds may be quoted in microseconds throughout with the conversion to milliseconds made at the end; the arithmetic is identical. A candidate who states the crossover as "about fifty executions" scores the last mark in (c), provided the exact value is also shown. Forfeits: including the disk read or the process start-up in the totals, which the stem excludes; treating the $12\,000$ tokens as $12\,000$ lines, which changes the arithmetic by a factor the candidate cannot justify.

Why this question is hard

This is an arithmetic question wearing a systems question's clothes, and the arithmetic is not the difficulty. Multiplying a token count by a per-token cost takes a minute; deciding *what to multiply* is the whole of the item.

The instinct, when asked which of two ways of running a program is faster, is to compare the running times: $18\ \mathrm{ms}$ against $3\ \mathrm{ms}$, a ratio of six. That comparison is correct and it is not the answer, because the compiled route has already spent $720\ \mathrm{ms}$ before any of its cheap runs happen. The candid way to put the question is over how many runs the comparison is made, and the answer is a crossover: for any number of runs below $48$, interpreting is cheaper in total. Part (c) asks for that number explicitly, which removes the ambiguity, but part (b) is where the reasoning has to be supplied before the arithmetic can be trusted, because the number of runs is not a property of the language -- it is a property of the workflow.

That is also why part (d) exists. The crossover of $48$ is computed on the assumption that the script never changes, and the stimulus explicitly says that it does change. Each edit forces a retranslation of the whole script, because the cost model given is a whole-script translation and there is no partial translation. So the honest statement is that $48$ is a lower bound on the crossover and the true figure depends on how often the price bands change, which the question deliberately does not supply. Recognising that a model has one unfixed parameter and saying which one it is, is more valuable than producing a confident number that the model does not support.

Part (a) is a separate lesson attached to the same stimulus, and it is the one that turns up in examinations most often. "The compiler finds the errors" is true and useless: the three stages find different errors for different reasons, and the reason is always that stage's own job. A scanner cannot report an undeclared variable because it has no symbol table; a parser cannot report a type mismatch for the same reason; and a semantic analyser never sees a character that could not be tokenised. The three fragments are chosen so that each has exactly one stage that can catch it and two that cannot, and a candidate who has the stages sorted will be able to say which is which without hesitating.

Original. Compiler against interpreter cost comparisons are standard in every A-level and AP-style treatment of translation; the version here fixes the workflow around a daily batch run with occasional hand edits -- the arrangement that makes the one-off translation cost decisive -- and asks for the model's unfixed parameter rather than for a recommendation.
Verification
Both per-run times were recomputed from the token count and the stated rates, and the crossover was obtained algebraically and then confirmed by evaluating both totals at n = 47, 48 and 49. The annual figures used in the discussion were obtained from 52 weeks x 5 weekdays. The three faulty fragments in part (a) were each checked against a small hand-written tokeniser and grammar for the described language to confirm that only one stage can report each of them.
