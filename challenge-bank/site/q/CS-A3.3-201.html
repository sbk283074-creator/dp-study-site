A3.3 One row that changes every aggregate: COUNT(*), COUNT(column), AVG, and NULL propagating through a computed column

Computer science HL · CS-A3.3-201

Theme A: Concepts of computer scienceA3.3 Database programming (SQL queries, aggregate functions, GROUP BY and HAVING, NULL handling)P1 · Section B16 marksdifficulty 4technology: not allowedExplainDetermineDetermineExplain

The orders table in a sales database

The table orders holds one row per order. customer_id identifies the customer who placed it, quantity is the number of units and unit_price is the price per unit at the time the order was taken.

The unit_price column is nullable by design: an order can be taken before the price list entry for that product exists, and the row is then stored with unit_price set to NULL while the price is confirmed later. Order 7 is the only row currently in that state.

The database engine follows the SQL standard in three respects that matter here. An aggregate function ignores NULL inputs. A NULL is not equal to anything, not even to another NULL, so it cannot be selected by an equality test. Any arithmetic expression that contains NULL evaluates to NULL, because the result of an operation on an unknown value is itself unknown.

Question

A manager is asked three things about this table: what the average unit price is, which customers have placed more than one order, and how much each of those customers has spent. The manager writes a set of queries without reading the note on how the engine treats NULL.

  1. [4 marks](a)

    Explain the difference between COUNT(*) and COUNT(unit_price) in a query over this table, and state the value that each of the two returns.

    (Explain)
  2. [5 marks](b)

    The manager writes SELECT SUM(unit_price) / COUNT(*) AS average_price FROM orders; and reports the result as 18.00. Determine the value that the engine's own AVG(unit_price) returns, and explain why the two expressions give different answers.

    (Determine)
  3. [4 marks](c)

    Determine which customers the query
    ``
    SELECT customer_id, SUM(quantity * unit_price) AS spend
    FROM orders
    WHERE order_id > 2
    GROUP BY customer_id
    HAVING COUNT(*) >= 2;
    ``
    returns, and the value it reports for each. State the result the manager intended, and identify the single clause responsible for the difference.

    (Determine)
  4. [3 marks](d)

    Explain why SUM(quantity * unit_price) for customer 104 returns NULL rather than 0, and state one change to the query that would make the reported total well defined for every customer.

    (Explain)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) COUNT(*) counts rows and COUNT(unit_price) counts values, so the first returns 7 and the second returns 6. The difference is exactly one row -- order 7 -- and the gap between the two numbers is the number of NULLs in the column being counted (A1)(A1).

The two functions are not two spellings of the same count. COUNT(*) answers "how many orders are there", which is a property of the table; COUNT(unit_price) answers "for how many orders do we know the unit price", which is a property of one column. On a table with no missing prices the two agree, which is why the distinction is invisible until the first NULL arrives (M1)(A1).

(b) AVG(unit_price) returns 21.00. The engine sums the six non-NULL prices (M1):

$$10.00 + 4.00 + 99.00 + 7.50 + 2.50 + 3.00 = 126.00 \tag{M1}$$

and divides by the number of values it actually summed, which is six (A1):

$$\frac{126.00}{6} = 21.00 \tag{A1}$$

The manager's expression uses the same numerator, because SUM also ignores NULL, but divides by COUNT(*) instead (M1):

$$\frac{126.00}{7} = 18.00 \tag{A1}$$

So SUM(x) / COUNT(*) is not a way of computing the average of $x$. It is the average of $x$ diluted by every row in which $x$ is unknown. The error is systematic rather than random: whenever some values are missing and the remaining values are positive, the reported figure is too low, and the size of the error grows with the *proportion* of missing values rather than with the size of the table. The gap here is $126.00/6 - 126.00/7 = 3.00$, which is the price of one row spread across the whole report.

(c) WHERE is evaluated before grouping, so the rows it removes are gone by the time HAVING counts anything (M1). WHERE order_id > 2 keeps orders 3, 4, 5, 6 and 7, which is one row for customer 101, two rows for customer 102, one row for customer 103 and one for customer 104 (M1). HAVING COUNT(*) >= 2 then keeps only customer 102, whose two surviving rows contribute (A1)

$$1 \times 99.00 + 6 \times 3.00 = 117.00$$

The query therefore returns a single row, $(102,\ 117.00)$ (A1).

The manager intended the two customers who have placed more than one order, which are 101 and 102. Customer 101 has orders 1, 2 and 5, worth

$$3 \times 10.00 + 5 \times 4.00 + 4 \times 2.50 = 60.00$$

and customer 102 is worth 117.00, so the intended answer is a total of 177.00 across the two customers (M1). The clause responsible is the WHERE: a row filter and a group filter are not interchangeable when the group filter is a count, because the count is taken over whatever the row filter happened to leave behind. Deleting the WHERE clause and keeping the HAVING clause gives the intended result.

(d) For order 7 the expression quantity * unit_price is 10 * NULL, and any arithmetic expression containing NULL evaluates to NULL, so that row yields no value at all rather than the value $10 \times 0 = 0$ (M1). SUM ignores NULLs, but customer 104 has only one row, and ignoring the only value in a group leaves nothing to sum, so the aggregate over that group returns NULL rather than 0 (A1).

A change that makes the total well defined is to wrap the aggregate: COALESCE(SUM(quantity * unit_price), 0). Wrapping the product instead, SUM(COALESCE(quantity * unit_price, 0)), also returns 0 here (A1).

The two placements are not equivalent and neither is a correction. The outer form reports 0 only for a group in which *no* line has a price, and it leaves every other group untouched; the inner form treats each unpriced line as zero revenue, which quietly understates any customer who has a mix of priced and unpriced orders. Neither recovers the missing price, so the choice is a decision about what an unknown is worth in the report, and a business that needs the real figure has to obtain the price rather than choose a default for it.

Markscheme notes

(a) (A1) for 7, (A1) for 6, (M1) for the statement that COUNT(column) counts non-NULL values, (A1) for locating the difference in the single NULL row. A candidate who says only "one ignores NULL and one does not", without saying *what* each one counts, earns the first A1 only.

(b) (M1) for the sum 126.00, (M1) for dividing by 6, (A1) for 21.00, (M1) for identifying COUNT(*) as the wrong denominator, (A1) for 18.00 and the direction of the error. A candidate who reports 21.00 with no comparison to 18.00 cannot score the last two marks, because the part asks for the reason the two differ. Follow-through: a candidate whose sum is wrong but who divides by the correct count keeps the last two marks.

(c) (M1) for WHERE running before GROUP BY, (M1) for the surviving rows per customer, (A1) for 117.00, (A1) for the single returned row. The intended result -- 101 at 60.00 and 102 at 117.00 -- is worth the final (M1) and must be distinguished from the returned result, not merely restated.

(d) (M1) for NULL propagating through quantity * unit_price, (A1) for the group having no non-NULL value left to sum, (A1) for a well-formed COALESCE change. A candidate who writes WHERE unit_price IS NOT NULL earns the third mark only if they state that this discards the row rather than repairing it.

Forfeits: treating NULL as 0 throughout, which gives 18.00 for the average and 0.00 for customer 104 and makes every part of the item consistent but wrong; claiming that AVG counts rows and SUM counts values, which inverts the rule. Condonation: a candidate who writes the average as $21.00$ or as $21$ should be given full credit, and a candidate who quotes 0.8125-type intermediate values to more figures than the data supports should not be penalised.

Why this question is hard

Every one of the three failures in this item comes from the same place: the query says what the engine should compute but not which rows it should compute it over, and those two things come apart as soon as a value is missing. That is why the item is not really about SQL syntax. Writing SELECT AVG(unit_price) FROM orders is a two-line exercise that any student can produce, and it is also the version that gets the right answer, so the difficulty cannot live in the syntax.

What makes the item hard is that the naive path is *self-consistent*. Treating NULL as zero gives an average of 18.00, a spend of 0.00 for customer 104, and a report in which no row is ever missing. Nothing in the output looks broken, and nothing in the code raises an error. The student has to know, in advance, that NULL is a marker for "unknown" rather than a synonym for zero, and that the standard's choice to exclude NULLs from aggregates is a deliberate rule rather than an implementation detail. A student who does not know that will not be able to tell the two answers apart by inspection, because both are plausible numbers.

Part (c) adds a second layer that is independent of NULL and is the one most often missed in practice. WHERE and HAVING look like two ways of writing the same filter, and they are not: one selects rows and the other selects groups, and a filter on a count is only meaningful after the rows have been collected. Combining them wrongly produces a query that runs, returns a plausible row, and answers a different question -- the same failure mode as part (b), arriving by a different route.

Part (d) is the conceptual close, because it asks what the fix means rather than how to write it. Both placements of COALESCE make the output well defined and only one of them is safe for a report, and the reason is that a business total is a claim about money while a NULL is a claim about ignorance. Deciding that an unknown price is worth zero is a business decision, not a database operation, and an item that pushes the student to say so is testing judgement rather than recall.

Challenge lever
An aggregate is not a function of the table, it is a function of the rows the engine decides to feed it, and that set is not the same for every aggregate. `COUNT(*)` counts rows, `COUNT(unit_price)` counts values, and `AVG(unit_price)` divides a NULL-excluding sum by a NULL-excluding count. All three read like variations on "how many", and only one of them answers the question a manager thinks they asked. The same NULL then propagates silently through a computed column, so a customer's spend becomes NULL rather than a number, and the failure surfaces as a missing row in a report rather than as an error.

The archetype is the missing-value problem in data analysis: a data set with a hole in it, and a summary statistic that silently changes meaning depending on how the hole is treated. The schema, the seven rows, the three queries and the four parts are written here.

Every figure was recomputed from the seven rows directly: the non-NULL prices were summed and divided by the number of values and by the number of rows to obtain both averages, the per-customer totals were accumulated row by row for both the intended query and the filtered one, and the acid test of the item -- that the two averages differ by exactly one seventh of the sum -- was checked as an identity rather than by comparing the two rounded results.
