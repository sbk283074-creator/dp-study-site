A loop that is linear only while the data keeps moving

Computer science HL · CS-B2.3-001

B2.3 Programming constructs (sequence, selection, iteration, nested loops, loop conditions and termination, tracing the execution of a loop)P2 · Section B16 marksdifficulty 5technology: not allowedpythonExplainConstructEvaluate

PulseTrack - steady-run detection

PulseTrack is a wearable heart-rate monitor. It samples the wearer's heart rate once per second and stores each day's readings as a list of integers.

For every reading the device reports the length of the steady run ending at that reading: the number of immediately preceding readings such that every step between consecutive readings in that run differs by no more than a tolerance of 5 beats per minute. A reading with no steady predecessor has run length 0. So for the series [70, 72, 71, 90, 89, 88, 87] the run lengths are [0, 1, 2, 0, 1, 2, 3].

A developer wrote the function below and claims it runs in linear time: "the while loop stops as soon as it reaches a reading that differs from the one before it by more than the tolerance, and in a real recording that happens after a step or two."

The device records 86,400 readings per day, one per second for 24 hours, and runs the analysis each night on the day's readings. The analysis must finish within a few seconds.

def steady_runs(readings, tol=5):
    runs = []
    for i in range(len(readings)):
        count = 0
        j = i
        while j > 0 and abs(readings[j] - readings[j - 1]) <= tol:
            count += 1
            j -= 1
        runs.append(count)
    return runs

Question

The readings are stored as a list of integers, one per second. The nightly analysis must finish in a few seconds on the device, and it must report the run lengths exactly.

  1. [3 marks](a)

    Explain, by tracing the loop, what steady_runs returns for the readings [70, 72, 71, 90, 89, 88, 87] with the default tolerance of 5.

    (Explain)
  2. [4 marks](b)

    Explain why the developer's claim that the function runs in linear time is unsound. State the property of the input that the claim assumes, and describe the input pattern on which the function performs the greatest number of steps.

    (Explain)
  3. [5 marks](c)

    Construct a Python function that returns exactly the same result as steady_runs but runs in linear time. You may not import any module and you may not use the abs function. A Java version of this paper requires the same algorithm, so write the algorithm rather than a demonstration of syntax.

    (Construct)
  4. [4 marks](d)

    A colleague proposes to fix the performance by adding a limit inside the while loop so that it stops after at most 1,000 steps. Evaluate this proposal, using your answers to parts (b) and (c).

    (Evaluate)

Total: 16 marks. Try the question before revealing anything below.

Reveal the answer

(a) Tracing the loop for readings = [70, 72, 71, 90, 89, 88, 87] with tol = 5:

| i | readings[i] | comparisons in the while | result |
|---|---|---|---|
| 0 | 70 | j = 0, loop does not run | 0 |
| 1 | 72 | $\lvert 72-70 \rvert = 2 \le 5 \rightarrow 1$ | 1 |
| 2 | 71 | $\lvert 71-72 \rvert = 1$, then $\lvert 71-70 \rvert = 1$ | 2 |
| 3 | 90 | $\lvert 90-71 \rvert = 19 > 5$ | 0 |
| 4 | 89 | $\lvert 89-90 \rvert = 1$, then $\lvert 89-71 \rvert = 18 > 5$ | 1 |
| 5 | 88 | $1$, then $2$, then $\lvert 88-71 \rvert = 17 > 5$ | 2 |
| 6 | 87 | $1$, then $2$, then $3$, then $\lvert 87-71 \rvert = 16 > 5$ | 3 |

The function returns [0, 1, 2, 0, 1, 2, 3]. (M1) for tracing the loop as a walk backwards while consecutive differences stay within the tolerance, (A1) for the correct values, (A1) for the list as a whole, including the reset to 0 at index 3 and the growing run at the end.

(b) The claim is unsound because the number of steps the inner loop performs is not a constant — it is the length of the steady run, which is a property of the *data*, not of the code. (M1) The claim assumes that consecutive readings almost always differ by more than the tolerance, so that the loop exits after one or two steps. (A1) That assumption is false for this application: heart rate sampled once a second during steady exercise changes by far less than 5 beats per minute between consecutive samples, so long runs are the normal case and the loop walks back a long way. (A1) The greatest number of steps occurs when every consecutive difference is within tolerance — a constant series, or a slow monotonic drift. For each $i$ the loop then runs all the way back to index 0, giving $0+1+2+\dots+(n-1) = \frac{n(n-1)}{2}$ steps, which is quadratic rather than linear. (A1)

(c)

def steady_runs(readings, tol=5):
    n = len(readings)
    runs = [0] * n
    for i in range(1, n):
        step = readings[i] - readings[i - 1]
        if -tol <= step <= tol:
            runs[i] = runs[i - 1] + 1
    return runs

(M1) for a single pass that keeps no inner loop. (A1) for the observation that makes it work: the steady run ending at i is either empty or it is the run ending at i - 1 extended by exactly one reading, so the answer for i can be read off the answer for i - 1. (A1) for runs[i] = runs[i - 1] + 1 and (A1) for initialising every entry to 0, which is what makes the run reset after a step larger than the tolerance. (A1) for using no library module and no abs, expressing the tolerance as the two-sided test -tol <= step <= tol.

The work done is $n-1$ comparisons and one assignment per reading, so the time is $O(n)$ and the extra memory is $O(n)$ for the output. A Java version of this paper asks for the same algorithm; the translation is a for loop over the array indices and the identical recurrence, so the language is irrelevant to the reasoning.

(d) The proposal should be rejected, for three reasons.

First, it does not change the complexity. The inner loop can still run up to 1,000 steps for every reading, so the worst case is still proportional to $1000n$; capping the loop divides the running time by a constant, and a constant factor is not a change of order. (M1) With 86,400 readings a day the uncapped worst case is $86{,}400 \times 86{,}399 / 2 = 3{,}732{,}436{,}800$ inner steps, the capped version still performs up to $86{,}400 \times 1000 = 86{,}400{,}000$, and the linear version performs 86,399. (A1)

Second, and more seriously, the cap makes the result *wrong* precisely where the app matters. A steady run of 1,500 readings would be reported as 1,000, and a run of 4,000 as 1,000; the error is silent, it is always an under-report, and it is concentrated on the longest runs — which are exactly the steady states the app exists to find. (A1)

Third, the trade is unnecessary, because part (c) already gives an exact linear algorithm. Capping the loop trades a correctness guarantee for a constant factor when a change of order was available at the same cost. (A1)

Markscheme notes

(a) Accept any trace, as a table or as prose. The essential marks are the mechanism (walk backwards while *each consecutive pair* is within tolerance) and the result. A candidate who compares every earlier reading against the current reading rather than against its own predecessor has misread the function and forfeits the trace marks — this is the single most common error.

(b) The two discriminating marks are the unstated assumption (that consecutive readings usually differ by more than the tolerance) and the worst-case count $n(n-1)/2$. A candidate who writes "it is actually O(n squared)" without naming the assumption earns one mark only. Accept a description of the worst case as "a constant series", "a steady recording" or "a slow drift"; require the recognition that the loop runs to index 0 each time.

(c) Accept any single-pass algorithm that returns the same list, including one that builds the list by appending rather than pre-allocating it. Do not award the linear mark to a candidate who keeps a nested loop, even a faster one — the question is about the order of growth. A candidate who uses abs despite the prohibition should be told the constraint was stated; the reasoning marks may still be awarded. A candidate who uses the csv-style two-pointer scan but does not derive the recurrence should be capped at two marks.

(d) The evaluation must distinguish a constant-factor improvement from a change of order. A candidate who says "1,000 is small enough" has missed that the cap silently corrupts the longest runs, and that those runs are the app's output. Award the final mark only when the answer connects the cap to a correctness loss rather than to performance alone.

Why this question is hard

The question is built around a claim that is easy to believe and easy to falsify: "the inner loop breaks almost immediately, so the function is linear". The claim is not about the code at all; it is about the input. A complexity statement is a statement about *all* inputs, and one input family is enough to destroy it. The family here is a steady recording, and the irony is that steady recordings are exactly what the app is designed to detect. The algorithm is slowest on the data it exists to find.

The mechanism is worth stating in general terms because it recurs everywhere. When a loop's work per iteration depends on the data, the total work is the sum of those per-iteration amounts, and the average tells you nothing about the maximum. Here the per-iteration amount is the run length; if run lengths are bounded by a small constant the total is linear, and if a single run can be as long as the input the total is quadratic. The programmer's sentence — "in a real recording that happens after a step or two" — is the unstated assumption, and it is the whole question. Students are used to reasoning about the *average* case implicitly and calling it the complexity; this item forces them to notice that they have done so.

Part (c) is where the algorithmic insight has to appear. The nested loop is recomputing something that is already known: the run ending at i is the run ending at i - 1, plus one, whenever the last step is small enough. Recognising that the answer for one input can be read off the answer for the previous one — dynamic programming in its smallest form — turns the quadratic scan into a single pass. The two-line recurrence is easy to write once the observation is made, and almost impossible to reach by optimising the loop.

The classic wrong turns are all present. Measuring on one typical recording and concluding "it is fast"; fixing the performance by adding a break or a cap, which corrupts the longest runs; assuming that abs() or function-call overhead is the bottleneck; and confusing the *amortised* case with the worst case. A further subtlety is worth noting for the strongest answers: the linear algorithm is correct only because the run is defined by *consecutive* differences. If the definition were "all earlier readings within the tolerance of the current reading", a running counter would be wrong, and the fix would be a different data structure. The recurrence is not a trick; it depends on the definition, and saying so is part of understanding why it works.
