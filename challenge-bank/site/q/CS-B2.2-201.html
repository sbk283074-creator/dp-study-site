B2.2 A very sparse matrix held in a dense two-dimensional array, where the cost of the representation grows with the square of the order while the data grows linearly, and the unit-test scale is far too small to reveal it

Storage of a routing matrix at two scales

A delivery company precomputes travel times between every pair of nodes in its network and stores the result in a matrix whose entry in row i and column j is the travel time from node i to node j, or zero when no route between them exists. Almost every pair of nodes is not directly connected, so almost every entry of the matrix is zero. A single routine multiplies this matrix by a vector of node weights once per scheduling run. The team writes its unit tests against a small matrix of the same density, and then deploys the same code against the production matrix. The table gives the two matrices. Every entry is held as an 8-byte floating-point number, and the deployment target is a server with 64 GB of memory.

Question

A sparse matrix is held in a dense two-dimensional array, and the same code is used for the unit tests and for production. The matrix, the two scales and the cost of one entry are given in the table. Answer all parts using the figures in the table.

  1. [3 marks](a)

    Calculate the number of entries a dense two-dimensional array stores for each of the two matrices, and state the memory each array occupies in bytes and in gigabytes.

    (Calculate)
  2. [3 marks](b)

    Calculate the memory a sparse representation requires if each non-zero entry is stored as an 8-byte value together with a 4-byte row index and a 4-byte column index, and express the result for the production matrix in megabytes.

    (Calculate)
  3. [4 marks](c)

    Determine the number of floating-point operations one matrix-vector product performs on the production matrix under each representation, state the time each takes if the processor performs 10^9 operations per second, and hence determine the ratio of the two.

    (Determine)
  4. [2 marks](d)

    Explain why the unit tests give no warning of the problem, and state one property of the data that a designer must check before choosing between the two representations.

    (Explain)

Reveal the answer

(a) A dense array stores one cell for every pair of row and column indices, whether or not the entry is used. For the unit-test matrix that is
$$1000 \times 1000 = 1\,000\,000 \text{ entries},$$
and at 8 bytes per entry that is $1\,000\,000 \times 8 = 8\,000\,000$ bytes, which is 8 MB (M1)(A1). For the production matrix the same count is
$$200\,000 \times 200\,000 = 4 \times 10^{10} = 40\,000\,000\,000 \text{ entries},$$
and the memory is $4 \times 10^{10} \times 8 = 3.2 \times 10^{11}$ bytes, that is 320 GB (A1). The first array fits comfortably in the 64 GB server and the second one does not fit at all, which is the whole of the difficulty: the two counts differ by a factor of forty thousand because the order differs by a factor of two hundred, and the cost of a dense array goes as the square of the order.

(b) A sparse representation stores one record for each non-zero entry and nothing for the zeros. Each record needs $8 + 4 + 4 = 16$ bytes (M1). For the unit-test matrix that is $10 \times 16 = 160$ bytes, which is negligible (A1). For the production matrix it is
$$400\,000 \times 16 = 6\,400\,000 \text{ bytes} = 6.4 \text{ MB},$$
which is one hundred thousand times smaller than the 320 GB the dense array would need and fits in the server with room to spare (A1). The comparison is worth stating in both directions: the sparse form is not merely smaller, it is smaller by a factor of
$$\frac{3.2 \times 10^{11}}{6.4 \times 10^{6}} = 50\,000,$$
so the two representations are not two ways of doing the same thing. One of them is possible and the other is not.

(c) A dense matrix-vector product performs one multiply and one add for every entry of the array, because the code cannot know which entries are zero without looking at them:
$$200\,000 \times 200\,000 = 4 \times 10^{10} \text{ operations}.$$
At $10^{9}$ operations per second that is 40 seconds for a single multiplication (M1). A sparse product touches only the stored entries, so it performs one multiply and one add per non-zero entry:
$$400\,000 \text{ operations},$$
which at the same rate takes $400\,000 / 10^{9} = 4 \times 10^{-4}$ seconds, that is 0.4 milliseconds (A1). The ratio is
$$\frac{4 \times 10^{10}}{4 \times 10^{5}} = 100\,000,$$
so the sparse product is one hundred thousand times cheaper in arithmetic as well as fifty thousand times cheaper in memory (M1)(A1). The two ratios are not equal because memory is charged per cell while arithmetic is charged per non-zero entry, and the dense form pays the first cost for every cell it holds and the second for every cell it visits.

(d) The unit tests give no warning because the property that makes the dense array unusable is the one property the tests hold fixed. Both matrices have the same density, about 0.001 per cent, and the test matrix is small enough that its dense form is 8 MB and allocates and runs in about a millisecond (M1). Every test therefore passes, and the suite is evidence about the correctness of the indexing arithmetic rather than about the cost of the representation. The property a designer must check is the density, and specifically whether it stays small as the order grows: the decision rule is to compare the number of non-zero entries with the square of the order, and to choose the sparse form whenever the first is much smaller than the second (A1). A useful discipline is to test at the largest order the system will ever see, or at least to assert the density in a test, because a test suite that only exercises the small case cannot distinguish a representation that scales from one that does not.

Markscheme notes

(a) (M1) for multiplying the two dimensions rather than adding them, (A1) for $1\,000\,000$ entries and 8 MB for the unit-test matrix, (A1) for $4 \times 10^{10}$ entries and 320 GB for the production matrix. A candidate who answers $400\,000$ entries for the production matrix has counted the non-zero entries and answered part (b) instead of part (a); that scores no mark here even though the number is correct for the other question. Accept the memory in either bytes or gigabytes provided the unit is stated.

(b) (M1) for the 16 bytes per record, with the three components identified, (A1) for $160$ bytes at the test scale, (A1) for $6\,400\,000$ bytes, which is 6.4 MB, at the production scale. Accept a candidate who stores the row index only and relies on the records being grouped by row, provided the assumption is stated, but the memory total must be recomputed consistently with that choice. The comparison with the dense figure is not required for the marks but is expected in a good answer.

(c) (M1) for the dense operation count as the square of the order, (A1) for 40 seconds at the stated rate, (A1) for the sparse count as the number of non-zero entries, (A1) for the ratio of 100 000. A candidate who writes the sparse count as $200\,000$ rather than $400\,000$ has confused the order with the number of non-zero entries and loses the final (A1) but keeps the method marks. Follow-through: a candidate whose operation counts are wrong but whose ratio is computed consistently from them keeps the final mark.

(d) (M1) for the observation that the test matrix is small and therefore cheap in dense form, or equivalently that both matrices have the same density so the test exercises nothing that changes with scale, (A1) for naming the density, or the ratio of non-zero entries to the square of the order, as the property to check. An answer that says only 'the tests were too small' without identifying what the tests failed to vary scores (M1) only. Do not accept 'the server needs more memory' as the property to check: that is a remedy, not a property of the data.

Forfeits: treating the matrix as dense in part (b) and quoting the part (a) figures again; quoting the memory ratio of 50 000 as the answer to part (c), which mixes the two currencies; and answering part (d) with a statement about test coverage in general rather than about the density of the data.

Why this question is hard

This item is about the difference between a cost that grows with the size of the container and a cost that grows with the size of the contents. A dense array is a container: its cost is set by the number of rows and columns, and it is the same whether the matrix holds four hundred thousand values or none at all. A sparse representation is a record of contents: its cost is set by the number of values that are actually there. When the two are compared at a fixed density, the container's cost grows with the square of the order and the contents' cost grows linearly, so the gap between them grows without bound and the choice between them stops being a matter of taste.

The reason this is worth a question is that the arithmetic is trivial and the decision is not. Every number in the item is a multiplication. What the candidate has to supply is the recognition that the two multiplications are measuring different things, one a capacity and one an occupancy, and that a test suite run at a small scale cannot distinguish them because both are small. The unit-test matrix is eight megabytes, which is nothing; the production matrix is three hundred and twenty gigabytes, which is five times the memory of the machine it is deployed to. Nothing happens between those two figures except that the order changed, and the order enters one of them twice.

The density is the same in both rows of the table, and that is the deliberate part of the design. A candidate might reasonably think that the test is unrepresentative because the test matrix is sparse in a different way from the production matrix, and the table forecloses that: the two densities agree to three significant figures. What differs is the scale, and the scale is exactly the variable that a dense representation is sensitive to. So the test suite is not merely unrepresentative, it is unrepresentative in the one direction that matters, which is why the failure appears only at deployment.

The two ratios, fifty thousand in memory and one hundred thousand in arithmetic, are worth separating. Memory is charged per cell stored, so the ratio is the ratio of the cell count to the entry count. Arithmetic is charged per cell visited, and a dense routine visits every cell while a sparse one visits only the stored entries, so the same comparison applies. The factor of two between them comes from the 16 bytes a sparse record costs against the 8 bytes a dense cell costs. A candidate who reports a single ratio for both has not noticed that the two costs are charged on different quantities, and that is a real and common confusion about asymptotic arguments.

The item is claimed at difficulty 3 because it has one lever. A candidate who sees that the representation must match the density has everything else the item needs, and the remaining work is three multiplications and a division. There is no second idea in it: the numbers are clean, the two representations are both familiar, and the only thing the question asks the candidate to notice is that a container and a record are not the same kind of thing.

It is worth being clear about what the remedy is, because the item invites the wrong one. Buying more memory does not repair the design, it postpones the failure: at order two hundred thousand the dense array is already five times the size of the machine, and the next increase in the order doubles that ratio. The representation has to change, and the change is small, which is what makes the wrong choice expensive rather than merely unfortunate. The cost of the mistake is not the memory that was wasted, it is the deployment that could not be made.

At the unit-test scale of a thousand the array is eight megabytes and allocates without complaint; at the production scale of two hundred thousand it is three hundred and twenty gigabytes and cannot be allocated at all. The lever is a single one: the representation must be matched to the density of the data, and the density is identical at both scales, so the test suite is exercising the one property that does not change.
