The collaborative sciences project

Ten hours, one group, at least two DP sciences in it, one shared investigation and one presentation. It carries no marks towards your IB grade, which is exactly why it is useful: it is the only place in the DP where you can practise collecting real data, handling it computationally, and defending your choices in front of an audience before any of it counts. Treat it as a rehearsal for the IA and for Paper 1's data-based questions, not as a break.

10 recommended hours, shared across the group 4 sciences Not externally assessed — but a required element of the course Best done in DP1, before the IA Skills: question design · schema · cleaning · uncertainty · presentation
Why the IBO requires it

The DP sciences share a set of practices — planning, collecting evidence, handling uncertainty, presenting conclusions — and the IBO's view is that no student should finish two years of science without doing them across subject boundaries. For computer science the requirement is more pointed: it puts you in a room with people who have a scientific question and no way to process the data, which is the situation every working programmer is actually in. Your value in the group is not "knowing Python"; it is turning a vague question into a data pipeline that answers it.

There is a second, colder reason to take it seriously. The skills rehearsed here — interviewing someone who does not share your vocabulary, agreeing a data structure before you need it, quantifying how wrong you might be, and reporting honestly — are exactly the skills the IA and Paper 1 reward. Students who treat these ten hours as a real investigation routinely finish the IA weeks faster, because the expensive part of the IA is not the coding; it is knowing what to write down.

2. How the group should work

The failure mode of interdisciplinary work is that the physicist asks the question, the biologist collects the data, the chemist writes it up, and the computer scientist is handed a spreadsheet at the end and asked to make a chart. That is not collaboration, and it teaches you nothing.

RoleOwnsWhat the CS student specifically brings
Question owner (usually the science student)The research question, the variables, the experimental design.You force the question to be answerable with data: what is measured, how often, with what precision, and what would count as an answer.
Data ownerCollection, calibration, and the raw record.Automated logging (sensors, scripts, image capture), so you get 2,000 rows instead of 20 — and a schema agreed before collection starts.
Processing owner (usually you)Cleaning, analysis, modelling, visualisation. Validation rules, handling of missing values, the choice of model or statistic, and reproducible scripts that can be re-run.
Communication ownerThe presentation and the report.Charts that show the actual effect, honest error bars, and a live demo rather than a slide of screenshots.
How to use it — the two rules that make interdisciplinary groups work
  1. Agree the data schema in the first hour. One shared CSV or sheet with named columns, units in the header, one row per observation, and a column for who collected it. Everything afterwards depends on this; every hour spent here saves three later.
  2. Everyone must be able to run the analysis. Put your script in a shared file, keep it under 100 lines, and show the others how to run it in the first session. If only you can produce the numbers, you have built a dependency, not a collaboration — and you will be doing all the work at 11 pm.
Why this works Why schema-first is not bureaucracy
  1. Every later decision reads the data: the cleaning rules, the statistic, the chart, the conclusion. The schema is the interface they all depend on.
  2. If the interface changes after collection — a column renamed, units moved into cells, two measurements merged into one cell — then every downstream artefact must be rewritten, and the rewrites are where errors enter silently.
  3. Changing a schema costs one minute before collection and one hour after. That asymmetry is the entire argument.
  4. When this advice is wrong: if you are exploring a phenomenon with no hypothesis and will throw the first dataset away anyway, a loose schema is fine. Label that dataset exploratory and keep it out of the final analysis.

2.1 Running the group: the mechanics nobody tells you

Most group projects collapse for organisational reasons, not intellectual ones. Three habits prevent almost all of them.

A decision log, not a chat thread

One shared document. Every meeting adds: date, present, decisions, who does what by when, and what was rejected and why. When someone asks in week six "why are we measuring at 50 Hz?", the answer is on record rather than reconstructed from memory.

Version control from hour one

Put the scripts in a shared repository (GitHub, GitLab, or even a shared folder with numbered versions). Commit with a message saying what changed. The first time someone overwrites the analysis, you will be glad. This is also the habit Paper 2 and the IA assume.

A named fallback for every critical task

If the person who owns the sensor falls ill, who collects? If the analysis script breaks, who fixes it? Naming a second person costs thirty seconds and removes the single-point-of-failure that ruins most group work.

Divide by artefact, not by slide

Splitting "you do slides 1–4, I do 5–8" produces parallel work. Splitting by artefact — one owns the raw data file, one the cleaning script, one the chart, one the uncertainty paragraph — produces pieces that must connect, which forces collaboration.

Trap — the three organisational failures
  1. The "we'll meet next week" spiral. Three meetings cancelled, then a frantic weekend. Fix: book the next four sessions in the first meeting, with a deliverable attached to each.
  2. One person becomes the bottleneck. Usually you, because only you can run the script. Fix: pair with someone in session one and make them run it while you watch.
  3. The last-two-days rebuild. The analysis is thrown away and rewritten in panic, losing the documented decisions. Fix: freeze the pipeline one week before the presentation and only fix bugs after that.

3. Choosing a question that data can answer

This is the single highest-leverage hour of the project. A vague question produces a vague dataset, which produces a chart that shows nothing, which produces a presentation where you apologise for your results.

How to use it — operationalising a question
  1. Name the phenomenon in one sentence, without jargon: "the trolley slows down faster on carpet than on the lab floor."
  2. Choose the independent variable — what you deliberately change (surface type: carpet, vinyl, polished wood).
  3. Choose the dependent variable — what you measure (time for the trolley to travel 1.0 m).
  4. List the controlled variables — everything else you must hold still (trolley mass, release height, gradient, wheel alignment, who releases it).
  5. State the precision of each measurement before collecting (time ±0.01 s on a light gate, distance ±1 mm).
  6. Decide in advance what would count as an answer — "a difference larger than about 0.05 s, given our timing uncertainty." This step is what separates an investigation from a demonstration.
Worked example 1 Operationalising "does caffeine affect reaction time?"

Question. A biology student proposes: "Does caffeine make people react faster?" Turn this into a plan that produces answerable data.

  1. Phenomenon: people who have consumed caffeine respond more quickly to a visual stimulus.
  2. Independent variable: caffeine condition — 0 mg (control), 100 mg, 200 mg. Crucially this must be blinded: the participant and the person timing must not know which condition, or you measure expectation rather than caffeine.
  3. Dependent variable: reaction time in milliseconds, measured with a computer-based test (key press after a shape appears), recorded automatically — not with a stopwatch.
  4. Controlled variables: time of day, hours of sleep, time since last food, hand used, screen brightness, practice trials discarded.
  5. Precision: the display refreshes at 60 Hz, so the timing resolution is about 17 ms — that is your floor, and it must be stated.
  6. What counts as an answer: a difference in mean reaction time larger than roughly twice the standard error, with a sufficient number of trials and participants.
  7. Ethics: human participants, so consent, no pressure to consume caffeine, medical conditions respected, data anonymised and deletable.
Why the CS contribution is structural here: the test program must randomise trial order, blind the condition, timestamp every response, and export one row per trial. Without that you have 15 handwritten numbers and no way to detect a practice effect.
Worked example 2 Operationalising "which light makes plants grow fastest?"

Question. "Which light colour makes seedlings grow best?" — the most common vague biology proposal, and the easiest to fix.

  1. Problem with the original: "best" is undefined and "colour" is not a quantity. Red and blue LEDs differ in wavelength and intensity, so if you only change colour you have confounded two variables.
  2. Fixed independent variable: wavelength band (450 nm blue, 660 nm red, broad-spectrum white control) at matched photon flux. Measure the flux and report it; do not trust the LED label.
  3. Dependent variable: stem height in mm, measured from a fixed reference in a photograph taken daily at the same time and distance.
  4. Controlled: watering schedule, soil batch, temperature, photoperiod, pot position rotated daily to remove the window-side advantage.
  5. Precision: ruler ±1 mm by hand; ±0.3 mm if you calibrate the photograph with a scale object in frame.
  6. What counts as an answer: a difference in mean growth rate larger than the spread between seedlings in the same tray — which is why you need several seedlings per condition, not one.
Why the CS contribution is structural here: daily automated photography plus pixel-to-millimetre calibration gives you 30 days × N seedlings of measurements instead of three ruler readings, and it lets you fit a growth rate rather than compare final heights. The rotation schedule also has to be generated, not remembered.
Trap — four ways to ruin the question
  1. Confounding. You change two things at once and cannot attribute the effect. Always ask: "what else changed when I changed this?"
  2. No control condition. Without a baseline you can only say the groups differ, not that your variable caused it.
  3. Too few repeats. One seedling per condition measures that seedling, not the light. Repeats are what let you estimate spread, and spread is what makes a conclusion defensible.
  4. A question with no possible negative result. If every outcome is "consistent with the hypothesis", you have not designed a test. State in advance what result would surprise you.

4. Designing the data schema

The schema is the contract between the people collecting and the people analysing. Agree it before you collect a single number.

How to use it — the schema rules
  1. One row per observation. Not one row per participant with columns for each trial — that is "wide" format and it breaks the moment the number of trials differs.
  2. Units live in the header, never in the cell. Write time_s, not time with values like "1.23 s". A cell containing text cannot be averaged.
  3. Every column has a declared type — integer, real, category, timestamp, boolean — and a rule for what is valid (e.g. 0 < time_s < 10).
  4. Record metadata, not just measurements: who collected it, which instrument, the condition, and any anomaly noticed at the time.
  5. Never overwrite the raw file. Cleaning writes a new file. This is the habit that makes your IA defensible.
Worked example 3 A schema for the light-gate trolley experiment

Question. Design a CSV schema for measuring how long a trolley takes to travel 1.0 m over three surfaces, with five repeats each.

Schema:

trial_id,surface_material,repeat_no,time_s,distance_m,gate_id,collected_by,anomaly_note
1,carpet,1,1.42,1.000,A,lucas,
2,carpet,2,1.39,1.000,A,lucas,
3,carpet,3,1.51,1.000,A,lucas,released early
4,vinyl,1,0.88,1.000,A,lucas,
...
  1. Why trial_id: a stable key so a row can be discussed, excluded, or traced without referring to "the third one".
  2. Why anomaly_note: the observation "released early" is worth more than the number, and it is forgotten within minutes if not recorded.
  3. Validation rules: time_s real and between 0.2 and 5.0; surface_material one of {carpet, vinyl, wood}; repeat_no integer 1–5; anomaly_note may be empty, everything else must not be.
  4. A minimal validation check (Python):
VALID_SURFACES = {"carpet", "vinyl", "wood"}
for row in rows:
    if row["surface_material"] not in VALID_SURFACES:
        log("bad surface", row["trial_id"])
    if not (0.2 <= float(row["time_s"]) <= 5.0):
        log("implausible time", row["trial_id"])
    if not row["collected_by"]:
        log("missing collector", row["trial_id"])
Answer: a schema of eight columns with declared types, units in headers, and three validation rules — agreed before collection, so that no downstream artefact needs rewriting.
Connection

This is A3 databases in miniature: entity, attributes, data types, validation rules, and a primary key. If you can design this CSV properly, normalisation and SQL constraints are the same idea with more machinery. It is also the direct rehearsal for the IA design section.

5. Collecting data: sensors, sampling and precision

Hand-collected data is the main reason these projects produce nothing interesting. Automate wherever you can: a sensor logging at a fixed rate gives you more rows, a timestamp for every row, and an audit trail.

ConceptWhat it meansWhy it matters for your analysis
Sampling rateHow many measurements per second (Hz).Sample far faster than the effect you are looking for. For a pendulum with period ~1 s, 50 Hz gives ~50 points per swing — ample. For a collision lasting 20 ms, 50 Hz gives one point and you learn nothing.
ResolutionThe smallest change the instrument can represent (e.g. a 10-bit ADC over 0–5 V resolves ~4.9 mV).Sets the floor on your precision. Quoting a mean to five decimal places from a 10-bit sensor is dishonest.
Accuracy vs precisionAccuracy = closeness to the true value; precision = repeatability.A sensor can be precisely wrong (consistently offset). Calibration fixes accuracy; repeated trials reveal precision.
CalibrationComparing the instrument against a known standard.Without it you cannot distinguish "the effect" from "the sensor's offset". Record the calibration data too.
Audit trailRaw file, unmodified, plus the script that cleaned it.Lets anyone — including you in six months — reproduce every number in the presentation.
Worked example 4 Choosing a sampling rate for a cooling curve

Question. You are logging the temperature of hot water as it cools to room temperature. The whole experiment runs for 20 minutes. What sampling rate do you choose, and why?

  1. Identify the timescale of the effect. Newton's cooling is exponential with a time constant of roughly 5–10 minutes here. The fastest meaningful change is therefore on the order of tens of seconds.
  2. Apply the rule of thumb: sample at least ten times faster than the fastest change you care about. Tens of seconds → sample about once per second (1 Hz).
  3. Check the total volume: 1 Hz × 20 min × 60 s = 1,200 rows. Entirely manageable, and enough to fit an exponential with confidence.
  4. Consider the alternative: 100 Hz would give 120,000 rows — no extra information about a 10-minute process, but a much larger file and slower processing. More data is not automatically better.
  5. Add margin for the unexpected: if you might later study the first two seconds (e.g. the sensor's own response time), log at 10 Hz and downsample for the cooling fit.
Answer: 1 Hz is sufficient and 10 Hz is a safe choice; 100 Hz is wasted effort. The reasoning is to match the sampling rate to the timescale of the effect, not to maximise the number of rows.
Exam link

Sampling, resolution and analogue-to-digital conversion are examined directly in A1. Being able to say "our 10-bit ADC over 0–5 V gives 4.9 mV resolution, which is far below the 0.1 °C change we are studying, so resolution is not our limiting factor" is exactly the kind of justified reasoning Paper 1 rewards.

6. Cleaning and validating data

Real data is dirty. The professional habit is not to avoid that but to make every cleaning decision explicit, reversible and logged.

How to use it — the cleaning procedure
  1. Copy, never edit. raw.csv is read-only. All cleaning produces clean.csv.
  2. Validate types first — anything that will not parse as its declared type is either a collection error or a schema violation.
  3. Handle missing values explicitly. Decide per column: exclude the row, or impute, or leave as missing and let the analysis skip it. Write the decision down.
  4. Find impossible values (negative mass, temperature of 900 °C in a water bath) and trace them to the source before deciding.
  5. Treat outliers as questions, not as dirt. An outlier is often the most interesting measurement. If you exclude it, say so, say why, and report what happens to the conclusion if you keep it.
  6. Log every exclusion with the trial id and the reason.
Worked example 5 Cleaning a temperature log with a sensor dropout

Question. A 1,200-row temperature log contains 14 rows where the sensor returned -999 (a standard "no reading" sentinel), 3 rows with the value null, and one run of 40 consecutive identical values followed by a jump of 2.4 °C. Clean it, justifying each decision.

  1. Identify the sentinel. -999 is not a temperature; it is the sensor reporting failure. Replace with missing — never treat it as a number, because averaging it in would corrupt the mean catastrophically.
  2. Count the damage. 14 + 3 = 17 of 1,200 rows = 1.4 %. Small enough to exclude rows without biasing the fit, provided the dropouts are not clustered at a particular temperature.
  3. Check for clustering. If all dropouts occur in the first minute (sensor warming up), the missingness is not random and excluding them is defensible only if you state it. Here they are scattered, so exclusion is safe.
  4. The flat run and the jump. 40 identical values then a 2.4 °C jump is the signature of a sensor that stalled and then re-synced. The flat values are not measurements and the jump is not a physical event — water at this scale cannot change 2.4 °C instantaneously. Exclude the flat run and treat the first value after the jump as suspect; verify against the neighbouring trend.
  5. Log it. Excluded: rows 412–425 (sentinel), 700, 811, 999 (null), 1040–1079 (stall). Reason recorded for each.
  6. Sanity check: after cleaning, re-plot and confirm the remaining curve is smooth and monotonic decreasing. If a jump survives, you have not finished.
Answer: 57 of 1,200 rows removed (4.8 %), every removal justified and logged, with the raw file untouched. The key insight is that -999 and a stalled sensor are instrument states, not measurements, and the flat-run-plus-jump pattern identifies them.
Trap — three cleaning sins
  1. Deleting outliers to make the graph look better. This is scientific misconduct even at school level, and examiners can smell it. Exclude only with a stated, instrument-based reason.
  2. Averaging in sentinel values. A single -999 in 1,200 rows moves the mean by about 0.8 °C — enough to manufacture or destroy an effect.
  3. Overwriting raw.csv. Once it is gone you cannot answer "what did the sensor actually say?", and neither can anyone checking your work.

7. Choosing the analysis: match the method to the question

The most common analytical error in these projects is using a complicated method when a simple one answers the question, or a simple one when the question demands more. Decide from the question, not from the software you happen to have open.

If your question is…UseDo not use
"Is there a difference between groups?"Mean or median per group with a measure of spread, and error bars on the chart.A single bar per group with no spread — this cannot support any conclusion.
"Do the two variables move together?"Scatter plot first, then correlation, then a fitted line if the relationship looks linear.Correlation alone as evidence of causation.
"What is the underlying law?"Fit the model your science predicts (exponential cooling, inverse square, SIR curve) and inspect the residuals.A high-degree polynomial that passes through every point and predicts nothing.
"Can we predict a category?"A simple classifier with a train/test split and a confusion matrix. A deep neural network on 200 rows — it will memorise and you will not be able to explain it.
"How confident are we?"Standard error, confidence interval, or bootstrapping.A p-value quoted with no effect size and no context.
Why this works Why you fit the model your science predicts
  1. A model is a claim about mechanism. Newton's law of cooling predicts an exponential approach to ambient temperature; fitting an exponential therefore tests that claim.
  2. A flexible curve (a high-degree polynomial) can follow any data, including noise. It fits the past perfectly and predicts the future badly — it has memorised rather than learned.
  3. The diagnostic is the residuals: the differences between data and model. If the residuals show a pattern, your model is missing structure. If they look random, your model has captured what there is to capture.
  4. When a flexible model is right: when you have no theory and only want interpolation within the measured range. Say so explicitly, and do not extrapolate.
Worked example 6 Line or exponential? Choosing by residuals

Question. You have 1,200 temperature readings over 20 minutes. Should you fit a straight line or an exponential decay, and how do you decide?

  1. Fit both. Straight line: residual pattern is a clear U-shape — the data lies below the line at the start, above in the middle, below at the end. Exponential: residuals look like noise.
  2. Interpret. The U-shaped residual pattern is not bad luck; it is the signature of fitting the wrong shape. A curve that bends is being forced through a straight model.
  3. Quantify. Compare the spread of residuals: the exponential leaves residuals roughly three times smaller than the line. That is a large improvement for the same number of parameters.
  4. Check the physics. The exponential's fitted constant should be positive and the fitted ambient temperature should be close to the room temperature you measured independently. If the fit says the room is at 4 °C, something is wrong with the data, not with Newton.
Answer: the exponential, chosen because its residuals are patternless and three times smaller, and because its parameters correspond to measurable physical quantities.
Trap — analysis errors that cost you the conclusion
  1. Correlation stated as causation. "Ice cream sales and drownings both rise" does not mean ice cream causes drowning; both track temperature. Always name the plausible third variable.
  2. No spread reported. "The mean was 1.42 s" with nothing else is not a result. A mean without a spread cannot support "faster" or "slower".
  3. Testing until something is significant. Trying twenty variables and reporting the one that reached significance is how false discoveries are manufactured. Decide the test in advance, or state that the finding is exploratory.

8. Uncertainty: the part everyone skips

This is the section that separates a project worth presenting from a poster with a chart on it. Every measurement is wrong by some amount; the question is by how much, and whether that amount is small enough for your conclusion to survive.

Why this exists

A result without an uncertainty is a claim that cannot be checked. "The carpet was slower" is either a measurement of the world or an artefact of your timing precision, and without the uncertainty you cannot tell which. This is also precisely what Paper 1 asks you to evaluate: not "what did they find?" but "should we believe it?"

Why this works Why independent uncertainties combine in quadrature
  1. Suppose a quantity depends on two independent measurements, each with its own uncertainty. Sometimes the first is high and the second low; sometimes the reverse.
  2. Because the errors are independent, they partly cancel. Adding them directly (worst case) would assume both are always at their extreme in the same direction, which is pessimistic and rarely true.
  3. The honest combination is the square root of the sum of squares — in quadrature — which sits between "they cancel" and "they both conspire against you".
  4. When this is wrong: if the errors are correlated (both come from the same mis-calibrated instrument), they do not cancel, and you must add them directly. Identify shared sources and treat them separately.
Worked example 7 Is the difference real? Error bars on the trolley data

Question. Five runs on carpet give times 1.42, 1.39, 1.51, 1.44, 1.48 s (one run flagged "released early" and excluded, leaving four: 1.42, 1.39, 1.51, 1.44). Five runs on vinyl give 0.88, 0.91, 0.86, 0.90, 0.89 s. Is the carpet genuinely slower, given a timing precision of ±0.02 s?

  1. Carpet mean: (1.42 + 1.39 + 1.51 + 1.44) / 4 = 5.76 / 4 = 1.44 s.
  2. Carpet spread: values range 1.39 to 1.51, so roughly ±0.06 s around the mean — three times the instrument precision, meaning the run-to-run variation dominates, not the clock.
  3. Vinyl mean: (0.88 + 0.91 + 0.86 + 0.90 + 0.89) / 5 = 4.44 / 5 = 0.888 s, spread about ±0.025 s.
  4. Compare: the difference is 1.44 − 0.89 = 0.55 s. The combined spread is roughly 0.06 + 0.03 = 0.09 s. The difference is about six times larger than the spread.
  5. Conclusion: yes — carpet is genuinely slower under these conditions. The effect is far larger than the measurement variation, so the conclusion does not depend on the exact statistical test.
  6. Report it properly: "Carpet 1.44 ± 0.06 s, vinyl 0.89 ± 0.03 s (mean ± spread, n = 4 and 5). The difference of 0.55 s is about six times the combined spread, so it is not attributable to measurement variation. Run-to-run variation exceeded instrument precision, indicating the release mechanism is the dominant source of uncertainty — repeating with a mechanical release would tighten this."
Answer: the difference is real, and — more usefully — the analysis identifies the release mechanism, not the stopwatch, as the thing to fix next time.
Exam link

Questions that ask you to evaluate or discuss a data-based finding are really asking about validity and uncertainty: was the sample big enough, was the variation controlled, could the conclusion be an artefact? Practise writing that paragraph here, at no cost, and it becomes automatic in Paper 1.

9. Visualisation that shows the effect

A chart is an argument. Choose the one that makes your point honestly, and refuse the ones that exaggerate it.

You want to showUseAvoid
Comparison between a few categoriesBar chart with error bars, or better, a dot plot showing every measurement.A bar chart whose axis starts at 0.8 to make a small difference look huge.
Relationship between two quantitiesScatter plot, with a fitted line if appropriate. Joining the points with a zig-zag line, which implies measurements between points you never took.
Change over timeLine graph with time on the horizontal axis.Using an index-number category axis that spaces unequal time intervals equally.
Distribution / spreadHistogram or box plot.A single "average" bar that hides the spread entirely.
CompositionStacked bar (few categories only).A pie chart with twelve slices and no labels.
Trap — four dishonest charts
  1. Truncated axis. Starting the vertical axis above zero multiplies a small difference visually. If you must truncate (e.g. to show variation around a baseline), label it unmistakably.
  2. No error bars. A bar with no spread invites the reader to over-trust it.
  3. No units on the axes. "Time" could be seconds or milliseconds; the reader should not have to guess.
  4. 3D effects and dual axes. Both distort perception for no informational gain. Two separate charts are clearer than one chart with two y-axes.

10. The process, hour by hour

0.5 h
Form the group and pick a direction. Confirm at least two group 4 subjects are represented. Brainstorm phenomena, not methods. Choose something where the volume of data is the point.
1 h
Operationalise the question. Independent, dependent and controlled variables written down; measurement precision stated; "what would count as an answer" agreed. Ethics checked (human data? consent?).
0.5 h
Agree the schema. Column names with units, types, validation rules, metadata columns. Everyone signs off. Set up the shared repository and the decision log.
3 h
Collect. Automate wherever possible. Calibrate first. Record anomalies as they happen. Back up the raw file immediately.
3 h
Process. Validate, clean with a log, choose the analysis from the question, quantify uncertainty, and produce charts with error bars and units. Keep every script in version control.
1 h
Stress-test. Try to break your own conclusion: what is the strongest alternative explanation? What would a sceptical teacher ask? Prepare those answers.
1 h
Present. Question → method → what the data shows → what it does not show → what next. Include a live run of the analysis.

Pick the project where the volume of data is the point. If the experiment produces 20 readings, a scientist with a calculator does not need you, the collaboration is cosmetic, and there is nothing for you to present. If it produces 20,000 readings, or needs a simulation, or needs the same analysis run 500 times, then your contribution is structural and the project is genuinely interdisciplinary.

12. Ethics and safety

Check these before you collect anything, and record that you checked them. It takes fifteen minutes and it is the difference between a professional investigation and a careless one.

Human participants

Informed consent, the right to withdraw, no coercion (especially with anything ingested), anonymised data, and a stated deletion plan. If you are under 18, your school will have a specific procedure — follow it.

Animals and environment

No harm, no distress, no removal from habitat. Observational studies are almost always the right choice at school level. Check local rules before collecting from a natural environment.

Data privacy

If you log location, images or identifiable data, you are handling personal data. Minimise it, anonymise it, and do not publish raw identifiable records in your slides.

Academic honesty

This project is genuinely collaborative and shared. Your IA is not. Keep the two clearly separate: do not reuse this dataset or these scripts for the IA without your teacher's explicit permission, and never submit group work as individual work.

14. How to document and present it

Presenting — ten minutes that work

Two minutes on the question and why it matters; two on the method, with the apparatus or a photo; one on the data (how much, how collected, what went wrong); three on the finding, with the chart and the uncertainty; two on what you would do differently. Then questions. Do not spend the time explaining your code — show it running and explain the decision behind it, in the same way you will in the IA.

Prepare for three questions you will definitely be asked: "how do you know that is not just noise?" (uncertainty), "what would you do differently?" (evaluation), and "what did you personally contribute?" (your role). Have a specific answer ready for each, with a number in it.

15. Common failure modes

Trap — the ways this goes wrong
  1. Four parallel projects. Each student does their own thing and the slides are stapled together. Test: can any member of the group explain the whole investigation? If not, it is not collaborative.
  2. The CS student is the chart-maker. You are brought in at the end to draw a graph. Prevent it by owning the schema in hour one: whoever designs the data structure is structurally necessary throughout.
  3. Too little data. Twenty readings and a bar chart. Insist on automated or repeated collection so that computation actually matters.
  4. No uncertainty. A single number with no spread, no error bars and no discussion of precision. This is the habit that costs marks in both Paper 1 and the IA evaluation, so kill it here.
  5. Over-engineering. A machine-learning model where a mean would do, or a web app nobody needs, built in the last two days. The brief is ten hours; a clean pipeline and an honest chart beats a half-finished system every time.
  6. Confusing the group project with the IA. The IA must be your own work. Keep the artefacts separate and check with your teacher before reusing anything.

16. Practice

  1. A group of four computer science students runs an excellent data-logging investigation and presents it together. Explain why this does not satisfy the requirement.

    Show answer

    The requirement is interdisciplinary: the group must contain students from at least two group 4 subjects. Four CS students may produce excellent work, but there is no cross-subject collaboration, which is the entire point of the exercise — learning to work with people whose questions, vocabulary and standards of evidence differ from yours. That is also the part that transfers to the IA, where your client is a non-specialist.

  2. Your group has collected 15 readings by hand. Give two reasons the computer science contribution is weak in this design, and one change that would fix it.

    Show answer
    1. With 15 readings the analysis is trivial: any scientist can compute a mean and draw a chart by hand, so the CS contribution is presentational rather than structural.
    2. Hand collection also gives no audit trail and no way to quantify within-condition variation reliably, so the uncertainty discussion — the most valuable part — is hollow.
    3. Fix: automate the measurement (sensor logging at a fixed rate, repeated trials, or a simulation over many parameter sets) so that you produce hundreds or thousands of rows and the analysis genuinely determines the answer.

  3. Identify two stages of this project that practise the same skill as the IA's client interview, and explain the link.

    Show answer

    (i) Agreeing the research question and variables with a science partner is the same skill as interviewing a client: you translate someone else's vague need into something measurable, and you discover that their first phrasing was not what they meant. (ii) Reporting the finding back is the same skill as acceptance testing: you show a non-specialist what you built, they use it, and their difficulties become your evaluation. In both cases the transferable habit is reporting to someone who does not share your assumptions.

  4. Explain why "everyone in the group can explain every part" is a useful test of whether the project was genuinely collaborative.

    Show answer

    If each member only understands their own section, the group produced parallel work rather than a shared investigation, and no cross-subject learning has happened — the biology student has not engaged with the model, and you have not engaged with the experimental design. The test also protects you in the question session: a group that can all answer all questions clearly worked together, and it shows.

  5. A sensor logs temperature with a 10-bit ADC over a range of 0–50 °C. Calculate the resolution in °C and comment on whether it is adequate for detecting a 0.2 °C change.

    Show answer
    1. A 10-bit ADC has 210 = 1,024 levels.
    2. Over 50 °C, the resolution is 50 / 1,024 ≈ 0.049 °C, i.e. about 0.05 °C.
    3. A 0.2 °C change corresponds to about 0.2 / 0.049 ≈ 4 ADC levels.
    4. Adequate? Yes, but only just: four levels is enough to detect the change but too few to measure it precisely. You would report the measured change to no better than about ±0.05 °C, and you should state that noise may consume one or two of those levels.
    Answer: ≈0.05 °C resolution; adequate to detect a 0.2 °C change but marginal for measuring it precisely.

  6. You fit a straight line to data that is really exponential. Describe what the residuals would look like and explain why that pattern is diagnostic.

    Show answer

    The residuals would show a systematic curved pattern — below the line at one end, above in the middle, below at the other (or the reverse). This is diagnostic because random error produces residuals scattered without structure; a pattern means the model's shape is wrong, so part of the signal has been left in the residuals. The fix is to fit the shape the science predicts (here an exponential), after which the residuals should look like noise.

  7. Explain the difference between accuracy and precision, and describe an experiment where a sensor could be precise but inaccurate. How would you detect it?

    Show answer

    Accuracy is closeness to the true value; precision is repeatability. A thermometer with a constant +2 °C offset is precise (it gives the same reading every time) but inaccurate (that reading is wrong by 2 °C). You detect it by calibration — measuring a known standard, such as ice water at 0 °C or boiling water at 100 °C (corrected for altitude) — and comparing. Precision alone cannot reveal this, which is why repeating a badly calibrated measurement only makes you consistently wrong.

  8. Your dataset contains a value of -999 in a temperature column. Give two things you should do and one thing you must never do.

    Show answer
    1. Do: recognise it as a sentinel (an instrument "no reading" code, not a measurement) and convert it to missing.
    2. Do: log the exclusion with the row id, and check whether the dropouts cluster in time — clustered missingness is not random and must be stated.
    3. Never: include it in any average. A single −999 among 1,200 readings around 20 °C drags the mean down by roughly 0.85 °C, which can manufacture or destroy an apparent effect.

  9. A group measures reaction times before and after a task and reports "the mean fell from 312 ms to 298 ms, so the task improves reaction time." Identify the missing information and state what would make the claim defensible.

    Show answer

    Missing: the spread within each condition, the number of trials and participants, the measurement resolution, whether a control group did the same task, and whether practice effects were controlled. To make it defensible: report mean ± spread with sample sizes (e.g. "312 ± 40 ms before, 298 ± 38 ms after, n = 30 trials"), note that the difference (14 ms) is much smaller than the spread (about 40 ms), and therefore conclude that the data do not support the claim without many more trials or a control condition. The honest finding here is "no detectable effect", which is a legitimate and useful result.

  10. Explain why overwriting raw.csv is a serious problem even if you are confident your cleaning is correct.

    Show answer

    Confidence is not the issue; auditability is. Once the raw file is gone, nobody — including you — can verify that a cleaning decision was reasonable, reproduce the numbers, or recover from a mistaken exclusion. A single overwritten file turns an investigation into an unverifiable claim. Keeping raw.csv read-only and writing clean.csv costs nothing and makes every number traceable, which is exactly the standard the IA and Paper 1 expect.

Vocabulary
collaborative sciences project — the shared group 4 investigation, about 10 hours, involving at least two DP sciences.
interdisciplinary — involving more than one subject area working on one problem.
group 4 — the IB sciences subject group: physics, chemistry, biology, computer science, and related options.
research question — the specific question the investigation is designed to answer.
variable — a quantity that can change; independent (you change it), dependent (you measure it), controlled (you hold it fixed).
schema — the agreed structure of the data: column names, types, units and validation rules.
data collection — the process of gathering measurements.
sampling rate — how many measurements are taken per second, in hertz (Hz).
resolution — the smallest change an instrument can represent.
accuracy — how close a measurement is to the true value.
precision — how repeatable a measurement is.
calibration — comparing an instrument against a known standard to correct systematic error.
uncertainty — the range within which the true value is expected to lie.
error bars — marks on a chart showing the spread or uncertainty of each value.
outlier — a value far from the rest of the data; investigate before excluding.
missing value — a data point that was not recorded; handle explicitly, never silently.
sentinel value — a special code (e.g. −999) meaning "no reading", not a real measurement.
validation — checking that data matches its declared type and expected range.
residual — the difference between an observed value and the value a model predicts.
simulation — a computer model that imitates a system over time.
model fitting — choosing the parameters of a model so it best matches the data.
visualisation — representing data graphically.
reproducible — able to be run again by someone else and produce the same result.
audit trail — the record of what was done, in what order, and why.
consent — permission given by a participant before data is collected about them.
limitation — a stated weakness or boundary on what a result shows.
live demo — running the actual analysis during the presentation rather than showing screenshots.
