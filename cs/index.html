Computer science HL: the 2027 course

You are sitting a different course from the one nearly every free IB resource describes. The 2014 guide — seven flat topics, four options, a standalone HL Paper 3 on the case study — is gone. What replaces it is two themes (A: how computing systems work; B: how you use them to solve problems), a pre-seen case study examined inside Paper 1, an internal assessment built explicitly around the computational thinking process, a paper you answer in real Java or Python, and a ten-hour collaborative project shared with the sciences. This page is the map: what you are examined on, how the marks are actually won, and where to go next for each topic. It is written for a May 2028 candidate, which means it is honest about one awkward fact — there is almost no past-paper bank for this course yet, so your technique has to come from the method rather than from repetition.

HL: 240 teaching hours · SL: 150 HL only: A1.4 · A3.4 · A4.2 · A4.3 · B3.2 · all of B4 Paper 1: theme A + case study · Paper 2: theme B (Java or Python) External / internal at HL: 80 / 20
Why this page matters more than it looks

Search "IB computer science topic 4" or "IB CS option D" and you will find thousands of pages describing content that is no longer examined. Worse, the old guide's numbering (1 systems, 2 computer organisation, 3 networks, 4 computational thinking…) overlaps misleadingly with the new A/B codes, so a resource can look current and be a decade stale. Revise from an old one and you will spend hours on an option that no longer exists, a Paper 3 format that has been abolished, and a case study that is now examined completely differently — while missing machine learning, sets and hash tables, translation and alternative databases, none of which appear in any old index. Learn the new map first, then fill it in.

There is a second reason to read this page before the topic pages. Computer science HL is unusual among DP sciences: the two papers reward almost opposite habits. Paper 1 wants developed prose about consequences and trade-offs. Paper 2 wants surgical precision — the exact index, the exact value printed, a semicolon in the right place. Students who are good at one are often careless at the other, and the fix is knowing which hat you are wearing. That is what sections 5 to 8 of this page are for.

1. What the course actually is

Strip away the syllabus document and computer science HL is three things braided together. First, a body of knowledge about how computing systems work: what a bit is, how a processor fetches and executes an instruction, how a packet finds its way across a continent, how a database guarantees that two users cannot corrupt each other's data, how a program written in English-ish text becomes electrical signals. That is theme A, and it is mostly facts with mechanisms.

Second, a practical craft: taking a messy problem somebody actually has, deciding what matters, designing an algorithm, writing it in a real language, testing it against data you did not choose, and judging it honestly. That is theme B plus the internal assessment, and it is mostly decisions with reasons.

Third, and this is the part students underestimate, a habit of arguing about technology: who is affected, who benefits, who carries the risk, what the failure mode is, whether the trade-off is worth it. That is the case study and a large share of Paper 1, and it is where the difference between a 5 and a 7 actually lives, because almost everyone can define a router and very few can evaluate one.

What people expect it to be

Learning to code. Students arrive expecting a programming course and are surprised that Paper 1 contains no code at all, that roughly half the marks are prose, and that the hardest examinable skill is reading a five-line algorithm they did not write and stating exactly what it prints.

What it really is

A course in precise thinking that happens to be checkable by a machine. The programming is the laboratory, not the subject. You can get a 7 while writing nothing more advanced than an array and a loop — provided every answer you write has a mechanism, a consequence, and the right command term.

Be honest about what is hard

Three things reliably hurt HL candidates, and none of them is "coding is difficult". (i) B4 abstract data types — HL-only, the largest single jump in the course, and it assumes you can already trace recursion in your sleep. (ii) Handwriting code for two hours with no compiler, no autocomplete and no error message, which is a completely different skill from writing code in an editor. (iii) Eight- and twelve-mark evaluate questions, where accurate knowledge presented as description earns roughly half the marks no matter how much of it there is. Everything on this page is arranged around those three.

Core concepts you must know

Computer science has more basic vocabulary than any other subject on this site, and the vocabulary is not decoration: half of Paper 1 is prose in which the mark is awarded for naming the right mechanism. Everything below is defined in one sentence here and treated in full on the topic pages. Learn the definitions tightly enough that you can say them out loud — then practise the harder skill, which is explaining why the mechanism has the consequence it has.

How a computer system works — A1 and A2

bit, byte and number bases — a bit is one binary digit; eight make a byte; binary, denary and hexadecimal are the same quantity written in base 2, 10 and 16, and hex exists because it compresses binary four bits to a digit.
two's complement — the way signed integers are stored: invert the bits and add one, so the leading bit is the sign and addition works unchanged for negative numbers.
floating-point representation — a number stored as mantissa × baseexponent, which gives huge range at the cost of rounding error — the reason 0.1 + 0.2 is not exactly 0.3.
character set — the agreed mapping from numbers to symbols: ASCII for 128 characters, Unicode for every writing system, with UTF-8 the variable-length encoding that stores it efficiently.
Boolean logic and gates — AND, OR, NOT, XOR, NAND are the physical building blocks of decision; a truth table defines a circuit and Boolean algebra simplifies it.
Von Neumann architecture — one memory holding both instructions and data, fetched and executed in a cycle by the control unit, ALU and registers; the shared bus is why it is fast and also why it is a bottleneck.
fetch–decode–execute cycle — the processor repeatedly fetches the next instruction from memory, decodes what it means, and executes it; clock speed sets how often, cores let it happen in parallel.
cache and the memory hierarchy — small, fast memory sitting between the processor and RAM, holding recently used data because programs reuse it; hits are fast, misses cost a trip to main memory.
primary and secondary storage — primary (RAM, ROM, cache) is fast and volatile or firmware; secondary (magnetic, solid state, optical) is slower, cheaper and persistent.
operating system, scheduling and virtual memory — the OS allocates the processor, memory and devices; scheduling decides which process runs next; virtual memory lets a program use more address space than physical RAM by paging to disk.
interrupt — a signal that makes the processor stop, save its state, service the urgent event and resume — the mechanism that lets one processor appear to do several things.
translator: assembler, compiler, interpreter — three ways to turn source into action: assembler for one-to-one machine instructions, compiler for the whole program ahead of time, interpreter line by line at run time.
encryption, hashing and TLS — symmetric uses one shared key, asymmetric uses a public and a private key, and hashing is one-way and used to verify integrity; TLS combines them to secure a connection.
network, topology and the devices between nodes — a network connects devices; the topology is the shape of the connections; hubs repeat, switches forward to one port, routers join networks, gateways join unlike networks.
MAC address, IP address and subnetting — MAC is the hardware identity, IP is the routable logical address, and a subnet mask splits an address into network and host parts.
packet, routing, TCP and UDP — messages are chopped into packets and routed independently; TCP guarantees delivery with a handshake and retransmission, UDP is faster and does not.
application protocols: DNS, HTTP/S, FTP, SMTP — the named jobs at the top of the stack: names to addresses, web transfer, file transfer, email.
error detection: parity, checksum, Hamming — adding redundant bits so corruption can be detected, and in Hamming's case located and corrected without retransmission.

Data at scale — A3 and A4

database, table, record, field — a database is a structured, persistent collection of data; tables hold records (rows) made of fields (columns).
primary, composite and foreign keys — a primary key uniquely identifies a record, a composite key needs two or more fields to do it, and a foreign key points at a primary key in another table, creating the relationship.
relationships — one-to-one, one-to-many and many-to-many; the last is implemented with a link table, which is the step students forget.
normalisation (1NF, 2NF, 3NF) — a procedure for removing redundancy and the anomalies it causes: atomic values, then no partial key dependence, then no transitive dependence.
SQL — the declarative language for asking questions of a database: SELECT with WHERE, ORDER BY, GROUP BY, aggregates and JOIN.
transaction and ACID — a unit of work that is Atomic, Consistent, Isolated and Durable, so a half-completed transfer can never be stored.
NoSQL and the CAP theorem — non-relational stores (document, key–value, column, graph) that trade some relational guarantees for scale; CAP says a distributed system cannot have full consistency and full availability during a partition.
machine learning — inverting programming: instead of writing the rules you supply data and answers, and the system infers a model that maps features to labels.
supervised, unsupervised, reinforcement — learning from labelled answers, from structure alone (clustering), or from reward and penalty.
classification vs regression — predicting a category versus predicting a number; examiners ask this distinction almost every session.
training, validation and test sets — separate data for fitting, tuning and final judgement; testing on training data is the classic way to fool yourself.
overfitting and underfitting — memorising noise versus missing the pattern; a model that is perfect on training data and poor on test data has overfitted.
bias in data and ethics — a model inherits the biases of its training data, so "the algorithm decided" is never an excuse and always an evaluation point.

Computational thinking and programming — B1 to B4

abstraction — keeping the features that matter for the problem and discarding the rest; it is the single most examined idea in the course, and "vague" is not the same as "abstract".
decomposition — breaking a problem into sub-problems that can be solved, tested and named independently.
algorithm — a finite, ordered, unambiguous set of steps that solves a problem; it is the idea, not the code.
pseudocode, flowchart, structure chart, trace table — the four representations: prose-like code the IB defines, diagrams of flow and hierarchy, and a table for hand-executing an algorithm step by step.
the five strands of computational thinking — thinking procedurally (order and sub-tasks), logically (decisions), ahead (inputs, outputs, preconditions), concurrently (what can happen at once), abstractly (what to keep).
concurrency vs parallelism — concurrency is the structure of a program that manages several tasks; parallelism is actually running them simultaneously. Hazards arise when shared data is updated in an uncontrolled order.
variable, constant and data type — a named store whose value can change, one that cannot, and the kind of value each holds (integer, real, string, Boolean), which decides the operations allowed.
selection and iteration — branching on a condition, and repeating: definite iteration for a known number of times, conditional iteration until a condition changes.
array and list — a fixed-size indexed collection versus a resizable one; choosing between them is a decision about memory, insertion cost and access speed.
sub-procedure, function, parameter and return value — a named block you can call; parameters pass data in, a return value passes a result out, and the interface is the contract.
recursion — a procedure that calls itself, always with a base case that stops it; elegant for trees and for problems defined in terms of smaller versions of themselves.
testing: error types and test data — syntax, runtime and logic errors; normal, boundary and erroneous data. Validation checks the input is sensible, verification checks you built the right thing.
class, object, instance, constructor — the class is the blueprint, the object the thing built from it, an instance one such object, and the constructor sets its initial state.
encapsulation and access modifiers — bundling data with the methods that use it and hiding the internals, so state can only change through the intended interface.
inheritance, polymorphism, abstraction (OOP) — sharing structure down a hierarchy; one interface with many implementations (overloading versus overriding); abstract classes and interfaces that fix the contract and leave the behaviour.
abstract data type (ADT) — a structure defined by its operations and their contracts, independently of implementation: stack, queue, list, tree, graph, hash table.
stack, queue, tree, graph, hash table — LIFO, FIFO, hierarchical with traversals, networked with BFS and DFS, and key-to-index mapping with a collision strategy.
algorithm efficiency and Big-O — how the number of steps grows as the input grows, written O(n), O(n2), O(log n); it compares growth, not absolute speed on small inputs.

How the two halves meet

Theme A and Theme B are not two courses. A program you write in B2 is stored as binary in two's complement and floating point, compiled by a translator, scheduled by an operating system, and — if it holds anything worth keeping — persists it through normalised tables and transactions. The abstraction you practised in B1 is exactly the skill that makes a database schema or a feature set defensible, and the complexity you can state in B4 is the reason a choice of structure is a decision rather than a preference. The internal assessment is where the examiner checks that you can do both at once, and the case study is where you argue about what a real system does to real people.

"Explain" means mechanism plus consequence

The difference between a 2-mark and a 4-mark answer in this subject is almost always this: a describe answer says what happens ("the router forwards the packet"), an explain answer adds the mechanism and its consequence ("the router reads the destination IP, consults its routing table and forwards the packet on the interface for that network, so the packet moves one hop closer without the sender needing to know the path"). Build every explain answer as mechanism → consequence and you stop losing the second mark.

Three confusions that cap a 7

Abstraction is not vagueness. "The app is easy to use" is vague; "the app exposes three operations and hides the storage format" is abstraction. Big-O is growth, not speed. An O(n2) sort can beat an O(n log n) sort on ten items, but not on ten million. A compiler is not better than an interpreter. Compiled code runs faster; interpreted code is easier to debug and more portable. Every technology answer in this course is a trade-off, and "which is better" is never the question.

Exam technique — the two-hour arithmetic

HL papers run about 60–70 marks in two hours, which is roughly 1.7 minutes per mark. That sounds generous until you meet a twelve-mark evaluate. Budget it deliberately: 90 seconds reading the whole paper and ticking the questions you can do cold; do those first and fast; leave the big evaluate, discuss and to what extent items for last with a ring-fenced 20–25 minutes. An unfinished eight-mark evaluation costs far more than a slow three-mark explanation ever will, and writing the evaluation first is the classic way to run out of time with six marks of SQL unwritten.

4.1 Why this matters specifically to a May 2028 candidate

Three practical consequences, in order of how much they should change your behaviour.

  1. There is nearly no past-paper bank for your course. The first assessment is 2027, so by the time you sit Paper 1 in May 2028 there will be very few released papers in the new format, and the ones that exist will be guarded by your school. You cannot revise by grinding past papers the way a physics or economics student can. Substitute: specimen material, your teacher's own questions, and — most importantly — questions you write yourself from the syllabus, because writing a markscheme is the highest-yield revision there is.
  2. Your resources will be a mixture, and you are the filter. Textbooks published before 2024, websites with no update date, and even some school schemes of work describe the old course. Three tells that a resource is old: it numbers topics 1–7; it mentions "the option" or "Option D"; it says Paper 3. Two tells it is new: codes like A1.2 or B4.1, and any mention of the collaborative sciences project.
  3. Content is the safe part; format is the risky part. Binary, SQL, OOP and networking all survive, so old material on those is still useful for learning. What old material cannot give you is the new content (A4, B4, A1.4, A3.4) and the new question styles. Treat any old exam question as content practice, never as format practice.
Trap — "but I found a great resource"

The most expensive version of this is a complete set of beautifully organised notes for the 2014 course. You will read them, feel productive, and never notice that three topics you will be examined on are absent from the index. Before you invest in any resource, open its contents page and look for four strings: A4, B4, collaborative, and Paper 1 (not Paper 3). If two of those four are missing, close it.

5. The three skills that carry the marks

Almost every mark lost in computer science HL is lost in one of three ways, and none of them is "not knowing the content". Learn these three first and every topic page on this site becomes easier to use.

5.1 Skill one — reading and tracing unfamiliar code

Paper 2 will show you an algorithm you have never seen, possibly doing something pointless, and ask what it outputs or what it does. There is no trick to this beyond doing it slowly and on paper, but there is a procedure (section 6), and the habit of never answering a trace from a glance is worth several marks a paper.

Worked example 1 Skill one · 4 marks · trace a DIV/MOD loop

Question. State the output of this algorithm.

n = 5
total = 0
loop while n > 0
    total = total + (n MOD 2)
    n = n DIV 2
endloop
output total
  1. Identify what changes. Two variables: total accumulates, n is repeatedly halved with integer division. The loop runs while n > 0.
  2. Iteration 1: n = 5. 5 MOD 2 = 1, so total = 1. 5 DIV 2 = 2, so n = 2.
  3. Iteration 2: n = 2. 2 MOD 2 = 0, so total stays 1. 2 DIV 2 = 1, so n = 1.
  4. Iteration 3: n = 1. 1 MOD 2 = 1, so total = 2. 1 DIV 2 = 0, so n = 0.
  5. Exit: n = 0 fails n > 0, so the loop ends and output total prints once.
Answer: 2. The recognition worth having: repeated MOD 2 plus DIV 2 counts the set bits in a binary number — 5 is 101, which has two 1s. That is an A1 idea appearing inside a Paper 2 question, and candidates who see it answer in fifteen seconds.

5.2 Skill two — explaining rather than describing

This is the difference between a 4 and a 7 in Paper 1, and it is a vocabulary problem more than a knowledge problem. A description says what a thing is. An explanation says how it works and therefore what follows. The reliable test: if your answer contains no "so", "therefore" or "because", it is probably a description.

Worked example 2 Skill two · 4 marks · turn a description into an explanation

Question. Explain why a school might choose a star network topology rather than a bus topology for its teaching block. [4 marks]

A 1-mark answer (pure description): "A star topology has a central switch and every device connects to it with its own cable." True, accurate, and worth one mark, because it answers "describe", not "explain".

A 4-mark answer (mechanism + consequence, twice):

  1. "In a star topology each node has a dedicated cable to the central switch, so a break in one cable disconnects only that node and the rest of the network keeps running." — mechanism 1 plus its consequence.
  2. "Collisions are also avoided because the switch forwards frames only to the intended recipient, so adding more devices does not degrade performance the way it does on a shared bus where every device contends for the same medium." — mechanism 2 plus its consequence.
  3. "The cost is that the switch is a single point of failure, so if it fails the whole network goes down — which is why a school would specify a managed switch with a spare." — the balancing consequence, which is what pushes the answer into the top band.
Where the marks are: one per mechanism-consequence pair, and the fourth for the counterweight. Notice that the strong answer contains no fact the weak answer did not already imply — the difference is entirely in the connectives.

5.3 Skill three — designing before coding

In Paper 2 and in the IA, marks are allocated for the decision, not the typing. "I used an array" scores nothing; "I used an array rather than a linked list because the number of elements is fixed at twelve and I need positional access, and a linked list would add pointer overhead for no benefit" scores the design mark and, usually, an efficiency mark alongside it.

Worked example 3 Skill three · 6 marks · design before you write a line

Question. A sports club with 60 members wants a program that records who attended each training session during a 12-week term and lists any member whose attendance falls below 50 %. (a) Decompose the problem. (b) Choose a data structure for the attendance records and justify it against one alternative. (c) Describe the algorithm.

  1. (a) Decomposition — four independently testable sub-problems: (i) store the member list; (ii) record attendance for one session (date plus the set of members present); (iii) for one member, count sessions attended and compute a percentage; (iv) filter to those below 50 % and output. The test of the decomposition: you can test (iii) on invented data without any of the rest existing.
  2. (b) Structure and justification. A dictionary (map) keyed by member ID whose value is a set of session dates. Justification: membership tests in a set are constant-time, so counting attendance for one member is immediate, and a set cannot contain the same date twice — which prevents the double-counting bug a list would allow. Alternative rejected: a 60 × 84 two-dimensional boolean array. It is fast and simple, but it wastes memory on absent members, it fixes the term length at compile time, and it cannot record a session on an unexpected date without resizing.
  3. (c) Algorithm. For each member, divide the size of their date set by the number of sessions held so far; if the result is below 0.5, add the member to the report list; sort the report list by name and output. One pass, so the complexity is O(n) in the number of members — worth stating, because at HL silence about efficiency is conspicuous.
  4. The design decisions that earn marks are the rejected alternative and the complexity statement. Neither requires a single line of working code.
Answer: a four-part decomposition, a dictionary-of-sets justified against a 2D array, and a single-pass algorithm with a stated complexity. Every mark came from a decision, not from syntax.
Connection — the three skills are the same skill in different clothing

All three are forms of making your reasoning visible. A trace table shows the reader the steps you took; an explanation shows the causal chain; a design shows the alternatives you weighed. The IA rewards exactly the same thing, which is why students who are good at these three routinely finish the IA documentation faster. See B1 for the formal version and the IA page for the long version.

6. How to read and trace code

A trace table records the value of every variable after each significant step. It is the only reliable way to answer "state the output of this algorithm" and the only reliable way to debug a loop you have just written. Do it on paper every time, even when you think you can see the answer — most lost trace marks are from candidates who traced in their head and got one iteration out of step.

How to use it — the tracing procedure
  1. List the variables first. One column each, plus one column for output. Include the loop counter and any accumulator — these are the two people forget.
  2. Write the initial values as row one, before any line has run. If a variable is never initialised, write "?" — that is often the answer to a follow-up question.
  3. Work one line at a time, in order. Add a new row every time any variable changes. Do not skip iterations because they look identical; the differences are usually where the question lives.
  4. Evaluate the loop condition separately from the body. Check the condition, then either run the body or exit. Most off-by-one errors are made by running the body one more time after the condition has gone false.
  5. Write output as it happens, in the output column, in the row where it happens. Output inside a loop produces one value per iteration; output after the loop produces one value total.
  6. For a sub-procedure, start a fresh table and copy in the arguments. Note whether each parameter is by value (the original cannot change) or by reference (it can) — in Java, objects and arrays are passed by reference; in Python, lists and dictionaries are too.
  7. Sanity-check the last row. Does the final value have the right sign, the right magnitude, the right type? A trace that ends with a count of −1 or an average of 0.5 when every input was an integer has gone wrong somewhere.

Worked trace 2 A loop bound that depends on the outer counter · 6 marks

Question. State the output, and state how many times the inner loop body runs in total.

count = 0
loop for i = 1 to 3
    loop for j = 1 to i
        count = count + 1
    endfor
endfor
output count
  1. Spot the dependency. The inner loop runs i times, not a fixed number. This is the whole difficulty; everything else is counting.
  2. i = 1: j runs 1 time → count = 1.
  3. i = 2: j runs 2 times → count = 3.
  4. i = 3: j runs 3 times → count = 6.
  5. Total inner iterations: 1 + 2 + 3 = 6, which equals the final value of count because the body only increments. For n outer iterations the total is n(n + 1)/2, so the algorithm is O(n²) — the kind of statement that turns a correct trace into full marks at HL.
Answer: 6, with six inner iterations in total. The general form 1 + 2 + … + n = n(n + 1)/2 is worth memorising; it appears whenever an inner bound depends on the outer counter.
Why this works Why 1 + 2 + … + n = n(n + 1) / 2, and why it matters for complexity
  1. Write the sum forwards and backwards beneath it: S = 1 + 2 + … + (n − 1) + n, and S = n + (n − 1) + … + 2 + 1.
  2. Add the two lines term by term. Every column sums to n + 1: the first is 1 + n, the second is 2 + (n − 1) = n + 1, and so on.
  3. There are n columns, so 2S = n(n + 1), and therefore S = n(n + 1) / 2.
  4. Check with the trace: n = 3 gives 3 × 4 / 2 = 6, which is exactly the value the algorithm printed.
  5. Why it matters: the formula has an n² term, so a loop whose inner bound depends on the outer counter is quadratic. Doubling the input roughly quadruples the work — which is the whole content of the O(n²) statement you are expected to make at HL.
  6. When it is the wrong tool: when the inner loop runs a fixed number of times independent of the outer counter, the total is c × n, which is linear, not quadratic. Check the bound before you quote a complexity.
Worked trace 3 Recursion: trace the call tree · 8 marks

Question. State the output, state how many times puzzle is called in total (including the first call), and comment on the efficiency.

function puzzle(n)
    if n < 2 then
        return n
    else
        return puzzle(n - 1) + puzzle(n - 2)
    endif
endfunction

output puzzle(5)
  1. Identify the base case. When n < 2 the function returns n immediately, with no further calls. So puzzle(1) = 1 and puzzle(0) = 0.
  2. Expand from the top, but evaluate from the bottom. puzzle(5) = puzzle(4) + puzzle(3); puzzle(4) = puzzle(3) + puzzle(2); and so on. Write the tree, then fill in values from the leaves upwards.
  3. Leaves: puzzle(1) = 1, puzzle(0) = 0.
  4. puzzle(2) = puzzle(1) + puzzle(0) = 1 + 0 = 1.
  5. puzzle(3) = puzzle(2) + puzzle(1) = 1 + 1 = 2.
  6. puzzle(4) = puzzle(3) + puzzle(2) = 2 + 1 = 3.
  7. puzzle(5) = puzzle(4) + puzzle(3) = 3 + 2 = 5. Output: 5.
  8. Call count. Counting every node in the tree: puzzle(5) once, puzzle(4) once, puzzle(3) twice, puzzle(2) three times, puzzle(1) five times, puzzle(0) three times — 15 calls in total to compute the fifth value.
  9. Efficiency comment. The same sub-problems are recomputed from scratch (puzzle(3) is evaluated twice, puzzle(2) three times), so the number of calls grows exponentially with n. It is the Fibonacci recurrence, and it is why this algorithm is unusable for large n — a point worth one or two marks on its own if the question says "comment".
Answer: output 5, fifteen calls in total, exponential behaviour. The trap is expanding the tree correctly and then reading the values in the wrong order: always evaluate the leaves first.
Trap — the four tracing errors that cost the most marks
  1. Off-by-one on the loop bound. loop for i = 0 to LENGTH(list) - 1 is right; loop for i = 0 to LENGTH(list) runs one time too many and usually throws an out-of-range error or, worse, silently processes a default value.
  2. Output inside versus outside the loop. One output statement inside a loop prints once per iteration. Candidates routinely write a single value when the answer is a column of them.
  3. By reference versus by value. Passing an array or a list into a sub-procedure and modifying it changes the caller's variable. Passing an integer does not. In Java and Python, arrays/lists/dictionaries are the ones that change.
  4. Integer division. 1 DIV 4 is 0, not 0.25, and in Java 1 / 4 is also 0 when both operands are int. This is the origin of "why is my average always zero?".

7.1 The same question answered badly and well

Question. "Explain why a hospital might store patient records in a relational database rather than in a flat file. [4 marks]"

Weak answer (1–2 marks)Strong answer (4 marks)
"A relational database stores data in tables and uses primary keys and foreign keys. It is organised and it uses SQL. Flat files are just one long list and they are not as good." "In a relational database the patient is stored once in a PATIENT table and every appointment refers to that row by foreign key, so changing a patient's address updates every appointment automatically — in a flat file the address is repeated on each row and one update can leave contradictory copies. Furthermore, the database can enforce referential integrity, so an appointment cannot exist for a patient who is not in the system, which a flat file cannot prevent. However, this comes at the cost of a fixed schema and the overhead of running a DBMS."
Why it fails: everything here is description of features. There is no mechanism–consequence pair and no context, so it cannot access the higher markband even though every sentence is true. Why it works: two mechanism–consequence pairs, each anchored to the hospital context, plus a balancing limitation. Note the connectives — "so", "furthermore", "however" — which are the surface evidence of the reasoning.
Worked example 4 Rebuilding a 6-mark evaluate answer from a weak draft

Question. "Evaluate the proposal to replace the school's on-site file server with a cloud storage subscription. [6 marks]"

Weak draft: "Cloud storage is when data is stored on remote servers and accessed over the internet. It is very popular and many companies use it. It means you can access files from anywhere. The school should do it because it is modern."

Diagnosis: the first two sentences describe, the third states one advantage with no mechanism, and the conclusion is an assertion with no criteria. Maximum about 2 of 6.

Rebuilt answer:

  1. Criteria, in context: "The relevant criteria for a school are availability during lesson time, ongoing cost, data protection obligations concerning pupils, and dependence on the internet connection."
  2. Advantage with mechanism: "Cloud storage replicates data across multiple data centres, so a single hardware failure or a fire in the server room does not lose work, whereas the current single on-site server is a single point of failure."
  3. Advantage with mechanism: "Access from anywhere means staff can work from home without a VPN, so the cost and complexity of remote access falls."
  4. Disadvantage with mechanism: "Access becomes dependent on the internet link, so a WAN outage stops every lesson that uses shared files — currently teaching continues because the server is on the LAN."
  5. Disadvantage with mechanism: "Pupil data would be processed by a third party, possibly in another jurisdiction, so the school must satisfy its data protection obligations through contractual safeguards, which is an ongoing administrative cost."
  6. Judgement: "On balance the proposal is worth adopting for staff collaboration and disaster recovery, but the school should keep a local cache of lesson-critical resources and should only proceed once the provider's data processing terms have been reviewed."
Where the marks are: 1–2 for contextualised criteria, 2–3 for developed advantages and disadvantages with mechanisms, 2 for a supported judgement. The single move that converts a 2 into a 6 is adding the judgement paragraph — and noticing that a judgement must say which consideration wins.

8. Programming expectations: pseudocode, Java and Python

The exam uses two different notations and asks for three. Knowing which is which is worth several marks per paper.

IB pseudocode — read and write it

Questions are set in the IB's own pseudocode, and any question that says "write pseudocode" or "construct an algorithm" wants it back in the same notation. It looks like English: output, input, if … then … else … endif, loop while … endloop, MOD, DIV. There are no semicolons, no braces and no type declarations.

Real Java or real Python — write one

When a question says "write Java" or "write Python", it means real, syntactically valid code. You choose one language and stay in it from B2 onwards. Both score full marks; the IBO sets Paper 2 so that either works.

The other language — read it

You must be able to read whichever one you did not choose, because textbooks, classmates and published answers use both. The B2, B3 and B4 pages of this site show both, labelled, for exactly this reason.

8.2 One algorithm in three notations

Task: count how many values in a collection exceed a given limit. This is the kind of four-mark "construct" question that appears constantly, and it is worth being able to produce in all three notations without thinking.

IB pseudocode — use this when the question says "construct an algorithm" or "write pseudocode":

function countAbove(list, limit)
    total = 0
    loop for i = 0 to LENGTH(list) - 1
        if list[i] > limit then
            total = total + 1
        endif
    endfor
    return total
endfunction

Python:

def count_above(values, limit):
    total = 0
    for value in values:        # iterate over values, not indices
        if value > limit:
            total += 1
    return total

Java:

public static int countAbove(int[] values, int limit) {
    int total = 0;
    for (int value : values) {  // enhanced for-loop
        if (value > limit) {
            total++;
        }
    }
    return total;
}

Notice what is identical across all three: the accumulator initialised before the loop, the comparison, the increment, the return. Notice what is not: how you say "for each element", whether you need an index at all, and where the block boundaries are. Learn the invariant, then the punctuation.

Trap — the three language errors examiners see most
  1. Pseudocode inside a real-language answer. output "x" in a Python script, or endif in Java, is not a stylistic choice; it is a syntax error and it costs marks that are otherwise free.
  2. == on strings in Java. a == b compares references; a.equals(b) compares content. This is the single most common Java bug in DP scripts.
  3. Mixing loop idioms. Writing for (int i = 0; i < a.length; i++) and then using a instead of a[i] inside the body — a habit formed by writing Python-style for x in a: and translating it literally.
How to choose Java or Python, in order of importance
  1. Which one does your school teach through to the end of B3 and B4? This dominates. Self-teaching Java's type system and class syntax late in DP2 is an expensive use of time.
  2. Which do you write faster by hand? Python is terser — a dictionary literal instead of a HashMap, a list instead of an ArrayList, roughly 40 % fewer characters. In a handwritten two-hour exam that is a genuine advantage.
  3. Which makes the IA stronger? If it needs a GUI, a web API or a data-science library, Python wins. If it needs to show off inheritance, interfaces and encapsulation, Java's explicitness helps — the marker can see extends, implements and private.
  4. What should not influence you: which language you imagine the examiner prefers. Neither scores more.

9.1 Choosing an IA topic

Three filters, applied in order. If a candidate topic fails any of them, discard it before you write a line.

  1. Is there a real client who will answer questions? Not "my friend said it would be cool" — a person with a measurable pain who can tell you what "solved" would look like and will sign a dated success criteria list. Without a client voice, the specification and evaluation strands cannot reach the top band, and those strands are a quarter of the marks.
  2. Is the scope right? Big enough to need real decomposition (four to eight sub-problems, typically 300–800 lines of code, at least one non-trivial data structure), small enough to finish six weeks before the deadline. The most common IA error is choosing something that would take a professional team a month.
  3. Can you show off the syllabus deliberately? The strongest submissions use themes A and B on purpose: a normalised database (A3) behind a program with classes and inheritance (B3), running over a network with authentication (A2), with a documented decomposition (B1). The IBO calls the IA a "unifying assessment" and means exactly this.
Connection

Both components reward the same underlying habit: reasoning about a system you did not build for people who are not you. The IA does it with a client you interview; the case study does it with stakeholders you are told about. Practise the second on the case study page and the first gets easier; do the collaborative project seriously and both get easier.

10. The collaborative sciences project

Ten hours, a group containing students from at least two group 4 subjects, one shared investigation and a presentation. No marks go to the IB. The requirement exists so that no DP science student finishes two years without planning an investigation, handling real data, quantifying uncertainty and defending a conclusion across subject boundaries.

For you it is the cheapest rehearsal available. Your value in the group is not "knowing Python" — it is turning a vague scientific question into a data pipeline that answers it: agreeing the schema before collection, automating the logging so you get two thousand rows instead of twenty, cleaning with a logged procedure, choosing an analysis the question actually justifies, and putting error bars on the chart. Students who take these ten hours seriously typically finish the IA weeks faster, because the expensive part of the IA is not the coding; it is knowing what to write down. The full method, a schema worked example and sixteen project ideas are on the collaborative project page.

12. How to revise for a course that is half knowledge and half code

Reading notes does not work for Paper 2, and writing code does not work for Paper 1. You need four different practices, and the mistake most students make is doing only the first.

1 · Recall the facts (theme A)

Cover-and-write on terminology: what a router does, what normalisation removes, what a compiler emits. Make a deck of one-term-per-card and do it in both directions (term → meaning, meaning → term). Ten minutes a day from DP1 beats ten hours in the last week, because A2 and A1 are vocabulary-heavy and vocabulary decays.

2 · Trace by hand (Paper 2)

Two traces a day in the last eight weeks, on paper, with a table, no compiler. Use the procedure in section 6. This is the single highest-yield habit in the course, because it trains exactly the skill Paper 2 tests and nothing else trains it.

3 · Write full answers to real command terms (Paper 1)

Never "make notes" on an evaluate question. Write the answer, timed, in full sentences, then mark it against the command-term table in section 7. One timed eight-mark evaluation a week from the middle of DP1 changes your grade more than anything else on this page.

4 · Write a markscheme

With almost no past papers available, this is your substitute. Take a syllabus bullet, write the question you think the IBO would ask, then write the markscheme. You cannot do this without knowing the content properly, and it teaches you where the marks are — which is the same knowledge that makes you faster in the exam.

0–5 min
Set up. Paper copy of the question, a pencil, plenty of space, a timer. No computer, no phone. Paper 2 is handwritten, so every practice session should be too.
5–15 min
Do the cold questions first. The traces, the SQL, the conversions — the ones with a right answer. Write trace tables in full even when you can see the answer, because the table is what catches the off-by-one.
15–45 min
The construction question. Write the algorithm in the notation asked for. Then check it against three inputs: a normal case, a boundary case (empty collection, first or last element) and an erroneous case (wrong type, out of range). If your answer has no boundary check, you have not finished.
45–70 min
The extended response. Plan it in forty words before writing: criteria, two developed advantages, two developed disadvantages, judgement. Then write it in full sentences with connectives. Stop at the time limit even if unfinished — an unfinished answer is data.
70–90 min
Mark it honestly. Use the command-term table. Give yourself a mark, then write one sentence naming the single change that would have gained the most marks. That sentence is the product of the session.
Exam technique — the last eight weeks

Weekly rhythm that works: one full paper under exam conditions (two hours, no interruptions), one ninety-minute skills session built from the plan above, and twenty minutes of terminology recall daily. In the final fortnight, stop learning new content and instead write, from memory, a one-page summary of each topic: the definitions, the standard algorithms in pseudocode, and one evaluation you have prepared in advance. Being able to redraw that page on the morning of the exam is the difference between panic and routine. The exam toolkit and the study plan at the site root have the scheduling detail.

13. Practice

Answer these in full sentences, timed, before opening anything. The marks in brackets are the IB-style allocations.

  1. State the output of the following algorithm. [4 marks]

    a = 7
b = 2
loop while a > 0
    a = a DIV b
    b = b + 1
endloop
output a, b
    Show the answer
    1. Initial: a = 7, b = 2.
    2. Condition 1: a > 0 is true. a = 7 DIV 2 = 3; b = 3.
    3. Condition 2: a > 0 is true. a = 3 DIV 3 = 1; b = 4.
    4. Condition 3: a > 0 is true. a = 1 DIV 4 = 0 (integer division — not 0.25); b = 5.
    5. Condition 4: a > 0 is now false, so the loop exits and the single output prints once.
    Answer: 0 and 5. Why this is worth knowing: the divisor changes inside the loop, so the condition must be re-checked with the new value of a each time, and 1 DIV 4 is 0 — the two ideas this question exists to test.

  2. A question asks: "Evaluate the use of facial recognition for registering attendance at this school." A student writes four accurate sentences describing how facial recognition works. Explain why this cannot score high marks, and state what an evaluate answer must contain. [6 marks]

    Show the answer
    1. Why it caps: the command term is evaluate, which requires weighing advantages against disadvantages and reaching a supported judgement. Description answers a different question, so the answer cannot access the higher markband — the markscheme simply does not contain marks for features.
    2. What it must contain — criteria in context: for a school, accuracy across different skin tones and lighting, the time saved in registration, pupil data protection and consent, cost, and what happens when it fails.
    3. Developed advantages with mechanisms: registration becomes automatic, so teachers regain several minutes per lesson; and the record is harder to falsify than a paper register, because a pupil cannot sign in for a friend.
    4. Developed disadvantages with mechanisms: biometric data is special-category personal data, so the school takes on significant storage and consent obligations; and false negatives fall disproportionately on some groups of pupils, so an error means a pupil is marked absent when present.
    5. Judgement: a conclusion that names which consideration wins for this school — for example, that the time saved does not justify the data protection burden unless the system processes images locally and pupils can opt out.
    Answer: criteria, both sides with mechanisms, and a judgement. Why this is worth knowing: an evaluation with no "however" and no "therefore" is not an evaluation, and this is the most common single cause of lost Paper 1 marks.

  3. Using the algorithm from Worked trace 3, state the output of puzzle(6) and the total number of calls made, and explain why a programmer should be concerned. [6 marks]

    Show the answer
    1. puzzle(0) = 0 and puzzle(1) = 1 by the base case.
    2. puzzle(2) = 1 + 0 = 1; puzzle(3) = 1 + 1 = 2; puzzle(4) = 2 + 1 = 3; puzzle(5) = 3 + 2 = 5; puzzle(6) = 5 + 3 = 8.
    3. Calls: the pattern is 1, 1, 3, 5, 9, 15 for n = 5 down the tree; for n = 6 the total is 25 calls (1 + 1 + 3 + 5 + 9 + 15 for the distinct sub-problems, counted with multiplicity).
    4. Why it matters: the same sub-problems are recomputed from scratch, so the number of calls grows exponentially with n. The sixth value already needs 25 calls; n = 40 would need hundreds of millions. This is the Fibonacci recurrence and it is the standard classroom example of a recursive solution that is correct and useless.
    5. The fix, stated: store each computed value (memoisation) or build upwards iteratively, reducing the work to O(n). Naming either is what the "comment" mark is for.
    Answer: 8, with 25 calls; exponential growth. Why this is worth knowing: HL questions increasingly follow a correct trace with "comment on the efficiency" — the trace is the easy half, the comment is the mark that separates candidates.

  4. A student submits the following as a Python answer to a question that said "write Python". Identify four distinct errors. [4 marks]

    output "Enter a mark"
input mark
if mark >= 50 then
    print("Pass")
else
    print("Fail")
endif
    Show the answer
    1. output is IB pseudocode, not Python. It should be print("Enter a mark").
    2. input mark is pseudocode. Python is mark = int(input("Enter a mark")) — and the int() matters, because input() returns a string and comparing a string to 50 raises a TypeError.
    3. then is not Python. The line must end with a colon: if mark >= 50:.
    4. endif does not exist in Python. Block structure is indentation, and the else: needs its own colon.
    Answer: the four errors above. Why this is worth knowing: every one of them is a habit carried over from pseudocode, and together they would reduce a four-mark answer to zero even though the logic is perfect.

  5. A program must store the words of a document and report how many times each word occurs, in alphabetical order. Choose a data structure, justify it against one alternative, and state the complexity of building it. [6 marks]

    Show the answer
    1. Choice: a dictionary (hash map) mapping word → count, then sort the keys.
    2. Justification: each word is looked up once per occurrence and the count incremented, which is constant-time on average in a hash map. Building the structure is therefore O(n) in the number of words.
    3. Alternative rejected: a two-dimensional array of (word, count) pairs with a linear search for each occurrence. It needs no hashing and is easy to code, but each lookup costs O(m) in the number of distinct words, giving O(nm) overall — and with a document of 10,000 words and 2,000 distinct words that is twenty million comparisons instead of ten thousand operations.
    4. The ordering requirement: since the output must be alphabetical and a hash map has no order, sort the keys once at the end: O(m log m). Total: O(n + m log m), which is dominated by the sort when the vocabulary is large.
    5. At HL, say the last sentence. Stating the complexity in words or in O-notation, and comparing two candidate designs, is exactly what the design mark and the efficiency mark ask for.
    Answer: a hash map, justified against a linear-search array, O(n) to build plus O(m log m) to sort. Why this is worth knowing: the mark is for the rejected alternative and the complexity, not for naming a structure.

  6. Explain why a web server might keep recently requested pages in a cache rather than retrieving them from disk each time. [4 marks]

    Show the answer

    A full-mark answer gives two mechanism–consequence pairs:

    1. "Cache memory (RAM) has access times orders of magnitude shorter than a disk, so a cached page is returned to the client far more quickly, reducing the server's response time."
    2. "Web requests are highly repetitive — a small number of pages account for most hits — so storing the most recently used pages means a large fraction of requests never touch the disk at all, which reduces disk I/O and lets the server handle more concurrent users."
    3. "The cost is that the cache must be invalidated when the underlying page changes, so without a suitable replacement policy the server can serve stale content."
    Answer: two developed mechanism–consequence pairs (2 marks each), with the third as a balancing remark. Why this is worth knowing: "it is faster" on its own scores one mark; the mark is for saying why it is faster and what the consequence is.

  7. Identify the six HL-only content codes in the 2027 guide and state, in one clause each, what each adds. [6 marks]

    Show the answer
    1. A1.4 Translation — how high-level code becomes machine code: compilers, interpreters, assemblers, bytecode and virtual machines.
    2. A3.4 Alternative databases and data warehouses — non-relational (NoSQL) models and why they exist, plus warehouses for analysis.
    3. A4.2 Data preprocessing — cleaning, normalising, encoding and splitting data before a model sees it.
    4. A4.3 Machine learning approaches — supervised, unsupervised and reinforcement learning, and the algorithms associated with each.
    5. B3.2 OOP for multiple classes — inheritance, polymorphism, aggregation and composition, and UML between classes.
    6. B4 Abstract data types — the whole topic: ADT principles, linked lists, binary search trees, sets and hash tables.
    Answer: the six codes above. Why this is worth knowing: this list is the shortest answer to "what does HL add?", it tells you precisely where an SL resource stops being enough, and it is a ready-made recall test.

  8. Explain why the internal assessment is worth a smaller percentage at HL (20 %) than at SL (30 %) even though both levels are given the same 35 recommended hours. [4 marks]

    Show the answer
    1. HL candidates sit four hours of external assessment against SL's two and a half, so the total assessment burden is larger at HL.
    2. The IA is the same size at both levels, so it forms a smaller share of a larger total.
    3. The consequence for you: HL grades are decided more by the exams, so a strong HL candidate should not over-invest in the IA at the expense of Paper 1 and Paper 2 practice.
    4. The counterweight: the IA is still 20 %, and it is the component where careful, visible work is most reliably rewarded — so do it properly, then move on.
    Answer: a larger exam burden at HL dividing the same 35 hours of coursework. Why this is worth knowing: it is an explain question, so each mark needs a cause and an effect, not just the two percentages.

Vocabulary
theme — one of the two halves of the syllabus: A (concepts of computer science) or B (computational thinking and problem solving).
syllabus code — the identifier for a sub-topic, such as A1.4 or B3.2; the letter is the topic and the number is the sub-topic.
case study — an IBO-published description of an emerging technology in real use, studied in class and examined in Paper 1.
internal assessment (IA) — coursework marked by your teacher and moderated by the IB; here, the computational solution.
computational solution — the new name for the CS IA, emphasising the thinking process rather than the finished program.
collaborative sciences project — the ten-hour interdisciplinary group 4 investigation, shared with the sciences.
external assessment — the examined components: Paper 1 and Paper 2.
weighting — the share of the final grade a component carries.
moderation — the IB's check on your teacher's IA marks, using a sample of the cohort's work.
command term — the verb at the start of a question (state, explain, evaluate) that tells you the shape of the answer.
mechanism — how something works; half of what an explain answer needs.
consequence — what follows from the mechanism; the other half, and the part students omit.
evaluate — weigh advantages against disadvantages and reach a supported judgement.
to what extent — how far a statement is true, and where it breaks down.
stakeholder — a person or group affected by a system; always name the specific one.
trace table — a column per variable showing the value after each significant step.
trace — working through an algorithm line by line to find its output or behaviour.
off-by-one error — a loop that runs one time too many or too few, usually from a wrong bound.
pseudocode — a language-neutral way of writing an algorithm; the IB has its own convention.
by reference — a parameter through which the callee can change the caller's variable (arrays, lists, objects).
by value — a parameter that is a copy, so the caller's variable cannot change.
integer division — division that discards the remainder: 7 DIV 2 = 3.
modulo — the remainder after division: 7 MOD 2 = 1.
recursion — a function that calls itself, with a base case that stops the calls.
base case — the input for which a recursive function returns without calling itself.
complexity — how the work grows with the size of the input, written O(n), O(n²) and so on.
abstraction — deciding what to keep and what to discard, and naming what is left.
decomposition — breaking a problem into sub-problems that can each be solved and tested alone.
data structure — a way of organising data in memory: array, list, stack, queue, tree, hash table.
abstract data type (ADT) — what a structure does, separated from how it is implemented.
normalisation — restructuring tables to remove redundancy and the anomalies it causes.
relational database — data in linked tables with keys, queried with SQL.
emerging technology — a technology new enough that its consequences are still being worked out — the case study's subject.
client — the real person whose problem your IA solves; the source of your success criteria.
success criteria — measurable statements of what "solved" means, agreed with the client.
validation — checking that input matches its expected type and range.
specimen paper — an official example paper showing the format of a new course.
