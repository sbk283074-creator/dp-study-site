B3 · Object-oriented programming

Object-oriented programming is a way of organising a program around the things it deals with rather than the steps it performs. That sounds like a stylistic preference. It is not: it changes which bugs are even possible, and it changes how much of your program you must rewrite when the requirements change. This page explains each mechanism, then — more importantly — why each mechanism exists, because Paper 2 questions rarely ask "what is encapsulation"; they ask you to design a class, extend a hierarchy, or justify a choice, and you cannot do that from definitions alone. All main code is in Java; the last section shows the same ideas in Python.

Theme B · examined in Paper 2 (answer in Java or Python) B3.1 Fundamentals of OOP for a single class B3.2 Fundamentals of OOP for multiple classes — HL only
Why this topic is on the syllabus

Every large program is eventually changed by someone who did not write it. The central question of B3 is: what can I arrange now so that a later change stays small? Encapsulation, inheritance, polymorphism and abstraction are four different answers to that one question, and every exam question on this topic is really asking you to pick the right answer for a given situation.

B3.1a · Why OOP exists: the procedural pain it removes

Start with a real task: a school library tracks its items. A procedural solution holds the facts in parallel arrays and writes functions that act on them.

// Procedural version — data and the code that uses it are separated
String[] titles = new String[100];
String[] authors = new String[100];
boolean[] onLoan = new boolean[100];
int count = 0;

void borrowItem(int index) {
 if (onLoan[index]) { System.out.println("already out"); return; }
 onLoan[index] = true;
}

This works for a week. Then three things go wrong.

1. Nothing keeps the arrays in step

Sorting titles without sorting authors and onLoan the same way silently corrupts every record. There is no mechanism in the language that prevents it — the four arrays are four unrelated objects that you happen to keep aligned by discipline.

2. Every fact can be set to nonsense

Any of the two hundred places that touch this data can write onLoan[7] = true without checking anything. When a book turns out to be both "on loan" and "available", every one of those places is a suspect.

3. A new item type edits every function

Add DVDs. Now borrowItem, printItem, isOverdue and sortItems each need a branch on the item type. One new noun means editing every verb.

The object-oriented version groups the facts about one item with the operations that make sense for that item:

public class Book {
 private String title; // the data ...
 private String author;
 private boolean onLoan;

 public void borrow() { // ... and the only code allowed to change it
 if (onLoan) { throw new IllegalStateException("already out"); }
 onLoan = true;
 }
}
Why it works The three arguments for bundling data with behaviour
  1. Invariant protection. Every class has an invariant — a sentence about its fields that must always be true. For Book: "if onLoan is false then no member holds it". If the fields are public, all 200 call sites can break that invariant. If the fields are private and the only mutating code is borrow() and returnItem(), the number of suspects drops from 200 to 2. The benefit is not secrecy; it is a short suspect list when something goes wrong.
  2. Change locality. Adding a DVD in the object-oriented version means writing one new class. Code like for (LibraryItem it : items) { out += it.describe(); } does not change at all, because it never asks what kind of item it has — it asks the item to describe itself. That property has a name: polymorphism, and it is the reason hierarchies are worth the indirection.
  3. Shared vocabulary with the client. The librarian talks about books, members and loans. A class diagram uses those same words, so you can hold it up in a meeting and be corrected. You cannot do that with four arrays. This matters directly for your IA, where the client's understanding of the design is part of the evidence.

The honest counter-argument. OOP is not free. It adds files, boilerplate and a layer of indirection that makes a program harder to read top-to-bottom. For a forty-line script it is overkill, and for a program that is essentially one long data transformation (read a file, filter it, write a file) a few plain functions are clearer. Say this in an evaluation question; examiners reward it.

Trap

"OOP models the real world" is a slogan, not an answer. In an exam, never write "because it is easier" or "because it is more realistic". Write the mechanism and the consequence: "private fields mean the balance can only change through withdraw(), which refuses amounts greater than the balance, so the invariant balance ≥ 0 cannot be broken by calling code."

B3.1b · Classes, objects and instances

A class is a blueprint: it describes what fields and methods its objects will have. An object (an instance of the class) is a concrete thing in memory created from that blueprint at run time. One class, many objects — each with its own copy of the fields, sharing one copy of the method code.

public class Book {
 // ---- attributes (fields): the state of ONE book ----
 private String title;
 private String author;
 private int pages;

 // ---- constructor: runs once, when the object is created ----
 public Book(String t, String a, int p) {
 title = t;
 author = a;
 pages = p;
 }

 // ---- methods: what a book can do or tell you ----
 public String getTitle() { return title; }
 public int getPages() { return pages; }

 public String describe() {
 return title + " by " + author + " (" + pages + " pages)";
 }
}
// Creating and using objects
Book b1 = new Book("Klara and the Sun", "Ishiguro", 303);
Book b2 = new Book("Norwegian Wood", "Murakami", 296);
Book b3 = b1; // b3 refers to the SAME object as b1

System.out.println(b1.describe()); // Klara and the Sun by Ishiguro (303 pages)
System.out.println(b2.getTitle()); // Norwegian Wood
System.out.println(b1 == b3); // true — same object
System.out.println(b1.equals(b2)); // false — different content (unless equals is overridden)
Traps — object identity
  • == on objects compares references, not content. Use .equals() for content, and remember that your own classes must override equals() for that to work — otherwise it inherits the reference comparison from Object.
  • Comparing strings: if (name == "Amara") may work by accident and then fail. Always if (name.equals("Amara")).
  • Passing an object to a method passes a copy of the reference. The method cannot make the caller's variable point somewhere else, but it can change the object that both references name.
How to use it — writing a class from a description
  1. Underline the nouns that have state → these are your classes (Book, Member, Loan).
  2. For each noun, list the facts you must remember about it → private fields with types.
  3. List what the noun must be asked or told → public methods. Questions become getters and boolean queries; commands become void methods.
  4. Write the constructor so that it sets every field and rejects invalid starting values.
  5. Ask: "what must always be true?" Add guards to any method that could break it.

B3.1c · Constructors

A constructor has the same name as the class and no return type — not even void. It runs when new allocates the object, and its job is to leave the object in a valid state. A constructor that leaves a field unset has failed.

public class Student {
 private String name;
 private int grade;
 private String house;

 // Parameterised constructor
 public Student(String name, int grade, String house) {
 this.name = name; // this.name = the field; name = the parameter
 this.grade = grade;
 this.house = house;
 }

 // Overloaded convenience constructor — delegates with this(...)
 public Student(String name, int grade) {
 this(name, grade, "Unassigned");
 }

 public String getName() { return name; }
}
Why it works Why the constructor must set every field, and what this really is

In Java a field you never assign still has a value — 0 for numbers, false for booleans, null for objects. That is the trap: an unassigned field does not cause an error, it causes a plausible wrong answer. A Student whose house is null will print fine and then crash three classes later when something calls house.length(). Java's default values exist because the language guarantees memory is zeroed before use; the cost is that "forgot to initialise" is invisible at the point of the mistake.

this is a reference to the object the method was called on. It is needed when a parameter shadows a field — writing name = name; assigns the parameter to itself and silently does nothing, one of the most common silent bugs in student Java. this(...) as the first line of a constructor calls a different constructor of the same class, which is how you avoid copy-pasting the assignment block.

Rule to remember: if your class has any constructor, Java no longer supplies the default no-argument one. Code that calls new Student() then fails to compile until you write it yourself.

Traps — constructors
  • Writing public void Book(...) — that is a method, not a constructor, and your fields stay at their default values.
  • Putting a return type on a constructor, or giving it a different name from the class.
  • this(...) or super(...) not on the first line — compile error.
  • Using this inside a static method: there is no object, so there is no this.

B3.1d · Encapsulation, access modifiers and getters/setters

Encapsulation means keeping an object's fields private and exposing a controlled public interface. It is the mechanism that makes the invariant argument above real.

ModifierVisible toUse it for
privateOnly code inside this classAll fields, by default. Helper methods nobody else should call.
protectedThis class, subclasses, and the same packageFields/methods subclasses legitimately need but the outside world does not.
(no modifier) package-privateEverything in the same packageRarely chosen deliberately. Avoid in exam answers.
publicEveryoneThe class's intended interface: constructors and the methods clients should call.

Here is the difference made concrete. First a class with no encapsulation:

public class BankAccount {
 public double balance; // anyone can write anything
}

BankAccount a = new BankAccount();
a.balance = -100000; // legal. catastrophic. no error, ever.

Now encapsulated, with the invariant balance ≥ 0 and owner never changes:

public class BankAccount {
 private double balance;
 private final String owner; // final: must be set in the constructor, then never reassigned

 public BankAccount(String owner, double opening) {
 if (opening < 0) {
 throw new IllegalArgumentException("opening balance cannot be negative");
 }
 this.owner = owner;
 this.balance = opening;
 }

 public double getBalance() { return balance; }
 public String getOwner() { return owner; } // getter only: no setter for owner

 public void deposit(double amount) {
 if (amount <= 0) { throw new IllegalArgumentException("deposit must be positive"); }
 balance = balance + amount;
 }

 public boolean withdraw(double amount) {
 if (amount <= 0 || amount > balance) { return false; } // refuse, do not go negative
 balance = balance - amount;
 return true;
 }
}
Why it works Getters and setters are not ceremony — they are the only place a rule can live

Look at what the encapsulated version buys you and count the places that can make the balance negative: zero. There is no setter for balance, deposit rejects non-positive amounts, and withdraw returns false rather than overdrawing. The invariant balance ≥ 0 is now enforced by the structure of the class rather than by the hope that callers behave.

The second, less obvious benefit: the setter is where the validation goes, and there is exactly one of them. If the rule changes tomorrow ("withdrawals over £500 need approval"), you edit one method. With a public field you would have to find every assignment in the program.

The third: a getter lets you change the storage without changing the interface. If balance later becomes pence held as a long to avoid floating-point error, getBalance() can divide by 100 on the way out and no caller changes.

When a getter/setter pair for every field is wrong. If you find yourself writing setBalance(), you have undone the encapsulation and just added typing. Generate only the accessors that a client genuinely needs; leave the rest off. An examiner spotting public void setBalance(double b) on a bank account will mark it as a misunderstanding, not as thoroughness.

Worked example 1 IB-style · 6 marks · encapsulation with a trace

Question. Consider the BankAccount class above. State the output, or the error, produced by each line of the following code.

BankAccount acc = new BankAccount("Mei", 100.0);
System.out.println(acc.getBalance()); // (i)
System.out.println(acc.withdraw(30.0)); // (ii)
System.out.println(acc.withdraw(90.0)); // (iii)
System.out.println(acc.getBalance()); // (iv)
acc.deposit(-5.0); // (v)
BankAccount bad = new BankAccount("Tom", -1.0); // (vi)
  1. (i) 100.0 — the constructor accepted a valid opening balance.
  2. (ii) true — 30 ≤ 100 so the withdrawal succeeds and the balance becomes 70.0.
  3. (iii) false — 90 > 70, so withdraw takes the refusal branch and returns without changing the balance. The balance is still 70.0.
  4. (iv) 70.0.
  5. (v) No output: an IllegalArgumentException is thrown because the amount is not positive. The program terminates unless the call is inside a try block.
  6. (vi) The exception is thrown in the constructor, so bad is never assigned — the object fails to be created at all.

Answer: (i) 100.0   (ii) true   (iii) false   (iv) 70.0   (v) IllegalArgumentException, deposit must be positive   (vi) IllegalArgumentException, opening balance cannot be negative.

Where the marks are

One mark per line. The two marks everyone drops are (iii) — candidates print false and then give the balance as -20.0, forgetting that the guard returns before the subtraction — and (v), where candidates write "prints nothing" instead of naming the exception and its message.

B3.2a · Inheritance HL only

Inheritance lets one class (subclass / child) acquire the fields and methods of another (superclass / parent) and then add or change what it needs. Java spells it extends. Test the relationship with the words is-a: a Circle is-a Shape. If "is-a" sounds wrong — a Circle is-a Point? no — inheritance is the wrong tool.

public class Shape {
 private String name;

 public Shape(String name) { this.name = name; }

 public String getName() { return name; }

 public double area() { return 0.0; } // placeholder, replaced below

 public String describe() { return name + " with area " + area(); }
}

public class Circle extends Shape {
 private double radius;

 public Circle(double radius) {
 super("Circle"); // MUST be the first statement
 this.radius = radius;
 }

 @Override // annotation: forces the compiler to check this really overrides
 public double area() { return Math.PI * radius * radius; }
}

public class Rectangle extends Shape {
 private double width;
 private double height;

 public Rectangle(double w, double h) {
 super("Rectangle");
 width = w;
 height = h;
 }

 @Override
 public double area() { return width * height; }
}
Why it works What super(...) is doing and why the first line rule exists

A subclass object contains the superclass part. Constructing a Circle therefore means: allocate the object, then run the Shape constructor to initialise the Shape part, then run the Circle constructor body to initialise the Circle part. Order matters — the subclass body may use inherited fields, so those fields must already exist. That is why super(...) must be the first statement.

If you omit it, Java silently inserts super(); — a call to a no-argument superclass constructor. If the superclass has no such constructor, you get the classic error constructor Shape in class Shape cannot be applied to given types, which looks mysterious until you know about the invisible insertion. Fix it by writing an explicit super(...).

The subtle and examined consequence: describe() is defined once, in Shape, but it calls area() — and at run time area() resolves to the subclass version. So new Circle(2.0).describe() prints the circle's area even though no circle code appears in describe(). A method in a parent can depend on behaviour supplied by a child that did not exist when the parent was written. This is the engine behind everything polymorphic on this page.

B3.2b · Polymorphism: overloading vs overriding HL only

Polymorphism means "many forms": one name, behaviour chosen for the situation. Java has two quite different mechanisms with the same word attached, and exam questions love the contrast.

OverloadingOverriding
What changesThe parameter list (type, count, order)Nothing — the signature is identical
WhereSame class (or a subclass)A subclass replaces a superclass method
Return typeMay differ freelyMust be the same or a subtype (covariant)
AccessMay differ freelyCannot be more restrictive (public → private is illegal)
DecidedCompile time — static / early bindingRun time — dynamic / late binding
Based onThe declared types of the argumentsThe actual class of the object
AnnotationNone@Override
 
// OVERLOADING — same name, different parameters, chosen by the compiler
public class Printer {
 public void show(String s) { System.out.println("String: " + s); }
 public void show(int n) { System.out.println("int: " + n); }
 public void show(String s, int n) { System.out.println("both: " + s + n); }
}

Printer p = new Printer();
p.show("A"); // String: A
p.show(7); // int: 7
p.show("A", 7); // both: A7

// The declared type decides, not the object
Object o = "hello";
p.show(o); // COMPILE ERROR unless a show(Object) overload exists
// OVERRIDING + dynamic dispatch
Shape[] shapes = { new Circle(2.0), new Rectangle(3.0, 4.0) };

double total = 0.0;
for (Shape s : shapes) {
 total = total + s.area(); // s is DECLARED Shape, but each object answers for itself
}
System.out.println(total); // 24.566370614359172

for (Shape s : shapes) {
 System.out.println(s.describe()); // describe() is Shape's; area() inside it is the subclass's
}
Why it works How the run time finds the right method, and why it is worth the cost

With overloading, the compiler can see the declared types of the arguments, so it can pick the method once and burn the choice into the compiled code. Nothing is left to decide later. The surprising consequence — and a real exam trap — is that if a variable is declared Shape, the compiler picks the show(Shape) overload even when the object actually held is a Circle.

With overriding the compiler genuinely cannot know: s is declared Shape, but at run time it may hold a Circle, a Rectangle, or a class nobody has written yet. So the compiler emits an instruction that looks up the object's actual class and jumps to that class's entry for area(). The cost is one extra indirection per call — negligible — and the payoff is large:

  1. for (Shape s : shapes) { total += s.area(); } contains no if and no type test. Adding a Triangle class requires no change to this loop, even though the loop was written before Triangle existed.
  2. The alternative — if (s instanceof Circle) {...} else if (s instanceof Rectangle) {...} — must be edited for every new shape, and forgetting one branch produces a wrong answer with no error.

When it is the wrong tool. If you find yourself writing if (x instanceof Circle) to decide what to do, you have defeated polymorphism; the behaviour you want probably belongs as an overridden method on the classes themselves. An occasional instanceof before a downcast is acceptable, but a chain of them is a design smell and examiners are trained to spot it.

Worked example 2 IB-style · 8 marks · predict output with inheritance, overriding and overloading

Question. State the exact output.

public class A {
 public String greet() { return "A"; }
 public String greet(String s){ return "A:" + s; }
 public String show() { return "showA-" + greet(); }
}
public class B extends A {
 @Override public String greet() { return "B"; }
 public String extra(){ return "extraB"; }
}

A x = new A();
A y = new B();
B z = new B();

System.out.println(x.greet()); // (i)
System.out.println(y.greet()); // (ii)
System.out.println(y.show()); // (iii)
System.out.println(y.greet("hi")); // (iv)
System.out.println(z.extra()); // (v)
System.out.println(y.extra()); // (vi)
  1. (i) A — x holds an A.
  2. (ii) B — y is declared A but holds a B, and overriding resolves on the actual class. This is the mark everyone gets wrong; if you said A you are thinking about overloading.
  3. (iii) showA-B — show() is not overridden, so A's version runs; when it calls greet() the call dispatches to B's override. Result: the parent's text with the child's behaviour.
  4. (iv) A:hi — greet(String) is overloaded, not overridden (B does not redefine it), and overload resolution is done at compile time from the declared type A, which does have that method.
  5. (v) extraB — z is declared B, so extra() is visible.
  6. (vi) Compile error. y is declared A, and A has no extra(). The object really is a B, but the compiler only knows the declared type. To call it you would need a cast: ((B) y).extra().

Answer: (i) A   (ii) B   (iii) showA-B   (iv) A:hi   (v) extraB   (vi) compile error — extra() is not a member of type A.

Where the marks are

Six outputs plus two explanation marks. The rule to write down before you start: the compiler looks at the declared type to decide what is legal; the run time looks at the actual class to decide what happens. (vi) is a legality question; (ii) and (iii) are behaviour questions.

B3.2c · Abstraction: abstract classes and interfaces HL only

Abstraction means working with the idea of a thing while ignoring the details you do not need right now. In Java it is implemented by two constructs that look similar and are chosen for different reasons.

public abstract class Shape {
 private String name;

 public Shape(String name) { this.name = name; }

 public String getName() { return name; }

 public abstract double area(); // no body: every subclass MUST supply one

 public String describe() { // concrete method that USES the abstract one
 return name + " with area " + area();
 }
}

Shape s = new Shape("blob"); // COMPILE ERROR — Shape is abstract; cannot be instantiated
public interface Payable {
 double calculatePay(); // implicitly public abstract
 String getPayeeName();
}

public class Teacher implements Payable {
 private String name; private double rate; private int hours;

 public Teacher(String name, double rate, int hours) {
 this.name = name; this.rate = rate; this.hours = hours;
 }
 @Override public double calculatePay() { return rate * hours; }
 @Override public String getPayeeName() { return name; }
}

public class SalariedEmployee implements Payable {
 private String name; private double annual;
 public SalariedEmployee(String name, double annual) { this.name = name; this.annual = annual; }
 @Override public double calculatePay() { return annual / 12.0; }
 @Override public String getPayeeName() { return name; }
}

// One loop, no type tests, works for any future Payable class
Payable[] staff = { new Teacher("Mei", 40.0, 20), new SalariedEmployee("Tom", 48000) };
double bill = 0;
for (Payable p : staff) { bill = bill + p.calculatePay(); }
System.out.println(bill); // 800.0 + 4000.0 = 4800.0
Why it works Why abstract classes are allowed to call methods that do not exist yet

An abstract method has a signature and no body, so new Shape(...) is forbidden: the JVM would have an object whose area() has nothing to run. But inside Shape, the call area() is perfectly safe, because Shape can only ever be the superclass part of some concrete subclass, and the language guarantees that subclass implemented area(). The compiler checks the promise at the subclass; the run time keeps it with dynamic dispatch.

The payoff is a specific and powerful pattern: the superclass owns the algorithm, the subclass fills in one step. In the library example below, renew() is written once and complete, yet it calls the abstract maxRenewals() — so books get two renewals and DVDs get one without a single duplicated line or a single if.

Why interfaces exist: the diamond problem. Suppose Printer and Scanner both extend Device and both override start(). A class MultiFunction extends Printer, Scanner now has two competing implementations of start() and, worse, two copies of Device's fields. Which one runs? Whose serialNumber is it? Languages that allow this must invent complicated rules. Java's answer is blunt and effective: inherit implementation from at most one class; implement as many interfaces as you like. A classic interface has no state and no body, so there is nothing to be ambiguous about — implementing two interfaces that both declare start() is fine because there is only one implementation: yours.

When it is the wrong tool. An abstract class with no concrete methods and no fields is really an interface; use the interface. An interface you are tempted to give lots of default methods is turning back into a class.

Choose…WhenBecause
Abstract classThe classes share state and code, and are genuinely the same kind of thing (is-a)It can hold fields and give every subclass working methods for free. One superclass only.
InterfaceUnrelated classes share a capability, not an identity (can-do)A Teacher and an Invoice are nothing alike but both can be Payable. A class implements many.
BothCommon in real designsclass Book extends LibraryItem implements Reservable — identity from the parent, capability from the interface.
Traps — abstract vs interface
  • Interface methods are public abstract whether you write it or not. Declaring one private is a compile error. Implementing it with weaker access (package-private) is also an error.
  • A class that implements an interface must implement every method of that interface, or it must itself be declared abstract.
  • implements for interfaces, extends for classes. An interface can extend another interface (never implement).
  • Constructors cannot be abstract, and static and abstract cannot appear on the same method — there would be no object to dispatch on.

UML class diagrams

A UML class diagram is the standard way to show a design without writing the code. Paper 2 will both give you one and ask you for one. A class box has three compartments.

The four relationship arrows are what most candidates muddle. The difference between the middle two is not syntax but lifetime.

RelationshipArrowUML meaningThe test to apply
AssociationPlain line, optional verb and multiplicitiesObjects know about each other; neither owns the other"They interact but live independent lives."
AggregationHollow diamond at the whole endWeak has-a: the whole has parts, the parts outlive it"Delete the whole — does the part still make sense? Yes."
CompositionFilled diamond at the whole endStrong has-a: parts are created and destroyed with the whole"Delete the whole — does the part still make sense? No."
GeneralisationHollow triangle pointing at the parentis-a; inheritance"A Circle is a Shape." If it reads wrong, do not inherit.
Why it works Why aggregation and composition look identical in code but are not the same decision

Both are written the same way — a field holding a collection of references:

// Aggregation: the Student objects were created elsewhere and are passed in
public class School {
 private ArrayList<Student> roll = new ArrayList<Student>();
 public void enrol(Student s) { roll.add(s); } // the School did NOT make s
}

// Composition: the Order creates its own OrderLine objects
public class Order {
 private ArrayList<OrderLine> lines = new ArrayList<OrderLine>();
 public void addLine(String item, int qty) {
 lines.add(new OrderLine(item, qty)); // the Order MAKES the line
 }
}

The difference is lifetime and ownership, and it is decided by the answer to one question: if the whole is deleted, does the part still mean anything? A Student who leaves the school is still a person with a name and a record. An OrderLine without its Order is a quantity of something for nobody — it is meaningless. So School→Student is aggregation and Order→OrderLine is composition.

Why bother distinguishing them? Because the answer tells you who is allowed to create and destroy the part, which in turn determines where the code goes. In composition the parent's constructor and destructor own the part's life, so no other class can leak a half-built part into the system. In aggregation the part arrives from outside and must be treated as shared — you must not modify it in ways its other owners would not expect.

In an exam: justify with the deletion test, not with a definition. "An OrderLine cannot exist independently of its Order, so the relationship is composition" earns the mark; "composition is a strong has-a relationship" does not.

B3.2d · A full worked design: the school library HL only

The brief

A school library tracks its items. Every item has a unique ID, a title and a publication year. Books also have an author and a page count; DVDs also have a director and a running time in minutes. Every item may be borrowed for up to 21 days. A book may be renewed twice, a DVD once. The librarian wants a list of all currently overdue items and a printable catalogue.

Step 1 — the classes. Nouns with state: LibraryItem (shared facts), Book and Dvd (specific facts), Library (the collection). Because Book is-a LibraryItem and the differences are only in some fields and one rule, inheritance fits. LibraryItem should be abstract: you never lend a generic item, and there is no sensible default for maxRenewals().

Step 3 — the code.

public abstract class LibraryItem {
 private String id;
 private String title;
 private int year;
 private boolean onLoan;
 private int daysOnLoan;
 private int renewalsUsed;

 public LibraryItem(String id, String title, int year) {
 this.id = id; this.title = title; this.year = year;
 this.onLoan = false; this.daysOnLoan = 0; this.renewalsUsed = 0;
 }

 public String getId() { return id; }
 public String getTitle() { return title; }
 public boolean isOnLoan() { return onLoan; }

 // ---- the two things only a subclass can know ----
 public abstract int maxRenewals();
 public abstract String describe();

 // ---- behaviour written ONCE, for every kind of item ----
 public void borrow() {
 if (onLoan) { throw new IllegalStateException(title + " is already on loan"); }
 onLoan = true;
 daysOnLoan = 0;
 renewalsUsed = 0;
 }

 public void returnItem() {
 onLoan = false;
 daysOnLoan = 0;
 }

 public boolean renew() { // calls the abstract method
 if (!onLoan) { return false; }
 if (renewalsUsed >= maxRenewals()) { return false; }
 renewalsUsed = renewalsUsed + 1;
 daysOnLoan = 0;
 return true;
 }

 public void addDay() { // the Library calls this once per day
 if (onLoan) { daysOnLoan = daysOnLoan + 1; }
 }

 public boolean isOverdue() { return onLoan && daysOnLoan > 21; }
}
public class Book extends LibraryItem {

 private int pages;

 public Book(String id, String title, int year, String author, int pages) {
 super(id, title, year);
 this.author = author;
 this.pages = pages;
 }

 @Override public int maxRenewals() { return 2; }
 @Override public String describe() {
 return "Book: " + getTitle() + " by " + author + " (" + pages + " pages)";
 }
}

import java.util.ArrayList;

public class Library {
 private ArrayList<LibraryItem> items;

 public Library() { items = new ArrayList<LibraryItem>(); }

 public void addItem(LibraryItem item) { items.add(item); }

 public ArrayList<LibraryItem> listOverdue() {
 ArrayList<LibraryItem> result = new ArrayList<LibraryItem>();
 for (LibraryItem it : items) {
 if (it.isOverdue()) { result.add(it); }
 }
 return result;
 }

 String out = "";
 for (LibraryItem it : items) {
 out = out + it.describe() + "\n"; // dynamic dispatch picks Book.describe or Dvd.describe

 }

 public void nextDay() {

 }
}
Worked example 3 IB-style · 8 marks · trace the design above

Question. State the output of the following, and state the value returned by listOverdue().size() at the end.

Library lib = new Library();
Book b = new Book("B01", "Klara and the Sun", 2021, "Ishiguro", 303);
Dvd d = new Dvd ("D01", "Arrival", 2016, "Villeneuve", 116);
lib.addItem(b);
lib.addItem(d);

b.borrow();
d.borrow();

System.out.println(b.renew()); // (i)
System.out.println(b.renew()); // (ii)
System.out.println(b.renew()); // (iii)
System.out.println(d.renew()); // (iv)
System.out.println(d.renew()); // (v)

for (int day = 1; day <= 22; day = day + 1) { lib.nextDay(); }
System.out.println(b.isOverdue()); // (vi)
System.out.println(lib.listOverdue().size()); // (vii)
System.out.print(lib.printCatalogue()); // (viii)
  1. (i) true. The book is on loan, renewalsUsed is 0 and maxRenewals() for a Book is 2, so 0 ≥ 2 is false. The renewal succeeds: renewalsUsed becomes 1 and daysOnLoan resets to 0.
  2. (ii) true. 1 ≥ 2 is still false; renewalsUsed becomes 2.
  3. (iii) false. Now 2 ≥ 2, so the book has used its allowance. Note the ordering: the check happens before the increment, so a book gets exactly two renewals, not three.
  4. (iv) true. The DVD's maxRenewals() returns 1, so the first renewal passes.
  5. (v) false. 1 ≥ 1 — the DVD has used its single renewal. The same method renew() produced different limits for the two objects without an if anywhere.
  6. (vi) true. Both items ran 22 days. After the final renewal daysOnLoan was reset to 0 and then incremented once per day to 22, and 22 > 21.
  7. (vii) 2 — both the book and the DVD are overdue, because both were borrowed at the start and both had their counter reset on the last successful renewal.
  8. (viii) 
    Book: Klara and the Sun by Ishiguro (303 pages)
DVD: Arrival, dir. Villeneuve (116 min)
    One loop, one line of code, two different describe() implementations — dynamic dispatch.

Answer: (i) true (ii) true (iii) false (iv) true (v) false (vi) true (vii) 2 (viii) the two lines shown above.

Where the marks are

One mark per output plus two for explaining why (iii) and (v) differ. The explanation mark wants the words overriding, abstract method and dynamic dispatch, in that chain: renew() is inherited and concrete; it calls the abstract maxRenewals(); at run time the call is dispatched to Book.maxRenewals() or Dvd.maxRenewals() depending on the actual object. Candidates who write "because the book class says 2" usually get one of the two.

Why it works What duck typing gains and what it costs

Java checks at compile time that a Circle really is a Shape and really implemented every abstract method. Python checks nothing until the line runs; if .area() is missing you get an AttributeError at the moment of the call, possibly weeks later in production. That is a real cost, and it is why Python projects lean heavily on tests.

The gain is flexibility and far less code. A function that needs "something with an area()" needs no interface declared, no import, and no shared ancestor — which is why Python is pleasant for small programs and why large Python codebases add type hints and linters to recover some of Java's checking.

The honest contrast for an exam answer: Java's private and abstract are enforced guarantees; Python's equivalent conventions are social ones. Neither is automatically better — a small script does not need the ceremony, a system handling money probably does. Say which you would choose for the scenario in front of you and why.

Exam technique for OOP questions

How to use it
  1. Read any given code or diagram before the question. Use the exact class, method and attribute names from the paper. Inventing getBalance() when the paper defined balance() throws away marks.
  2. "State the output": find every point where the declared type and the actual class differ. That is where the question lives. Everything else is arithmetic.
  3. "Construct a class diagram": three compartments per box; visibility markers +/-/#; attributes as name : type; methods as method(p : type) : returnType; relationship arrows with multiplicities; italic or <<abstract>> for abstract classes and methods.
  4. "Explain the use of X": name the mechanism, then name the consequence for this scenario. "Encapsulation means the fields are private, so the balance can only be changed by deposit() and withdraw(), which validate their arguments, so the balance can never become negative."
  5. "Extend the design": write the new class only. Show extends / implements, the constructor calling super(...) correctly, and every abstract or interface method implemented with @Override.
  6. "Justify inheritance over X": use the is-a test and the change-locality argument ("adding a new type requires one new class, not edits to every method").
The eight mistakes that cost the most marks
  • Confusing a class with an object — "the class b1" instead of "the object b1 of class Book".
  • Giving a constructor a return type, or naming it differently from the class.
  • Writing name = name; without this..
  • Using == to compare strings or object content.
  • Saying the declared type wins for an overridden method (it wins for overloads and for what is legal; the actual class wins for what runs).
  • Putting super(...) or this(...) somewhere other than line one.
  • Generating a setter for every field and calling it encapsulation.
  • Drawing the generalisation arrow pointing at the subclass. The triangle points at the parent.

Practice

  1. A school records modules, each with a code, a title and a list of enrolled students. Identify: one class, two attributes, and one method that is not a simple getter.

    Show answer

    Class: Module. Attributes: code (String), title (String) — or the ArrayList<Student> enrolled list.

    Method that is not a getter: enrol(Student s), which adds a student and should check they are not already enrolled and that the module is not full. Other valid answers: averageScore(), isFull().

    Why examiners reject getters here: a getter transfers data out and decides nothing. The question is testing whether you can see behaviour that belongs on the class — something the class must do, having applied a rule.

  2. Write a complete Java class Member with private fields name (String) and points (int). Include a constructor, getters, and a method addPoints(int n) that ignores non-positive values. Points must never become negative.

    Show answer
    public class Member {
 private String name;
 private int points;

 public Member(String name, int openingPoints) {
 if (openingPoints < 0) { throw new IllegalArgumentException("points cannot be negative"); }
 this.name = name;
 this.points = openingPoints;
 }

 public String getName() { return name; }
 public int getPoints() { return points; }

 public void addPoints(int n) {
 if (n <= 0) { return; } // ignore: non-positive adds nothing
 points = points + n; // points can only rise, so it stays non-negative
 }
}

    Marks: private fields (1), constructor that assigns both and validates (2), two getters (1), addPoints with the guard (2). The common error is an else that prints an error message instead of silently ignoring — read the wording: "ignores".

  3. Explain, with reference to a specific example, what is meant by encapsulation and why it is used.

    Show answer

    Encapsulation is keeping the fields of an object private and allowing access only through public methods. In a BankAccount class, balance is private so no other class can write to it directly.

    Why: the class has an invariant — balance ≥ 0. Because the only way the balance changes is through deposit() and withdraw(), and withdraw() refuses amounts larger than the balance, the invariant cannot be broken by calling code. If the balance were public, any class could set it to a negative value and the error would surface far from the place that caused it.

    A second reason: if the storage changes (for example to pence in a long), only the methods change; callers are unaffected.

    Marks: definition (1) + a concrete private-field example (1) + the consequence for the invariant (2). Candidates who only write "it hides the data" usually score 1 of 4.

  4. State the output.

    class Animal { public String speak() { return "..."; }
 public String feed() { return "eats " + speak(); } }
class Dog extends Animal { @Override public String speak() { return "woof"; } }
class Cat extends Animal { @Override public String speak() { return "miaow"; } }

Animal[] pets = { new Dog(), new Cat(), new Animal() };
for (Animal a : pets) { System.out.println(a.feed()); }
    Show answer
    eats woof
eats miaow
eats ...

    feed() is defined once in Animal and is not overridden. Each time the loop runs, feed() calls speak(), and that call is dispatched to the actual class of the object — Dog, Cat, Animal — even though the array is declared Animal[]. This is dynamic dispatch.

  5. Give two differences between overloading and overriding.

    Show answer

    Any two of:

    • Overloading uses a different parameter list; overriding keeps the signature identical.
    • Overloading happens within one class (or a subclass); overriding requires a subclass and a superclass.
    • Overloading is resolved at compile time from the declared argument types; overriding is resolved at run time from the actual class of the object.
    • An overridden method must not reduce visibility; an overload may use any visibility.

    Do not write "overriding is when there are two methods with the same name" — that is overloading in the parent and child, and it is wrong.

  6. A program has classes Car, Bicycle and Boat. Each needs to be taxable: the system must be able to call calculateTax() on any of them. Should this use an abstract superclass or an interface? Justify.

    Show answer

    An interface, for example public interface Taxable { double calculateTax(); }, with class Car implements Taxable, and so on.

    Justification: the relationship is a shared capability (can-be-taxed), not a shared identity. A car, a bicycle and a boat have almost no common state and no common behaviour beyond this one method, so a superclass would carry no reusable code and would force an artificial is-a relationship. Using an interface also leaves each class free to extend a class of its own.

    The scoring sentence: "they are otherwise unrelated, so inheritance would imply an is-a relationship that does not exist". Candidates who only say "interfaces allow multiple inheritance" get one mark — that is a property of interfaces, not a reason to choose one here.

  7. The diagram shows Customer 1 —— 1..* Order and Order ◆—— 1..* OrderLine. Name the two relationships and explain the difference in terms of what happens when an Order is deleted.

    Show answer

    Customer → Order is aggregation (or a plain association). Order → OrderLine is composition.

    When an Order is deleted, its OrderLine objects are deleted with it, because a line has no meaning without the order it belongs to — that is what the filled diamond records. The Customer, by contrast, continues to exist; deleting an order does not delete the person.

    Marks: naming both (2) + the deletion test applied to both (2).

  8. A system has abstract class Employee with abstract double monthlyPay(), and subclasses SalesEmployee (salary plus commission) and HourlyEmployee (rate times hours). Write HourlyEmployee in full and explain why Employee must be abstract.

    Show answer
    public class HourlyEmployee extends Employee {
 private double rate;
 private int hours;

 public HourlyEmployee(String name, double rate, int hours) {
 super(name);
 this.rate = rate;
 this.hours = hours;
 }

 @Override
 public double monthlyPay() {
 return rate * hours;
 }
}

    Employee must be abstract because monthlyPay() has no sensible general implementation — there is no such thing as the pay of "an employee" until you know which kind. Declaring it abstract (a) prevents new Employee(...), which would be an object with a method that has nothing to run, and (b) forces every subclass to provide an implementation, so any code holding an Employee reference can safely call monthlyPay().

    Note that a concrete method in Employee, such as printPayslip(), can call monthlyPay() even though the body has not been written — dynamic dispatch fills it in at run time.

  9. Design question. A cinema sells tickets for films shown in screens at set times. Identify three classes, one inheritance relationship (or explain why there is none), and one composition relationship.

    Show answer

    Classes: Film (title, certificate, duration), Screening (film, screen, start time, seats remaining), Booking (screening, customer, seats).

    Composition: Screening ◆—— Seat (or a collection of seats). A seat row belongs to one screening — if the screening is cancelled, its seating grid goes with it. Equally valid: Booking ◆—— Ticket, since a ticket cannot exist without its booking.

    Inheritance: there is a possible one — StandardSeat and PremiumSeat extending Seat, differing in price. A strong answer points out that this is only worth doing if the subclasses differ in behaviour, not just in a price number; if the only difference is a field, one Seat class with a price attribute is the better design.

    The mark that separates a 6 from an 8: recognising that inheritance should not be used just because you can draw it. Justify with "the subclasses would differ only in a field value, so a single class with an attribute is simpler and avoids extra classes".
