B4 · Abstract data types HL only

An abstract data type is a promise. A stack promises "the last thing you put in is the first thing you get out" and it does not say how. That separation — what it does versus how it does it — is the most important idea in this topic, and it is why seven structures that look nothing alike in memory can be compared at all. This page covers every ADT on the HL syllabus: arrays and records, stacks, queues, circular queues, linked lists, binary trees and binary search trees, sets, and hash tables. For each one you get the logical behaviour, a real implementation, the reason the implementation works, and a hand-trace of the kind Paper 2 asks for.

B4.1a · What an abstract data type actually is

A data type is a set of values plus the operations on them: an integer is the values …, −1, 0, 1, … together with +, −, MOD, comparison, and so on. An abstract data type (ADT) goes one step further: it specifies the operations and the behaviour they must have, and says nothing about how the values are stored.

The logical view (the ADT)

Stack: a collection where insertion and removal happen at one end only, called the top.

  • push(item) — add to the top
  • pop() — remove and return the top
  • peek() — return the top without removing it
  • isEmpty() — true when there is nothing in it

The physical view (the implementation)

The stack could be:

  • an array with an integer top index
  • a singly linked list where the head is the top
  • two arrays, or a resizable array, or something exotic

All of them satisfy the promise. The user of the stack cannot tell and does not care.

Why it works Why separating "what" from "how" is worth an entire topic
  1. You can change the implementation without touching the users. If profiling shows your array-based stack keeps hitting its capacity limit, you swap in a linked-list version. Every line of code that called push() and pop() is untouched, because those names and their behaviour never changed.
  2. You can reason about correctness once. "A stack reverses the order of its contents" is proved once, at the ADT level, and then holds for every implementation. If you reasoned about the array version, you would have to redo the work for the linked-list version.
  3. You can compare structures fairly. Only because both a linked list and a hash table can be described as "a collection with insert, find and delete" can you ask which is faster and get a meaningful answer. The comparison table at the end of this page exists because of this abstraction.
  4. It is the same idea as encapsulation. In B3 you made fields private and exposed methods. An ADT is that principle applied to an entire data structure: the array, the node pointers and the indices are all private; push/pop are the public interface.

When it is the wrong tool. Abstraction costs an indirection, and sometimes you genuinely need to reach inside. Numerically heavy code that iterates over millions of elements may need the raw contiguous array, and pretending otherwise costs real performance. Say so in an evaluation: an ADT is a trade-off between conceptual cleanliness and direct access, not a free win.

B4.1b · Static structures: arrays and records

Before the dynamic structures, the two static ones — and the reasons they are not enough.

One- and two-dimensional arrays

An array stores a fixed number of elements of the same type in contiguous memory, addressed by an integer index. "Fixed" and "contiguous" are not incidental details; they explain every advantage and every weakness.

Why it works Why indexing an array is O(1) — and what that costs you

Suppose the array starts at memory address \(B\) and each element occupies \(S\) bytes. Then element \(i\) lives at

\[ \text{address}(i) = B + i \cdot S \]

One multiplication, one addition, one memory read. The work does not grow with \(i\), and it does not grow with the length of the array — so access by index is \(O(1)\), which is why arrays are the default structure and why random access is described as "free".

Now the bill for contiguous storage:

  • Insertion into the middle is \(O(n)\). To put a value at index \(k\) you must shift every element from \(k\) onwards one place right, or the contiguity breaks. With 1,000,000 elements that is 1,000,000 moves.
  • The size must be decided in advance. Over-allocate and you waste memory; under-allocate and you overflow. A "dynamic array" (Python's list, Java's ArrayList) hides this by allocating a bigger block and copying everything across when it runs out — which is usually \(O(1)\) amortised but occasionally \(O(n)\).
  • Deletion leaves a hole unless you shift, which is another \(O(n)\).

When it is the wrong tool. Any workload with frequent insertions or deletions at arbitrary positions, or where you cannot predict the maximum size. That is the gap linked lists exist to fill.

A two-dimensional array is an array of arrays — a grid. It is stored row-major: row 0 in full, then row 1, and so on, so grid[r][c] is at \(B + (r \cdot \text{columns} + c) \cdot S\). This matters twice over: nested loops should iterate the outer index over rows and the inner over columns so that access walks memory in order (cache-friendly), and a 2-D array is really a 1-D array with arithmetic on the index.

Records

A record (a struct in C, a class with no methods in Java, a dataclass or NamedTuple in Python) groups a fixed set of named fields that may have different types.

class StudentRecord: # a record: heterogeneous, named, fixed
 def __init__(self, sid, name, year, avg):
 self.sid = sid # str
 self.name = name # str
 self.year = year # int
 self.avg = avg # float

recs = []
recs.append(StudentRecord("S001", "Amara", 12, 6.4))
recs.append(StudentRecord("S002", "Bo", 12, 5.1))

print(recs[1].name) # Bo — array index then field name
Three views of the same thing
  • An array is homogeneous (all one type), accessed by position.
  • A record is heterogeneous (mixed types), accessed by name.
  • An array of records is a database table: the record is the row, the field is the column, and the array is the table. See A3.
  • A record with methods attached is an object. See B3.

B4.1c · Stacks

A stack is a LIFO structure — last in, first out. Only the top is accessible. Think of a pile of plates: you add to the top and you take from the top; reaching the bottom plate means removing every plate above it.

OperationBehaviourTimeFailure
push(item)Place item on top\(O(1)\)Overflow — the stack is full
pop()Remove and return the top\(O(1)\)Underflow — the stack is empty
peek() / top()Return the top without removing it\(O(1)\)Underflow
isEmpty()True if nothing is stored\(O(1)\)—
isFull()True if capacity is reached (array version)\(O(1)\)—
 
class Stack:
 def __init__(self, capacity):
 self.items = [None] * capacity # fixed-size array
 self.capacity = capacity
 self.top = -1 # -1 means empty

 def isEmpty(self):
 return self.top == -1

 def isFull(self):
 return self.top == self.capacity - 1

 def push(self, item):
 if self.isFull():
 raise OverflowError("stack overflow")
 self.top = self.top + 1 # move up FIRST ...
 self.items[self.top] = item # ... then write

 def pop(self):
 if self.isEmpty():
 raise IndexError("stack underflow")
 item = self.items[self.top]
 self.top = self.top - 1 # the slot is now garbage, and that is fine
 return item

 def peek(self):
 if self.isEmpty():
 raise IndexError("stack underflow")
 return self.items[self.top]
Why it works Why popping only decrements top instead of clearing the slot

After pop(), items[top+1] still physically holds the old value. It does not matter, because top is the only thing that defines where the stack ends. Anything at an index greater than top is outside the stack by definition, and the next push will overwrite it before any code can read it through the interface.

That is the ADT boundary doing real work: the logical stack is "the elements at indices \(0 \ldots \text{top}\)" and the leftover bytes above are not part of it. Clearing them would cost a write and buy nothing. (The one exception is security-sensitive code, where you may deliberately overwrite memory that held a password — a good honest aside in an evaluation answer.)

Note also that push increments before writing, because top = -1 must map to index 0 on the first push. Getting this backwards produces an off-by-one that either wastes slot 0 or writes to index −1, which in Python silently hits the last element — a genuinely nasty bug.

How to use it — where stacks belong
  • The call stack. Every function call pushes an activation record; every return pops one. This is why infinite recursion raises a stack-overflow error rather than hanging forever (see B2).
  • Undo. An editor pushes the previous state on every edit; Ctrl+Z pops it. Redo is a second stack.
  • Backtracking. A maze solver pushes each cell it enters; when it hits a dead end it pops back to the last junction.
  • Balanced-bracket checking and expression evaluation — worked below.
  • Browser history, DFS on a graph, parsing.

When it is the wrong tool: anything where the oldest item must be handled first (that is a queue) or where you must reach an item in the middle (that is an array or a tree).

B4.1d · Queues and circular queues

A queue is FIFO — first in, first out. Items enter at the rear and leave from the front. It models any waiting line, and it is the structure behind printer spoolers, keyboard buffers, breadth-first search, and every scheduling system that must be fair.

OperationBehaviourTimeFailure
enqueue(item)Add at the rear\(O(1)\)Overflow — the queue is full
dequeue()Remove and return the front\(O(1)\)Underflow — the queue is empty
peek() / front()Return the front without removing it\(O(1)\)Underflow
isEmpty()True when nothing is stored\(O(1)\)—

The problem with the naive array queue

The obvious implementation keeps an array, a front index and a rear index. Enqueue writes at rear and increments it; dequeue reads from front and increments it. Both indices only ever increase.

Why it works Why the naive queue reports "full" while four fifths of it is empty

Start with an array of size 5, front = 0, rear = 0. Enqueue A, B, C, D — rear is now 4. Dequeue twice — front is now 2. The array holds [_, _, C, D, _] with front = 2 and rear = 4: only two items, but the next enqueue writes at index 4 and then rear becomes 5, which is off the end.

The structure is full in the only sense the code can detect — rear has reached the end of the array — while slots 0 and 1 sit empty and unreachable. Every dequeue permanently retires a slot. After \(n\) dequeues the queue is unusable no matter how few items it holds.

Two fixes exist, and the second is the one on the syllabus:

  1. Shift everything left after each dequeue. Correct, but every dequeue becomes \(O(n)\), which destroys the main reason to use a queue.
  2. Let the indices wrap around. Treat the array as a ring: after index \(n-1\) comes index \(0\). Both operations stay \(O(1)\) and every slot is reusable. This is the circular queue.

The circular queue

The array stays exactly where it is — a normal, linear, contiguous block of memory. What becomes circular is the arithmetic on the indices:

\[ \text{rear} = (\text{rear} + 1) \bmod n \qquad\qquad \text{front} = (\text{front} + 1) \bmod n \]

where \(n\) is the array length. Conventions on this page (an exam will state its own — apply whatever you are given):

The convention used here
  • front = index of the first (oldest) item
  • rear = index of the next free slot
  • count = number of items currently stored
  • Empty when count == 0; full when count == n
class CircularQueue:
 def __init__(self, n):
 self.items = [None] * n
 self.n = n
 self.front = 0
 self.rear = 0
 self.count = 0

 def isEmpty(self):
 return self.count == 0

 def isFull(self):
 return self.count == self.n

 def enqueue(self, item):
 if self.isFull():
 raise OverflowError("queue overflow")
 self.items[self.rear] = item
 self.rear = (self.rear + 1) % self.n # wraps: n-1 -> 0
 self.count = self.count + 1

 def dequeue(self):
 if self.isEmpty():
 raise IndexError("queue underflow")
 item = self.items[self.front]
 self.front = (self.front + 1) % self.n # wraps too
 self.count = self.count - 1
 return item

 def peek(self):
 if self.isEmpty():
 raise IndexError("queue underflow")
 return self.items[self.front]
Why it works Why front == rear is ambiguous, and the two ways out

With the convention "front = first item, rear = next free slot", an empty queue has front == rear (nothing stored, rear has nowhere to advance to). A full queue also has front == rear (every slot taken, rear has wrapped all the way round to front). Two different states, one identical picture. This is the single hardest idea in the topic and it is why you cannot test for fullness with front == rear.

Solution A — keep a count (used above). Empty is count == 0, full is count == n. All \(n\) slots are usable; the cost is one extra integer and one extra update per operation. This is the easiest version to trace and to write under pressure.

Solution B — sacrifice one slot. Declare the queue full when \((\text{rear} + 1) \bmod n == \text{front}\). The queue then holds at most \(n-1\) items, and the number stored is \((\text{rear} - \text{front} + n) \bmod n\). No extra variable, one wasted slot. Many textbooks use this, so you must be able to read it.

Which is better? A count is one integer; a wasted slot is \(S\) bytes, and for a queue of large records \(S\) is far bigger than an integer. So the count version is usually the better engineering choice — but it only works if every operation maintains the count correctly, which is one more thing to get wrong. State the trade-off and pick one; do not sit on the fence in an exam answer.

Why % and not /: % is the remainder operator (IB pseudocode: mod), and it maps any non-negative integer into \(0 \ldots n-1\). Rearranging, the structure walks \(0, 1, 2, \ldots, n-1, 0, 1, \ldots\) forever without ever leaving the array bounds.

Where the marks are

One mark per correct row (up to 6), one for the three returned values in order, one for the final state, one for naming overflow on the last operation. The two rows everyone botches are 7 (forgetting the wrap, and writing rear = 5) and 12 (writing that the queue "stores I somewhere" instead of stating that the operation is refused and the state is unchanged). A linear queue would have overflowed at step 7 — if your trace does not show that difference, you have not demonstrated the point of the structure.

B4.1e · Linked lists

A linked list stores its elements in nodes scattered anywhere in memory. Each node holds the data and a pointer (next) to the following node. The list is reached through a single pointer, head; the last node's next is null.

class Node:
 def __init__(self, data):
 self.data = data
 self.next = None

class LinkedList:
 def __init__(self):
 self.head = None

 def isEmpty(self):
 return self.head is None

 def insertAtHead(self, data):
 n = Node(data)
 n.next = self.head # 1. new node points to the old first node
 self.head = n # 2. head now points to the new node

 def insertAfter(self, target, data):
 n = Node(data)
 n.next = target.next # 1. FIRST: link the new node to what followed
 target.next = n # 2. THEN: link the predecessor to the new node

 def deleteAfter(self, target):
 if target.next is None:
 return
 target.next = target.next.next # bypass the node; it is now unreachable

 def search(self, value):
 cur = self.head
 while cur is not None:
 if cur.data == value:
 return True
 cur = cur.next
 return False

 def traverse(self):
 cur = self.head
 while cur is not None:
 print(cur.data)
 cur = cur.next
Why it works Why the order of the two pointer assignments matters, and why deletion needs the predecessor

Insertion after a node target is two assignments. Do them in the wrong order and the rest of the list is lost:

target.next = n # WRONG FIRST STEP: the only pointer to the rest of the
 # list is overwritten. Everything after target is now
 # unreachable — leaked, and silently gone.
n.next = target.next # now reads n.next and assigns it to n.next: a no-op.

The correct order reads the old chain before breaking it. The general rule for any pointer surgery: always set the new node's outgoing pointer first, then rewire the existing node. Draw the arrows on paper for every linked-list question; nobody traces these reliably in their head.

Deletion in a singly linked list is \(O(n)\) even though the deletion itself is one assignment, because the assignment needs a pointer to the predecessor, and finding the predecessor requires walking from the head. Given only a pointer to the node you want to delete, you cannot reach backwards. That single fact motivates the doubly linked list.

A doubly linked list adds a prev pointer, so a node can be deleted in \(O(1)\) once found: node.prev.next = node.next; node.next.prev = node.prev (with null checks at both ends). The cost is one extra pointer per node and twice as many assignments on every insert and delete.

A circular linked list makes the last node's next point back to the head, so "have I gone all the way round?" is a comparison against head rather than against null. It is the natural structure for round-robin scheduling, where a process list is cycled forever. The danger: every traversal loop must have a guaranteed exit, or it spins indefinitely.

Worked example 3 IB-style · 6 marks · pointer manipulation on a linked list

Question. A singly linked list currently holds 12 → 99 → 7 → 41 → null, with head pointing at the node holding 12.

(a) Write the statements needed to insert a new node holding 25 between the nodes holding 7 and 41, assuming you already have a pointer p to the node holding 7.

(b) Write the statements to delete the node holding 99, assuming you have a pointer q to the node holding 12.

(c) State the resulting list.

  1. (a) The new node sits between p (7) and p.next (41). Link forwards first, then rewire:
    n = Node(25)
    n.next = p.next   // n → 41
    p.next = n       // 7 → 25
  2. (b) The node to delete is q.next. Bypass it:
    q.next = q.next.next   // 12 → 7, skipping 99
  3. (c) 12 → 7 → 25 → 41 → null.

Answer: (a) n.next = p.next; p.next = n (b) q.next = q.next.next (c) 12 → 7 → 25 → 41 → null.

Where the marks are

Two marks each for (a) and (b), and both marks in (a) depend on the order: if you write p.next = n first you have destroyed the only route to the node holding 41, and the pair scores zero even though both lines appear. One mark for (c). A common extra error in (b) is q.next.next = q.next, which points 7 back at 99 and creates an infinite loop.

B4.1f · Binary trees and binary search trees

A binary tree is a set of nodes where each node has at most two children, called the left and right child.

Root

The single node with no parent. There is exactly one.

Leaf

A node with no children.

Parent / child

A node directly above / below another, joined by an edge.

Subtree

Any node together with all of its descendants. A subtree is itself a tree — this is what makes recursion natural.

Depth

Number of edges from the root to this node. The root has depth 0.

Height

Number of edges on the longest path from this node down to a leaf. A leaf has height 0.

The binary search tree ordering property

A binary search tree (BST) is a binary tree with one extra rule:

The BST invariant

For every node: every value in its left subtree is less than the node's value, and every value in its right subtree is greater than it. (Decide once what to do with duplicates — "go right" is the usual choice — and apply it consistently.)

Why it works Why a BST searches in \(O(\log n)\) — and why it can collapse to \(O(n)\)

Searching is a sequence of comparisons. At the root you compare and then move left or right. Because of the invariant, that single comparison does not just eliminate the root — it eliminates the entire subtree on the other side. Move left from the root and you have discarded every value greater than the root, which could be half the tree.

A tree of height \(h\) therefore needs at most \(h+1\) comparisons. A tree with \(n\) nodes of height \(h\) can hold at most \(2^{h+1}-1\) nodes, so for a bushy tree \(n \approx 2^{h+1}\) and

\[ h \approx \log_2 n \quad\Rightarrow\quad \text{search cost} = O(\log n) \]

Compare that with a linked list or an unsorted array, where finding a value costs \(O(n)\). With \(n = 1\,000\,000\) that is roughly 20 comparisons against 1,000,000 — the difference between instant and unusable.

Now the catch, and it is a big one. That bound holds only if the tree is balanced. Insert keys in ascending order — 1, 2, 3, 4, 5 — and every new key goes right of every existing key. The result is a chain: a "tree" with height \(n-1\) that is really a linked list with extra memory. Search becomes \(O(n)\), and the BST buys you nothing. Self-balancing trees (AVL, red-black) exist precisely to prevent this, by rotating nodes during insertion to keep the height near \(\log_2 n\).

The honest summary for an exam: a BST gives \(O(\log n)\) search, insert and delete on average, for randomly ordered input, and \(O(n)\) in the worst case. Average-case claims depend on the input distribution, and sorted input is the pathological case.

class TreeNode:
 def __init__(self, value):
 self.value = value
 self.left = None
 self.right = None

class BST:
 def __init__(self):
 self.root = None

 def insert(self, value):
 self.root = self._insert(self.root, value)

 def _insert(self, node, value):
 if node is None:
 return TreeNode(value) # empty slot = the base case
 if value < node.value:
 node.left = self._insert(node.left, value)
 elif value > node.value:
 node.right = self._insert(node.right, value)
 # equal: ignore (or count duplicates)
 return node

 def search(self, value):
 cur = self.root
 while cur is not None:
 if value == cur.value:
 return True
 elif value < cur.value:
 cur = cur.left
 else:
 cur = cur.right
 return False
How to use it — insertion is recursion on the invariant
  1. Start at the root.
  2. If the value is smaller, go left; if larger, go right.
  3. If you reach None, you have found the only place the value can legally go. Create the node there.
  4. Return the (possibly new) node so the parent's pointer can be updated.

Step 3 is the whole insight: you never "find a slot", you fall off the bottom of the tree, and the first empty child pointer you meet is where the value belongs.

Tree traversals

A traversal visits every node exactly once in a defined order. The three depth-first orders are named for when the root is visited relative to its subtrees. All three are naturally recursive: to traverse a tree, traverse its left subtree, traverse its right subtree, and visit the root — in the order the name specifies.

 return

 return

Why it works Why in-order on a BST prints the values in sorted order

Take any node with value \(v\). By the BST invariant, everything in its left subtree is \({}< v\) and everything in its right subtree is \({}> v\). In-order prints all of the left subtree, then \(v\), then all of the right subtree — so \(v\) appears after every smaller value in its subtree and before every larger one. That is precisely the definition of sorted order.

The same argument applies recursively at every node, so the whole output is sorted. No sorting was performed: the order was baked in at insertion time. This is the payoff of maintaining the invariant — you pay \(O(\log n)\) per insert and get a sorted listing for the price of an \(O(n)\) walk.

Contrast with pre-order, which on a BST gives the root first and tells you nothing about ordering, but which is the traversal you need to rebuild the tree, because it identifies the root of every subtree before its contents.

Why it works Two implementations, and why one of them turns set algebra into machine instructions

Implementation 1 — a hash set (next section). Membership is \(O(1)\) average, and union/intersection run in \(O(n)\) by iterating the smaller set and testing membership in the larger. This is what Python's set and Java's HashSet do.

Implementation 2 — a bit string (characteristic vector). If the universe of possible elements is small and known — say the 26 letters, or 64 students — assign each element an index and store one bit per element: 1 means present, 0 means absent. Then:

  • membership = read one bit: \(O(1)\)
  • union = bitwise OR
  • intersection = bitwise AND
  • difference = A AND (NOT B)

This is the same Boolean algebra from A1.2, now doing real work. A 64-element universe fits in a single 64-bit register, so a union of two sets is one machine instruction instead of a loop. That is why database engines and search indexes use bitmaps for filtering.

The trade-off. The bit string is \(O(U)\) in space where \(U\) is the size of the universe, regardless of how few elements are actually in the set — 64 students costs 64 bits even for an empty set. It is brilliant when sets are dense over a small universe and wasteful when the universe is large or the sets are sparse. A hash set is \(O(n)\) in space for \(n\) stored elements, with slower but still \(O(1)\) operations.

B4.1h · Hash tables

A hash table stores key–value pairs and aims for \(O(1)\) access. The idea: instead of searching for a key, compute where it must be.

How to use it
  1. A hash function \(h\) turns a key into an integer.
  2. The index is \(h(k) \bmod m\), where \(m\) is the table size. Taking the modulus is what forces the result into the range \(0 \ldots m-1\).
  3. Store the value at that index. To look it up, recompute the index and go straight there.
  4. Two different keys can produce the same index. That is a collision, and it is unavoidable — you must plan for it, not hope it does not happen.
Why it works Why collisions are guaranteed, and why \(O(1)\) is a claim about averages

Collisions are not bad luck; they are arithmetic. If you place \(n\) items into \(m\) slots, and \(n > m\), then by the pigeonhole principle at least one slot holds two items. Even with \(n \ll m\), the birthday paradox makes a collision likely far sooner than intuition suggests: with \(m = 365\) slots, a collision is more likely than not once \(n\) reaches just 23.

So the real question is never "will there be a collision" but "what happens when there is one". Two answers:

  • Open addressing (linear probing): if slot \(i\) is taken, try \(i+1\), then \(i+2\), wrapping with \(\bmod\, m\), until you find an empty slot.
  • Separate chaining: every slot holds a list of all the keys that hashed to it. Collisions just make the list longer.

Why \(O(1)\) degrades. Define the load factor

\[ \alpha = \frac{n}{m} \]

where \(n\) is the number of stored items and \(m\) the number of slots. With chaining, the average chain length is \(\alpha\), so a successful search costs about \(1 + \alpha/2\) comparisons. With linear probing the situation is worse, because occupied slots clump into runs: a key landing anywhere in a run must walk to its end, and every new insertion makes the run longer. This is primary clustering, and probing costs grow roughly like \(\frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)\) — which is fine at \(\alpha = 0.5\) (about 1.5 probes) and catastrophic as \(\alpha \to 1\).

The remedy is rehashing. When \(\alpha\) exceeds a threshold (commonly 0.75), allocate a bigger table — usually about double the size, ideally a prime number — and re-insert every element, because the modulus changed so every index changed. Rehashing is \(O(n)\) and halts the program briefly, but it is amortised over the \(O(1)\) insertions that caused it, so the average stays constant.

What makes a good hash function: it must be fast, deterministic (the same key always gives the same index, or you can never find anything again), and it must spread keys uniformly over the slots. A hash that sends all keys to one slot reduces the table to a linked list — technically still correct, and \(O(n)\).

Where the marks are

Table state (3), probe counts (2), average (1), comment (2). The comment mark wants the word clustering and a consequence — "the table is full, so search is now \(O(n)\) and it should be rehashed". Simply writing "it is slow" scores nothing. Note also this specific trap: a candidate who forgets the wrap on the last key and declares overflow has produced a plausible, completely wrong final table.

Traps — hash tables
  • Deletion with linear probing breaks searches. If you simply empty a slot that was part of a probe chain, later searches for keys that probed past it will hit the empty slot and conclude the key is absent. The fix is a tombstone marker that means "was occupied, keep probing", with the slot reused on the next insertion.
  • Probing must wrap. The sequence is \((h(k)+i) \bmod m\), never \(h(k)+i\).
  • \(O(1)\) is an average, not a guarantee. With a bad hash function or \(\alpha \approx 1\), both strategies degrade to \(O(n)\).
  • The hash function must be deterministic. Hashing on a mutable field that you then change makes the entry unreachable.
  • Separate chaining needs no rehash to keep working — it just slows down — whereas open addressing genuinely fails when the table is full. That is the main practical difference between them.

How to use it — answering "which structure would you use, and why?"
  1. Name the access pattern. FIFO → queue. LIFO → stack. Lookup by key with no ordering → hash table. Ordered data with updates → BST. Sequential scan only → array or list.
  2. State the complexity of the operations you will actually perform — not all of them. A print queue enqueues and dequeues and never searches, so its \(O(n)\) search is irrelevant.
  3. State the trade-off you are accepting. "A hash table gives \(O(1)\) average lookup but uses more memory than an array and returns items in no useful order."
  4. Mention size predictability. Known and fixed → array. Unknown and changing → linked structure or a dynamic array.
  5. Conclude with the deciding factor for this scenario. That final sentence is the mark.
Traps — the whole topic
  • Using front == rear to test a circular queue for full or empty — it is ambiguous by construction.
  • Forgetting the mod on the last probe or on the pointer advance, and reporting overflow or an index error instead.
  • Rewiring a linked list in the wrong order and losing the tail of the list.
  • Saying a BST is always \(O(\log n)\). It is \(O(h)\), and \(h\) can be \(n\).
  • Confusing pre-order and post-order: pre means the root comes first, post means it comes last; in both, left precedes right.
  • Writing the in-order traversal of a BST in insertion order. The traversal depends only on the shape of the tree, not on when the nodes arrived.
  • Saying hash tables eliminate collisions. They resolve them.
  • Quoting \(O(1)\) for a hash table without saying "average" or mentioning the load factor.

Practice

  1. Explain the difference between the logical and the physical view of a data structure, using the stack as your example. State one advantage of keeping them separate.

    Show answer

    The logical view of a stack is LIFO behaviour: items are added and removed at the top only, through push, pop, peek and isEmpty. It says nothing about storage.

    The physical view is a concrete implementation — an array with a top index, or a linked list whose head is the top.

    Advantage: the implementation can be changed (for example to a linked list so the stack no longer has a fixed capacity) without altering any code that uses the stack, because the operations and their behaviour are unchanged. Equally, correctness can be reasoned about once at the ADT level and then applies to every implementation.

    Marks: logical view (2), physical view with a concrete example (2), advantage (2).

  4. Describe how to insert a new node into a sorted singly linked list, given only a head pointer. Identify the two special cases and state the time complexity.

    Show answer
    1. If the list is empty, or the new value is smaller than head.data, insert at the head: n.next = head; head = n.
    2. Otherwise walk the list with two pointers, prev and cur, until cur is null or cur.data > value.
    3. Insert between them: n.next = cur; prev.next = n.
    4. If you reach the end, cur is null and the node becomes the new tail — the same two assignments still work, because n.next = None.

    Complexity: \(O(n)\) to find the position (you must walk, since there is no indexing), then \(O(1)\) to link. Total \(O(n)\).

    The two special cases candidates forget: inserting at the head (step 1 — there is no predecessor, and head itself must be reassigned) and inserting at the tail (step 4 — cur is null, so cur.data would crash the loop test if written in the wrong order).

    (a) A stack. Undo reverses the most recent action first, which is LIFO. Each edit pushes the previous state (or an inverse operation); Ctrl+Z pops. \(O(1)\) per operation. A queue would undo the oldest change first, which is not what a user expects.

    (b) A hash table keyed on the ID. Lookup by key is \(O(1)\) average, and no ordering is required. A BST would also work in \(O(\log n)\) but offers ordering that is not needed here; an array would be \(O(n)\) or would require the ID range to be small and dense.

    (c) A balanced binary search tree (or a self-balancing tree). It maintains ordering continuously, so an in-order traversal yields the alphabetical list in \(O(n)\), while insert and delete stay \(O(\log n)\). A sorted array keeps the order but every insertion costs \(O(n)\) to shift; a hash table gives fast lookup but no order at all.
