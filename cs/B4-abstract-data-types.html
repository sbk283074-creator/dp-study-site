B4 · Abstract data types

An abstract data type (ADT) is a contract: it says what a structure does — the operations you can perform and the rules they obey — without saying how it is built. A stack is "last in, first out, with push and pop", whether it is implemented with an array or with a chain of pointers. That separation of interface from implementation is the same trick you met at the very start of the course under computational thinking, and it is why the same queue appears in a printer, a breadth-first search, and a keyboard buffer. This page surveys the structures the IB names, always in two columns: the behaviour (what you can rely on) and the complexity (how long operations take). Keep the algorithms conceptual — the coding detail lives on the separate Python site; here you need the ideas and the Big-O.

B4.1 · The ADT concept

SL / HL

An abstract data type is defined by three things: a set of values it can hold, a set of operations on those values, and the axioms (rules) the operations obey. It says nothing about arrays, pointers, or memory. The same ADT can have several implementations, and you choose one by its performance and fitness for the problem.

Why interface/implementation separation pays off

Because the ADT fixes only behaviour, you can swap the implementation without changing the code that uses it. If an array-based queue is too slow when it grows, you replace it with a linked one; every caller that only ever called enqueue and dequeue keeps working. This is abstraction (from B1) applied to data: you program to the contract, not to the wires. The IB marks this distinction directly — "state the operations of the ADT" is a different question from "describe an implementation".

Trap — behaviour is not code

When asked for an ADT, do not write an implementation. "A stack is a list where you add at the end and remove from the end" is an implementation hint, not the ADT. The ADT answer is: "a stack supports push(item), pop(), peek(), isEmpty(); pop returns the most recently pushed item (LIFO); it is undefined to pop an empty stack." That is the contract.

B4.2 · Arrays vs linked lists

SL / HL

Both store a sequence, but their trade-offs are the heart of the topic.

OperationArrayLinked list
Access element iO(1) — direct by indexO(n) — must walk from head
Insert at endO(1) amortised (or O(n) if full)O(1) if tail pointer kept
Insert in middleO(n) — shift elementsO(1) once you are at the node
MemoryContiguous, may waste/need resizeNode-per-item overhead (pointers)

An array is a contiguous block addressed by index, so random access is instant. Its cost is insertion/deletion in the middle, which must shift everything after the point. A linked list is a chain of nodes, each holding data and a pointer to the next node. Insertion/deletion is just rewiring two pointers, but to reach the middle you must follow pointers from the head — O(n). A doubly linked list also keeps a pointer to the previous node, so you can walk backwards and delete a known node in O(1).

Exam tip

The array-vs-list question is a staple. Anchor your answer on the two operations that differ most: random access (array O(1), list O(n)) and insert/delete in the middle (array O(n) shift, list O(1) rewire). Then pick the structure from the dominant operation: "if we mostly search by index, use an array; if we mostly insert/remove, use a list."

B4.2 · Stacks

SL / HL

A stack is LIFO — last in, first out. The operations are push(item) (add to the top), pop() (remove and return the top), peek()/top() (look without removing), and isEmpty(). You can only touch the top.

Applications: the call stack of function calls (each call pushes a frame, returning pops it), undo buttons, expression evaluation (postfix / reverse Polish), and matching brackets. The bracket-matching use is classic: read left to right, push every open bracket, and on a close bracket pop and check it matches.

Worked example 1 IB-style · 5 marks · trace a stack

Question. Starting from an empty stack, perform: push(3), push(7), pop(), push(1), pop(), pop(). State the sequence of values returned by the pops and the final state.

  1. push(3): stack = [3].
  2. push(7): stack = [3, 7] (7 on top).
  3. pop(): removes 7, returns 7. Stack = [3].
  4. push(1): stack = [3, 1] (1 on top).
  5. pop(): removes 1, returns 1. Stack = [3].
  6. pop(): removes 3, returns 3. Stack = [] (empty).
  7. Pops returned 7, then 1, then 3 — last in first out. Final state is empty.
Answer: pops return 7, 1, 3; final stack empty. Marks: 1 per correct pop order step, 1 for final state, 1 for stating LIFO.
Worked example 2 IB-style · 6 marks · stack checks bracket matching

Question. Use a stack to decide whether the string ( [ a + b ] * c ) has balanced brackets.

  1. Read '(' → push '('. Stack: [(].
  2. Read '[' → push '['. Stack: [(, [.
  3. Read 'a','+','b' → not brackets, ignore.
  4. Read ']' → pop, top is '[' which matches ']'. Stack: [(].
  5. Read '*','c' → ignore.
  6. Read ')' → pop, top is '(' which matches ')'. Stack: [].
  7. End with empty stack and every close matched its open → balanced. (If a pop had found a mismatch, or the stack were non-empty at the end, it would be unbalanced.)
Answer: balanced — every close bracket matched the top of the stack and the stack ended empty. Marks: 2 for the push rules, 2 for the two correct pops, 2 for the empty-stack conclusion.
Trap — popping an empty stack

The ADT says popping an empty stack is undefined. A real program that does it crashes (underflow). In a trace question, if a pop is asked when the stack is empty, you must say "underflow / error", not invent a value. Similarly pushing onto a fixed-size array stack that is full is overflow.

B4.2 · Queues

SL / HL

A queue is FIFO — first in, first out. Operations: enqueue(item) (add at the rear), dequeue() (remove from the front), peek() (front without removing), isEmpty(). Uses: printer queues, task scheduling, and breadth-first search (see below).

Circular and priority queues

A circular queue stores a fixed capacity in an array and wraps the rear pointer back to the start when it passes the end, so you do not waste the space left by dequeued items at the front. A priority queue does not serve in arrival order; each item has a priority and dequeue returns the highest-priority item first (often implemented with a heap, O(log n) insert and remove). It models hospital triage and operating-system scheduling.

Why a queue models fairness

A FIFO queue is the computational expression of "wait your turn". That is why it appears wherever fairness or order matters: print jobs, network packets at a router, customers at a till. The priority queue is the admission that strict fairness is sometimes wrong — a heart attack should not wait behind a sprained ankle — and so it generalises the queue by adding a comparison. Both are still ADTs: same operations (enqueue/dequeue), different removal rule.

Trap — stack vs queue in one sentence

The classic confusion: a stack is "like a pile of plates" (last placed is first taken); a queue is "like a checkout line" (first to arrive is first served). If you ever write that a stack is first-in-first-out, that is the opposite of true and loses the mark. LIFO = stack, FIFO = queue.

B4.3 · Trees

SL / HL

A tree is a hierarchy of nodes where each node (except the root) has exactly one parent. A binary tree limits each node to at most two children (left and right). A binary search tree (BST) adds an ordering rule: every value in a node's left subtree is smaller, and every value in the right subtree is larger. That rule makes search fast.

Search and insert in a BST

Search: compare the target with the current node; if equal, found; if smaller, go left; if larger, go right; if you reach an empty child, it is absent. Each step descends one level, so search is O(h) where h is the height — O(log n) in a balanced tree, but O(n) in a degenerate (list-shaped) tree.

Insert: search for the value; when you reach the empty spot where it would belong, attach a new node there. Duplicates are usually rejected or sent consistently to one side.

Traversals

Three standard depth-first orders differ only in when you visit the node relative to its children:

  • In-order (left, node, right): on a BST this visits values in ascending order.
  • Pre-order (node, left, right): useful to copy/serialize a tree.
  • Post-order (left, right, node): useful to delete a tree (children before parent).
Worked example 3 IB-style · 6 marks · traverse the BST

Question. For the BST in Figure 2 (root 50, left 30/right 70, etc.), give the in-order, pre-order and post-order traversals.

  1. In-order (left, node, right): from 50 go left to 30 → left to 20, visit 20; visit 30; right to 40, visit 40; visit 50; right to 70 → left 60, visit 60; visit 70; right 80, visit 80. Result: 20, 30, 40, 50, 60, 70, 80.

  3. Post-order (left, right, node): left subtree 20,40,30; right subtree 60,80,70; then 50. Result: 20, 40, 30, 60, 80, 70, 50.
  4. Check in-order is sorted ascending — confirms it is a valid BST traversal. Good.
Answer: in-order 20,30,40,50,60,70,80; pre-order 50,30,20,40,70,60,80; post-order 20,40,30,60,80,70,50. Marks: 2 each for a correct full traversal.

Question. Into the BST of Figure 2, insert 35 and then 65. Show the path each takes.

Trap — in-order is special to BSTs

In-order gives sorted output only for a binary search tree. On an arbitrary binary tree, in-order is just "left, node, right" and is not sorted. Students write "in-order sorts any tree" — wrong. The sorting property comes from the BST ordering rule, not from the traversal.

B4.3 · Graphs

SL / HL

A graph is a set of vertices (nodes) joined by edges. Unlike a tree it may have cycles and any topology. We store it two ways:

RepresentationFormBest when
Adjacency matrixA V×V table; cell [i][j] = 1 if edge i–j existsDense graphs; fast edge check O(1)
Adjacency listEach vertex holds a list of its neighboursSparse graphs; saves space

Breadth-first search (BFS) explores level by level using a queue: visit the start, enqueue its neighbours, then dequeue and repeat. It finds the shortest path in an unweighted graph. Depth-first search (DFS) goes as deep as possible down one branch (using a stack or recursion) before backtracking. Both visit every reachable vertex in O(V + E).

Why BFS needs a queue

BFS must visit nodes in order of distance from the start: all at distance 1, then all at distance 2. A FIFO queue is exactly the structure that emits nodes in the order they were discovered, so the next vertex explored is always the closest unseen one. This is the queue ADT earning its keep — the same one from the printer example in B1.

B4.4 · Hashing

SL / HL

A hash table maps keys to values via a hash function h(key) that returns an array index. With a good function, insert and search are average O(1), far better than a list's O(n). A collision happens when two keys hash to the same index; you must handle it.

MethodHow it handles a collision
ChainingEach bucket holds a linked list of all keys that hashed there; search the list
Open addressingProbe the next free slot (linear/quadratic) and store the item there
Trap — average vs worst case

Hash tables are O(1) on average, but if every key collides (a pathological hash or a flooded bucket) they degrade to O(n) because you walk a long chain or probe many slots. The IB often asks for this worst case, so always pair "average O(1)" with "worst O(n) if many collisions". A good hash spreads keys evenly.

B4 · Recursion vs iteration

SL / HL

A recursive solution solves a problem by calling itself on a smaller sub-problem, with a base case that stops it. Iteration uses a loop. Anything recursive can be written iteratively and vice versa. Recursion is natural for trees (traversal is "visit node, recurse on children") and divide-and-conquer; iteration is often faster and uses less memory because it avoids a call stack.

Why recursion fits trees

A tree is self-similar: each subtree is itself a tree. So "traverse a tree" is literally "traverse the left subtree, traverse the right subtree" — the recursive definition mirrors the data. That is why in-order traversal is three lines recursively but needs an explicit stack iteratively. The cost is stack depth: a very deep recursion can overflow; iteration with an explicit stack avoids that.

// Conceptual only — the Python site has the runnable version.
function inOrder(node):
    if node is null: return          // base case
    inOrder(node.left)               // recurse on smaller sub-problem
    visit(node)
    inOrder(node.right)

// Iterative equivalent keeps an explicit stack instead of the call stack.
Trap — missing the base case

A recursion without a base case (or one never reached) calls itself forever until the call stack overflows. Every recursive answer you write must name the base case: "stop when the node is null" or "stop when n = 0". A markscheme checks for it explicitly.

B4.1 · ADT operation contracts in detail

SL / HL

Writing an ADT as a contract means listing, for each operation, its precondition, its effect, and its return. For a stack: push(x) requires the stack not be full (if fixed) and adds x on top; pop() requires the stack not be empty and removes and returns the top; peek() requires non-empty and returns the top without removing; isEmpty() returns a boolean. For a queue: enqueue(x) adds at the rear; dequeue() requires non-empty and removes from the front. For a list: get(i), set(i,x), insertAt(i,x), removeAt(i), size(), isEmpty(). The contract never mentions arrays or pointers — that is the point. Two implementations satisfy the same contract; a caller cannot tell which, which is why you can swap them safely.

Why the contract protects the caller

Because the caller only knows the contract, you can replace a slow implementation with a fast one (or fix a bug in one) without touching any caller code — provided the new implementation honours the same contract. This is the practical payoff of abstraction from B1: change the implementation, keep the interface, and nothing downstream breaks. The IB marks "state the operations" separately from "describe an implementation" precisely because this separation is the core idea.

B4.2 · List implementations — dynamic arrays and linked-list operations

SL / HL

A static array has a fixed size chosen at creation; overflow means failure. A dynamic array (like Python's list or Java's ArrayList) starts small and, when full, allocates a larger block (often double the size), copies the elements across, and frees the old block. This makes append O(1) amortised: most appends are O(1), and the occasional resize is O(n), but the cost averaged over many appends is constant. Amortised analysis is the right lens: a single expensive operation is fine if it is rare enough. For a linked list, insertion/deletion at a known node is O(1) (rewire two pointers), but you usually must first reach the node by walking from the head, which is O(n).

Worked example 5 IB-style · 6 marks · trace linked-list insert and delete

Question. A singly linked list holds A→B→C. (a) Insert D between B and C. (b) Then delete B. Show the pointer changes and final list.

  1. Start: A.next=B, B.next=C, C.next=null.
  2. (a) Insert D after B: set D.next = B.next (so D.next=C), then B.next = D. Now A→B→D→C.
  3. Two pointer writes, O(1) once B is known — no shifting, unlike an array.
  4. (b) Delete B: set A.next = A.next.next (i.e. A.next = B.next = D). Now A→D→C; B is unlinked and can be freed.
  5. Again two pointer writes; the element after A is reached via A.next.next.
  6. Final list: A→D→C. Every other node kept its data; only pointers changed.
Answer: insert D: D.next=C, B.next=D → A→B→D→C; delete B: A.next=D → A→D→C. Marks: 2 insert, 2 delete, 1 O(1) note, 1 final list.
Trap — knowing where vs getting there

Inserting after a known node is O(1), but finding the node is O(n) for a singly linked list. Students claim "linked list insertion is O(1)" forgetting the search. The honest complexity is O(n) to find + O(1) to insert. Only when you already hold the node (e.g. during a traversal) is the insert O(1). State both parts.

B4.2 · Stack application — postfix evaluation and the call stack

SL / HL

Postfix (reverse Polish) notation puts operators after their operands (3 4 +), needing no brackets because the order is unambiguous; a stack evaluates it: push operands, and on an operator pop the top two, apply it, push the result. This is how some calculators and compilers work. Recursion uses the same idea implicitly: each call pushes a stack frame (its parameters, local variables, return address); returning pops it. Deep recursion on a deep structure can overflow this call stack — which is why iteration with an explicit stack can be safer for very deep trees.

Worked example 6 IB-style · 6 marks · evaluate a postfix expression

Question. Evaluate the postfix expression 5 3 4 + * 2 - using a stack. Show each step.

  1. Read 5: push → [5].
  2. Read 3: push → [5, 3].
  3. Read 4: push → [5, 3, 4].
  4. Read +: pop 4 and 3, compute 3+4=7, push → [5, 7].
  5. Read *: pop 7 and 5, compute 5*7=35, push → [35].
  6. Read 2: push → [35, 2].
  7. Read -: pop 2 and 35, compute 35-2=33, push → [33]. End: result 33.
  8. Check: infix is 5*(3+4)-2 = 5*7-2 = 33. Matches.
Answer: 33. Marks: 1 per correct push/pop step (or 5 for the trace), 1 final, 1 infix check.

B4.2 · Queue implementation — circular array trace

SL / HL

A queue in a fixed array wastes space because the front creeps forward. A circular queue treats the array as a ring: the rear pointer advances (rear+1) mod capacity, wrapping to index 0 after the last slot. It is full when (rear+1) mod n == front (one slot sacrificed to distinguish full from empty), or you track a count. This keeps enqueue/dequeue O(1) without shifting.

Worked example 7 IB-style · 5 marks · circular queue trace

Question. Circular queue of capacity 5, indices 0–4, front=0, rear=2 (items at 0,1,2). Enqueue X then dequeue. Show pointers and the wrap.

  1. Items at 0,1,2; rear=2. Enqueue X at (rear+1) mod 5 = 3, so X goes to index 3, rear becomes 3. Items: 0,1,2,3.
  2. Dequeue: remove item at front=0, advance front to (0+1) mod 5 = 1. Items now at 1,2,3.
  3. If we later enqueue twice more (indices 4, then wrap to 0), rear would go 3→4→0; the modulo makes it wrap, no wasted gap at the end.
  4. This is why circular: after index 4 the next is index 0, so the array is reused as a ring.
  5. Full test: (rear+1) mod 5 == front would signal full; with a count variable you avoid the lost-slot ambiguity.
Answer: enqueue X at index 3 (rear→3); dequeue removes index 0 (front→1); wrap via modulo. Marks: 2 enqueue, 2 dequeue, 1 wrap explanation.

B4.3 · Trees — deletion, height, and balanced trees

SL / HL

BST deletion has three cases: a leaf (just remove it); a node with one child (replace it with the child); a node with two children (replace it with its in-order successor — the smallest node in its right subtree — then delete that successor, which has at most one child). Height is the longest root-to-leaf path; a balanced tree has height O(log n), keeping search O(log n). A degenerate (sorted-insertion) tree has height n, making search O(n). Self-balancing trees (AVL, red-black, conceptual only) rotate on insert/delete to keep height logarithmic — the IB wants the concept (why balance matters, O(log n) vs O(n)), not the rotation algorithm.

Worked example 8 IB-style · 6 marks · BST delete a two-child node

Question. In the BST (root 50, left 30 with children 20,40; right 70 with 60,80), delete 30.

  1. 30 has two children (20 and 40), so use the in-order successor: the smallest in its right subtree.
  2. 30's right subtree is 40 (no left child), so the successor is 40.
  3. Replace 30's value with 40, then delete the original 40 node (a leaf here).
  4. Tree becomes: root 50, left child now 40, with left child 20; right 70 with 60,80.
  5. Check BST property: 20 < 40 < 50, and 50 < 70; still valid, all ordering preserved.
  6. The alternative (predecessor 20) would also work; the rule is "swap with successor/predecessor then delete the duplicate".
Answer: replace 30 with its in-order successor 40, delete leaf 40. Marks: 2 two-child case, 2 successor choice, 2 result/check.
Trap — deleting by value-shuffle, not pointer-surgery only

The clean way to delete a two-child node is to copy the successor's value into the node and delete the successor (which is simple), not to rewire three subtrees by hand — the latter is error-prone. Students who try to move whole subtrees usually break the ordering. State "copy successor value, delete successor" and you have the marks.

B4.3 · Graph traversal — BFS and DFS traces

SL / HL

Both BFS and DFS visit every reachable vertex in O(V + E). BFS uses a queue and explores in order of distance, so it finds the shortest path in an unweighted graph; DFS uses a stack (or recursion) and goes deep first, useful for connectivity and cycle detection. You must mark visited vertices to avoid revisiting.

Worked example 9 IB-style · 6 marks · BFS trace

Question. Graph: A connected to B and C; B to D; C to D. BFS starting at A. Give the visitation order.

  1. Queue starts [A]; mark A visited. Dequeue A, enqueue its unvisited neighbours B, C → queue [B, C]. Order so far: A.
  2. Dequeue B (mark visited); B's neighbour D is unvisited → enqueue D. Queue [C, D]. Order: A, B.
  3. Dequeue C (mark visited); C's neighbour D is already queued/visited → skip. Queue [D]. Order: A, B, C.
  4. Dequeue D (mark visited); its neighbours A, B, C all visited → nothing new. Queue empty. Order: A, B, C, D.
  5. BFS order A, B, C, D reflects distance: A (0), then B and C (1), then D (2). D is reached first via B or C, both distance 2.
  6. Shortest path A→D has length 2, which BFS guarantees.
Answer: A, B, C, D. Marks: 2 queue steps, 2 order, 1 visited-marking, 1 shortest-path note.
Worked example 10 IB-style · 5 marks · DFS trace

Question. Same graph, DFS from A (visit neighbours in alphabetical order). Give the order.

  1. Push/visit A. Recurse to first neighbour B. Visit B.
  2. From B, first unvisited neighbour is D (B's neighbours A visited, D not). Visit D.
  3. From D, all neighbours (A,B,C) visited → backtrack to B, then to A.
  4. From A, next unvisited neighbour is C. Visit C.
  5. From C, neighbour D already visited → backtrack. Done.
  6. DFS order: A, B, D, C. Different from BFS, and it went deep (A→B→D) before exploring C.
Answer: A, B, D, C. Marks: 2 recursion steps, 2 order, 1 contrast with BFS.
Trap — forgetting to mark visited

Without a visited set, BFS/DFS re-enqueues the same vertex via cycles and either loops forever or explodes exponentially. The mark is explicitly tracking visited. Also, BFS order depends on neighbour order, but the shortest-path guarantee does not — state that the distance property holds regardless of tie order.

Weighted graphs and Dijkstra (concept)

A weighted graph labels edges with costs (distance, time, money). Dijkstra's algorithm (conceptual) finds shortest paths from one source: repeatedly pick the unvisited vertex with the smallest known distance, finalise it, and relax its edges (if via this vertex a neighbour is closer, update it). It needs non-negative weights and runs in O((V+E) log V) with a priority queue. The IB wants the idea and the greedy "nearest unvisited first" step, not the code. BFS is Dijkstra with all weights equal to 1.

Why Dijkstra is greedy and correct

Once you finalise the nearest unvisited vertex, no future path can reach it cheaper (all remaining edges are non-negative, so any detour only adds cost). That invariant is what makes the greedy choice safe. It is the same "make the locally optimal choice that is globally safe because of an invariant" pattern as the algorithms in B1.

B4.4 · Hashing in depth — functions, load factor, and collision handling

SL / HL

A hash function maps a key to an index. Good ones distribute keys evenly. The division method is h(k) = k mod m (choose m prime, not a power of two, to avoid clustering). The multiplication method is h(k) = floor(m · (k·a mod 1)) for a constant a. A perfect hash has no collisions for a known fixed key set (used in compilers for keyword lookup). The load factor α = n/m (items / slots) predicts performance: as α grows, collisions rise, so you rehash — allocate a bigger table and re-insert everything — when α exceeds a threshold (often ~0.75). Rehashing is O(n) but rare, so average insert stays O(1) amortised.

Worked example 11 IB-style · 5 marks · hash with chaining and load factor

Question. Hash table size 8, h(k)=k mod 8. Insert 3, 11, 19, 5 using chaining. What is the load factor, and where do collisions occur?

  1. h(3)=3 mod 8=3 → bucket 3.
  2. h(11)=11 mod 8=3 → bucket 3 already has 3, so chain: bucket 3 → [3, 11]. Collision (both ≡3 mod 8).
  3. h(19)=19 mod 8=3 → bucket 3 → [3, 11, 19]. Another collision; chain grows.
  4. h(5)=5 mod 8=5 → bucket 5 → [5]. No collision.
  5. Load factor α = n/m = 4/8 = 0.5. Worst-case search is the chain at bucket 3 (length 3) = O(3), not O(1), showing collisions degrade the average case.
Answer: buckets 3=[3,11,19], 5=[5]; collisions at bucket 3; α=0.5. Marks: 2 inserts, 1 collisions, 1 α, 1 worst-case note.

Collision strategies compared

Chaining keeps a linked list per bucket — simple, never fails to insert, but uses pointers and degrades to O(n) if many collide. Open addressing stores the item in another slot: linear probing (try +1, +2, …) is simple but clusters (primary clustering); quadratic probing (try +1², +2², …) reduces it; double hashing uses a second hash for the step, spreading best. Open addressing needs α well below 1 (table must have empty slots); chaining tolerates α > 1. The IB asks you to compare; the axis is pointer overhead vs clustering and the need for free slots.

Trap — average vs worst, restated for hashing

Hash tables are O(1) average but O(n) worst (all keys collide). A question "why is lookup not always O(1)" wants exactly this: a bad hash or high load factor makes one bucket hold everything. Always pair "average O(1)" with "worst O(n) when collisions cluster". This is the single most-tested nuance on hashing.

B4 · Recursion worked examples and complexity

SL / HL
Worked example 12 IB-style · 5 marks · recursive factorial and its cost

Question. Give a recursive factorial and state its time and space complexity, with the base case.

  1. Base case: factorial(0) = 1. Recursive step: factorial(n) = n × factorial(n−1) for n > 0.
  2. Each call reduces n by 1, so there are n calls → time O(n).
  3. Each call waits for the next, so n stack frames accumulate → space O(n) (the call stack).
  4. An iterative version uses O(1) space (one running product), so iteration wins on memory here.
  5. The base case is essential: without factorial(0)=1 the recursion never stops and overflows the stack.
Answer: f(0)=1; f(n)=n·f(n−1); time O(n), space O(n); base case stops it. Marks: 1 base, 1 step, 1 time, 1 space, 1 base-case necessity.
Worked example 13 IB-style · 6 marks · recursive Fibonacci and why it is slow

Question. Recursive fib(n)=fib(n−1)+fib(n−2), fib(0)=0, fib(1)=1. Explain its complexity and a fix.

  1. Each call spawns two, so the call tree is a binary tree of depth n → about 2n calls → time O(2n), exponential.
  2. It recomputes the same values wildly (fib(3) computed many times) — overlapping subproblems.
  3. A fix is memoisation: cache results so each fib(k) is computed once → O(n).
  4. Or iterate bottom-up keeping the last two values → O(n) time, O(1) space.
  5. The lesson: naive recursion can be exponentially slow where iteration or memoisation is linear — choose by complexity, not just "it looks recursive".
Answer: naive is O(2^n) due to recomputation; memoisation or iteration makes it O(n). Marks: 2 exponential, 1 recompute, 2 fix, 1 lesson.
Why recursion's cost is the stack

Every recursive call consumes a stack frame; deep or bushy recursion consumes memory and can overflow. Iteration with an explicit structure (loop, or an explicit stack for DFS/BFS) often uses less memory. The IB marks you for stating both time and space complexity and for knowing when to prefer iteration — recursion is a tool, not a religion. Trees favour recursion; flat loops favour iteration.

B4.2 · Priority queues and heaps (concept)

SL / HL

A priority queue serves the highest-priority item first, not the oldest. A binary heap is the usual implementation: a complete binary tree stored in an array where each parent is more extreme (lower for min-heap) than its children. insert and extract-min are O(log n) — the tree stays balanced by construction, so height is logarithmic. Heaps back Dijkstra (always pop the nearest vertex) and job schedulers (always run the highest-priority task). The IB wants the concept and the O(log n) complexity, not the sift-up/sift-down code. Contrast: a plain queue is FIFO (priority = arrival time); a priority queue is FIFO only when all priorities are equal.

Worked example 14 IB-style · 4 marks · priority queue behaviour

Question. A min-heap priority queue receives items with priorities 5, 1, 3 (in that order). In what order are they dequeued?

  1. The queue always removes the smallest priority first.
  2. Insert 5, 1, 3 → the heap orders them so the root is the minimum, 1.
  3. First dequeue returns 1 (smallest).
  4. Second returns 3, third returns 5 — order is 1, 3, 5, regardless of arrival order.
  5. This is why it is not FIFO: 1 arrived second but left first because it had the highest priority (lowest number).
Answer: dequeued 1, 3, 5 (by priority, not arrival). Marks: 1 min-first, 2 order steps, 1 not-FIFO note.

Stacks and queues — more applications

Beyond the basics: stacks back undo (each action pushed; undo pops and reverses it), the call stack, and expression parsing (compilers use a stack for grammar); queues back printer spooling, CPU scheduling (round-robin is a queue of ready processes), network buffers (packets queued at a router), and BFS. The recurring lesson: whenever "last thing started is first thing finished" → stack; "first come first served" → queue; "most urgent first" → priority queue. Recognising the pattern lets you pick the ADT without thinking.

Why these three cover most buffering

Nearly every "hold items and take them out later" problem is one of these three orderings. A web server's request buffer is a queue; its back-button is a stack; its task scheduler is a priority queue. Naming the right ordering is often the first step of a B1 decomposition, which is why B4 and B1 connect: the ADT is the data half of computational thinking.

B4.3 · Tree traversals — more practice and uses

SL / HL

Traversals are not just exam exercises; they have uses. In-order on a BST yields sorted data (used to list items in order). Pre-order (node, left, right) serialises a tree — record nodes in pre-order and you can rebuild it — used to copy a tree or save it. Post-order (left, right, node) deletes a tree safely (free children before the parent) and evaluates expression trees bottom-up (postfix). Level-order (BFS by levels) is a fourth, queue-based order used to print a tree row by row.

Worked example 15 IB-style · 5 marks · choose a traversal

Question. You must (a) list a BST's items in ascending order, (b) delete the whole tree safely, (c) copy a tree's structure. Which traversal for each?

  1. (a) In-order (left, node, right) — on a BST this visits values ascending.
  2. (b) Post-order (left, right, node) — delete children before the parent so you never dangle a pointer.
  3. (c) Pre-order (node, left, right) — record the root first, then subtrees, so replaying the list rebuilds the shape.
  4. Each task matches the traversal whose visitation order fits the operation's dependency.
  5. Level-order would not give sorted output nor safe deletion, so it is wrong for (a) and (b).
Answer: (a) in-order (b) post-order (c) pre-order. Marks: 2 for the three, 1 each reasoning or 3 for correct mapping.
Trap — traversal order is fixed by definition

Mixing them up loses the mark even if the result looks plausible. In-order is always left-node-right; do not "start at the root" for in-order. The root is visited in the middle for in-order, first for pre-order, last for post-order. Memorise the position of "node" in each name: In (middle), Pre (before), Post (after).

Arrays in depth: static, dynamic, and amortised cost

An array is a contiguous block of memory holding elements of one type, addressed by an integer index. Because the elements sit side by side, accessing arr[i] is O(1) — the address is simply base + i × element_size, computed in one step. That random access is the array's superpower and the reason it underpins so many other structures.

Static vs dynamic arrays

A static array has a fixed size chosen at creation; you cannot add beyond it. A dynamic array (e.g. Python list, Java ArrayList, C++ vector) grows on demand: when full, it allocates a larger block (typically double the size), copies the old elements across, and frees the old block. Appending is usually O(1) but occasionally O(n) when a resize happens.

Note — amortised analysis

Although a single append that triggers a resize costs O(n), resizes get rarer as the array grows (sizes 1, 2, 4, 8, 16 ...). The total cost of n appends is about n + n/2 + n/4 + ... ≈ 2n, so the amortised cost per append is O(1). "Amortised" means averaged over many operations, not each one. This is why dynamic arrays are efficient despite occasional expensive grows.

Multi-dimensional arrays

A 2-D array (matrix) is stored either row-major (row by row) or column-major. Indexing m[r][c] still reduces to one arithmetic address calculation, so access stays O(1). Use a 2-D array for grids, images, and tables; use a 1-D array of arrays (a "jagged" array) when rows have different lengths.

Trap — off-by-one and bounds

Array indices run from 0 to n−1. Accessing arr[n] is out of bounds and, in unsafe languages, corrupts memory; in managed languages it throws an exception. Always test i < length in loops. A classic bug is looping while i <= n, which reads one past the end.

Linked lists: singly, doubly, and circular

A linked list stores elements (nodes) scattered in memory; each node holds the value and a pointer (reference) to the next node. The list is reached through a head pointer; the last node points to null. Because nodes need not be contiguous, insertion and deletion in the middle are O(1) once you have the node — no shifting, unlike an array.

Insertion and deletion

To insert after node p: make a new node x, set x.next = p.next, then p.next = x (order matters — set x's next first or you lose the rest of the list). To delete after p: set p.next = p.next.next, dropping the target node for garbage collection. With a doubly linked list you can delete a known node in O(1) by rewiring its neighbours; with a singly linked list you need the predecessor.

Worked — build a list 3 → 7 → 9

Start head = null. Insert 3 at head: node(3) becomes head. Insert 7 at head: node(7).next = head (node 3); head = node(7). Insert 9 at head: node(9).next = head (node 7); head = node(9). Traversal from head yields 9, 7, 3 — the list is LIFO because we always insert at the head. Changing where we insert (tail vs head) changes the order, which is exactly how a stack or queue can be built on a list.

Stacks in depth: applications, overflow, and postfix evaluation

A stack is the LIFO structure whose whole contract is push (add to the top), pop (remove from the top), peek/top (read the top without removing), and isEmpty. Because every operation touches only the top, each is O(1). Two failure modes matter: stack underflow (popping an empty stack) and stack overflow (pushing onto a full fixed-size stack). A dynamic stack never overflows until memory is exhausted; a fixed array-based stack must check bounds.

Stacks are everywhere because computation itself is nested. Procedure calls use a call stack: each function call pushes its local variables and return address; returning pops them. This is why infinite recursion overflows the stack. Undo in an editor pushes each action and pops to revert. Backtracking (mazes, game trees) pushes moves and pops to retreat. Depth-first search of a graph is just a stack in disguise. The unifying idea is "remember where I was so I can return" — exactly LIFO.

From infix to postfix and evaluation

Humans write 3 + 4 (infix, operator between operands). Computers often prefer postfix / Reverse Polish Notation 3 4 + because it needs no parentheses and is trivial to evaluate with a stack: read left to right, push operands, and when an operator appears pop the top two, apply it, push the result.

Worked — evaluate postfix 3 4 + 2 *

Push 3. Push 4. See +: pop 4, pop 3, compute 3+4 = 7, push 7. Push 2. See *: pop 2, pop 7, compute 7×2 = 14, push 14. End: top is 14. So 3 4 + 2 * = 14, which matches the infix (3+4)×2. The stack removed the need for parentheses entirely.

Worked — convert infix to postfix (Shunting-yard)

Convert 3 + 4 * 2. Read 3 → output "3". Read + → push to operator stack. Read 4 → output "3 4". Read * → higher precedence than + on the stack, so push *. Read 2 → output "3 4 2". End → pop remaining operators: "3 4 2 * +". Check: 3 + (4*2) = 11, and evaluating 3 4 2 * +: 4×2=8, 3+8=11. Correct. The algorithm uses an operator stack and precedence rules to place operators after their operands.

Trap — pop order in binary ops

When you pop two operands for - or /, the first popped is the right operand and the second is the left. For 7 2 -, pop 2 then pop 7, compute 7−2 = 5, not 2−7. Reversing them is the most common postfix-evaluation error.

Balanced brackets

A stack neatly checks balanced parentheses: push each opening bracket; on a closing bracket, pop and check it matches the same type. If the stack is empty when you need to pop, or non-empty at the end, the expression is unbalanced. This is a classic stack application and a frequent exam question, often extended to three bracket kinds () [] {}.

Queues in depth: types and real applications

A queue is FIFO: enqueue at the rear, dequeue from the front. Like a stack, all operations are O(1) given proper pointers. The natural applications are anything first-come-first-served: print queues, task scheduling, network packet buffers, and breadth-first search.

Simple, circular, and priority queues

A simple (linear) queue on an array wastes space: after many dequeues the front marches right, leaving dead cells on the left. A circular queue wraps the rear around to the start using modulo arithmetic, reusing freed cells — the standard fix. A priority queue dequeues the highest-priority item first, not the oldest; it is usually implemented with a heap (O(log n) insert/extract) rather than scanning linearly (O(n)). A deque (double-ended queue) allows both ends to be added and removed, supporting both stack and queue behaviour.

Worked — circular queue fullness

With a fixed array of size N, front and rear pointers, the queue is empty when front == rear (after initialisation) and full when (rear + 1) % N == front. Notice we waste one slot to distinguish full from empty; alternatively keep a count variable. This modulo wrap is why a circular queue never "runs out of room" while cells remain free at the front.

Exam tip

Compare stack and queue in one line each: stack = LIFO, last in first out, used for undo and recursion; queue = FIFO, first in first out, used for scheduling and BFS. Mentioning the O(1) cost of both operations and the circular-queue optimisation shows deeper understanding.

Trees in depth: terminology, BST operations, and traversals

A tree is a hierarchical structure of nodes connected by edges, with a single root and no cycles; every node (except the root) has exactly one parent, and may have zero or more children. Nodes with no children are leaves. The depth of a node is its distance from the root (number of edges); the height of the tree is the maximum depth. A subtree is any node together with all its descendants. Trees model file systems, organisation charts, parse trees, and the call stack, and they underpin search, sorting, and compression.

Binary trees and binary search trees

A binary tree restricts each node to at most two children, called left and right. A binary search tree (BST) adds an ordering invariant: for every node, all keys in its left subtree are smaller and all keys in its right subtree are larger. That invariant makes search, insert, and delete run in O(h) where h is the height. In a balanced BST h ≈ log n, so operations are O(log n); in a degenerate (chain-like) tree h = n and they degrade to O(n) — which is why self-balancing trees (AVL, red-black) exist, rotating nodes to keep height logarithmic.

Insertion

To insert a key, start at the root and compare: if the key is smaller go left, if larger go right, repeating until you reach an empty child position, where you attach the new node. Because the path is determined by comparisons, the BST property is preserved automatically. The shape depends on insertion order — inserting 1,2,3,4,5 in order yields a linked-list chain, while a shuffled order yields a bushier tree.

Worked — insert 50, 30, 70, 20, 40, 60, 80

Insert 50 as root. 30 < 50 → left child of 50. 70 > 50 → right child of 50. 20 < 50, then < 30 → left child of 30. 40 < 50, > 30 → right child of 30. 60 < 70, > 50 → left child of 70. 80 > 70 → right child of 70. The result is a balanced tree of height 2 with 7 nodes. Searching for 60 now takes two comparisons (50 → 70 → 60) instead of scanning all seven — the BST has halved the work at each step.

Deletion

Deleting from a BST has three cases. A leaf is simply removed. A node with one child is replaced by that child. A node with two children is replaced by its in-order successor (the smallest key in its right subtree, or equivalently the largest in its left) — copy that successor's key into the node, then delete the successor (which has at most one child, reducing to case one or two). This preserves the BST ordering.

Traversals — the required worked examples

A traversal visits every node exactly once. The three classic depth-first orders differ only in when the node itself is visited relative to its subtrees:

Worked 1 — in-order traversal (required)

Take the tree from the insertion example: root 50, left subtree (30 with children 20,40), right subtree (70 with children 60,80). In-order (left, node, right): from 50 go left to 30, whose left is 20; so 20, then 30, then 30's right 40; back to 50; then right subtree: 60, 70, 80. Worked 2 — post-order traversal (required)

Same tree. Post-order (left, right, node): left subtree 30 → visit 20 (leaf), then 40 (leaf), then 30; right subtree 70 → visit 60, then 80, then 70; finally the root 50. The root is printed last, and every node is visited only after both children — exactly what you need when freeing or deleting a tree (never delete a parent before its children, or you lose the pointers to them).

Trap — which order gives sorted output

Only in-order on a BST yields ascending keys. Pre-order and post-order do not sort. Students often write the in-order list from a non-BST and are surprised it is unsorted — the ascending property depends on the BST invariant, not on the traversal alone. If the question does not state it is a BST, do not assume sorted output.

Other important trees

A heap is a complete binary tree where every parent is ordered relative to its children (max-heap: parent ≥ children; min-heap: parent ≤ children). Heaps back priority queues and heapsort. An AVL tree is a BST that rebalances after every insert/delete to keep height within a constant factor of log n, guaranteeing O(log n) worst case. A B-tree / B+ tree is a balanced tree with many children per node, minimising disk reads — this is what almost every database index actually is. A trie stores strings by sharing prefixes, giving fast prefix lookups. Knowing the family and when each is used is more valuable than memorising every rotation.

Exam tip

For a traversal question, draw the tree, label left/right clearly, and walk the order mechanically writing each value as you "visit the node". State the order name and its defining position of the node (pre = before subtrees, in = between, post = after). Two marks for the correct sequence, one for naming the order — easy marks if you are systematic.

Graphs in depth: representation, BFS, DFS, and shortest paths

A graph is a set of vertices (nodes) joined by edges. Unlike a tree, a graph may have cycles and need not be connected. An edge may be undirected (two-way) or directed (one-way, an arrow); it may be weighted (carrying a cost, distance, or capacity) or unweighted. Graphs model networks of every kind: road maps, social connections, the world wide web, computer networks, dependencies between tasks, and state spaces in games.

Representing a graph

Two standard representations trade space for speed. An adjacency matrix is an n×n table where cell [i][j] is 1 (or the weight) if an edge joins i and j, else 0. It answers "are i and j connected?" in O(1) and suits dense graphs, but uses O(n²) space. An adjacency list stores, for each vertex, a list of its neighbours; it uses O(V + E) space and suits sparse graphs, though an edge lookup takes O(degree). Choose the matrix when the graph is dense or you frequently test adjacency; choose the list when it is sparse or you iterate over neighbours.

Breadth-first vs depth-first search

Both visit every reachable vertex, but in different orders and with different uses. BFS explores level by level using a queue: visit the start, enqueue its neighbours, then dequeue and repeat. BFS finds the shortest path in edges on an unweighted graph and is the basis of many network broadcasts. DFS goes as deep as possible first using a stack (or recursion): descend, backtrack when stuck. DFS detects cycles, topologically orders tasks, and explores mazes. Both run in O(V + E); the difference is the order and the auxiliary structure (queue vs stack).

Worked — BFS order

Graph: A connected to B, C; B to D; C to D, E; start at A. BFS: visit A (queue [A]); dequeue A, enqueue B, C (queue [B,C]); dequeue B, enqueue D (queue [C,D]); dequeue C, enqueue E (queue [D,E]); dequeue D (no new); dequeue E (no new). Visited order: A, B, C, D, E. Notice D is reached via B before C's branch is exhausted — that level-by-level behaviour is what guarantees BFS finds the fewest-edge path from A to any node.

Shortest path: Dijkstra's algorithm

For a weighted graph with non-negative edges, Dijkstra's algorithm finds the shortest total weight from a source to all vertices. Maintain a set of distances, initially infinity except the source at 0. Repeatedly pick the unvisited vertex with the smallest known distance, mark it visited, and relax its neighbours: if going through it is cheaper, update their distances. A priority queue makes this efficient. Dijkstra fails on negative edges (use Bellman–Ford there).

Worked — Dijkstra

Vertices A,B,C,D with edges A–B(4), A–C(1), C–B(2), B–D(1), C–D(5). Source A. Start dist: A0, others ∞. Visit A: relax B to 4, C to 1. Visit C (smallest, dist 1): relax B via C to 1+2=3 (better than 4, update), relax D to 1+5=6. Visit B (dist 3): relax D to 3+1=4 (better than 6, update). Visit D. Final shortest distances: A0, C1, B3, D4. Path to D is A→C→B→D with total weight 4, not the direct A→C→D (weight 6). Dijkstra correctly preferred the longer-looking detour because it was cheaper overall.

Minimum spanning tree and topological sort

A minimum spanning tree (MST) connects all vertices with the minimum total edge weight and no cycles — useful for laying cable cheaply. Kruskal's algorithm sorts edges and adds the smallest that does not form a cycle; Prim's grows the tree from one vertex, always adding the cheapest edge reaching a new vertex. A topological sort orders vertices of a directed acyclic graph so every edge points forward — used to schedule tasks with prerequisites (a course before its dependent). If the graph has a cycle, no topological order exists, which itself detects impossible dependency loops.

Trap — BFS vs Dijkstra

BFS gives the shortest path in number of edges (unweighted). On a weighted graph, the fewest-edge path can be the most expensive, so you need Dijkstra. Using BFS on weighted edges to answer "shortest distance" is a frequent mistake — check whether edges have weights first.

Exam tip

For any graph algorithm question, state: (1) the structure used (queue for BFS, stack/recursion for DFS, priority queue for Dijkstra), (2) the time complexity O(V+E) or O(E log V), and (3) what it computes (shortest edges, reachability, shortest weight, MST). That three-part answer covers the usual marks.

Hashing in depth: functions, collisions, and load factor

A hash table maps keys to values for average O(1) lookup, insert, and delete — faster than arrays (O(1) access but fixed content) or trees (O(log n) search). A hash function takes a key and returns an index into an array (the bucket array). For the string "cat", a simple hash might sum character codes then take sum mod table_size. A good hash function distributes keys uniformly across buckets and is deterministic (same key always same index) and fast to compute.

Collisions and resolution

A collision happens when two keys hash to the same bucket — unavoidable once you store more items than buckets, by the pigeonhole principle. Two main resolutions:

  • Separate chaining: each bucket holds a linked list (or tree) of colliding items. Insert appends to the list; search walks the list. Simple and degrades gracefully; needs pointers.
  • Open addressing: colliding items are placed in another bucket by a probe sequence — linear probing (try +1, +2, ...), quadratic probing (+1, +4, +9, ...), or double hashing (a second hash gives the step). Search follows the same probe sequence until the key or an empty slot is found.
Worked — separate chaining collision

Table size 10, hash = key mod 10. Insert keys 12, 25, 33. 12 mod 10 = 2 → bucket 2. 25 mod 10 = 5 → bucket 5. 33 mod 10 = 3 → bucket 3. Now insert 22: 22 mod 10 = 2, but bucket 2 already holds 12 — collision. With chaining, bucket 2 becomes the list [12 → 22]. Searching for 22 hashes to 2, walks the list, finds 22 in two steps. With linear probing instead, 22 would be placed in bucket 3 if 2 and 3... (here 3 is free) so 22 goes to 3. Both strategies resolve the clash; chaining keeps items at their hash index, probing spreads them out.

Load factor and rehashing

The load factor α = n / m (items ÷ buckets) measures how full the table is. As α grows, collisions multiply and lookups slow toward O(n) in the worst chain. Keep α low (often under 0.75) by rehashing: when α crosses a threshold, allocate a larger bucket array (often double) and re-insert every item, recomputing indices with the new size. Rehashing is occasional and amortised cheap, like dynamic-array growth.

Trap — clustering in linear probing

Linear probing suffers primary clustering: colliding runs merge into long blocks, so even empty buckets far away get probed slowly. Quadratic probing reduces this but can fail to find a free slot unless the table size is prime and α < 0.5. Double hashing avoids clustering best but needs a second independent hash. Know the trade-off for the exam.

Uses of hashing

Hash tables back sets, dictionaries/maps, caches, symbol tables in compilers, password storage (store a salted hash, never the plaintext), and fast duplicate detection. They are the right choice whenever you need "is this key present?" or "what value goes with this key?" and order does not matter.

Recursion in depth: base cases, tree recursion, and memoisation

A recursive function solves a problem by calling itself on a smaller subproblem, with two essential parts: a base case that stops the recursion (otherwise it never ends), and a recursive step that reduces the problem toward the base case. Every recursive solution can be rewritten as iteration with an explicit stack, but recursion is often clearer for naturally nested problems (trees, divide-and-conquer, backtracking).

Linear and tree recursion

Linear recursion makes at most one recursive call per step (e.g. summing a list, factorial) — its call stack depth is O(n) and it is easily iterative. Tree recursion makes multiple calls (e.g. Fibonacci: fib(n) = fib(n-1) + fib(n-2)) — the number of calls explodes exponentially because subproblems overlap and are recomputed. The naive Fibonacci does roughly 2ⁿ calls, which is why it is the textbook warning.

Worked — factorial and its call stack

fact(n): if n == 0 return 1; else return n * fact(n-1). Computing fact(4): fact(4) calls fact(3) calls fact(2) calls fact(1) calls fact(0) → 1, then unwinds: 1×1=1, 2×1=2, 3×2=6, 4×6=24. The base case n==0 stops it; without it the calls would continue to negative infinity and overflow. Notice the work (the multiplication) happens on the way back up the stack — a hallmark of linear recursion.

Memoisation and dynamic programming

Memoisation caches results of expensive recursive calls so repeated subproblems are not recomputed: fib(n) stores its answer the first time and returns it instantly thereafter, turning exponential time into O(n). Dynamic programming is the bottom-up cousin — build the answer in an array from the smallest subproblem up, also O(n), with no recursion overhead. Both exploit overlapping subproblems; the choice is top-down (memoised recursion) vs bottom-up (iteration).

Worked — Fibonacci with memoisation

fib(5) needs fib(4) and fib(3); fib(4) needs fib(3) and fib(2). Without memo, fib(3) is computed twice. With a cache, after fib(3) is computed once it is returned from the cache, so the total calls drop from 15 to 9 for fib(5), and from exponential to linear for large n. The cache is just a hash table keyed by n — a neat meeting point of two topics on this page.

Divide and conquer, and tail recursion

Divide and conquer splits a problem, conquers each half, and combines: merge sort splits the array, sorts each half, merges them in O(n) — overall O(n log n); quicksort picks a pivot, partitions around it, and recurses — average O(n log n). Tail recursion is recursion where the recursive call is the last action; some compilers reuse the stack frame (optimising to a loop), avoiding stack growth. Non-tail recursion (like factorial's multiplication after the call) cannot be so optimised and can overflow on deep input.

Trap — infinite recursion

Forgetting or mis-writing the base case, or a recursive step that does not shrink the problem (e.g. calling f(n) instead of f(n-1)), causes infinite recursion and a stack overflow. Always verify: (1) is there a base case? (2) does each call move strictly toward it? If either is no, the function is broken.

Exam tip

For a recursion question, write the base case first, then the reduction, then trace two or three small inputs by hand to show the unwinding. Mentioning the time/space cost (e.g. "tree recursion without memo is exponential; with memo it is linear") earns the algorithm-analysis marks that separate grade 6/7 answers.

ADT contracts and invariants

An ADT is defined by its contract: the operations it exposes and the axioms / invariants they must preserve. A stack's invariant is "the most recently pushed item is the next popped"; a queue's is "the oldest enqueued item is the next dequeued"; a BST's is "left subtree < node < right subtree". The contract lets you swap implementations (array vs linked list, balanced vs plain) without changing calling code — this information hiding is the whole point of abstract data types and of object-oriented design generally. You program to the interface, not the internals.

Sorting is the canonical use of arrays, recursion, and divide-and-conquer, and a favourite exam topic. The main contenders:

Worked — insertion sort trace

Sort [5, 2, 4, 6, 1, 3]. Take 2: shift 5 right, insert 2 → [2,5,4,6,1,3]. Take 4: shift 5 right, insert before 5 → [2,4,5,6,1,3]. Take 6: already in place → [2,4,5,6,1,3]. Take 1: shift 2,4,5,6 right, insert at front → [1,2,4,5,6,3]. Take 3: shift 4,5,6 right, insert → [1,2,3,4,5,6]. Sorted. Each step inserts the next element into the already-sorted prefix; cost is O(n) per element in the worst arrangement, so O(n²) overall, but only O(n) when the input is nearly sorted — which is why insertion sort is useful in practice for small or almost-ordered data.

Trap — quicksort worst case

Quicksort degrades to O(n²) if the pivot is consistently the smallest or largest element (e.g. always picking the first element of an already-sorted array). Mitigate by randomising the pivot or using median-of-three. Never assume quicksort is always O(n log n) — state "average case" when you claim it.

Implementing ADTs: pseudocode and the array vs list choice

Because an ADT is a contract, the same structure can be built several ways. Seeing two implementations side by side cements the idea that the interface is what matters, not the internals.

Stack on an array

STACK: array of size N
top ← -1                     // empty when top == -1

PUSH(x):
  IF top == N-1 THEN ERROR "overflow"
  top ← top + 1
  STACK[top] ← x

POP():
  IF top == -1 THEN ERROR "underflow"
  x ← STACK[top]
  top ← top - 1
  RETURN x

PEEK():
  IF top == -1 THEN ERROR "empty"
  RETURN STACK[top]

The single top index is the stack's entire state; push and pop move it and read/write the end. This is O(1) and cache-friendly, but the array has a fixed ceiling (unless you grow it like a dynamic array).

Queue on a circular array

Q: array of size N
front ← 0, rear ← 0, count ← 0   // count avoids full/empty ambiguity

ENQUEUE(x):
  IF count == N THEN ERROR "full"
  Q[rear] ← x
  rear ← (rear + 1) MOD N
  count ← count + 1

DEQUEUE():
  IF count == 0 THEN ERROR "empty"
  x ← Q[front]
  front ← (front + 1) MOD N
  count ← count - 1
  RETURN x

Tracking count cleanly distinguishes a full queue from an empty one without wasting a slot. The modulo wrap makes the array circular so space is reused.

Worked — stack on a linked list

Represent the stack as a list with head pointing to the top node. PUSH(x): create node x, set x.next = head, head = x — O(1), no overflow. POP(): if head == null error underflow; else t = head, head = head.next, return t.value — O(1). Compared with the array version, this never overflows (until memory runs out) and needs no top variable, at the cost of a pointer per node. Both honour the LIFO contract identically, so calling code cannot tell which is underneath — exactly the abstraction payoff.

Recursion vs iteration — a worked comparison

Summing 1..n shows the trade. Iterative: total = 0; for i = 1 to n: total += i; return total — O(n) time, O(1) space. Recursive: sum(n): if n == 0 return 0 else return n + sum(n-1) — O(n) time but O(n) space for the call stack. For this problem iteration is better (same time, less space). Recursion wins when the problem is naturally recursive (tree traversal, divide-and-conquer) and the iterative version would need an explicit stack you would be reimplementing by hand.

Trap — tail vs non-tail

Only tail recursion (the call is the final operation) can be turned into a loop by an optimising compiler without extra stack. Factorial as written is non-tail (it multiplies after the call returns), so a deep input can still overflow even in languages that optimise tail calls. To make factorial tail-recursive, pass the running product as an extra parameter so the multiplication happens before the call.

ADTs in real libraries and why the idea matters

Every modern language ships ADTs as built-ins, and recognising them saves you from reinventing wheels. Python's list is a dynamic array (O(1) append, O(n) insert-middle); its collections.deque is a double-ended queue; dict and set are hash tables; heapq is a binary heap. Java's ArrayList is a dynamic array, LinkedList a doubly linked list, HashMap a hash table, TreeMap a red-black tree, PriorityQueue a heap. The names differ; the contracts are the same ADTs you have studied. When you choose a collection in code, you are really choosing an ADT by its complexity guarantees.

The deeper lesson is abstraction: a stack is a stack whether it sits on an array, a list, or a disk file. By programming to the contract (push/pop) rather than the representation, you can change the implementation for performance or memory without touching the rest of the program. This separation of what a structure does from how it does it is the foundation of good software design and appears again in object-oriented programming (B3) and in the way operating systems present files and processes as clean interfaces over messy hardware.

Exam tip

If asked "why use an abstract data type?", give three points: (1) it hides implementation details so they can change; (2) it guarantees a known set of operations with predictable complexity; (3) it reduces errors by enforcing an invariant (e.g. LIFO). That trio is the standard marks for any "advantages of abstraction" question.

Invariants as a reasoning tool

An invariant is a property that is always true of a structure between operations. For a BST it is the ordering rule; for a stack it is "top is the last pushed"; for a queue it is "front is the oldest". Reasoning with invariants lets you prove correctness: show the invariant holds initially, is preserved by every operation, and implies the operation does what is claimed. This is how computer scientists argue a data structure is right without testing every input — and it is the same logic used to verify algorithms and protocols elsewhere in the syllabus.

More worked examples: heaps, DFS, and topological sort

Worked — heap insert and extract-min

Build a min-heap from 5, 9, 3, 1. Insert 5 (heap: [5]); insert 9 (parent 5 ≤ 9, stays: [5,9]); insert 3 (3 < parent 5, swap: [3,9,5]); insert 1 (1 < parent 3, swap: [1,9,5,3] then bubble: 1's parent is 3? actually 1 at index 0, no swap needed; final [1,3,5,9] after placing 1 and 3 swapping). The root is always the minimum, so extract-min returns 1 and replaces the root with the last element, then sifts down (swap with the smaller child) to restore the heap. Heap insert and extract are both O(log n), which is why heaps power priority queues and heapsort efficiently.

Worked — DFS order and cycle detection

Graph A→B, A→C, B→D, C→D, D→(none); start at A. DFS (visit node, then recurse deepest first): visit A, go to B (not yet visited), from B go to D; D has no unvisited neighbours, backtrack to B, backtrack to A, go to C; C's neighbour D is already visited, so stop. Visited order: A, B, D, C. Compare with the earlier BFS order A, B, C, D — same nodes, different sequence, because DFS plunges deep before broadening. Had there been an edge D→A we would have revisited A and, detecting a node on the current path (not just visited), confirmed a cycle.

Worked — topological sort

Tasks: "Study arrays" (A) before "Study lists" (B); "Study lists" (B) before "Study trees" (C); "Study stacks" (S) before "Study recursion" (R); no cycle. Edges A→B→C and S→R. A valid topo order respecting all edges is A, B, C, S, R (or S, R, A, B, C, etc. — any order where each task precedes its dependents). To compute it, repeatedly take a node with no incoming edge, output it, and remove its outgoing edges; Kahn's algorithm does exactly this with a queue of zero-indegree nodes. If you cannot find a zero-indegree node before finishing, a cycle exists and no order is possible.

Trap — visited vs on-stack

In DFS, "already visited" is not the same as "cycle". A cross-edge to an already-finished node is fine; a back-edge to a node still on the current recursion path is a cycle. Confusing the two makes you report false cycles. Track a separate "currently in the path" set, not just "visited".

Evaluating and comparing abstract data types

The IB often asks you to evaluate a choice, not just describe it. Use explicit criteria so the answer is defensible: time complexity of the operations you actually perform, space overhead, implementation simplicity, and suitability for the access pattern. A hash table beats a BST for pure lookup but loses if you need range queries or sorted order; an array beats a linked list for indexed access but loses for frequent middle insertions; a stack beats a queue only when LIFO is what the problem needs.

Worked — evaluate for a browser history

Need: go back through visited pages (most recent first), and forward again. Choice: two stacks — one for "back" (push each new page; back pops), one for "forward" (cleared on a new navigation, refilled when going back). Why not a queue: a queue is FIFO, but history is LIFO (last page visited is the first to return to), so a stack matches the invariant. Why not a list: a list works but managing the "current position" pointer is exactly reimplementing two stacks. Conclusion: two stacks are the natural, simplest structure. This shows evaluation: match the invariant to the operation, reject mismatched alternatives with a reason.

Exam tip

Structure an evaluation as: state the requirement → name the structure → give the key operation's complexity → say why alternatives are worse → conclude. One sentence per step. This disciplined shape is what moves an answer from description (low marks) to evaluation (high marks).

Performance in practice: locality, memory, and honest trade-offs

Big-O tells you how cost grows with n, but constant factors and the memory hierarchy decide real speed. An array is contiguous, so sequential access streams through the CPU cache efficiently — this locality of reference makes arrays fast even when a linked list has the same Big-O for the operation. A linked list scatters nodes across memory, so traversing it causes cache misses and is often slower in practice than an array despite identical O(n) traversal. This is why, for moderate sizes, a dynamic array usually beats a linked list even at insert-in-middle, unless inserts are extremely frequent and random.

Memory overhead also matters. A linked list spends a pointer (8 bytes on a 64-bit machine) per node — significant for millions of small items. A tree node carries two child pointers plus the value. A hash table keeps a bucket array plus, for chaining, a pointer per entry. When memory is tight (embedded systems, huge datasets), these overheads influence the choice as much as asymptotic complexity.

Designing your own ADT

When a problem needs behaviour no built-in offers, design an ADT: (1) name the operations the caller needs; (2) state the invariant each operation must preserve; (3) pick a representation that makes the common operations cheap; (4) hide the representation behind the operations. Example: a "recently used" cache is a hash table (O(1) lookup) plus a doubly linked list (move-to-front on access, evict tail) — the classic LRU cache. Combining ADTs is how real systems are built, and the IB rewards students who can name the pieces and why they fit.

One-paragraph mental model

An abstract data type separates what a collection does (its operations and invariant) from how it is built (array, list, tree, hash). Arrays give O(1) indexed access but O(n) middle edits; linked lists flip that; stacks and queues are restricted arrays/lists for LIFO and FIFO; trees and BSTs add hierarchy and O(log n) ordered search; graphs model arbitrary connections with BFS/DFS/Dijkstra; hash tables buy O(1) lookup by relaxing order; recursion solves nested problems by calling itself with a base case. Pick the structure whose fast operations match your access pattern, and program to the contract so the implementation can change.

Balanced trees and structures working together

A plain BST's performance depends on insertion order and can degrade to a chain (height n, operations O(n)). Self-balancing trees fix this by restructuring after modifications to keep height near log n. An AVL tree tracks a balance factor (height of left subtree minus height of right) at each node and performs rotations when it leaves the range −1..+1, guaranteeing O(log n) operations. A red-black tree colours nodes red/black with rules that also bound height, used in many language libraries (e.g. Java's TreeMap) because rotations are cheaper on average. You are not required to memorise rotation code, but you should know why balancing exists: to keep the BST's logarithmic promise regardless of input order.

Worked — why balance matters

Insert 10, 20, 30, 40, 50 into a plain BST: each is larger than the last, so every node is a right child — the tree is a straight chain of height 4 for 5 nodes. Searching for 50 walks all five nodes, O(n). In an AVL tree the same inserts trigger a left rotation after 30 (around 20), producing 20 as root with 10 left and 30 right, then later rotations keep it bushy; searching for 50 now takes about 2–3 steps, O(log n). The data is identical; only the shape — and therefore the speed — differs. This single contrast explains the entire motivation for balanced trees.

B-trees and databases

A B-tree (and its variant the B+ tree) is a balanced tree where each node holds many keys and many children, so the tree is shallow and wide. Because a node maps to a disk block, a B-tree minimises the number of disk reads to reach a record — exactly what a database index needs when data is too big for RAM. A B+ tree keeps all values in the leaves, linked in a list, so range queries ("all customers with id between 100 and 200") scan leaves sequentially without traversing the tree repeatedly. This is the structure behind virtually every relational index you studied in databases (A3): the two topics meet here.

Structures combine in real systems

Real software rarely uses one ADT alone. A cache pairs a hash table (O(1) lookup) with a doubly linked list (order by recency) for LRU eviction. A graph algorithm stores the graph as an adjacency list (linked lists or arrays) and uses a priority queue (heap) for Dijkstra and a queue (BFS) or stack (DFS) for traversal. A compiler uses a hash table for its symbol table and trees for the parse tree. Recognising these combinations — and naming the role of each piece — is the most impressive thing you can write in an evaluation question, because it shows you understand ADTs as engineering building blocks, not isolated exam facts.

The big picture: why abstract data types are foundational

Step back and the whole B4 topic is one idea repeated at different scales: separate behaviour from representation, and choose the representation by the operations you perform most. A variable is the simplest data structure; an array groups variables by index; a list frees them from a fixed size; stacks and queues restrict access to make intent explicit; trees add hierarchy; graphs add arbitrary connection; hash tables trade order for speed. Recursion is the natural way to traverse the hierarchical ones. None of this is trivia — it is the vocabulary every programmer uses to turn a messy problem into code that is correct, fast, and maintainable.

This matters beyond the exam. When you later study algorithms, operating systems, databases, or machine learning, you will meet the same structures: a file system is a tree, a process schedule is a queue or heap, an index is a B-tree, a neural network's computation graph is a directed acyclic graph, a search is BFS or DFS. Mastering ADTs now is mastering the grammar of the rest of computer science. The invariant-first habit — state what must always be true, then prove each operation preserves it — is the same rigorous thinking the whole subject trains you in.

Worked problem patterns you will recognise

Many exam questions are variations on a few patterns. Learning the pattern saves time under pressure.

Pattern 1 — "Is this balanced?" (brackets)

Push every open bracket; on a close, pop and confirm matching type; the stack must be empty at the end and never empty when popping. This is the universal bracket-check and a frequent warm-up question.

Pattern 2 — "Evaluate this expression" (postfix)

Push operands, on an operator pop two (second popped is left), compute, push result. Watch operand order for − and ÷. This is the universal RPN evaluator and a reliable 4–6 mark question.

Pattern 3 — "Traverse this tree"

Pick the order (pre/in/post), write the rule (node position), and walk it mechanically, labelling left/right. In-order on a BST yields sorted output — state that only for a BST.

Pattern 4 — "Shortest path"

If unweighted, BFS; if weighted, Dijkstra with a relaxation table. Show the distance table shrinking as you settle vertices. State the final path and its total weight.

Pattern 5 — "Recommend a structure"

Name it, state the key operation's complexity, give the invariant, and reject an alternative with a reason. End with a one-line conclusion. This is the evaluation pattern that earns the top band.

Trap — pattern without checking the premise

Before applying a pattern, confirm its premise: is the tree actually a BST (for sorted in-order)? are edges actually weighted (for Dijkstra)? is the structure actually a stack (for LIFO)? Applying the right pattern to the wrong premise is the most common way to produce a confident, wrong answer. Ten seconds checking the premise prevents it.

With these five patterns and the complexity table in your head, almost every B4 question reduces to "which pattern, applied to what data?" — which is exactly the structured thinking the exam rewards.

Self-check

  1. Define an abstract data type and explain why a stack can be implemented with either an array or a linked list.

    Show answer
    An ADT specifies a set of values, operations, and axioms (rules) without committing to an implementation. A stack's contract is just push/pop/peek/isEmpty with LIFO behaviour; both an array (using an end index) and a linked list (adding/removing at the head) can honour that contract, so either implementation is valid and interchangeable behind the same interface.

  2. Compare arrays and linked lists on random access and on insertion in the middle. Give the Big-O of each.

    Show answer
    Array: random access O(1) by index, but middle insertion O(n) because later elements must shift. Linked list: random access O(n) (walk from head), but middle insertion O(1) once you are at the node (rewire two pointers). Choose by the dominant operation.

  3. A stack starts empty. Perform push(5), push(2), pop(), push(9), pop(), pop(). What do the pops return, and what is the final state?

    Show answer
    push(5) → [5]; push(2) → [5,2]; pop() returns 2 → [5]; push(9) → [5,9]; pop() returns 9 → [5]; pop() returns 5 → []. Pops return 2, 9, 5 (LIFO); final stack empty.

  4. Name the three tree traversals and state what in-order gives for a BST.

    Show answer
    In-order (left, node, right), pre-order (node, left, right), post-order (left, right, node). For a binary search tree, in-order visits the values in ascending (sorted) order — but only because of the BST ordering rule, not the traversal itself.

  5. In a BST, what is the worst-case time for search, and when does it happen?

    Show answer
    Average O(log n) when balanced, but worst case O(n) when the tree is degenerate — e.g. keys inserted already sorted, so the tree becomes a linked-list shape with height n. Each comparison then only removes one node.

  6. Contrast an adjacency matrix with an adjacency list, and say which BFS uses.

    Show answer
    Adjacency matrix: a V×V table, edge check O(1), but O(V²) space — good for dense graphs. Adjacency list: each vertex lists its neighbours, space O(V+E), good for sparse graphs. BFS itself does not depend on the representation; it uses a queue to explore in distance order and visits every vertex and edge in O(V+E) either way.

  7. What is a hash collision and how does chaining handle it? What is the worst-case cost?

    Show answer
    A collision is when two different keys hash to the same index. Chaining stores a linked list at each bucket, so both keys live in that list and search walks the list. Average insert/search is O(1), but worst case is O(n) if many keys collide into one bucket (bad hash function or overload).

  8. Why must every recursive algorithm have a base case, and give a tree example?

    Show answer
    Without a reachable base case the function calls itself forever until the call stack overflows. In-order tree traversal stops at the base case "if node is null, return" before recursing on left and right children. The base case bounds the recursion and is explicitly checked in markschemes.
