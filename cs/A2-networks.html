Computer Science HL · Theme A · A2

A2 · Networks

A computer on its own is a calculator; a computer on a network is part of civilisation. This topic is about how machines talk — the rules (protocols) they obey, the addresses they use to find each other, the boxes that move data between them, and the ways that conversation can be attacked. The IB treats networks as applied theory: you are far more likely to be asked to explain why TCP exists than to memorise a port number. Learn the models (OSI and TCP/IP) as a map of responsibilities, learn the difference between an IP address and a MAC address as a difference between "where" and "who", and learn the three or four security mechanisms as a mechanism-plus-consequence story. The two traps are confusing the layers (a switch is layer 2, a router is layer 3 — never swap them) and treating security as a list of product names instead of a set of threats and the control that defeats each one.

Why this exists

Two computers cannot simply "send a message". They must agree on which wire to use, how to address the receiver, how to break a long message into pieces, what to do if a piece is lost, and how to know the sender is who they claim. Every one of those agreements is a protocol, and protocols are arranged in layers so that you can change the physical wire without rewriting the email program. Networks are the clearest example in the course of abstraction done right: each layer hides the one below it, and the whole internet is just seven (or four) such layers stacked in agreement. Learn the layers as a story — "how does a keystroke become a packet and back?" — and the facts fall into place.

1 · What a network is, and the three scales

SL / HL

Intuition

A network is two or more devices that can exchange data. The scale determines the technology. A PAN (personal area network) is the bubble around one person — a phone talking to earbuds over Bluetooth, a few metres. A LAN (local area network) is one site — a school, an office — typically Ethernet and Wi-Fi, owned and managed by one organisation. A WAN (wide area network) spans cities or continents; the internet itself is a WAN of WANs, and no single entity owns it. The distinction matters because different scales have different speeds, ownership, and trust: you secure your LAN differently from a public WAN link.

Formal idea: the vocabulary of connection

A node is any device on the network (computer, printer, phone). A host is a node with a full implementation of the internet protocols (usually a computer or server). A link is a single connection; a medium is what carries the signal (copper, fibre, radio). Bandwidth is the maximum data rate of a link (measured in bits per second); latency is the time for one bit to travel end to end; throughput is the actual achieved rate, always ≤ bandwidth, and reduced by congestion, errors and protocol overhead. A channel can be simplex (one way only, like a TV broadcast), half-duplex (either way but not both at once, like a walkie-talkie) or full-duplex (both ways at once, like a phone call).

Exam technique — bandwidth is a rate, not an amount

Bandwidth is bits per second, so a "100 Mbps" link is not "100 megabytes" — divide by 8 for bytes, and then by a real factor for overhead. A 10 MB file (80 Mb) on a 100 Mbps link takes at least 0.8 s in a perfect world, but usually longer because of protocol headers and congestion. The classic markscheme question is "how long to download X", and the working is size ÷ bandwidth, with an explicit note that throughput is less than bandwidth.

2 · Topologies and the devices between nodes

SL / HL

Intuition

The topology is the shape of the connections. A bus runs one shared cable that every node taps into — cheap, but a break kills the whole network and only one device can speak at a time. A star wires every node to a central switch; one cable failing isolates only that node, and the switch lets several conversations happen at once — which is why nearly every modern LAN is a star. A ring passes a token around; a mesh connects many nodes to many others for redundancy (the internet's backbone is a mesh). A hybrid mixes them. The topology you choose trades cost, reliability and capacity.

The boxes: hub, switch, router, gateway

These are the most-confused terms. A hub is a dumb repeater: it copies any incoming frame to every port, so all nodes share one collision domain (obsolete). A switch is layer 2: it learns which MAC address lives on which port and forwards a frame only to the right port, so different pairs can talk at the same time. A router is layer 3: it connects different networks and forwards packets based on IP addresses, choosing a path across the internet. A gateway translates between different protocol families (e.g. your home router is really a router + switch + NAT gateway + firewall in one box, which is why the names blur at home).

Trap — switch vs router vs hub

A switch forwards by MAC address within one network (layer 2); a router forwards by IP address between networks (layer 3); a hub floods everywhere. If a question says "connects the school LAN to the internet", that is a router, not a switch. If it says "lets ten PCs share one collision-free segment", that is a switch. Swapping them loses the mark.

Comparing the topologies

The topology is a design choice with three consequences: cost (how much cable/equipment), reliability (what a single failure breaks), and performance (can several pairs talk at once, and is there contention?). The table collects the usual comparison; an evaluation question is almost always "recommend a topology for X and justify", and the justification is one of these three columns.

Exam technique — recommend by the dominant constraint

"Recommend a topology for a small office" → star (cheap enough, resilient per-node, concurrent). "For a life-critical control network" → mesh (survives failures). "For a temporary cheap link between two rooms" → bus (lowest cost). State the constraint you are optimising (cost / resilience / capacity) and the topology follows; an answer with no stated constraint is only half a mark.

3 · The layered models: OSI and TCP/IP

SL / HL

Intuition

Networks are built in layers so each layer only has to please the one above and below it. The OSI model is the seven-layer teaching reference; the TCP/IP model is the four-layer stack the internet actually uses. You should know both and how they map. The golden rule: data is encapsulated as it goes down — each layer wraps the layer above's data in its own header — and decapsulated as it comes up.

Why layers — the "letter in an envelope in a box" analogy

Think of sending a letter: you write the message (application), put it in an envelope with an address (transport/network), hand it to a courier who puts it in a crate with a tracking label (data link), who drives a truck on a road (physical). At the far end each wrapper is opened in reverse. No layer needs to know how the road works to deliver the message; that is the whole point of layering. When you "explain the journey of a packet", walk down the layers adding headers and up the layers removing them.

What each OSI layer actually does

Trap — "the internet uses OSI"

The internet implements the TCP/IP model (four layers: Application, Transport, Internet, Link), not the seven-layer OSI model. OSI is the teaching reference; TCP/IP is what runs. When a question says "which OSI layer?", answer in OSI terms (it is testing the model); when it says "what does the internet use?", say TCP/IP. Conflating "the network layer" with a specific OSI number is fine, but don't claim the real protocol stack has seven layers.

Worked example 1 IB-style · 6 marks · map a fault to a layer

Question. A user can ping a server (so the network and transport layers work) but cannot load its web page. (a) At which OSI layer is the fault most likely? (b) Name the protocol involved and one other fault that would sit at a different layer.

  1. (a) Because ICMP ping uses the network/transport layers successfully, the fault is at the application layer (layer 7) — most likely the web server's HTTP service is down, or a firewall is blocking port 80/443, or the DNS name did not resolve to the right address.
  2. (b) The protocol is HTTP/HTTPS (application). A different-layer fault: a broken cable (layer 1 physical) would stop ping too; a wrong subnet mask (layer 3 network) would also stop ping. The key reasoning is "lower layers work, so the fault is higher".
Marks: 2 for correctly isolating the application layer with the reasoning that lower layers succeed, 2 for naming HTTP(S), 2 for a valid contrasting fault at another layer. The mark is in the reasoning (eliminate from the bottom up), not in naming a product.
Trap — TLS sits across the boundary

TLS (the S in HTTPS) is often placed at OSI layer 6 (presentation) because it encrypts, but it is invoked by the application. In the TCP/IP model it lives inside the application layer, beneath HTTP. If asked "which layer provides confidentiality?", say "presentation (layer 6) in OSI, or within the application layer in TCP/IP" — naming only one model is fine, but don't say "the network layer", which is IP and is not encrypted by default.

Walking one message down and up the stack

To make the layers concrete, follow a web request from a laptop to a server. Down at the sender: the browser writes the HTTP request (application); TCP adds a port header and splits it into segments (transport); IP adds the source and destination addresses to make a packet (network); Ethernet adds the MAC addresses of the next hop and a frame check to make a frame (data link); the bits go onto the wire or air (physical). At each router, only the network and below are touched — the router reads the IP, decides the next hop, rewrites the Ethernet frame (new MACs) and forwards; the TCP and HTTP headers are untouched. Up at the receiver the process reverses: physical → data link (check frame, strip MAC) → network (check IP) → transport (reassemble segments, check port) → application (hand the HTTP response to the browser). Encapsulation is why a change at the physical layer (fibre instead of copper) requires no change to your code.

Worked example 1b IB-style · 6 marks · which header changes at a router

Question. A packet travels from your laptop, through your home router, across three ISP routers, to a web server. (a) Which layer-3 and layer-2 headers change at each router, and which never change? (b) Why does the TCP header survive unchanged?

  1. (a) At each router the data-link (Ethernet) header is rewritten — the source and destination MAC addresses become those of the router's incoming and outgoing interfaces. The IP (network) header stays the same end to end (same source/destination IP), as does the TCP and HTTP content.
  2. (b) The TCP header survives because routing is a network-layer function; routers do not open or modify transport-layer data. Only the frame wrapping changes per hop, which is exactly what lets IP provide end-to-end delivery while the link technology varies.
  3. The takeaway: MAC addresses are hop-by-hop and reset each time; IP addresses are end-to-end and fixed for the journey.
Marks: 2 for "Ethernet/MAC header rewritten each hop", 2 for "IP/TCP/HTTP unchanged end to end", 2 for explaining routers act at layer 2/3 only. The single most-missed point is that the IP address does NOT change at a router — only the MAC does.

4 · Addressing: MAC, IPv4, IPv6, and subnetting

SL / HL

Intuition

Two addresses live on every networked device and students constantly confuse them. The MAC address is burned into the network card at manufacture — it identifies who the device is, and never changes. The IP address is assigned by the network — it identifies where the device is right now, and changes when you move. MAC is used for delivery on one local link (layer 2); IP is used for delivery across the whole internet (layer 3). A helpful image: the MAC is the device's face, the IP is its current postal address. The MAC gets a frame to the next hop; the IP gets the packet to the final destination, possibly across many hops.

Formal idea: IPv4, subnet masks, and the concept of subnetting

An IPv4 address is 32 bits, written as four decimal octets (e.g. 192.168.1.20). A subnet mask (or CIDR suffix like /24) says which bits are the network part and which are the host part. In 192.168.1.20 with mask 255.255.255.0 (/24), the first 24 bits (192.168.1) are the network and the last 8 bits are the host, so this network holds host numbers 1–254 (0 is the network address, 255 is the broadcast). Two devices are on the same subnet if their network parts match; otherwise traffic must go via a router. Subnetting is splitting a large network into smaller ones, to limit broadcast traffic, improve security, and use addresses efficiently. IPv6 uses 128 bits (written in hex groups like 2001:0db8::1) and exists because IPv4's ~4.3 billion addresses ran out; it has no need for NAT and includes features like stateless address auto-configuration.

Worked example 2 IB-style · 8 marks · subnet mask and "same subnet?" test

Question. Host A is 10.0.2.30 /24. Host B is 10.0.3.40 /24. (a) State the network address of each. (b) Determine whether they are on the same subnet, and state what device must carry traffic between them if not. (c) How many host addresses does the /24 subnet provide?

  1. (a) Apply the /24 mask (255.255.255.0): keep the first three octets. A's network = 10.0.2.0. B's network = 10.0.3.0.
  2. (b) The network parts differ (10.0.2 vs 10.0.3), so they are not on the same subnet. Traffic between them must pass through a router.
  3. (c) A /24 has 8 host bits → 2⁸ = 256 addresses, minus the network address (.0) and the broadcast address (.255) = 254 usable host addresses.
  4. Sanity check: if the mask had been /23 (255.255.254.0), the boundary falls between 10.0.2 and 10.0.3, and both could be in one subnet — which is exactly why the mask, not the IP, decides subnet membership.
Marks: 2 for the two network addresses, 3 for the correct "different subnet ⇒ router" conclusion with the AND reasoning, 2 for 254 usable hosts, 1 for the sanity note. The classic error is saying "they are on the same subnet because the first two octets match" — only the masked bits count.

Why IPv6, and how it differs

IPv4's 32-bit space (about 4.3 × 10⁹ addresses) was exhausted as phones and devices multiplied, which is why NAT (network address translation) was invented to let many devices share one public IP. IPv6's 128-bit space (3.4 × 10³⁸ addresses) removes that pressure; it also simplifies headers, mandates features like auto-configuration, and was designed with security (IPsec) in mind, though TLS is still used on top. You are not asked to configure IPv6 by hand, but you must explain why it exists (address exhaustion) and that it is written in hex, not dotted decimal.

The default gateway and a second subnetting example

A host that wants to reach another subnet does not send directly; it sends the packet to its default gateway — usually the router on its own LAN — which then routes it onward. The gateway's IP is in the same subnet as the host (so they can talk directly) and it knows how to reach the rest of the world. Subnetting is the administrative act of carving an allocated block; the size of the carved pieces is the mask. A smaller mask (e.g. /16) means fewer, larger subnets; a larger mask (e.g. /28) means many tiny subnets. The choice trades wasted addresses against routing table size and administrative separation.

Worked example 2b IB-style · 7 marks · a /28 subnet and host count

Question. An organisation is given 192.168.10.0 /28. (a) How many usable host addresses does this provide? (b) What are the network and broadcast addresses? (c) Could host 192.168.10.14 be on this subnet? Explain.

  1. (a) /28 leaves 32 − 28 = 4 host bits, so 2⁴ = 16 addresses total.
  2. (b) Network address = 192.168.10.0 (all host bits 0). Broadcast = 192.168.10.15 (all host bits 1).
  3. (c) Usable hosts are .1 to .14 — that is 14 addresses (16 total minus network and broadcast). So 192.168.10.14 IS a usable host address on this subnet (it is the last usable one, just below broadcast .15).
  4. Check: .15 is broadcast, not a host, so the highest usable host is .14 — a common trap is calling .14 the broadcast.
Marks: 2 for 16 total / 14 usable, 2 for the network and broadcast addresses, 3 for correctly classifying .14 as usable with the reasoning (only .15 is broadcast). The "off-by-one" between the last usable host and the broadcast is the classic mark-loser.
Exam technique — "host bits" = 32 minus the prefix

For any CIDR question, the number of host bits is 32 − prefix. Total addresses = 2^(host bits); usable = total − 2 (reserve network and broadcast). For IPv6 the maths is the same but with 128-bit addresses and no broadcast (it uses multicast instead). Write the exponent step explicitly — "32 − 24 = 8, so 2⁸ = 256, 254 usable" — because the marks sit on the method, and a bare "254" with no working is capped.

NAT and a quantitative throughput calculation

NAT (network address translation) lets many devices on a private network (e.g. 192.168.x.x) share one public IP. The gateway rewrites the source address of outgoing packets to its public IP and remembers the mapping, so replies can be sent back to the right internal device. NAT postponed IPv4 exhaustion and adds a little obscurity, but it breaks the "every host has a unique IP" model (which is why incoming connections to a NATted device need port forwarding) and is largely unnecessary under IPv6. A companion calculation you should be able to do is transfer time = data size ÷ throughput, remembering to convert units and that overhead reduces real throughput below the link's bandwidth.

Worked example 4b IB-style · 6 marks · download time and NAT role

Question. A 50 MB file is downloaded over a 20 Mbps link whose real throughput is 80% of bandwidth. (a) Estimate the download time in seconds. (b) Explain the role of NAT if the downloading device is on a home 192.168.1.x network.

  1. (a) File = 50 × 8 = 400 Mb. Effective throughput = 20 × 0.8 = 16 Mbps. Time = 400 Mb ÷ 16 Mbps = 25 seconds.
  2. (b) The home devices use private 192.168.1.x addresses that are not routable on the public internet. The gateway performs NAT: it replaces the device's private source IP with the home's single public IP as packets leave, and translates replies back, so all devices share that one public address. Without NAT (or IPv6), each device would need its own public IP.
  3. Sanity: if you forgot the ×8 (MB→Mb), you would get 3.125 s, which is wrong — always convert bytes to bits when dividing by a bit-per-second bandwidth.
Marks: 3 for the 25 s with correct unit conversion (×8, ×0.8), 3 for NAT's address-translation role and why private addresses need it. The classic error is mixing MB and Mbps; state the conversion explicitly for the mark.
Exam technique — always convert, then divide

Bandwidth is in bits/s; file sizes are usually in bytes. Step 1: bytes × 8 = bits. Step 2: apply any overhead factor (throughput as a fraction of bandwidth). Step 3: size ÷ throughput = time. Write each step; the marks are on the conversion, not on the final number, and a wrong unit is the most common way to lose all of them.

5 · Packets, routing, and the transport protocols

SL / HL

Intuition

No message crosses the internet whole. It is chopped into packets, each with its own source and destination IP, sent independently, and reassembled at the far end. This is robust: if one route is congested, packets take another; if one is lost, only it is resent. A router reads the destination IP of each packet and forwards it toward the next hop using a routing table (a list of "for destination network X, send via interface Y"). Routing is the distributed decision of where each packet goes next; no router knows the whole path, only the next step — like posting a letter that gets forwarded city by city.

Formal idea: TCP vs UDP

TCP (Transmission Control Protocol) is connection-oriented and reliable: it sets up a connection, numbers each byte, acknowledges receipt, and retransmits anything lost, presenting the receiver with a perfect, ordered stream. It is used for web pages, email and files, where correctness beats raw speed. UDP (User Datagram Protocol) is connectionless and unreliable: it fires datagrams and hopes; no ack, no retransmit, but far lower delay and overhead. It is used for live video, voice and games, where a late packet is worthless and dropping it beats waiting. The choice is a trade-off: reliability (TCP) versus latency (UDP). Ports (numbers like 80, 443, 25, 53) let one machine run many services; the IP gets the packet to the machine, the port gets it to the right application.

ProtocolReliable?Connection?Use whenExamples
TCPYes (acks, retransmit, order)Yes (handshake)Correctness matters more than delayHTTP, HTTPS, SMTP, FTP
UDPNoNoLow delay matters more than lossVideo call, DNS, gaming
Exam technique — justify TCP vs UDP by the cost of loss

The mark is for linking the protocol to the consequence of a lost packet. "A lost web byte corrupts the page, so use TCP" earns it; "video uses UDP because it is faster" is weaker unless you add "a late video frame is useless, so retransmitting is pointless". Always state what goes wrong if a packet is lost, then the protocol follows.

Worked example 3 IB-style · 6 marks · choose the protocol

Question. A stock-trading app must send buy/sell orders. (a) State whether TCP or UDP is appropriate and why. (b) Explain what would go wrong if the other were used. (c) Which port-level identifier gets the packet to the trading service?

  1. (a) TCP — a lost or reordered order could buy the wrong amount or duplicate a trade, so reliability is essential and the small extra delay is acceptable.
  2. (b) With UDP, a dropped order might never arrive (the trade is missed) or arrive out of order (sell before buy), causing real financial loss; there is no automatic recovery.
  3. (c) The destination port number (agreed with the server) directs the packet to the trading application after the IP delivers it to the machine.
Marks: 2 for TCP with the correctness reasoning, 2 for the concrete failure mode under UDP, 2 for the port. Note the two-level addressing: IP reaches the host, port reaches the process.

The TCP three-way handshake and congestion control

TCP does not just send; it first agrees to talk. The three-way handshake is: (1) the client sends SYN (synchronise, "I want to connect, here is my initial sequence number"); (2) the server replies SYN-ACK (it acknowledges and proposes its own sequence number); (3) the client sends ACK. Only then does data flow. This sets up the sequence numbers that make reliable, ordered delivery possible and protects against old duplicate connection attempts. Congestion control is TCP's behaviour when the network is busy: it starts slow (slow start), increases the window until packets are lost, then backs off — the internet's way of being polite so no single flow floods everyone. UDP has none of this; it is fire-and-forget, which is why it is called "unreliable" without meaning "bad".

Worked example 3b IB-style · 6 marks · read a routing table

Question. A router has this table: (i) 10.0.1.0/24 → port A; (ii) 10.0.2.0/24 → port B; (iii) 0.0.0.0/0 → port C (default). To which port does it forward a packet for (a) 10.0.1.55, (b) 10.0.2.7, (c) 8.8.8.8?

  1. (a) 10.0.1.55 matches rule (i) exactly (same /24 network) → forward out port A.
  2. (b) 10.0.2.7 matches rule (ii) (same /24) → port B.
  3. (c) 8.8.8.8 matches no specific rule, so the router uses the default route 0.0.0.0/0 (meaning "any address") → port C. The default is the catch-all for everything not otherwise listed, typically the link to the wider internet.
  4. The longest-prefix (most specific) match wins; the default is the shortest (zero bits), so it is the last resort.
Marks: 1 each for A and B, 3 for C with the explanation that the default route catches all unmatched destinations. The mark is knowing the default route exists as the "otherwise" rule and that specific prefixes beat it.
Trap — a router does not "know the whole path"

Routing is next-hop only. A router decides where to send the packet for the next step; it does not compute or store the full route to the destination (that is what traceroute reveals hop by hop). Saying "the router looks up the destination and sends it all the way" is wrong — each router along the path repeats the same local table lookup. The end-to-end path is emergent from many local decisions.

6 · Application protocols: DNS, HTTP/S, FTP, SMTP

SL / HL

Intuition

These are the application-layer protocols you actually use. DNS (Domain Name System) translates a name like example.com into an IP address — the internet's phone book. HTTP (and its encrypted form HTTPS) is how browsers fetch web pages; the S adds TLS encryption. FTP (File Transfer Protocol) moves files between machines. SMTP (Simple Mail Transfer Protocol) sends email from your client to a server and between servers. Each sits on top of TCP (except some DNS, which may use UDP for small queries) and is identified by a well-known port.

Formal idea: what each one does step by step

DNS resolution: you type a name; the resolver asks a root server, which points to a TLD server (.com), which points to the authoritative server, which returns the IP — often cached on the way back so the next lookup is instant. HTTP request/response: the browser sends a request with a method (GET to fetch, POST to submit) and a URL; the server returns a status code (200 OK, 404 not found, 301 redirect, 500 error) and the content. HTTPS wraps this in TLS so an eavesdropper sees only ciphertext. FTP opens a control connection (port 21) and a separate data connection, and transmits credentials and files in the clear unless FTPS/SFTP is used. SMTP pushes mail to port 25; retrieving it at the client uses POP3 or IMAP.

Note — the port numbers are worth a mark, not a page

You should know the headline ports: HTTP 80, HTTPS 443, FTP 21 (control), SMTP 25, DNS 53, SSH 22. A question may ask "which protocol and port for a secure web page?" → HTTPS on 443. But the deeper marks are for what the protocol achieves (name→address, fetch, transfer, send), not for reciting numbers. Use the numbers to show you know which layer/protocol, then explain the function.

HTTP methods and status codes in detail

The method tells the server what to do. GET retrieves a resource (and should not change server state); POST submits data to create or update something; PUT replaces a resource; DELETE removes one; HEAD asks for just the headers. The status code tells what happened: 2xx success (200 OK, 201 created), 3xx redirection (301 moved permanently, 304 not modified — used for caching), 4xx client error (400 bad request, 401 unauthorized, 403 forbidden, 404 not found), 5xx server error (500 internal, 503 unavailable). Knowing these lets you interpret what a browser or API is telling you, and they are a common source of "state the meaning of this response" marks. HTTPS adds a TLS handshake before any HTTP exchange, so the HTTP bytes are encrypted inside the TLS record — the method and URL are hidden from an on-path observer (though the server name can leak via SNI unless encrypted too).

Worked example 6 IB-style · 5 marks · interpret a response

Question. A browser requests a page and receives (a) 404, then (b) 301 to a new URL, then (c) 200. Explain each, and state which of the three is an error the client caused.

  1. (a) 404 Not Found — the server has no resource at that URL. This is a client-side error (wrong address / broken link), a 4xx.
  2. (b) 301 Moved Permanently — the resource now lives at a different URL; the browser should follow the Location header to the new address. Not an error, just redirection.
  3. (c) 200 OK — the request succeeded and the response body is the page.
  4. Only the 404 is a client-caused error (4xx); the 301 is redirection and the 200 is success. The 5xx class would be the server's fault instead.
Marks: 1 each for the three meanings, 2 for classifying 404 as the client error (4xx) and noting 5xx would be server-side. The markscheme rewards the class (2xx/3xx/4xx/5xx) as much as the specific number.

7 · Wireless networking and Wi-Fi security

SL / HL

Intuition

Wireless is the same layered stack with radio as the physical medium. Wi-Fi (the family of IEEE 802.11 standards) is a LAN without cables; devices associate with an access point that acts as the layer-2 hub. Because anyone in range can hear the radio, Wi-Fi needs encryption at the link layer, and the schemes have a history of getting stronger: WEP (broken, do not use), WPA, WPA2 (AES-based, still common), and WPA3 (currently recommended). The lesson: wireless security is a moving target, and "it's password-protected" is only as good as the scheme — WEP with a password is still insecure.

Trap — WEP is not secure, and "encrypted Wi-Fi" is vague

If a question asks about securing a wireless network, name the scheme: WPA2 or WPA3 with a strong passphrase, not merely "use encryption". WEP has known flaws (short IV, weak key scheduling) and is explicitly insecure — saying "use WEP" loses the mark. Also distinguish securing the link (WPA) from securing the session (TLS/HTTPS): WPA protects your traffic from neighbours on the Wi-Fi, but the site still needs HTTPS to protect it from the internet beyond the router.

Serial vs parallel transmission

Serial transmission sends one bit at a time along a single channel; parallel sends many bits at once along multiple wires (like the old parallel printer cable, or the lanes inside a bus). Serial won the modern world because at high speeds the parallel wires suffer from skew (bits on different wires arrive at slightly different times) and crosstalk, and serial is cheaper (fewer wires). So USB, SATA, PCIe and networking are all serial now, despite the intuitive "more wires = faster" assumption. The rule: parallel is simple and fast at low speeds over short distances; serial scales to higher speeds over longer distances.

Exam technique — "why serial not parallel today?"

The mark is for skew and crosstalk at high speed, plus cost (fewer wires). A common weak answer is "serial is faster", which is backwards as a first principle — parallel is faster at low speed; serial wins at high speed because it avoids timing problems. State the timing problem and you have the mark.

How Wi-Fi shares the air: CSMA/CA and the bands

Unlike a wired switch, a wireless medium is shared by everyone in range and a node cannot hear its own collision while transmitting — so Wi-Fi uses CSMA/CA (Carrier Sense Multiple Access with Collision Avoidance): a device listens; if the channel is busy it waits a random back-off; before sending it may reserve the channel with a short request-to-send / clear-to-send exchange so others stay quiet. This "avoidance" is why Wi-Fi is half-duplex on a channel and why many devices on one access point slow each other down. The 2.4 GHz band travels farther and penetrates walls better but is crowded (microwaves, Bluetooth share it) and has fewer non-overlapping channels; the 5 GHz band is faster and less crowded but shorter range. The upcoming 6 GHz (Wi-Fi 6E/7) adds more room still. The evaluation point: higher frequency = more bandwidth but shorter range, a direct echo of the bandwidth-versus- latency-versus-physics trade-off everywhere in this topic.

Worked example 7 IB-style · 5 marks · choose a band and a scheme

Question. A café wants Wi-Fi that reaches the garden (through a wall) and is secure. (a) Which frequency band is the better default and why? (b) Which security scheme should they enable, and what does it protect against that HTTPS alone does not?

  1. (a) 2.4 GHz reaches farther through the wall, so as the default it serves the garden; 5 GHz would be faster but might not penetrate. The trade-off is range versus speed.
  2. (b) Enable WPA2 or WPA3 (not WEP). WPA protects the link so a neighbour in the café cannot read the user's traffic over the air. HTTPS also encrypts, but only between the user and a specific website — WPA protects all traffic on the local link, including DNS and any plaintext site, and stops a local eavesdropper regardless of the site.
Marks: 2 for 2.4 GHz with the range/penetration reason, 3 for WPA2/3 plus the distinction that WPA secures the local link while HTTPS secures the end-to-end session. The point the markscheme wants is the two-level (link vs session) protection, not "use a password".

8 · Network security: threats and the control that defeats each

SL / HL

Intuition

Security is best learned as threat → control, not as a shopping list. Each attack has a specific defence, and the mark is almost always for pairing them. A firewall filters traffic by rules (block port 23, allow 443) — it defends against unauthorised access from outside. A proxy sits between client and server, forwarding requests (and can cache and filter content). A VPN (virtual private network) tunnels your traffic through an encrypted channel so an eavesdropper on the Wi-Fi or ISP cannot read it. A DoS / DDoS (denial of service / distributed DoS) floods a server with traffic to exhaust its resources — defended by filtering, rate-limiting and absorption (CDNs). A man-in-the-middle (MITM) attack intercepts and possibly alters traffic between two parties — defended by encryption (TLS) and, for identity, certificates. The through-line: encryption defeats eavesdropping and tampering; filtering defeats unauthorised access; redundancy defeats flooding.

Worked example 4 IB-style · 7 marks · MITM and its defence

Question. A user logs into a bank on public Wi-Fi without HTTPS. (a) Describe a man-in-the-middle attack that could result. (b) State what an attacker could obtain. (c) Explain how the attack is prevented.

  1. (a) The attacker sets up a rogue access point or poisons ARP/DNS so the user's traffic flows through the attacker's machine. The attacker relays it to the real bank, so neither side notices; the attacker sits "in the middle".
  2. (b) Because the login is in plaintext (no HTTPS), the attacker reads the username and password directly as the packets pass through, and could also alter the page (e.g. inject a fake form) or silently redirect funds.
  3. (c) HTTPS/TLS encrypts the session so the attacker sees only ciphertext they cannot read, and the bank's certificate lets the browser verify the server's identity, defeating the impersonation. Additionally, the user should avoid unknown Wi-Fi or use a VPN, which encrypts the link before the traffic leaves the device.
Marks: 2 for describing the interception/relay, 2 for the credentials-in-cleartext consequence, 3 for TLS encryption + certificate-based authentication (and optionally VPN). The mark is not "use a password" — it is "encrypt and authenticate the endpoint".
Trap — a firewall is not antivirus, and VPN is not anonymity

A firewall controls network traffic by rules; it does nothing about a malicious file already on the machine. A VPN encrypts your link and hides your IP from the next hop, but it does not make you anonymous from the VPN provider itself, and it does not protect you from a phishing site. Pair each control with the threat it actually addresses; a generic "use a firewall and a VPN" answer scores little if the threat was eavesdropping (VPN yes, firewall only indirectly).

Defence in depth, phishing, and encryption at rest

No single control is enough, which is why real systems use defence in depth: layers so that if one fails, another still protects. A web service might combine TLS (confidentiality in transit), a firewall (perimeter access control), strong authentication (passwords plus a second factor), input validation (stopping injection), and encryption at rest (so a stolen database is unreadable). Phishing and social engineering are attacks on the human, not the maths: an attacker tricks a user into revealing a password or clicking a bad link, which bypasses every technical control. That is why training and multi-factor authentication (MFA) matter — MFA means a stolen password alone is useless. Encryption at rest (e.g. a full-disk-encrypted laptop, or a database whose columns are encrypted) protects data sitting on storage, complementing TLS which only protects data moving. Confidentiality, integrity and availability — the CIA triad — are the three goals these controls serve; a good evaluation names which of the three each control advances.

Note — the CIA triad names the security goals

Confidentiality: only authorised parties can read (TLS, encryption at rest, access control). Integrity: data is not altered undetected (hashing, digital signatures, checksums). Availability: the service works when needed (redundancy, DoS defence, backups). When an evaluation question asks you to assess a security design, walk the CIA triad and say which control supports which goal — that structure is what a top-band answer looks like, and it is the same triad used in the case-study and A4 ethics discussions.

9 · Error detection: parity, checksum, and Hamming

SL / HL

Intuition

Bits get flipped by noise on a wire or in the air. Before you can correct an error you must detect it. Parity is the simplest: add one bit so the total number of 1s is even (even parity) or odd (odd parity); if a single bit flips, the parity is wrong and the error is spotted — but you can't tell which bit, and two flips cancel out and go undetected. A checksum (and its stronger cousin the CRC, cyclic redundancy check) folds the whole message into a short value; the receiver recomputes it and compares. Hamming code goes further: it adds enough parity bits in clever positions that a single-bit error can be both detected and located, so it can be corrected, not just flagged.

Formal idea: even parity and the Hamming layout

In a parity scheme, for the byte 1011001₁ (three 1s, odd), even parity appends a 0 to make four 1s (total even): 10110010. The receiver counts 1s; an odd count means an error occurred. For Hamming, parity bits live at positions that are powers of two (1, 2, 4, 8…) and each covers a specific set of data bits; by checking which parity bits fail, you compute the exact position of the single flipped bit and flip it back. Hamming can correct one error and detect two; it trades bandwidth for reliability, which matters on noisy channels.

Worked example 5 IB-style · 8 marks · even parity and a single-bit Hamming correction

Question. (a) A system uses even parity on 7-bit ASCII. The received byte is 11001011 (8 bits, last bit parity). State whether an error is detected and explain. (b) In a Hamming (7,4) code the receiver finds parity bits at positions 1 and 2 in error but position 4 correct. State the position of the flipped bit and the corrected data bit.

  1. (a) The data bits are 1100101; count the 1s: positions with 1 are 1,2,5,7 → four 1s (even). The parity bit is 1, making five 1s total — odd. Even parity expects an even total, so an error is detected. (If instead total were even, no single-bit error is detected by parity.)
  2. (b) In Hamming, the failing parity bits' positions are added: 1 + 2 = 3, so bit 3 is the one in error. Flip bit 3; the remaining bits are the corrected data. Position 4 being correct tells us the error is not in the half it covers, which is consistent with position 3.
  3. The power of Hamming: the set of failing parity bits is a binary number giving the bad position — no guesswork, no resend needed for a single error.
Marks: 2 for detecting the parity error with the even-total reasoning, 2 for knowing parity can't locate the bit, 3 for "1+2=3 ⇒ bit 3" and flipping it, 1 for noting Hamming corrects (not just detects) single errors. The trap is claiming parity can say which bit broke — it cannot.
Exam technique — say what each method can and cannot do

The markscheme loves the comparison: parity detects single-bit errors but not their location and misses double errors; a checksum detects most multi-bit errors over a block but still only flags; Hamming detects and corrects single-bit errors (and detects double). If asked "which to use on a noisy satellite link?", Hamming (correction avoids a costly resend); on a wired LAN, a checksum is enough because errors are rare. Match the method to the channel.

Worked example 5b IB-style · 9 marks · construct and decode a Hamming (7,4) code

Question. Encode the 4 data bits 1011 using Hamming (7,4) with parity bits at positions 1, 2, 4 (even parity). Then show how the receiver corrects the code if bit 6 is flipped in transmission.

  1. Layout: positions 1,2,4 are parity; positions 3,5,6,7 hold data. Place data 1011: bit3=1, bit5=0, bit6=1, bit7=1.
  2. Compute parity: p1 covers bits 1,3,5,7 → bits 3,5,7 are 1,0,1 (two 1s, even) so p1=0. p2 covers 2,3,6,7 → 1,1,1 (three 1s, odd) so p2=1 to make even. p4 covers 4,5,6,7 → 0,1,1 (two 1s, even) so p4=0.
  3. Codeword: position 1=p1=0, 2=p2=1, 3=d=1, 4=p4=0, 5=d=0, 6=d=1, 7=d=1 → 0 1 1 0 0 1 1.
  4. Transmit with bit 6 flipped: received = 0 1 1 0 0 0 1 (bit6 now 0).
  5. Receiver checks: p1 covers 1,3,5,7 = 0,1,0,1 → two 1s, even, OK. p2 covers 2,3,6,7 = 1,1,0,1 → three 1s, odd → ERROR. p4 covers 4,5,6,7 = 0,0,0,1 → one 1, odd → ERROR.
  6. Locate: failing parity bits are p2 (position 2) and p4 (position 4); 2 + 4 = 6 → bit 6 is wrong. Flip it back to 1. Corrected codeword 0 1 1 0 0 1 1, data 1011 recovered.
Marks: 3 for the correct codeword, 3 for the parity checks identifying bits 2 and 4 as failing, 3 for "2+4=6 ⇒ flip bit 6" and recovering the data. The elegant part the markscheme rewards: the set of failing parity bits is a binary address of the bad bit — no resend needed for a single error.

Checksums and CRC in brief

A checksum adds the bytes of a message (often with ones-complement addition) into a short sum sent alongside it; the receiver adds the same way and compares — a mismatch means corruption. It is simple and catches most errors but is weak against certain patterned errors. A CRC (cyclic redundancy check) treats the message as a polynomial and divides it by a standard generator polynomial, sending the remainder; the receiver divides and checks the remainder is zero. CRCs catch far more error patterns (including burst errors) and are what Ethernet and many storage formats actually use. Both detect but do not locate/correct (unlike Hamming); on detecting, the usual response is "ask the sender to retransmit that packet" — which is exactly what TCP's acknowledgement mechanism does.

Note — detection triggers retransmission, not magic repair

Parity, checksum and CRC only tell you "something is wrong"; they do not know the original value. The recovery is a retransmission (TCP resends the lost/corrupt segment) or, for Hamming, an in-place flip. So error control has two halves: detection (these methods) and recovery (retransmit, or Hamming-correct). A complete answer names both; a detection-only answer leaves the "then what?" unanswered.

Self-check

  1. State the difference between a MAC address and an IP address, and say which layer of the OSI model each belongs to.

    Show the answer

    A MAC address identifies the device's hardware ("who", layer 2, data link) and is fixed; an IP address identifies where the device is on the network ("where", layer 3, network) and can change. MAC is used for delivery on one link, IP for routing across networks.

    Why this matters: the who/where analogy is the single most-tested distinction in the topic; getting the layers right is half the mark.

  2. Host X is 172.16.5.10 /16 and host Y is 172.16.9.20 /16. Are they on the same subnet? How many usable host addresses does the subnet provide?

    Show the answer

    /16 keeps the first 16 bits (172.16) as the network. Both share 172.16, so they are on the same subnet and can talk directly. Host bits = 16, so 2¹⁶ = 65536 addresses, minus network (.0.0) and broadcast (.255.255) = 65534 usable.

    Why this matters: only the masked bits decide subnet membership; the third octet differing does not matter under /16.

  3. A video call and a file download start at the same time. Which transport protocol suits each, and why?

    Show the answer

    The call uses UDP (a late packet is useless, so low delay beats reliability, and retransmitting is pointless); the download uses TCP (a corrupted byte ruins the file, so reliability and ordering matter more than a little delay).

    Why this matters: always justify by "what happens if a packet is lost?" — that single question picks the protocol.

  4. Explain the role of DNS and state what would happen if it failed.

    Show the answer

    DNS translates domain names to IP addresses (the internet's directory). If it failed, you could still reach sites by typing their IP address directly, but names like example.com would not resolve, so normal browsing would break even though the network itself was fine.

    Why this matters: DNS is application-layer infrastructure; a DNS failure is not a cable failure, which is why "ping by IP works" is the tell-tale sign.

  5. A school wants to stop students on the Wi-Fi reading each other's traffic and also stop outsiders reaching the admin server. Name one control for each goal.

    Show the answer

    To stop neighbours reading traffic: use WPA2/WPA3 encryption on the Wi-Fi (link-layer confidentiality). To block outsiders from the admin server: a firewall rule that denies external access to the admin server's port, allowing only internal addresses.

    Why this matters: pair each threat with its control — encryption for eavesdropping, firewall for unauthorised access. Don't confuse them.

  6. A 7-bit message 0110100 uses even parity as an 8th bit. What is the transmitted byte, and what does the receiver conclude if it gets 01101011?

    Show the answer

    Data 0110100 has three 1s (odd), so even parity appends 1 → 01101001 (four 1s, even). Received 01101011 has five 1s (odd), so the receiver detects a single-bit error. Parity cannot say which bit, only that something is wrong.

    Why this matters: parity detects but does not locate; that limitation is exactly why Hamming exists for correction.

  7. Explain why modern high-speed links use serial rather than parallel transmission.

    Show the answer

    At high speeds, parallel wires suffer skew (bits on different wires arrive at different times) and crosstalk, and cost more; serial avoids these and scales to higher rates over longer distances, so USB/SATA/networking are serial despite the intuition that more wires is faster.

    Why this matters: the mark is the timing problem (skew), not "serial is faster" — parallel is faster at low speed.

  8. Compare a firewall and a VPN in the threats they address.

    Show the answer

    A firewall filters traffic by rules to block unauthorised access (a perimeter control); a VPN encrypts a tunnel so an eavesdropper on the path cannot read your traffic. They address different threats — access control vs confidentiality — and are complementary, not substitutes.

    Why this matters: naming the threat each addresses is the mark; a vague "both improve security" scores nothing.
