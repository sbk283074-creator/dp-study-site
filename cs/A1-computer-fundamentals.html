Computer Science HL · Theme A · A1

A1 · Computer fundamentals

Everything a computer does, from streaming video to training a neural network, is the fetch–decode–execute cycle running billions of times a second over patterns of bits. This topic is where you learn what those bits are, how they are stored, how they are moved, and how the machine is organised to move them. It is the most self-contained topic in the course and the most reliably scorable in Paper 1 — there is no opinion in "convert 173 to hexadecimal", only right and wrong. Master the number systems, the arithmetic, the logic, and the box-and-arrow architecture picture, and you have a bank of marks that never depend on a question writer's mood. The two traps are arithmetic slips (always show your carries) and confusing representation with value (the number 10 is the same whether it is written 1010 in binary, A in hex, or "ten" in English).

Why this exists

A computer has no concept of "ten" or "the letter A". It has only two stable electrical states: high voltage and low voltage, conventionally written as 1 and 0. Every fact the machine holds — a pixel's colour, a bank balance, a program instruction — is a pattern of those two states. So the first job of computer fundamentals is to give you a reliable way to encode the human world (numbers, text, instructions) as bits, and to transform between that code and the decimal world you think in. Everything else on the page — arithmetic, logic, the CPU, storage — is the machinery that operates on those bits. Learn the encoding first; the hardware is just a very fast bit-shuffler.

1 · Number systems and why we use more than one

SL / HL

Intuition

You already use more than one number base. When you tell the time you think in base 60 (60 seconds in a minute), when you count you think in base 10, and when you talk about a dozen eggs you use base 12. "Base" simply means how many symbols you have before you need a new column. Decimal (base 10) has ten symbols, 0–9; binary (base 2) has two, 0 and 1; hexadecimal (base 16) has sixteen, 0–9 then A–F. The value of a digit depends on its column, and the column's weight is the base raised to the column's position, counting from zero on the right.

So in decimal the number 173 means 1×10² + 7×10¹ + 3×10⁰ = 100 + 70 + 3. In binary, 10101101 means 1×2⁷ + 0×2⁶ + 1×2⁵ + 0×2⁴ + 1×2³ + 1×2² + 0×2¹ + 1×2⁰ = 128 + 0 + 32 + 0 + 8 + 4 + 0 + 1 = 173. Same value, different spelling. Hexadecimal exists purely as shorthand for binary: every group of four bits maps to exactly one hex digit, so a long binary number becomes a short, readable hex one with zero arithmetic risk.

Formal idea: positional notation

A number in base b with digits dk…d1d0 has the value dk·bk + … + d1·b¹ + d0·b⁰. To convert any base to decimal, multiply each digit by its column weight and add. To convert decimal to another base, repeatedly divide by the new base and read the remainders bottom-up (this is "division by radix"), or, for binary, subtract the largest power of two you can and record which powers you used.

How to use it — decimal to binary/hex by repeated division
  1. Divide the decimal number by 2 (for binary) or 16 (for hex); write the remainder as the rightmost digit.
  2. Replace the number with the quotient (the whole-number part) and repeat, writing each new remainder to the left.
  3. Stop when the quotient is 0. The remainders, read from last to first, are the answer.
  4. Binary↔hex shortcut: split the binary into groups of four bits from the right; convert each group to its hex digit (0000=0 … 1111=F). Pad the leftmost group with leading zeros if needed.
Worked example 1 IB-style · 6 marks · convert decimal to binary and hex

Question. Convert the decimal number 173 (a) to binary, showing your method, and (b) to hexadecimal. (c) State one reason hexadecimal is used in computing.

  1. (a) Repeated division by 2: 173 ÷ 2 = 86 r 1 (least significant bit). 86 ÷ 2 = 43 r 0. 43 ÷ 2 = 21 r 1. 21 ÷ 2 = 10 r 1. 10 ÷ 2 = 5 r 0. 5 ÷ 2 = 2 r 1. 2 ÷ 2 = 1 r 0. 1 ÷ 2 = 0 r 1 (most significant bit). Reading the remainders from bottom to top: 10101101.
  2. Check by place value: 128 + 32 + 8 + 4 + 1 = 173. Correct.
  3. (b) Hex: group 10101101 as 1010 1101 → 1010 = A, 1101 = D, so AD16. Alternatively 173 ÷ 16 = 10 r 13 (13 = D), 10 ÷ 16 = 0 r 10 (A), giving AD.
  4. (c) Reason: hex is far denser and less error-prone than writing long binary strings; one hex digit represents exactly four bits, so a memory address or a colour value is easy to read and transcribe without arithmetic mistakes.
Marks: 3 for the correct binary with a correct method shown (repeated division or place value), 1 for the hex, 2 for a sensible reason (density, readability, direct 4-bit mapping, or "memory addresses are long in binary"). A bare answer "10101101" with no working is typically capped at 1 mark.
Worked example 2 IB-style · 5 marks · convert hex to decimal and binary

Question. The byte stored in memory is 3F. (a) Write it in binary. (b) Hence state its decimal value. (c) A register holds the 16-bit value 1A2F. Write it in binary.

  1. (a) 3 = 0011, F = 1111, so 3F = 00111111.
  2. (b) 00111111 = 0×128 + 0×64 + 1×32 + 1×16 + 1×8 + 1×4 + 1×2 + 1×1 = 32 + 16 + 8 + 4 + 2 + 1 = 63. (F in a single hex digit is 15, and 3 in the next digit is 3×16 = 48, so 48 + 15 = 63 — same result, faster.)
  3. (c) 1 = 0001, A = 1010, 2 = 0010, F = 1111 → 0001 1010 0010 1111.
Answer: 00111111; 63; 0001101000101111. Marks: 1 each for the two binary conversions, 2 for the decimal with a valid method. The single most common slip is transcribing F as 1110 or 1001 instead of 1111 — learn the 4-bit table by heart.
Trap — "the number is big in binary so it must be a big value"

Representation and value are different things. The binary string 10000000 is eight characters long but its value is only 128; the hex string "FF" is two characters but its value is 255. Never compare magnitudes by counting digits across bases. Also, always state the base when you write a number: "1010" is ten in binary but one thousand and ten in decimal. IB questions expect a subscript or the words "binary"/"hex"; an unbased number is ambiguous and may lose the mark.

Character sets: ASCII, Unicode and BCD

Text is numbers too. A character set is a code that maps each character to a number; a character encoding is how that number is stored as bits. ASCII (American Standard Code for Information Interchange) uses 7 bits, giving 128 codes: 32 are control characters (e.g. newline, tab), the rest are printable. Because 7 bits fits in a byte with one spare bit, an eighth bit was later used for parity (see section 9) or for extensions to 256 codes (extended ASCII), but 256 is nowhere near enough for the world's writing systems.

Unicode is the modern standard: it assigns a unique code point to (almost) every character in every language, over 140,000 of them, from Latin letters to Chinese hanzi to emoji. Unicode is a catalogue, not a storage format; the storage format is an encoding such as UTF-8, which uses 1 byte for ASCII characters (so English text stays compact and old ASCII files still work) and 2–4 bytes for other characters, or UTF-16, which uses 2 bytes for most characters and 4 for the rest. Choosing UTF-8 matters: a file that is "just text" still has an encoding, and opening UTF-8 data as if it were a 1-byte set produces mojibake — the famous black diamonds with question marks.

BCD (Binary-Coded Decimal) is a different idea: instead of storing a decimal number as one binary value, store each decimal digit as its own 4-bit group. So 59 is stored as 0101 1001, not as 00111011 (which is 59 in true binary). BCD wastes bits (it uses ten of the sixteen possible 4-bit patterns) but it makes decimal arithmetic and display trivial and avoids the rounding errors that binary fractions cause — which is why calculators and financial systems use it. The price is slower arithmetic and more storage.

Worked example 1c IB-style · 5 marks · BCD storage and addition

Question. (a) Show how the decimal number 73 is stored in packed BCD. (b) Add the BCD values for 27 and 15, showing how you correct if a digit exceeds 9. (c) State one reason a bank might prefer BCD to true binary for balances.

  1. (a) 7 = 0111, 3 = 0011, so packed BCD = 0111 0011 (one byte, two digits).
  2. (b) 27 = 0010 0111, 15 = 0001 0101. Add the bytes as if binary: 0010 0111 + 0001 0101 = 0011 1100, which reads as digits "3" and "12" — the low digit 1100 = 12 is not a valid BCD digit. Add the BCD correction 0110 (6) to that nibble: 1100 + 0110 = 0010 (carry 1 into the next nibble). So 0011 1100 + 0000 0110 = 0100 0010 = digits 4 and 2 = 42. Correct, since 27 + 15 = 42.
  3. (c) BCD stores and displays decimal exactly with no binary-fraction rounding error, so a balance of 0.10 is represented precisely; it also maps directly to the digits people read, simplifying display and audit. The cost is more storage and slower arithmetic, which a bank accepts for correctness.
Marks: 1 for 01110011, 2 for the addition with the +6 correction when a nibble exceeds 9, 2 for a correct reason. The +6 "BCD adjust" step is the specific thing tested; forgetting it leaves an invalid digit 12 in the answer.
Exam technique — say "encoding", not "font"

A question about why a Chinese document shows as boxes is an encoding question (the reader used the wrong encoding, so code points were mapped to the wrong glyphs), not a font question. Marks are given for naming Unicode/UTF-8 and explaining that the code point is the same but the byte layout differs. Also: if asked how many bytes a UTF-8 string is, count ASCII characters as 1 and non-ASCII as 2–4 — do not assume a fixed width.

Unicode in practice: planes, UTF-8 byte layout, and a string example

Unicode assigns a code point such as U+0041 for "A" or U+1F600 for the grinning emoji, but the code point is an abstraction — the bytes on disk depend on the encoding. UTF-8 is variable-length and self-synchronising: ASCII characters (code points below U+0080) take exactly one byte with the same bit pattern as ASCII, so every legacy ASCII file is already valid UTF-8; higher code points take 2, 3 or 4 bytes, with the leading bits of the first byte marking the total length (110…… for 2-byte, 1110…… for 3-byte, 11110…… for 4-byte) and continuation bytes all starting 10……. This design means a reader can find character boundaries without state, and a corrupt byte damages at most one character. UTF-16 uses 2 bytes for most characters and a surrogate pair of two 2-byte units for the rare ones above U+FFFF. The practical consequence: never assume "one character = one byte". A string of ten emoji is forty bytes in UTF-8, and a length() that counts bytes will report 40, not 10 — a classic off-by-ten bug in systems that forget text is variable-width.

Worked example 1b IB-style · 5 marks · code points to UTF-8 bytes

Question. Explain how the string "Hi" is stored in UTF-8, and how it would differ for the string "Hé" where é is U+00E9. State how many bytes each string occupies.

  1. "Hi": H = U+0048 = ASCII 72 = one byte 01001000; i = U+0069 = ASCII 105 = one byte 01101001. Total 2 bytes, identical to ASCII.
  2. "Hé": H is still one byte. é = U+00E9, which is above U+007F, so UTF-8 uses 2 bytes. The pattern for a 2-byte encoding of code point x is 110xxxxx 10xxxxxx, where the 11 bits of x fill the x's. U+00E9 = 11101001₂ (11 bits: 00011101001). First byte: 110 + 00011 = 11000011 (0xC3). Second byte: 10 + 101001 = 10101001 (0xA9). So é = C3 A9, two bytes.
  3. "Hé" occupies 1 + 2 = 3 bytes, not 2. A byte-counting length() would return 3 while a character-counting length() returns 2.
Marks: 2 for correctly showing "Hi" as 2 ASCII bytes, 2 for the 2-byte C3 A9 encoding of é with the continuation-byte rule, 1 for noting the byte count differs from the character count. The 110/10 prefix rule is the specific thing the markscheme rewards.

2 · Representing integers: two's complement and excess-N

SL / HL

Intuition

So far every number has been positive. But a computer must store negatives too, and it cannot draw a minus sign in a bit. There are three schemes; the IB expects you to know why two's complement won. Sign-and-magnitude reserves the left bit for the sign (0 = positive, 1 = negative) and uses the rest for the value. It is easy to read but has two zeroes (0000 and 1000), wastes a code, and makes addition need special circuitry. One's complement flips every bit to negate; it still has two zeroes. Two's complement stores −x as 2ⁿ − x (where n is the number of bits), and it has exactly one zero, makes negation a single rule, and — crucially — lets the same adder hardware add negatives and positives with no special case.

Formal idea: two's complement

In an n-bit two's complement system, the leftmost bit is the sign bit with weight −2n−1; the others have their usual positive weights. So in 8 bits, the value of a pattern is −128·b7 + 64·b6 + 32·b5 + … + 1·b0. The range is −2n−1 to +2n−1 − 1, so 8 bits hold −128 to +127 (note the asymmetry: one more negative than positive, the price of the single zero).

How to use it — negate a two's complement number
  1. Invert every bit (change 0↔1) — this is the one's complement.
  2. Add 1 to the result.
  3. That is the two's complement representation of the negative.
  4. To read a signed value: if the sign bit is 0, add the positive weights; if it is 1, subtract 2n from the unsigned value, or compute −128 + the rest.
Worked example 3 IB-style · 6 marks · two's complement subtraction

Question. Using 8-bit two's complement, calculate 47 − 38. Show every step, including the formation of −38 and the final overflow check.

  1. +47 in 8 bits: 32 + 8 + 4 + 2 + 1 = 00101111.
  2. +38 in 8 bits: 32 + 4 + 2 = 00100110.
  3. Form −38: invert 00100110 → 11011001; add 1 → 11011010. So −38 = 11011010.
  4. Add 47 + (−38): 00101111 + 11011010.
    Working the carries: 1+0=1, 1+1=0 carry 1, 1+1+1=1 carry 1, 1+1+1=1 carry 1, 0+1+1=0 carry 1, 1+0+1=0 carry 1, 0+1+1=0 carry 1, 0+1+1=0 carry 1. The 9-bit result is 1 00001001; the 9th bit is the carry out, which we discard in 8-bit arithmetic.
  5. Result (8 bits): 00001001 = 8 + 1 = 9. Correct: 47 − 38 = 9.
  6. Overflow check: the operands had opposite signs (47 positive, −38 negative), so overflow is impossible — overflow only happens adding two same-sign numbers. The carry out of bit 7 is irrelevant to signed overflow; what matters is that the sign bit of the result (0) matches the expectation for a positive 9.
Marks: 2 for +47 correct, 2 for forming −38 by the invert-and-add-1 rule, 1 for the binary sum, 1 for the overflow reasoning (opposite signs → no overflow). The key teaching point: subtraction is done as addition of a two's complement negative, so the CPU needs only one adder.

Excess-N (biased representation)

Some contexts — notably the exponent of a floating-point number (section 3) and certain measurement formats — store a value by adding a fixed bias N so that every stored code is non-negative. In excess-127, the actual exponent e is stored as e + 127. So an exponent of 0 is stored as 127 (01111111), and −3 is stored as 124. The benefit is that comparing exponents is just comparing unsigned integers, which is simpler in hardware; and the stored pattern for the smallest exponent is not all zeros, leaving all-zero for a special "zero" value. You are not required to do much arithmetic in excess-N, but you must recognise the phrase and know that "excess-127" means "add 127 before storing".

Worked example 3c IB-style · 4 marks · the range of an n-bit two's complement

Question. State the range of values representable in (a) 8-bit and (b) 16-bit two's complement, and explain why there is one more negative value than positive.

  1. (a) 8-bit: −2⁷ to +2⁷ − 1 = −128 to +127.
  2. (b) 16-bit: −2¹⁵ to +2¹⁵ − 1 = −32768 to +32767.
  3. Why the asymmetry: with n bits there are 2ⁿ patterns total. One pattern is used for zero (all zeros), leaving 2ⁿ − 1 patterns for non-zero values, split between positive and negative. The negative side gets the extra one because the all-ones-msb pattern with everything else zero (1000…0) represents −2ⁿ⁻¹, while the corresponding "most positive" magnitude 2ⁿ⁻¹ would need an extra bit. So negatives outnumber positives by exactly one.
Marks: 1 each for the two ranges, 2 for the asymmetry explanation tied to the single zero. A common slip is writing +128 as the top of the 8-bit range — it is +127; 10000000 is −128, not +128.
Trap — overflow in two's complement is silent

Adding 01111111 (+127) and 00000001 (+1) in 8-bit two's complement gives 10000000, which is −128, not +128. The result is wrong and the hardware only sets an overflow flag; it does not stop. Overflow occurs precisely when two numbers of the same sign produce a result of the opposite sign. Detect it by: if the carry into the sign bit differs from the carry out of the sign bit, overflow has occurred. Opposite-sign additions can never overflow.

Signed magnitude and one's complement (the alternatives you must compare)

Before two's complement became universal, two simpler schemes were tried, and the IB asks you to contrast them because the contrast shows why two's complement won. Sign-and-magnitude keeps the left bit as a sign (0 = +, 1 = −) and the remaining bits as the ordinary binary value. So in 8 bits, +5 is 00000101 and −5 is 10000101. It is intuitive to read but has two zeroes (00000000 and 10000000), wastes one code, and requires the hardware to treat addition of a negative number as a different operation from addition of a positive one. One's complement represents −x by flipping every bit of +x (the bitwise NOT); +5 = 00000101, −5 = 11111010. It still has two zeroes (00000000 and 11111111) and addition needs an "end-around carry" correction. Two's complement fixes both: exactly one zero, and ordinary unsigned addition works for signed numbers with no correction.

Worked example 3b IB-style · 5 marks · contrast the three signed representations

Question. (a) Write −5 in 8-bit sign-and-magnitude, one's complement and two's complement. (b) State one disadvantage of sign-and-magnitude that two's complement removes.

  1. (a) +5 = 00000101. Sign-and-magnitude: set the sign bit → 10000101. One's complement: flip all bits → 11111010. Two's complement: flip all bits then add 1 → 11111010 + 1 = 11111011.
  2. (b) Sign-and-magnitude has two representations of zero (00000000 and 10000000). This wastes a code and forces the ALU to test the sign bit and possibly use a different circuit for subtraction. Two's complement has a single zero, so the same adder handles all signs.
Marks: 1 each for the three correct 8-bit patterns, 2 for a valid disadvantage tied to the single-zero / unified-adder point. Writing "it is confusing" is not a mark; the wasted code and dual hardware path is.
Why two's complement is the universal choice

The decisive advantage is not elegance but economics of silicon: a CPU built around two's complement needs exactly one adder, and that same adder does add, subtract, and (combined with shifts) multiply and divide. A sign-and-magnitude machine needs a separate subtractor and sign-handling logic, which is more transistors for a slower, buggier result. When you are asked "why does the computer use two's complement?", the answer the markscheme wants is "one zero, and subtraction is just addition of a negated operand, so no extra hardware".

3 · Binary arithmetic and overflow

SL / HL

Intuition

Binary addition is the same long-addition you learned in decimal, but each column can only be 0 or 1, so the carry is either 0 or 1 and the sum digit is the XOR of the bits while the carry is their AND. Subtraction, as shown, is just addition of a two's complement negative — there is no separate subtractor in the CPU. Multiplication and division reduce to shifts and adds (shifting a binary number left multiplies by 2, like adding a zero in decimal). The one thing that can go wrong is overflow: when the true answer exceeds what n bits can hold, the result wraps around and is silently wrong.

Formal idea: half adder, full adder, and shifting

A half adder adds two single bits, producing a sum (A XOR B) and a carry (A AND B). A full adder adds two bits plus a carry-in, producing a sum and carry-out, so full adders chain to add whole numbers; its equations are sum = A XOR B XOR Cin and carry-out = (A AND B) OR (Cin AND (A XOR B)). Shifting is the binary analogue of multiplying or dividing by ten in decimal: shifting a number left by one place multiplies it by 2 and inserts a 0 on the right; shifting right divides by 2 (dropping the least significant bit). Multiplication by a constant is therefore just a shift (or a shift-and-add), which is why early CPUs without a multiply instruction could still multiply quickly.

Formal idea: the half adder and full adder

A half adder adds two single bits, producing a sum (A XOR B) and a carry (A AND B). A full adder adds two bits plus a carry-in, producing a sum and carry-out, so full adders chain to add whole numbers. The CPU's arithmetic logic unit (ALU) contains a chain of full adders — one per bit — which is why "add" is a single fast instruction. This is the physical realisation of the Boolean gates in section 4.

Worked example 4 IB-style · 6 marks · detect and explain overflow

Question. In 8-bit two's complement, add 01111100 (+124) and 00001010 (+10). State whether overflow occurs and explain your reasoning.

  1. 01111100 + 00001010: column by column with carries: the lower bits sum to 10000110 (124 + 10 = 134 in true value, = 10000110).
  2. The result 10000110 has a sign bit of 1, meaning it is interpreted as negative: −128 + 2 + 4 = −122.
  3. Both operands were positive (+124, +10) but the result is negative (−122). This is the signature of overflow.
  4. Detect formally: carry into the sign bit (bit 7) from bit 6 — is there a carry? 124 = 01111100, 10 = 00001010; bit 6 of 124 is 1, bit 6 of 10 is 0, no carry from bit 5 into 6 (bit5: 1+0, but lower bits 01111100 + 00001010 → bits 0–5 sum to 00110 with a carry into bit 6) — the carry into bit 7 is 1. The carry out of bit 7 is 0. They differ, so overflow = true.
Answer: overflow occurs; two positive numbers produced a negative result, and the sign-bit carries differ. The true sum 134 exceeds the 8-bit maximum of +127, so it wrapped into the negative half of the range. Marks: 2 for the binary addition, 2 for identifying overflow, 2 for the correct detection rule (same-sign inputs, opposite-sign output, or the carry-in/carry-out comparison).
Trap — confusing carry out with overflow

In unsigned arithmetic, carry out = overflow (the answer was too big). In signed (two's complement) arithmetic, they are different. Adding 255 + 1 as unsigned sets carry and overflow; adding 127 + 1 as signed sets no carry but does set overflow. Always state which interpretation you are using, because the same bits mean different things.

4 · Floating-point representation and rounding error

SL / HL

Intuition

Most real numbers cannot be written exactly in a fixed number of bits. Just as 1/3 = 0.3333… repeats forever in decimal, 0.1 is a repeating fraction in binary. A computer fakes real numbers with floating point: it stores a sign, a fixed number of significant digits (the mantissa), and a position for the binary point (the exponent). It is scientific notation for base 2: value = ± mantissa × 2exponent. This covers a huge range but at a cost — most values are approximated, and those approximations accumulate.

Formal idea: the IEEE-754 layout

In single precision (32 bits) the layout is: 1 sign bit, 8 exponent bits stored in excess-127, and 23 fraction bits (with an implicit leading 1, giving 24 bits of precision). In double precision (64 bits): 1 sign bit, 11 exponent bits in excess-1023, and 52 fraction bits. Normalising means writing the mantissa with exactly one non-zero digit before the binary point (1.xxxx…), which is why the leading 1 is implicit and need not be stored.

Why rounding error is unavoidable and why it matters

0.1 in binary is 0.0001100110011… repeating, so it cannot be stored exactly in a finite mantissa. Adding 0.1 ten times in many languages does not give exactly 1.0. For a school gradebook this is irrelevant; for a bank balance or a guidance-system trajectory it is catastrophic, which is why financial software uses BCD or integer fixed-point ("store cents, not dollars") and why you never compare floating-point numbers with = but with a tolerance like |a − b| < 1e−9.

Worked example 5 IB-style · 6 marks · represent and explain precision loss

Question. Explain why the value 0.1 cannot be represented exactly in binary floating point, and state why the result of 0.1 + 0.2 may not equal 0.3. What should a programmer do instead?

  1. Why not exact: 0.1 × 2 = 0.2, × 2 = 0.4, × 2 = 0.8, × 2 = 1.6 → record 1, remainder 0.6; ×2 = 1.2 → record 1, remainder 0.2; the remainder 0.2 has already appeared, so the pattern 0011 repeats for ever. A finite mantissa must truncate it, so the stored value is slightly off.
  2. Why 0.1 + 0.2 ≠ 0.3: each is stored as a nearby approximation; adding two approximations gives an approximation of 0.3 that is not bit-identical to the separately-stored approximation of 0.3. The comparison 0.1 + 0.2 == 0.3 is therefore false in most languages.
  3. What to do: compare with a tolerance (abs(diff) < epsilon), or use decimal/BCD types for money, or scale to integers (work in cents).
Marks: 2 for showing the repeating pattern, 2 for explaining that two approximations don't recombine to an exact 0.3, 2 for a correct mitigation (tolerance, BCD, or integer scaling). The phrase "floating point is an approximation of reals" alone is worth 1; the repeating-fraction demonstration is what earns the rest.

Worked example 5b IB-style · 6 marks · normalise a floating-point number

Question. A 12-bit floating-point format uses 1 sign bit, 4 exponent bits in excess-7, and 7 mantissa bits (with no hidden bit, so the mantissa is written in full). Represent the value 0.011012 × 2³ and then state its normalised form, giving the final mantissa and exponent fields.

  1. Start: the number is 0.01101₂ × 2³ (we write the mantissa exactly as given; the 2 subscript marks binary).
  2. Normalise: shift the mantissa left until there is a 1 before the point. 0.01101 → shift left once → 0.1101 (×2⁻¹, so exponent becomes 3−1 = 2) → shift left again → 1.101 (×2⁻¹ again, so exponent becomes 2−1 = 1). Normalised form: 1.101₂ × 2¹.
  3. Mantissa field: with no hidden bit the stored mantissa is the fractional part after the point, 1010000 (pad to 7 bits), and the leading 1 is stored explicitly because this format has no hidden bit.
  4. Exponent field: true exponent is 1, bias is 7, so stored exponent = 1 + 7 = 8 = 1000₂.
  5. Sign bit: positive, so 0.
  6. Full 12-bit pattern: 0 | 1000 | 1010000. The value is unchanged by normalisation; only the placement of the binary point moved.
Marks: 2 for the correct normalised mantissa and exponent, 2 for the exponent-in-excess calculation, 2 for assembling the bit fields. The common error is forgetting to reduce the exponent as you shift the mantissa left — each left shift divides the exponent by 2 in effect, i.e. subtracts 1.
Exam technique — "normalise" means move the point, not change the value

To normalise 0.001101 × 2³, shift the mantissa left until there is a 1 before the point and subtract from the exponent: 1.101 × 2⁰. The value is unchanged; only the representation changes. Normalisation packs the most significant digits into the stored field, which is why it maximises precision. State both the new mantissa and the new exponent, and note that the exponent is stored in excess-N.

Fixed-point representation: exact decimals without floating point

When rounding error is unacceptable but you still need fractions, systems use fixed-point: decide in advance that the binary point sits at a fixed position, and store the number as an integer of "scaled" value. To keep two decimal places you store everything ×100; the value 12.34 is held as the integer 1234, and the hardware (or software) remembers to divide by 100 when displaying. Fixed-point has a fixed range and fixed precision (you cannot represent 12.3456 if you only kept two places), but it is exact for the values it can hold and is far cheaper to compute than floating point — which is why embedded controllers and, historically, financial systems used it. The trade-off triangle is: floating point gives a huge range and variable precision but with rounding error; fixed point gives exactness and speed but a limited range and a fixed number of decimal places; BCD (section 1) gives exact decimal digits but wastes bits. Knowing which to choose is an evaluation question, not a definition.

Worked example 4b IB-style · 5 marks · fixed-point arithmetic

Question. A system stores money in fixed point with 2 decimal places (value ×100). Show how it stores £12.34 and £0.07, perform the addition, and state the displayed result. What goes wrong if a value needs 3 decimal places?

  1. £12.34 → 1234 (stored as an integer). £0.07 → 7 (stored as an integer; the leading zeros are implicit in the scale).
  2. Add as integers: 1234 + 7 = 1241.
  3. Display by inserting the point two places from the right: 1241 → £12.41. Exact, no rounding.
  4. If a value needs 3 decimal places, e.g. £0.007, it cannot be represented: 7 stored at ×100 means £0.07, not £0.007 — the value is silently wrong unless the scale is changed. This fixed precision is the method's hard limit.
Marks: 2 for the correct scaled integers and sum, 1 for the correct displayed result, 2 for explaining the fixed-precision limitation. The key idea the markscheme wants: fixed point is exact within its chosen scale but cannot represent finer values without re-scaling.

5 · Boolean algebra and logic gates

SL / HL

Intuition

Every decision a computer makes — "is this pixel red?", "should I branch?", "is the cache full?" — is a Boolean expression: true or false, 1 or 0. Boolean algebra is the arithmetic of true/false, and a logic gate is the physical component that computes one Boolean operation. You need six gates: AND, OR, NOT, XOR, NAND, NOR. AND and OR correspond to multiplication and addition (1·1 = 1, 1+1 = 1 in this algebra because there is no 2); NOT flips; XOR is "different"; NAND and NOR are the negated versions and are functionally complete — any circuit can be built from NAND alone, or from NOR alone.

Formal idea: laws and Karnaugh maps

Boolean expressions simplify by algebraic laws (identity, complement, commutative, associative, distributive, and De Morgan's). For small expressions a Karnaugh map (K-map) is a visual method: you lay the truth table out on a grid where adjacent cells differ in exactly one variable, then circle the largest possible groups of 1s that are powers of two (1, 2, 4, 8). Each circle drops one variable. The result is the minimal sum-of-products. K-maps are limited to about four variables by hand, which is exactly the size the IB uses.

Worked example 6 IB-style · 7 marks · simplify with a Karnaugh map

Question. A circuit has output F = Σ(0,1,2,4,6) for inputs A,B,C (minterms where F = 1). Use a 2×4 Karnaugh map to find the simplest expression for F.

  1. Layout: columns are A (0 then 1) over BC = 00, 01, 11, 10 (note the Gray-code order: only one bit changes between neighbours). Rows are A=0 and A=1.
  2. Fill 1s at minterms 0,1,2,4,6 → cells (A=0,BC=00),(A=0,BC=01),(A=0,BC=11),(A=1,BC=00),(A=1,BC=10).
  3. Circle groups of powers of two: (i) the two cells in column BC=00 (both A=0 and A=1) → this column has A'·B'·C' and A·B'·C', which combine to B'·C' (A drops out). (ii) the two cells (A=0,BC=01) and (A=0,BC=11) → A'·B'·C and A'·B·C combine to A'·C (B drops out).
  4. Result: F = B'·C' + A'·C. Check: this is simpler than the original four-term sum and matches all five minterms.
Marks: 2 for a correctly ordered K-map with the right 1s, 3 for valid groupings (each a power of two, as large as possible), 2 for the simplified expression. A common error is using binary column order (00,01,10,11) instead of Gray code, which makes adjacent cells differ by two variables and breaks the method.
Trap — XOR is not "OR"

A OR B is 1 when either or both are 1; A XOR B is 1 only when they differ. For A = B = 1, OR = 1 but XOR = 0. This matters in adders (the sum bit is XOR, the carry is AND) and in parity (section 9), where XOR is the natural "does the count of 1s differ in parity" operator.

Algebraic simplification and deriving an expression from a truth table

Besides K-maps, Boolean expressions simplify by algebraic laws. The ones the IB uses are: the identity laws (A + 0 = A, A·1 = A), the complement laws (A + A' = 1, A·A' = 0), the idempotent laws (A + A = A, A·A = A), the commutative / associative / distributive laws (exactly like arithmetic), and De Morgan's laws (NOT(A·B) = A' + B', and NOT(A + B) = A'·B'). De Morgan is the workhorse: it lets you turn an AND of negations into an OR, which is how you convert between NAND-only and OR-only circuits. When you are given a truth table and asked for the expression, the standard route is sum of products: for every row where the output is 1, write the AND of the inputs (using the unprimed variable when the input is 1, primed when 0), then OR all those terms together. That gives a correct but often un-minimised expression; a K-map then shrinks it.

Worked example 6b IB-style · 6 marks · expression from a truth table, then simplify

Question. For inputs A, B with output F = 1 only when (A=0,B=0) and (A=1,B=1), (a) write the sum-of-products expression, (b) simplify it using an algebraic law, and (c) name the single gate that computes it.

  1. (a) The 1-rows: (0,0) → A'·B'; (1,1) → A·B. So F = A'·B' + A·B.
  2. (b) Recognise A'·B' + A·B as "both inputs equal" — this is the definition of XNOR. Algebraically, by De Morgan on the XOR form: A⊕B = A·B' + A'·B, so F = (A⊕B)' = XNOR, which has no smaller sum-of-products but is a single gate.
  3. (c) One XNOR gate (or, equivalently, an XOR followed by a NOT) computes it. Note XNOR = NOT XOR, so it is also buildable from a NAND/NOR set.
Marks: 2 for the correct sum-of-products, 2 for identifying XNOR (the simplification step), 2 for naming the gate. The trap is writing F = A·B' + A'·B, which is XOR (output 1 when inputs differ) — the opposite of what the table asks.

Building circuits from gates: the half adder and NAND universality

A half adder is the smallest useful arithmetic circuit: it takes two input bits and produces a sum and a carry, built from one XOR gate (for the sum, since sum = A⊕B) and one AND gate (for the carry, since carry = A·B). A full adder adds a carry-in too and needs two XORs, two ANDs and an OR (or, equivalently, two half adders plus an OR). Because XOR, AND and OR can all be made from NAND alone (for example NOT A = A NAND A; A AND B = NOT(A NAND B); A OR B = (NOT A) NAND (NOT B)), a single gate type can build any circuit — this is functional completeness. Real chips are not built only from NAND for speed and power reasons, but NAND-only (and NOR-only) fabrics are used in some programmable logic and in teaching, precisely because they prove the point that the six gates are not independent primitives.

Exam technique — draw the gates, label the wires

When asked to draw a circuit, draw the standard gate shapes (section 5), label every input and output, and write the Boolean expression on or beside each gate. A correct expression with no diagram may score; a diagram with no labels scores little, because the examiner cannot tell which wire is the carry. And if asked "show the half adder uses only NAND", write NOT A = A NAND A and build AND/OR from NAND — three lines, three marks.

6 · Von Neumann architecture and the CPU

SL / HL

Intuition

A computer is a factory with one workbench. The Von Neumann architecture — the design of almost every general-purpose machine — stores both program instructions and data in the same memory, and a single control unit fetches them one at a time, decodes what to do, and tells the arithmetic logic unit to do it. The "stored program" idea is the whole point: you don't rewire the machine to change its job, you load a different program. The Harvard architecture splits instruction memory from data memory, which lets the CPU fetch an instruction and read data at the same time — faster, and used in digital signal processors and most microcontrollers.

The fetch–decode–execute cycle

The CPU runs a repeating loop. Fetch: copy the instruction at the address in the program counter (PC) from memory into the instruction register, then increment the PC. Decode: the CU works out which operation and which operands. Execute: the ALU performs it, or the CU directs a memory read/write. The registers are the CPU's scratchpad: the PC (next instruction's address), the accumulator (current ALU result), the memory address register (MAR) and memory data register (MDR) that hold the address and value being transferred, and the current instruction register (CIR). Buses carry these between parts: the address bus (CPU→memory, one-way), the data bus (both ways), and the control bus (read/write/clock signals).

Worked example 6b IB-style · 7 marks · trace one fetch–decode–execute cycle

Question. The PC holds 0x04. Memory at 0x04 contains the instruction "LOAD R1, [0x20]" (copy the byte at address 0x20 into register R1). Trace the cycle, naming the registers and buses used at each step.

  1. Fetch. The CU puts the PC value 0x04 on the address bus; the control bus asserts a read; the instruction byte travels back on the data bus into the memory data register (MDR), then into the current instruction register (CIR). The PC is incremented to 0x05.
  2. Decode. The CU inspects the CIR, recognises a LOAD instruction, and notes it needs a memory read from operand 0x20 into R1.
  3. Execute. The CU puts 0x20 on the address bus, asserts read on the control bus; the byte at 0x20 returns on the data bus into the MDR and is copied into register R1.
  4. The next cycle fetches the instruction at the new PC (0x05). The whole operation touched the address bus twice (once for the instruction, once for the data) and the data bus twice.
Marks: 2 for the fetch (PC→address bus→MDR→CIR, PC incremented), 2 for decode naming the CIR, 2 for execute (operand address on address bus, value into R1 via MDR), 1 for noting the bus usage. The frequently missed mark is that the PC is incremented during fetch, so the CPU is already pointing at the next instruction before the current one finishes executing.

Exam technique — name the register, not "the thing"

When asked what holds the next instruction's address, say program counter, not "a counter". When asked what holds the instruction being decoded, say current instruction register (CIR). The marks are on the specific register names. And state that the PC is incremented during fetch so execution continues in sequence unless a jump changes it.

Clock speed, the address bus width, and pipelining

The clock is a steady pulse; one fetch–decode–execute cycle (or one pipeline stage) happens per tick, so a 3 GHz CPU attempts about three billion ticks a second. Clock speed alone does not determine performance, because a cycle may do more or less work and a faster clock uses more power and emits more heat — which is why modern design favours more cores and smarter pipelines over ever-higher GHz. The address bus width sets the maximum memory the CPU can reference: an n-bit address bus addresses 2ⁿ locations, so a 32-bit bus tops out at 4 GB (2³² bytes) and a 64-bit bus at 16 exabytes. This is a hard ceiling independent of how much RAM you install. The data bus width (commonly 64 bits today) sets how many bits move per transfer, affecting throughput. Pipelining overlaps the stages: while instruction 2 is being decoded, instruction 1 is executing and instruction 3 is being fetched, so the CPU completes a new instruction every cycle instead of every three — like an assembly line. A pipeline stall (a cache miss or a branch) empties part of the line and costs cycles.

Note — why "64-bit" means more than bigger numbers

A "64-bit processor" mainly means a 64-bit address bus (so it can use more than 4 GB of RAM) and 64-bit registers (so it can do arithmetic on larger integers and addresses in one instruction). It does not mean it is twice as fast as a 32-bit one; it means it is not blocked by the 4 GB memory ceiling and handles bigger chunks per operation. When you evaluate "is 64-bit better?", the memory-addressing argument is the strongest, with wider registers a close second.

7 · Primary and secondary storage, and cache

SL / HL

Intuition

Storage is a hierarchy of speed versus cost. The closer to the CPU, the faster and the more expensive per byte. Registers and cache are inside the CPU and near-instant; RAM is fast but voluntary-powered (it forgets when off); ROM and flash keep their contents without power; SSD and hard disks hold terabytes but are slow. The art of the design is that the CPU mostly finds what it needs in the fast, small layers, because programs tend to reuse recent data (the principle of locality).

Cache levels and why they work

Modern CPUs have L1 (tiny, split into instruction and data, ~1 cycle), L2 (bigger, ~10 cycles) and L3 (shared, ~30–40 cycles) caches between registers and RAM. A cache hit (needed data is in cache) is fast; a miss (must fetch from RAM) is slow. Caches work because of temporal locality (recently used data is used again) and spatial locality (nearby addresses are used soon). Data moves in blocks called cache lines. Understanding cache is how you explain why a program that strides through a 2-D array in the wrong order can be many times slower.

Interrupt handling

An interrupt is a signal that makes the CPU pause its current task and run a small interrupt service routine (ISR). Sources include a key press, a timer, or a completed disk read. The CPU saves its state (registers, PC) on the stack, runs the ISR, then restores state and resumes. This is how one CPU appears to "do many things at once" — it rapidly switches between tasks in response to interrupts, which is the seed of the concurrency you met in B1.

Trap — RAM is volatile, but "memory" is ambiguous

In everyday speech "memory" means RAM, which is volatile. But ROM, flash and SSD are also memory (storage) and are non-volatile. When a question says "what is lost when the power goes off?", list RAM and cache (and registers) — not the hard disk or SSD. Conversely, firmware lives in ROM precisely because it must survive power loss.

How the media physically store bits

The abstract "non-volatile" hides very different physics, and the IB likes to ask why one medium suits a job. A magnetic hard disk (HDD) stores bits as tiny magnetised regions on spinning platters, read and written by a moving head on an arm — fast-ish but mechanical, so it is slow to seek and fragile to shock. An SSD / flash stores bits in floating-gate transistors that trap electrons; it has no moving parts, so it is far faster and shock-proof, but each cell wears out after a finite number of write cycles and the data slowly leaks if unpowered for years (retention, not volatility in the RAM sense). Optical media (CD/DVD/Blu-ray) store bits as pits and lands burned or pressed into a spiral track, read by a laser — cheap and durable for distribution, but slow and increasingly obsolete. ROM is manufactured with its contents (mask ROM) or written once (PROM/EPROM/EEPROM); modern firmware usually lives in EEPROM/flash so it can be updated. The performance ordering from fast to slow is roughly registers ≈ cache ≫ RAM ≫ SSD ≫ HDD ≫ optical, and the cost-per-byte ordering is the exact reverse — which is why the hierarchy exists at all.

Exam technique — justify a storage choice by the trade-off triangle

When asked "which storage for X?", score the three corners: speed, permanence (non-volatile?), and cost/capacity. A boot ROM wants permanence and cheapness over speed. A scratch buffer wants speed (RAM). An archive wants capacity and cost (HDD or optical). A laptop's system disk wants speed and shock-resistance (SSD). State two of the three corners and you have the mark; state all three and you have the top band.

8 · Operating systems, scheduling and virtual memory

SL / HL

Intuition

The operating system (OS) is the manager that sits between your programs and the hardware. Without it, every program would have to drive the disk, the screen and the network itself, and two programs would fight over memory. The OS owns four jobs: process management (deciding which task runs when), memory management (dividing RAM among programs), file and device management (the file system and drivers), and providing a user interface (a shell or GUI). Its defining trick is abstraction: it hides the messy hardware behind clean calls like "open this file".

Formal idea: scheduling and virtual memory

Scheduling decides which ready process gets the CPU. Round-robin gives each process a fixed time slice in turn — fair and responsive, good for interactive systems. First-come-first-served is simple but can let one long job block everything. Shortest-job-first minimises average waiting time but needs to know job lengths and can starve long jobs. Priority scheduling runs the most important first, risking starvation of low-priority work unless priority ages upward over time.

Virtual memory lets a program use more address space than physical RAM by using disk as an extension. Programs are divided into pages (fixed blocks, e.g. 4 KB); RAM holds a page table mapping virtual to physical frames. When a needed page is not in RAM, a page fault occurs and the OS swaps a less-used page out to disk and brings the needed one in. Too much swapping is thrashing — the machine spends more time moving pages than working. Virtual memory gives each process its own clean address space, which is also a security boundary: one program cannot accidentally read another's memory.

Exam technique — "virtual memory" is not "a big hard disk"

The mark is for explaining that virtual memory maps virtual addresses to physical frames via a page table and uses disk as a backing store, so programs can exceed RAM and are isolated from each other. Saying "it uses the hard disk to make memory bigger" scores one mark; explaining pages, the page table and page faults earns the rest. And note the cost: swapping is slow, so virtual memory is a safety net, not a substitute for enough RAM.

Scheduling in detail, with a Gantt example

To evaluate a scheduling algorithm you need a concrete case, so use a Gantt-style timeline. Suppose three jobs arrive together: P1 needs 5 ms of CPU, P2 needs 2 ms, P3 needs 8 ms. Under first-come-first-served the order is P1, P2, P3; P1 waits 0 and finishes at 5, P2 waits 5 and finishes at 7, P3 waits 7 and finishes at 15; average waiting time = (0 + 5 + 7)/3 ≈ 4.0 ms. Under shortest-job-first the order is P2, P1, P3; waits are 0, 2, 7 → average (0 + 2 + 7)/3 = 3.0 ms — better on average, because the short job is never stuck behind a long one. Under round-robin with a 2 ms slice they interleave: P1(2), P2(2, done), P1(2), P3(2), P1(1, done), P3(2), P3(2, done); no job waits more than about one round, so the system feels responsive even though the total time is the same. The evaluation point: SJF minimises average wait but can starve a long job forever if short jobs keep arriving, and it needs to know job lengths it usually doesn't have; round-robin is fair and responsive but has overhead from constant switching.

Worked example 8 IB-style · 6 marks · compare scheduling algorithms

Question. Jobs A(4), B(1), C(6) arrive together. (a) Give the completion order and average waiting time under shortest-job-first. (b) State one disadvantage of SJF in practice.

  1. (a) SJF order: B(1), A(4), C(6). B waits 0, finishes at 1. A waits 1, finishes at 5. C waits 5, finishes at 11.
  2. Average waiting time = (0 + 1 + 5)/3 = 2.0 ms.
  3. (b) Disadvantage: SJF can starve a long job if short jobs keep arriving, and the OS generally cannot know each job's true length in advance, so it must estimate — and a bad estimate undermines the benefit.
Marks: 2 for the correct order, 2 for the correct average waiting time, 2 for a valid practical disadvantage (starvation or unknown lengths). Showing the waiting-time arithmetic is what earns the marks; a bare "SJF is best" earns none.

A page-table walk, worked

To make virtual memory concrete, walk one address. Suppose pages are 4 KB (2¹² bytes, so the low 12 bits of an address are the offset within a page) and the page table says virtual page 5 maps to physical frame 20. A program uses virtual address 0x5004 (hex). The address splits into virtual page number = 0x5004 ÷ 0x1000 = 5, and offset = 0x5004 MOD 0x1000 = 4. The MMU looks up page 5 → frame 20, then forms the physical address = 20 × 0x1000 + 4 = 0x14004. If page 5 were not present (a 0 in its valid bit), the MMU raises a page fault; the OS picks a victim frame, writes it to disk if dirty, reads page 5 in from disk, updates the table, and restarts the instruction. The page table itself lives in RAM and is consulted on (almost) every memory access, which is why a translation lookaside buffer (TLB) — a tiny cache of recent translations — exists to avoid the lookup cost.

Trap — virtual addresses are not physical addresses

A program only ever sees virtual addresses; the physical RAM location is invisible to it and differs each run. This is what lets two programs both use "address 0x1000" without colliding — they map to different frames. If a question asks "where is variable X in RAM?", the only correct answer is "in the frame the page table maps its virtual page to"; guessing a raw number is wrong, because the mapping is the whole point.

9 · Translators: assembler, compiler, interpreter

SL / HL

Intuition

The CPU only runs machine code — bare 1s and 0s. Humans write assembly, or a high-level language like Python or Java. A translator bridges the gap, and there are three kinds with different trade-offs.

TranslatorInput → outputWhenTrade-off
AssemblerAssembly → machine codeOne-to-one, low levelFast to translate; human-readable machine code

Note — linkers and loaders

A compiler may produce object code that a separate linker combines with libraries into an executable, which a loader places into memory to run. The IB mostly wants the assembler/compiler/interpreter distinction; mention the linker only when asked how separately compiled modules become one program.

10 · Encryption, hashing and TLS

SL / HL

Intuition

Two ideas protect data in motion and at rest. Encryption scrambles data so only someone with the key can read it. Hashing produces a fixed-length fingerprint of data so you can detect any change. They solve different problems: encryption is reversible (with the key), hashing is not.

Formal idea: symmetric, asymmetric, hashing

Symmetric encryption (e.g. AES) uses one shared secret key for both encrypt and decrypt. It is fast but has the key-distribution problem: how do you safely give the other party the key over a public network? Asymmetric encryption (e.g. RSA) uses a public/private key pair: anyone can encrypt with your public key, only you can decrypt with your private key. It solves distribution but is slow, so real systems use asymmetric only to agree on a symmetric session key, then use symmetric for the bulk data — the best of both.

A hash function (e.g. SHA-256) maps any input to a fixed-length digest; it is one-way and collision-resistant (finding two inputs with the same hash is infeasible). Uses: password storage (store the hash, not the password; check by re-hashing), integrity checking, and digital signatures (hash the message, encrypt the hash with your private key). TLS (the S in HTTPS) is the protocol that wraps this: the browser and server use asymmetric crypto to agree a symmetric key, then encrypt the session, and the server proves its identity with a certificate signed by a trusted authority.

Trap — hashing is not encryption

You cannot "decrypt a hash" to recover the password; that is the point. Storing passwords as hashes (with a salt) is correct; storing them encrypted but recoverable means a leaked key reveals every password. And HTTPS (TLS) protects data in transit — it does nothing about a database that was breached at rest, which is why both layers matter.

How a key is agreed: the conceptual view

You do not need to compute RSA by hand, but you should understand the shape of the idea, because it is what makes the internet usable. Asymmetric key agreement rests on a mathematical one-way function: it is easy to multiply two large primes but (with current classical computers) infeasible to factor their product back into the primes. So a public key can be published widely, and only the matching private key (derived from the secret primes) can undo operations done with it. In practice the browser and server perform a handshake: they use asymmetric crypto only to agree on a fresh, random symmetric session key, then switch to fast symmetric encryption for the rest of the session. A digital signature is the reverse use: the sender hashes the message and encrypts the hash with their private key; the receiver decrypts it with the sender's public key and compares the hash, proving both integrity (the hash matches) and authenticity (only the true sender could have produced it). A certificate binds a public key to a domain name and is itself signed by a trusted certificate authority, which is how your browser knows the key really belongs to the site and not to an impostor.

Note — "why is this in fundamentals and again in A2?"

Here the focus is the concepts: symmetric vs asymmetric, hashing, the reason both are used. In A2 the focus shifts to the protocol (TLS runs over TCP, the handshake sits inside the HTTPS exchange, and a man-in-the-middle attack is what the certificate defeats). If a question asks "explain TLS", give the handshake-and-certificate story; if it asks "why two kinds of encryption", give the speed-vs-distribution story. They are complementary, not duplicated.

11 · Fractions in other bases and binary multiplication/division

SL / HL

Intuition: what the columns mean to the right of the point

To the right of the binary point, column weights are negative powers of two: 2⁻¹ = ½, 2⁻² = ¼, 2⁻³ = ⅛, and so on. So 0.101₂ = 1×½ + 0×¼ + 1×⅛ = 0.5 + 0.125 = 0.625₁₀. Converting a decimal fraction to binary is the mirror of integer conversion: repeatedly multiply by 2 and take the whole-number part as the next bit; the fractional remainder carries on. If the remainder never reaches zero, the representation repeats and you stop after the available bits — which is the same phenomenon behind the 0.1 problem in section 4. The same method works for any base: multiply by the base, take the integer part.

Worked example 11 IB-style · 6 marks · decimal fraction to binary

Question. Convert the decimal fraction 0.375 to binary, then convert it back to decimal to check. State what would happen with 0.1.

  1. 0.375 × 2 = 0.75 → bit 0.7 (integer part 0, keep fraction 0.75).
  2. 0.75 × 2 = 1.5 → bit 1 (integer part 1, keep fraction 0.5).
  3. 0.5 × 2 = 1.0 → bit 1 (integer part 1, fraction now 0, stop).
  4. Reading the integer parts top-down: 0.011₂.
  5. Check: 0.011₂ = 0×½ + 1×¼ + 1×⅛ = 0.25 + 0.125 = 0.375₁₀. Correct.
  6. 0.1: 0.1×2=0.2→0; 0.2×2=0.4→0; 0.4×2=0.8→0; 0.8×2=1.6→1; 0.6×2=1.2→1; 0.2 reappears, so the pattern 0011 repeats for ever: 0.000110011…₂. It never terminates, so it must be approximated.
Marks: 3 for the correct 0.011₂ with the multiply-by-2 method shown, 1 for the back-check, 2 for explaining the repeating 0.1. The back-check is itself a mark because it proves you did not just pattern-match.

Formal idea: multiply and divide by shifting

Because each left shift multiplies by 2 and each right shift divides by 2, multiplication by a power of two is a single shift, and multiplication by a general constant is a shift-and-add. To multiply 13 (1101₂) by 10, for instance, note 10 = 8 + 2 = 2³ + 2¹, so 13 × 10 = (13 ≪ 3) + (13 ≪ 1) = 104 + 26 = 130 — three operations instead of a full multiply. Integer division by 2 is a right shift, discarding the remainder (that is why 7 ≫ 1 = 3, the floor of 3.5). This is why bit operations are fast and why you will see them in low-level or performance code. For the IB you mostly need to recognise that a left shift is ×2 and explain it; you are not asked to implement a multiplier.

Worked example 12 IB-style · 4 marks · interpret a shift

Question. An 8-bit register holds 00010100₂ (20₁₀). State its value after (a) a logical left shift by 1, and (b) a logical right shift by 2. Explain what operation each shift performs.

  1. (a) Left shift by 1: 00010100 → 00101000 = 40. This is ×2 (20 × 2 = 40). The leftmost 0 is shifted out, a 0 enters on the right.
  2. (b) Right shift by 2: 00010100 → 00000101 = 5. This is ÷4 with the remainder discarded (20 ÷ 4 = 5). Two zeros enter on the left.
  3. Note: for unsigned numbers a logical and arithmetic right shift are the same; for signed numbers an arithmetic right shift replicates the sign bit instead of shifting in 0, to preserve the sign.
Marks: 1 each for the two correct results, 2 for stating ×2 and ÷4 (with remainder discarded). The sign-bit subtlety is the extra mark if the question mentions signed values.

12 · Synthesis: from key press to answer

SL / HL

A single narrative that uses the whole topic

It helps to see one end-to-end story so the pieces stop feeling like separate facts. You press a key. The keyboard raises a hardware interrupt; the CPU finishes its current instruction, saves its state, and runs the keyboard's interrupt service routine, which reads the scan code from the device (over the data bus) into a register. The OS's scheduler later gives the text editor process a time slice, and the editor appends the character — whose Unicode code point is stored as UTF-8 bytes in a buffer in RAM (copied through the cache). When you save, the bytes are written to an SSD; a hash of the file may be computed so integrity can be checked later. The spell-checker runs the string through Boolean comparisons in the ALU, and the whole program is machine code that an earlier compiler produced from your high-level source. Every term on this page appears in that one paragraph; if you can retell it, you have the topic.

Why this topic is the bedrock

Every other page assumes it. B1's conditions are Boolean expressions the ALU evaluates with the gates here. B2's variables live in the RAM/cache hierarchy here. B4's arrays are contiguous bytes addressed by the buses here. A2's packets are bytes moved by the same buses. A3's records are bytes on the same SSD. When a later question feels hard, it often helps to drop one level and ask "what are the actual bits doing?" — and that question is always an A1 question.

Self-check

  1. Convert the decimal number 212 to binary and to hexadecimal, showing your method.

    Show the answer

    Binary by repeated division: 212÷2=106 r0; 106÷2=53 r0; 53÷2=26 r1; 26÷2=13 r0; 13÷2=6 r1; 6÷2=3 r0; 3÷2=1 r1; 1÷2=0 r1 → reading up: 11010100. Hex: group as 1101 0100 → D4. Check: D=13, 13×16+4 = 212.

    Why this matters: grouping binary into fours is the fastest, least-error path to hex, and the division method gives you an audit trail the examiner can follow.

  2. Using 8-bit two's complement, calculate 25 − 47. Show the formation of −47 and state whether overflow can occur.

    Show the answer

    +25 = 00011001. +47 = 00101111 → invert 11010000, add 1 → 11010001 = −47. Add: 00011001 + 11010001 = 11101010, which is −128+64+32+8+2 = −22. Correct (25−47 = −22). Overflow cannot occur because the operands have opposite signs; signed overflow only happens adding same-sign numbers.

    Why this matters: subtraction is always performed as addition of a two's complement negative, so the ALU needs only an adder.

  3. Explain why 0.1 cannot be stored exactly in binary floating point, and describe one situation where the error is dangerous.

    Show the answer

    0.1 is a repeating binary fraction (0.000110011…), so a finite mantissa truncates it; 0.1 + 0.2 then does not equal the separately-stored 0.3. Danger: financial totals (interest, balances) accumulate the error; banks therefore use BCD or integer cents.

    Why this matters: recognise that floating point is an approximation, and that "exact decimal" and "exact binary" are different sets.

  4. State the function of the control unit, the ALU and the program counter, and describe the fetch phase of the cycle.

    Show the answer

    The CU fetches, decodes and directs; the ALU does arithmetic/logic on registers; the program counter holds the address of the next instruction. Fetch: copy the instruction at the PC's address from memory into the CIR, then increment the PC so execution proceeds in sequence.

    Why this matters: these three are the most-asked architecture terms; naming the register precisely is the mark.

  5. A program needs 500 MB of memory but the computer has only 256 MB of RAM. Explain how it can still run, and name the event that makes it slow.

    Show the answer

    Virtual memory maps the program's virtual addresses to physical frames and uses disk as backing store; pages not in RAM are brought in on a page fault. It is slow because disk is far slower than RAM, and excessive swapping is thrashing.

    Why this matters: virtual memory is about isolation and exceeding physical RAM, not a free upgrade in speed.

  6. Compare a compiler and an interpreter, giving one scenario where each is the better choice.

    Show the answer

    A compiler translates the whole program to machine code first (slow build, fast run, all errors at once); an interpreter runs line by line (fast start, easy debugging, slower run). Use a compiler for a shipped product where speed matters; an interpreter for development/scripting where quick iteration matters.

    Why this matters: the IB loves "evaluate" here — the trade-off is build-time vs run-time, not "one is better".

  7. Explain the difference between symmetric and asymmetric encryption, and why real systems use both.

    Show the answer

    Symmetric uses one shared key (fast, but how do you share the key safely?); asymmetric uses a public/private pair (solves distribution, but is slow). Real systems use asymmetric only to agree on a symmetric session key, then symmetric for the data — fast and secure.

    Why this matters: the "key distribution problem" is the reason both exist; an answer that only describes one misses the point.

  8. A logic circuit has inputs A, B, C and output F = A·B + A'·C. Draw the truth table and state what single gate type could replace the whole circuit in principle.

    Show the answer

    Truth table over A,B,C: F = 1 when (A=1 and B=1) or (A=0 and C=1). Rows with F=1: 100, 101, 110, 111. In principle any circuit can be built from NAND alone (functionally complete), so NAND could replace it.

    Why this matters: functional completeness (NAND or NOR) is a common conceptual mark; you do not need to draw the NAND version, just know it exists.
