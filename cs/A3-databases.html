A3 · Databases

A database is not a spreadsheet with aspirations; it is a system built so that many people can read and write the same data at once, safely, and ask questions of it in a declarative language. This topic has two halves that the IB examines differently: the design half (why you split tables the way you do — normalisation) and the use half (how you query them — SQL). Paper 1 asks you to justify a design and to write or interpret SQL; the internal assessment often lives or dies on whether your schema is normalised. Learn the keys, learn the three normal forms as a sequence of "remove this redundancy", and learn a dozen SQL clauses by heart, and you can answer almost any database question the syllabus throws at you.

A3.1 · The relational model

SL / HL

A relational database stores data in tables (relations). Each table has rows (records / tuples) and columns (fields / attributes). The whole model is built on one idea: every row is uniquely identified, and relationships between tables are represented by including a key from one table inside another, never by pointers or nesting.

Keys

KeyDefinitionExample
Primary key (PK)A column (or combination) that uniquely identifies each row; cannot be nullstudentID
Foreign key (FK)A column in one table that holds the PK of another table; it is the linkenrol.studentID → student.studentID
Candidate keyAny column that could serve as PK (unique, minimal)email, if unique
Compound / composite keyA PK made of two or more columns together(orderID, productID) on an order line
Why keys are the whole design

The primary key is a promise: "this value appears at most once in this table". The foreign key is a promise of a different shape: "this value must already exist in the other table". Those two promises are what make a relational database consistent without you writing code to check it. When a row references a student who does not exist, the database rejects it — that is referential integrity, and it is enforced by the foreign key, not by your discipline.

Trap — a foreign key need not be unique

A PK is unique; an FK is usually not. One student appears on many enrolment rows, so enrol.studentID repeats. Students confuse "key" with "unique" and wrongly say an FK must be unique. The FK's job is to match a PK, not to be unique itself. Only the PK (and candidate keys) are unique.

Relationships

Two tables relate as one-to-one, one-to-many, or many-to-many. A one-to-many is stored by putting the PK of the "one" side into the "many" side as an FK (e.g. one Module has many Enrolments). A many-to-many cannot be stored in either table directly, so you create a link table with two FKs — exactly the Enrolment table above. This is the single most-tested design move in the topic.

Exam tip

When a scenario says "each student takes many modules and each module has many students", the mark is for designing a third table, not for adding a column. Write: "introduce a link/associative entity Enrolment(studentID, moduleID, grade) with FKs to both." That one sentence is usually three or four marks.

A3.2 · Normalisation

SL / HL

Normalisation is the process of restructuring a table to remove redundancy and the update anomalies it causes. Redundancy is dangerous because it lets the same fact be stored in two places, and then the two copies can disagree. The three normal forms are a staircase: each removes one kind of problem.

First normal form (1NF)

A table is in 1NF when every cell holds one atomic value (no repeating groups, no lists in a cell) and there is a primary key. "Subjects: Maths, Physics" in one cell violates 1NF; split it so each subject is its own row.

Second normal form (2NF)

2NF requires 1NF and that every non-key column depends on the whole key, not just part of it. This only matters when the PK is compound. If a table has PK (orderID, productID) but stores productName against productID alone, productName depends on only half the key — that is a partial dependency, and you must move productName into a Product table keyed by productID.

Third normal form (3NF)

3NF requires 2NF and that no non-key column depends on another non-key column (no transitive dependency). If a table stores studentID → tutorName → tutorRoom, then tutorRoom depends on tutorName, not on the key; move tutor into its own table. After 3NF, every non-key fact depends only on the key, "the whole key, and nothing but the key".

Worked example 1 IB-style · 10 marks · unnormalised → 3NF

Question. A school stores one flat table Registration(studentID, name, tutor, tutorRoom, moduleID, moduleTitle, grade), with PK (studentID, moduleID). Normalise it to 3NF, naming each step and the anomaly it removes.

  1. Check 1NF. Assume each cell is atomic and the composite key (studentID, moduleID) identifies a row. It is in 1NF.
  2. Check 2NF. tutor and tutorRoom depend only on studentID, not on moduleID — a partial dependency on part of the key. moduleTitle depends only on moduleID — also partial. Move them out.
  3. 2NF result: Student(studentID, name, tutor, tutorRoom); Module(moduleID, moduleTitle); Enrol(studentID, moduleID, grade) (PK studentID+moduleID, FKs to the others).
  4. Check 3NF on Student. tutorRoom depends on tutor (a non-key attribute), not on studentID — a transitive dependency. Split out Tutor.
  5. 3NF result: Student(studentID, name, tutor); Tutor(tutor, tutorRoom); Module(moduleID, moduleTitle); Enrol(studentID, moduleID, grade).
  6. Anomalies removed: update (change a tutor's room once, not in 200 rows), insertion (a new module with no students can now exist), deletion (removing a student no longer deletes the module).
  7. Verify: every non-key column now depends on the whole key of its table and on nothing but the key. 3NF achieved.
Answer: four tables — Student(studentID,name,tutor), Tutor(tutor,tutorRoom), Module(moduleID,moduleTitle), Enrol(studentID,moduleID,grade). Marks: 2 for 1NF check, 3 for 2NF split + naming partial dependency, 3 for 3NF split + naming transitive dependency, 2 for the three anomalies.
Trap — 2NF only matters with a composite key

If the primary key is a single column, the table is automatically in 2NF (there is no "part of the key" to depend on). Students apply the 2NF split to single-key tables and invent problems. Only split for partial dependency when the PK has more than one column.

When NOT to over-normalise

Normalisation is not free: more tables mean more JOINs, and JOINs cost time. A read-heavy reporting system may deliberately keep some redundancy (a denormalised schema) for speed. The IB asks you to normalise, but a mature answer notes the performance trade-off — that nuance earns top-band evaluation marks.

A3.3 · SQL

SL / HL

SQL (Structured Query Language) is declarative: you state what you want, not how to get it. The database engine plans the steps. The clauses you must know are SELECT, FROM, WHERE, ORDER BY, GROUP BY, HAVING, and the JOINs.

Basic SELECT / WHERE / ORDER BY

SELECT studentID, name
FROM Student
WHERE tutor = 'Ross'
ORDER BY name ASC;

This returns the ID and name of every student whose tutor is Ross, sorted alphabetically. WHERE filters rows before grouping; HAVING filters groups after grouping.

Aggregates and GROUP BY

SELECT moduleID, COUNT(*) AS n, AVG(grade) AS avg_grade
FROM Enrol
GROUP BY moduleID
HAVING COUNT(*) > 5;

Group the enrolments by module, count and average each group, then keep only modules with more than five students. COUNT, SUM, AVG, MIN, MAX are the aggregate functions; anything in the SELECT that is not aggregated must appear in GROUP BY.

JOIN

SELECT s.name, m.moduleTitle, e.grade
FROM Enrol e
JOIN Student s ON e.studentID = s.studentID
JOIN Module  m ON e.moduleID  = m.moduleID
WHERE m.credits = 15;

An INNER JOIN returns only rows with a match in both tables. A LEFT JOIN keeps all left rows even when there is no match (filling the right side with NULL) — use it when you must list, say, all modules including those with no enrolments.

Worked example 2 IB-style · 6 marks · write a query

Question. Using the Student / Module / Enrol tables, write SQL to list the name and average grade of every module taught by tutor Ross, but only modules whose average grade is at least 60.

  1. We need module titles (from Module), the tutor (from Student, via Enrol), and grades (Enrol). Join all three.
  2. Filter tutor = 'Ross' in WHERE (a row-level condition, applied before grouping).
  3. GROUP BY module to compute one average per module.
  4. Use HAVING AVG(grade) >= 60 to keep only high-average modules (a group-level condition).
  5. Write it:
SELECT m.moduleTitle, AVG(e.grade) AS avg_grade
FROM Enrol e
JOIN Student s ON e.studentID = s.studentID
JOIN Module  m ON e.moduleID  = m.moduleID
WHERE s.tutor = 'Ross'
GROUP BY m.moduleID, m.moduleTitle
HAVING AVG(e.grade) >= 60;
Answer: the query above. Marks: 1 for the joins, 1 for WHERE tutor, 1 for GROUP BY, 1 for AVG, 1 for HAVING (not WHERE) on the average, 1 for selecting the right columns.
Worked example 3 IB-style · 4 marks · interpret a query

Question. What does this return, and why HAVING and not WHERE? SELECT moduleID, COUNT(*) FROM Enrol GROUP BY moduleID HAVING COUNT(*) > 1;

  1. It groups enrolments by module and counts students per module.
  2. HAVING COUNT(*) > 1 keeps only modules enrolled by more than one student.
  3. WHERE cannot be used because COUNT(*) is computed during grouping; WHERE filters raw rows beforehand and cannot see an aggregate. HAVING is the post-group filter.
  4. So the result is a list of popular modules (more than one student).
Answer: module IDs with >1 enrolment; HAVING is required because the condition uses an aggregate that exists only after grouping. Marks: 2 for the meaning, 2 for the WHERE-vs-HAVING reason.
Trap — WHERE vs HAVING

The single most common SQL error: putting an aggregate condition in WHERE. WHERE AVG(grade)>60 is a syntax error because AVG is not known yet. Aggregates go in HAVING, after GROUP BY. Row-level filters (tutor='Ross') go in WHERE. Know which side of the grouping each condition lives on.

Indexes

An index is an extra data structure (usually a B-tree) on a column that lets the database find rows by that column without scanning the whole table — like the index at the back of a book. It speeds up SELECT and JOIN but slows down INSERT/UPDATE/DELETE, because the index must be maintained. You add indexes on columns you search or join on often (foreign keys especially).

Why an index is a trade

Without an index, finding studentID=42 means reading every row until you hit it — O(n). With a B-tree index, you descend a balanced tree in O(log n) comparisons. On a billion rows that is the difference between a billion steps and about thirty. But every write must also update the tree, so a table with many indexes writes more slowly. The art is indexing the columns you query and no others.

A3.4 · Transactions and ACID

SL / HL

A transaction is a sequence of operations treated as one all-or-nothing unit: either all of it happens, or none of it does. This matters when two operations must stay consistent together — transferring money debits one account and credits another; if the system crashes between the two, you have lost money. ACID is the guarantee a transaction gives you.

PropertyMeaning
AtomicityThe transaction is all-or-nothing; a crash mid-way rolls back completely.
ConsistencyIt takes the database from one valid state to another; constraints hold before and after.
IsolationConcurrent transactions do not see each other's half-finished work.
DurabilityOnce committed, the change survives a crash / power loss.
How a transaction is controlled

BEGIN TRANSACTION opens it; the operations run; COMMIT makes them permanent, or ROLLBACK undoes them if something failed. The database uses a log so that after a crash it can replay committed transactions (durability) or undo uncommitted ones (atomicity). This is the same "save state before changing" idea you saw with interrupts in A1.

Worked example 4 IB-style · 4 marks · why a transfer needs a transaction

Question. A bank moves €100 from account A to account B. Explain why this must be one transaction, naming two ACID properties involved.

  1. The two steps are: debit A by 100, credit B by 100. They must both happen or neither.
  2. Atomicity: if the power fails after the debit but before the credit, the whole transfer rolls back, so no money vanishes.
  3. Consistency: the total money in the system stays the same (A−100, B+100); a half-done transfer would break that invariant.
  4. Durability: once COMMIT runs, even a later crash keeps the transfer; Isolation: another transaction cannot see the €100 missing from A before it appears in B.
Answer: the two steps must be atomic (all-or-nothing) and consistent (total preserved); durability and isolation also apply. Marks: 1 atomicity, 1 consistency, 1 the two-step explanation, 1 naming a second property correctly.
Trap — isolation is not the same as consistency

Consistency is about rules holding (totals balance); isolation is about concurrent transactions not stepping on each other's unfinished work. Students merge them. A good contrast: consistency could still hold while isolation is broken if two transfers interleave and you happen to get the right total — but you would see impossible intermediate states. They are separate guarantees.

A3.4 · NoSQL — the contrast

SL / HL

NoSQL databases abandon parts of the relational model for scale or flexibility. At a general level you should know two families:

TypeHow data is storedGood for

A "compare SQL and NoSQL" question is answered with a table in your head: schema (fixed vs flexible), relations (joins vs embedded/none), scaling (vertical vs horizontal), consistency (ACID vs eventual). You do not need product names; you need the axes of contrast. Mentioning that a document store embeds related data instead of joining is the key insight.

A3.1 · Entity-relationship modelling in depth

SL / HL

Before tables exist, designers draw an ER diagram to capture the real-world things and their links. An entity is a thing of interest (Student, Module); an attribute is a property; a relationship connects entities (enrols, teaches). Two quantities matter: cardinality (how many: one-to-one, one-to-many, many-to-many) and participation (whether every instance must take part: total/partial). A weak entity has no key of its own and depends on a parent (e.g. a Room depends on a Building); it is drawn with a double border. Associative entities are the link tables that resolve many-to-many, exactly the Enrolment table from earlier.

Why ER modelling prevents bad schemas

Drawing the ER diagram first forces you to state cardinality before writing any column. The classic mistake is modelling a many-to-many as a single foreign key — impossible — or as a comma-list in one cell — violates 1NF. The ER diagram makes the many-to-many visible so you create the link table deliberately. The IB often gives a scenario and asks you to "design the tables"; the hidden step is this ER reasoning, and the marks are for the right relationships and keys.

Normalisation worked examples — 1NF and 2NF

1NF worked: a table Player(name, teams) where teams = "A,B,C" is not 1NF (repeating group in one cell). Fix: one row per player-team pair — PlayerTeam(name, team). Now each cell is atomic. 2NF worked: Order(orderID, productID, productName, qty) PK (orderID, productID) — productName depends only on productID, a partial dependency. Fix: split Product(productID, productName) and keep OrderLine(orderID, productID, qty). Only composite-key tables can violate 2NF, so check the key shape first.

Worked example 5 IB-style · 6 marks · take a flat table to 2NF

Question. Sale(customerID, customerName, region, productID, productName, date, qty) with PK (customerID, productID, date). Normalise to 2NF, naming dependencies.

  1. customerName and region depend only on customerID (part of the key) → partial dependencies.
  2. productName depends only on productID (part of the key) → partial dependency.
  3. So split out Customer(customerID, customerName, region) and Product(productID, productName).
  4. Keep the remaining facts in Sale(customerID, productID, date, qty) with FKs to the two.
  5. Now every non-key column in each table depends on the whole key of that table → 2NF.
  6. Note: a single-key table cannot have partial dependency; 2NF only bites compound keys.
Answer: Customer(customerID,name,region), Product(productID,name), Sale(customerID,productID,date,qty). Marks: 2 for the two partial deps named, 3 for the split, 1 for the 2NF check.

A3.3 · SQL — subqueries, set operations, and more clauses

SL / HL

Beyond JOIN, SQL offers subqueries — a query nested inside another. A subquery in WHERE can return a single value (WHERE price > (SELECT AVG(price) FROM Product)) or a list (with IN). A correlated subquery re-runs for each outer row (references the outer table inside). EXISTS checks whether a subquery returns any row — efficient for "find customers who have at least one order". Set operations: UNION combines result sets (removing duplicates), UNION ALL keeps them. DISTINCT removes duplicate rows; LIKE matches patterns ('A%' starts with A, '%son' ends with son, '_a_' has a in the middle); BETWEEN is inclusive range; ORDER BY sorts (ASC/DESC); LIMIT caps rows (top-N queries).

Worked example 6 IB-style · 6 marks · subquery and EXISTS

Question. Using Student and Enrol, list students who are enrolled in at least one module. Use EXISTS.

  1. We want Student rows where a matching Enrol row exists.
  2. Write: SELECT s.name FROM Student s WHERE EXISTS (SELECT 1 FROM Enrol e WHERE e.studentID = s.studentID);
  3. For each student, the subquery checks the Enrol table for any row with that studentID; if found, EXISTS is true.
  4. This is correlated: the inner WHERE references s.studentID from the outer row.
  5. Alternative with JOIN would also work (and might be clearer), but EXISTS is the asked form and avoids duplicates naturally.
  6. Result: only students with ≥1 enrolment appear.
Answer: the EXISTS query above. Marks: 2 for EXISTS, 2 for the correlation, 1 for meaning, 1 for the alternative note.

Self joins, outer joins, and views

A self join joins a table to itself (aliased) to compare rows within it — e.g. employees and their managers, both in the Employee table. An OUTER JOIN (LEFT/RIGHT/FULL) keeps unmatched rows, filling the other side with NULL — essential when you must list all items including those with no match (all products including unsold). A view is a stored query appearing as a virtual table; it simplifies access and can restrict columns for security, but it is not stored data (it re-runs the query). Constraints enforce rules: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK (e.g. grade BETWEEN 0 AND 100), DEFAULT.

Trap — INNER vs OUTER join changes the row count

An INNER JOIN drops rows with no match; a LEFT JOIN keeps all left rows even with NULLs on the right. Students who write LEFT JOIN when they mean "only matching" get extra NULL rows and wrong counts. Decide first: "do I need rows with no match?" If no, INNER; if yes (list everything including orphans), OUTER. The choice changes results, not just style.

NULLs, data types, and triggers

NULL means unknown/absent, not zero. Aggregates ignore NULLs (COUNT(*) counts rows, COUNT(col) skips NULLs). NULL = NULL is not true — you test with IS NULL. Mishandling NULLs is a top source of wrong query results. Data types (INT, VARCHAR(n), DATE, DECIMAL, BOOLEAN) constrain what a column holds and how it sorts/compares; choosing DECIMAL for money avoids float rounding error from A1. A trigger is code that runs automatically on INSERT/ UPDATE/DELETE (e.g. log changes); a stored procedure is a saved routine you call — both move logic into the database, with the trade-off of less portability.

Exam tip

SQL questions award marks for: correct SELECT columns, correct JOINs with ON conditions, WHERE for row filters, GROUP BY matching non-aggregated columns, HAVING (never WHERE) for aggregate filters, and sensible aliases. Write the query top-to-bottom in that order and you rarely err. If asked to "improve" a schema, reach for a normalising split or an index on a searched foreign key.

A3.2 · 3NF worked example and the anomalies it removes

SL / HL

To make 3NF concrete, here is a second full walk. Start from a table that is already 1NF and 2NF but still has a transitive dependency. Employee(empID, name, dept, deptLocation) has PK empID. name and dept depend on empID (fine), but deptLocation depends on dept, not on empID — a transitive dependency. So it is not 3NF. Fix: split Department(dept, deptLocation) and keep Employee(empID, name, dept) with dept as FK. Now every non-key fact depends only on the key.

Worked example 7 IB-style · 7 marks · 3NF walk with anomalies

Question. Employee(empID, name, dept, deptLocation, manager) PK empID, where manager depends on dept. Normalise to 3NF and name the three anomalies removed.

  1. Check 1NF/2NF: assume atomic cells, single key empID, so no partial dependency → already 2NF.
  2. Transitive dependencies: deptLocation depends on dept; manager depends on dept. Both are non-key facts depending on another non-key (dept), not on empID.
  3. Split: Department(dept, deptLocation, manager) and Employee(empID, name, dept) FK→Department.
  4. Update anomaly removed: move a department's location once in Department, not in every employee row — previously you risked inconsistent locations.
  5. Insertion anomaly removed: a new department with no employees can now exist (insert into Department alone).
  6. Deletion anomaly removed: removing the last employee of a department no longer deletes the department's location/manager.
  7. Verify: in Employee, name and dept depend on empID; in Department, location/manager depend on dept. 3NF achieved.
Answer: Employee(empID,name,dept), Department(dept,deptLocation,manager). Marks: 2 deps named, 2 split, 3 for the three anomalies.

SL / HL
Worked example 8 IB-style · 6 marks · aggregate with HAVING and JOIN

Question. List modules (title) whose average enrolment grade is below 50, joining Module and Enrol.

  1. Join Enrol to Module on moduleID so we can select the title.
  2. GROUP BY module to compute one average per module.
  3. HAVING AVG(grade) < 50 keeps only weak modules (group-level filter, so HAVING not WHERE).
  4. SELECT m.moduleTitle, AVG(e.grade) AS a
FROM Enrol e JOIN Module m ON e.moduleID = m.moduleID
GROUP BY m.moduleID, m.moduleTitle
HAVING AVG(e.grade) < 50;
  5. Sanity: a module with no enrolments would not appear (INNER JOIN drops it); if we needed "all modules including empty", use LEFT JOIN and handle NULL avg.
Answer: the query above. Marks: 1 join, 1 group, 1 HAVING, 1 select, 1 alias, 1 NULL note.
Worked example 9 IB-style · 5 marks · self join for hierarchy

Question. Employee(empID, name, managerID) where managerID references empID. List each employee with their manager's name.

  1. Self join: alias the table E (employee) and M (manager).
  2. Join E.managerID = M.empID to bring the manager's row alongside.
  3. Use LEFT JOIN so the top boss (managerID NULL) still appears.
  4. SELECT E.name AS emp, M.name AS mgr
FROM Employee E LEFT JOIN Employee M
  ON E.managerID = M.empID;
  5. Result: each employee row carries their manager's name (or NULL for the CEO).
Answer: the self-join query above. Marks: 1 alias, 1 join condition, 1 LEFT JOIN, 1 select, 1 meaning.

Indexes in depth — B-trees and clustering

An index is usually a B-tree (balanced tree) so lookups, inserts, and deletes are all O(log n). The tree stays balanced: every leaf is at the same depth, so no search is ever much slower than another. A clustered index stores the table rows themselves in index order (one per table, typically the PK) — range scans are fast but the row order is fixed; a non-clustered index is a separate structure pointing to rows (many allowed). Composite indexes index several columns in order, helping queries that filter on the leading columns. Over-indexing slows writes and wastes space, so index the columns you actually search/join on. The IB treats indexes conceptually: speed up reads (O(log n) vs O(n) scan), cost writes.

Trap — an index does not help every query

An index on surname helps WHERE surname='Ross' but not WHERE firstname='Ann' unless there is an index starting with firstname. Composite indexes help only if the query uses a left prefix. Students claim "add an index and all queries speed up" — false; only queries matching the index's columns benefit, and every index slows INSERT/UPDATE/DELETE.

A3.4 · Transactions, isolation levels, and concurrency

SL / HL

Concurrent transactions can interfere. Classic problems: lost update (two reads, two writes, one write overwrites the other's); dirty read (reading uncommitted data that then rolls back); non-repeatable read (same query returns different rows mid-transaction); phantom read (a query's result set changes because another transaction inserted/deleted rows). Isolation levels trade correctness for concurrency: READ UNCOMMITTED allows dirty reads; READ COMMITTED prevents them; REPEATABLE READ prevents non-repeatable reads; SERIALIZABLE prevents all (effectively running one at a time, slowest). Locking (shared/exclusive) and two-phase locking (acquire all locks, then release) enforce isolation; a deadlock (seen in A1) is detected and one transaction is rolled back.

Worked example 10 IB-style · 5 marks · lost update and how to stop it

Question. Two transactions both read balance 100, each adds 50, each writes back. What happens without isolation, and how does a lock fix it?

  1. Without isolation: T1 reads 100, T2 reads 100, T1 writes 150, T2 writes 150 — final 150, but two deposits of 50 should give 200. One update is lost.
  2. This is a lost update caused by interleaving reads and writes.
  3. An exclusive lock on the row during the transaction makes T2 wait until T1 commits: T2 reads 150 (after T1), adds 50, writes 200. Correct.
  4. Alternatively, use a conditional update (UPDATE … SET balance = balance + 50) computed in the DB, not in the app — atomic by design.
  5. So isolation (or atomic DB-side updates) prevents the lost update.
Answer: lost update → 150 not 200; exclusive lock serialises so T2 sees 150 → 200. Marks: 2 for the bug, 2 for the lock, 1 for the atomic-update alternative.

A3.4 · NoSQL and the CAP theorem

SL / HL

Beyond document and key-value, NoSQL includes column-family stores (Wide-Column, e.g. for huge analytics) and graph databases (nodes/edges, ideal for social networks and recommendations). The CAP theorem says a distributed datastore can guarantee at most two of: Consistency (all nodes see the same data), Availability (every request gets a response), and Partition tolerance (survives network splits). Since partitions are unavoidable, systems choose CP (consistency over availability, e.g. some financial stores) or AP (availability over strict consistency, e.g. many web caches, offering eventual consistency — data converges soon, not instantly). This is the conceptual contrast with SQL's ACID: NoSQL often trades immediate consistency for scale.

Why the trade is unavoidable in distribution

If the network partitions, you cannot both answer every request (availability) and guarantee every node agrees (consistency) — a write on one side cannot reach the other. So you pick: refuse some requests to stay consistent (CP), or answer with possibly stale data to stay up (AP). The IB wants this reasoning, not product names. Mention that SQL's ACID is CP-leaning, while many NoSQL systems are AP with eventual consistency.

Backups, recovery, and OLAP

A backup copies the database (full, or incremental since the last) so data survives corruption, ransomware, or mistakes; a restore replays it. Journaling / write-ahead logging lets the DB recover to a consistent state after a crash by replaying committed transactions (the same log idea behind ACID durability). OLTP (online transaction processing) is the day-to-day adding/updating (what this topic is); OLAP (online analytical processing) is the heavy read/aggregate for reporting, often on a separate warehouse. The IB may ask you to justify separating them: analytics queries are slow and would disturb live transactions, so you copy data to a warehouse for analysis.

Exam tip — closing A3

The A3 essay shape is: model the entities and relationships (ER) → choose keys → normalise to 3NF naming anomalies → query with SQL (JOIN, GROUP BY, HAVING) → speed reads with indexes (cost writes) → protect writes with ACID transactions → contrast with NoSQL's scale/eventual-consistency trade. Hit those beats and a database question is a 7.

A3.3 · More SQL — set operations, grouping nuance, and query plans

SL / HL

UNION stacks two result sets with the same columns, removing duplicates; UNION ALL keeps duplicates (faster). INTERSECT (where supported) keeps only rows in both; EXCEPT keeps rows in the first but not the second. These mirror set theory and are often cleaner than equivalent joins. A subtlety: GROUP BY groups before aggregation, so a WHERE filter applied before grouping cannot use an aggregate, while HAVING filters after. NULL in a group becomes its own group. A query plan is what the DBMS actually does (scan vs index seek, join order); understanding that an index turns a scan into a seek is why indexing matters — the planner chooses the cheaper plan, and indexes make the cheaper plan available.

Worked example 11 IB-style · 5 marks · UNION and GROUP BY nuance

Question. List all student names who are either in module M101 or have grade > 90 in any module.

  1. Option A — UNION of two queries: students in M101, and students with a grade > 90; UNION removes duplicates.
  2. SELECT s.name FROM Student s
  JOIN Enrol e ON s.studentID = e.studentID
  WHERE e.moduleID = 'M101'
UNION
SELECT s.name FROM Student s
  JOIN Enrol e ON s.studentID = e.studentID
  WHERE e.grade > 90;
  3. Option B — single query with OR: WHERE e.moduleID='M101' OR e.grade > 90; both give the same set.
  4. The nuance: aggregation (HAVING grade>90 after GROUP BY) would wrongly require one row per student; here we want any enrolment satisfying the condition, so filter in WHERE, not HAVING.
  5. Result: the union of the two populations, duplicates collapsed.
Answer: the UNION (or OR) query above. Marks: 1 structure, 2 query, 1 OR alternative, 1 WHERE-not-HAVING note.

Integrity constraints and referential actions

Constraints enforce correctness without application code. PRIMARY KEY (unique, not null), FOREIGN KEY (must match a PK or be null), UNIQUE, NOT NULL, CHECK (e.g. salary > 0), DEFAULT. A foreign key can carry referential actions: ON DELETE CASCADE removes child rows when the parent goes; ON DELETE RESTRICT refuses to delete a parent that still has children; ON DELETE SET NULL nulls the FK. Choosing the action is a design decision: cascade is convenient but dangerous (one delete can wipe a subtree), restrict is safe but requires manual cleanup. The IB may ask you to justify one — the mark is weighing convenience against accidental data loss.

Trap — CASCADE can surprise you

ON DELETE CASCADE means deleting a department deletes all its employees automatically. That is sometimes right (a project and its tasks) and sometimes catastrophic (a customer and all their orders you needed for audits). The safe default for money/legal data is RESTRICT. Students write CASCADE everywhere "because it is simpler" — name the risk to earn the mark.

Data modelling discipline and the big picture

The whole database half of the syllabus is a pipeline: requirements → ER model → relational schema with keys → normalise to 3NF → populate → query with SQL → index for speed → protect writes with ACID → replicate/scale with NoSQL where needed. Each step exists to remove a class of error or cost from the previous one. Skipping normalisation invites update anomalies; skipping indexes invites slow queries; skipping transactions invites lost updates; skipping the ER model invites a schema that cannot express the relationships. The IB examines each step, but the high marks come from seeing them as one coherent discipline rather than isolated facts.

Why databases are a "systems" topic, not a syntax topic

You can memorise SQL and still design a bad database. The lasting skill is the design judgement: which tables, which keys, which normal form, which index, which transaction isolation. Those are engineering decisions with trade-offs, exactly like the architecture decisions in A1. That is why the IA (internal assessment) rewards a well-normalised schema and why Paper 1 asks you to justify, not just to write, a query.

    SL / HL
    Worked example 13 IB-style · 5 marks · dirty read and READ COMMITTED

    Question. Transaction T1 updates a row but has not committed. T2 reads it. What happens under READ UNCOMMITTED vs READ COMMITTED?

    1. Under READ UNCOMMITTED, T2 reads the uncommitted value (the "dirty" value).
    2. If T1 then rolls back, T2 has based decisions on data that never existed — a dirty read.
    3. Under READ COMMITTED, T2 is blocked (or sees the old committed value) until T1 commits or rolls back, so T2 never sees the dirty value.
    4. This is why READ COMMITTED is the common default: it prevents dirty reads at modest concurrency cost.
    5. The trade: stricter isolation (SERIALIZABLE) prevents more anomalies but serialises more, reducing throughput.
    Answer: READ UNCOMMITTED allows the dirty read; READ COMMITTED blocks/sees-committed, preventing it. Marks: 2 UNCOMMITTED, 2 COMMITTED, 1 trade-off.

    Document store in practice

    A document database stores records as documents (often JSON) with an ID and arbitrary fields. A user profile might be {id: 7, name: "Ada", tags: ["cs","math"], addr: {city:"Geneva"}} — nested, no fixed columns. You query by field (e.g. find users where tags includes "cs") and the store retrieves whole documents. Advantages: schema evolves without migration; related data is co-located (no join to fetch the address). Disadvantages: cross-document queries (all users in a city across documents) need scanning or indexing, and there is no enforced relational integrity between documents. The IB contrast: SQL joins; document stores embed. Choose by access pattern.

    Trap — embedding vs referencing

    In a document store you may embed related data (address inside user) or reference it (user holds an address ID). Embedding is fast to read but duplicates/limits if the same address is shared; referencing avoids duplication but needs a second fetch. Students pick one without noting the trade. The mark is stating both and when each fits — embed when owned and co-accessed, reference when shared.

    Query optimisation intuition

    How the DBMS executes a query explains indexing. Without an index on surname, a WHERE surname='Ross' forces a full table scan O(n). With a B-tree index, the planner seeks in O(log n) and scans only matches. A covering index even holds the needed columns, avoiding a trip to the table. Join order matters: the planner picks the smaller table first to limit intermediate rows. The IB treats this conceptually: an index turns scans into seeks; more indexes slow writes; the planner chooses the cheaper plan. You will not compute plans by hand, but you should explain why an index helps a slow query.

    Exam tip

    If a question says "a report is slow", the expected answer is: identify the filtered/joined columns, add indexes on them (composite if filtering on several), and accept the write-cost trade-off; possibly move analytics to a separate OLAP warehouse so reports do not disturb OLTP. That diagnosis—index the search columns, separate the workloads—is the 7-mark answer.

    A3.1 · Advanced key concepts

    SL / HL

    A few key subtleties the IB probes. A surrogate key is an artificial PK (an auto-increment ID) added when no natural column is unique and stable — better than using a mutable attribute like email as the PK. A natural key is a real-world unique attribute (e.g. ISBN for a book). A weak entity's PK includes the FK of its owner (a Room's PK is buildingID + roomNo). Referential integrity is the rule that an FK must match an existing PK (or be null); the DBMS enforces it, so you cannot orphan a row. Cardinality notation (crow's foot) records how many on each side; getting it wrong produces the wrong number of tables.

    Worked example 14 IB-style · 4 marks · surrogate vs natural key

    Question. A Person table uses email as PK. Argue for adding a surrogate ID instead.

    1. Email can change (user switches provider); a PK must be stable, so changing it forces updates to every FK referencing it — costly and error-prone.
    2. A surrogate auto-increment ID never changes and has no business meaning, so it is a stable PK.
    3. Keep email as a UNIQUE column (enforce uniqueness without making it the key).
    4. FKs reference the stable ID, so a later email change touches only one row.
    Answer: email is mutable, so use a surrogate ID as PK and keep email UNIQUE. Marks: 1 mutability, 1 stability, 1 email still unique, 1 FK benefit.

    A3.3 · JOINs in depth and a worked report query

    SL / HL

    A natural join joins on columns with the same name; an equi-join joins on an explicit equality (the ON clause you usually write); a self join joins a table to itself. The number of rows a join can produce ranges from zero (no matches) to the product of the tables (a cross join, usually a mistake). A cross join (Cartesian product) pairs every row with every row — sometimes legitimate (e.g. all size/colour combinations) but usually a missing ON condition. Aggregate joins combine GROUP BY with JOIN, but remember aggregates apply after the join, and outer joins change which rows survive before grouping.

    Worked example 15 IB-style · 6 marks · multi-table report

    Question. For each department, list its name and the number of employees, including departments with zero employees.

    1. We need Department rows even with no matching Employee, so use a LEFT JOIN from Department to Employee.
    2. Group by department (deptID, name) and count employees.
    3. COUNT(e.empID) counts only matched (non-null) employee rows, so a department with none shows 0 — correct (COUNT(*) would wrongly count the one department row as 1).
    4. SELECT d.deptName, COUNT(e.empID) AS n
FROM Department d LEFT JOIN Employee e
  ON d.deptID = e.deptID

    5. This is why LEFT JOIN + COUNT(column) matters: inner join would drop empty departments, hiding them.

    OLTP vs OLAP and data warehouses

    OLTP systems serve many small read/write transactions (booking a seat, updating stock) and must be fast and consistent — this is what a normalised relational DB does well. OLAP serves few but huge analytical queries (total sales by region per quarter) that scan millions of rows; these are slow on the live DB and would disturb transactions. A data warehouse copies data from OLTP systems (often de-normalised into a star schema: a fact table surrounded by dimension tables) for analysis. The IB asks you to justify separating them: analytics are heavy and read-only, so isolating them protects live performance and lets a different schema optimise reads.

    Trap — normalise OLTP, not the warehouse

    The OLTP database should be normalised (avoid anomalies); the warehouse is often deliberately de-normalised (star schema) because analytical queries read many attributes together and joins are expensive. Students apply "always normalise" to the warehouse and miss the point. The design goal flips: OLTP favours write integrity, the warehouse favours read speed.

    NULL, three-valued logic, and referential integrity

    A NULL is not a value — it is the absence of a value. It means "unknown", "not applicable", or "not yet entered". Treating NULL as if it were a number (or zero) is one of the most common exam mistakes. Because a comparison with an unknown can be neither true nor false, SQL uses three-valued logic (3VL): every predicate evaluates to TRUE, FALSE, or UNKNOWN.

    PredicateResult when one side is NULLWhy
    NULL = 5UNKNOWNYou cannot assert equality to something unknown.
    NULL <> 5UNKNOWNNor can you assert inequality.
    NULL AND TRUEUNKNOWNOnly FALSE forces AND to FALSE.
    NULL OR FALSEUNKNOWNOnly TRUE forces OR to TRUE.
    NULL AND FALSEFALSEOne FALSE is enough.
    NULL OR TRUETRUEOne TRUE is enough.
    Trap — NULL is not a value

    COUNT(*) counts rows; COUNT(column) counts non-NULL entries in that column, so they can differ. WHERE col = NULL never matches — use WHERE col IS NULL. In a WHERE clause, only rows where the condition is TRUE are kept; UNKNOWN is discarded just like FALSE. But in a CHECK constraint, UNKNOWN is accepted (only FALSE rejects the row) — a subtle asymmetry examiners love.

    Referential integrity guarantees a foreign key either matches an existing primary key in the parent table or is NULL. When the parent row is deleted or its key updated, the DBMS enforces the rule with an action:

    1. RESTRICT / NO ACTION — refuse the delete/update if children still reference the row.
    2. CASCADE — delete/update the child rows too (e.g. delete a student, also delete their enrolments).
    3. SET NULL — set the foreign key to NULL in children (only valid if the FK is nullable).
    4. SET DEFAULT — set the FK to a configured default value.
    Exam tip

    If a question asks what happens when you delete a parent row with CASCADE defined, state the exact consequence: "all child rows referencing it are also deleted", and name the risk — you can accidentally wipe dependent data, so backups precede bulk deletes.

    Advanced SQL: subqueries, set operations, and window functions

    A subquery is a SELECT nested inside another statement. It can return a single value (scalar), a single column (row set), or a whole table.

    -- Scalar subquery: find students above the average mark
SELECT name
FROM student s
WHERE s.mark > (SELECT AVG(mark) FROM student);

-- Correlated subquery: runs once per outer row
SELECT name
FROM student s
WHERE mark > (SELECT AVG(mark) FROM student s2 WHERE s2.tutor = s.tutor);

-- EXISTS: true if the subquery returns at least one row
SELECT name
FROM student s
WHERE EXISTS (SELECT 1 FROM enrolment e WHERE e.sid = s.sid);

    A correlated subquery references a column from the outer query, so it re-executes for every outer row — powerful but slower than a join. Prefer a join or window function when performance matters.

    Set operations

    OperatorEffect

    Window functions

    A window function computes a value across a set of rows related to the current row without collapsing them (unlike GROUP BY). The OVER (...) clause defines the window.

    -- Rank students within each tutor group by mark
SELECT name, tutor, mark,
       RANK() OVER (PARTITION BY tutor ORDER BY mark DESC) AS pos
FROM student;
    Note

    GROUP BY reduces many rows to one per group; a window function keeps every row and attaches an aggregated peer value beside it. Use window functions when you need both the detail and the summary.

    Worked — set operations and subquery

    Given cs_students(sid,name) and maths_students(sid,name). List students who take both subjects. Method 1 (INTERSECT): SELECT sid FROM cs_students INTERSECT SELECT sid FROM maths_students;. Method 2 (subquery): SELECT name FROM cs_students WHERE sid IN (SELECT sid FROM maths_students);. Both return the shared set. Method 3 (join): SELECT c.name FROM cs_students c JOIN maths_students m ON c.sid = m.sid;. The examiner accepts any correct approach, but the join is usually fastest and clearest.

    Concurrency, locking, and recovery

    When many users access a database at once, the DBMS must stop their actions from corrupting each other.

    Isolation problems

    ProblemCause
    Dirty readReading data another transaction has not yet committed
    Non-repeatable readA row you read changes because another transaction commits
    Phantom readRows appear/disappear as another transaction inserts/deletes in your range
    Lost updateTwo transactions overwrite each other's change

    Locking and two-phase locking (2PL)

    A shared (read) lock lets many transactions read but none write; an exclusive (write) lock lets only one write. Two-phase locking prevents anomalies: a transaction first only acquires locks (growing phase), then only releases them (shrinking phase). Once a lock is released, no new lock may be taken. This guarantees serialisable schedules.

    Trap — deadlock

    Two transactions each hold a lock the other needs (T1 holds A wanting B; T2 holds B wanting A). The DBMS detects the cycle and rolls back one transaction (the victim), freeing its locks. You should mention a deadlock-handling strategy: timeout, wait-for graph detection, or victim selection.

    Recovery: write-ahead logging and backup

    The write-ahead log (WAL) records every change before it is applied to the data file. After a crash, the DBMS replays committed transactions (redo) and undoes uncommitted ones (undo), restoring a consistent state. Backups come in levels: full (everything), differential (since last full), incremental (since last backup of any kind). A restore replays full → differential/incremental → the WAL tail.

    Exam tip

    "Why does the log help recovery?" — answer: because committed changes are recorded durably before (or atomically with) the data write, so after a crash the log can redo durable work and undo incomplete work, guaranteeing the ACID durability and atomicity properties.

    Distributed databases, data warehouses, and security

    Distributed databases

    A distributed database stores data across several sites but presents one logical schema. Two strategies:

    • Replication — copy the same data to multiple sites. Reads are fast and local; writes must propagate to all copies (consistency cost).
    • Fragmentation / sharding — split rows or columns across sites by a key (e.g. customers by region). Scales writes; a query spanning shards is slower.

    Data warehouse and OLAP

    An operational OLTP system is optimised for many small, fast transactions. A data warehouse is a separate, read-optimised store fed by ETL (Extract, Transform, Load) from OLTP sources. It uses a star schema: a central fact table (e.g. sales) surrounded by dimension tables (time, product, store). OLAP cubes let users slice, dice, and roll up aggregates. Keeping analytics off the live OLTP system prevents heavy reports from slowing customer transactions.

    ER modelling in depth: cardinality, weak entities, and notation

    The entity-relationship (ER) model is the design blueprint before tables exist. Entities become tables; relationships become foreign keys or junction tables; attributes become columns.

    Cardinality and participation

    RelationshipMeaningImplementation
    1:1One A to one BFK on either side (or merge)
    1:NOne A to many BFK on the "many" side (B)
    M:NMany A to many BJunction table with both FKs as a composite PK
    Note

    Participation is total (every entity must take part — drawn with a double line) or partial (some may not — single line). A "total" participation on the many side forces its FK to be NOT NULL.

    Weak entities and identifying relationships

    A weak entity has no key of its own; it is identified by its owner plus a partial key. Example: Payment(payment_no, amount) is weak, owned by Invoice(inv_no). Its PK is the composite (inv_no, payment_no), and the relationship to Invoice is an identifying relationship (double rectangle / double diamond). In SQL this becomes a junction-like table where the owner's PK is part of the child's PK.

    Ternary and associative entities

    A relationship among three entities cannot be three binaries — it is a ternary relationship (diamond touching three entities), or modelled as an associative entity (a table in its own right with three FKs). Example: Supply(supplier, part, project, qty) records how much of a part a supplier provides to a project.

    Beyond 3NF: BCNF, 4NF, and 5NF

    Higher normal forms fix rarer anomalies.

    • BCNF (Boyce–Codd): every determinant is a candidate key. 3NF allows a non-key attribute to determine another non-key attribute only if it is a candidate key; BCNF is stricter and removes even that. If a table has overlapping candidate keys with a dependency on a non-superkey, decompose it.
    • 4NF: no multi-valued dependency — two independent 1:N attributes should not share a row. Example: a student has several hobbies AND several jobs; store hobbies and jobs in separate tables, not one combined table with every hobby×job pair.
    • 5NF: no join dependency; a table that had to be split to avoid redundancy can be reconstructed by joining its pieces without spurious rows.
    Exam tip

    For the exam you are assessed mainly on 1NF/2NF/3NF with clear worked decompositions. Mention BCNF only if a dependency on a candidate key (not the PK) is the issue; 4NF/5NF are "awareness" level — name them and the problem they solve.

    Indexing strategies and query optimisation

    An index is a secondary structure (usually a B-tree) on one or more columns that lets the DBMS locate rows without scanning the whole table. The PK is automatically indexed (clustered index — rows stored in that order). A composite index on (last, first) helps queries filtering on last or on both, but not on first alone (leftmost-prefix rule).

    Trade-offWith indexWithout index
    Point lookup / rangeFast (log n)Slow (full scan)
    INSERT / UPDATE / DELETESlower (index maintained)Faster
    SpaceExtra storageMinimal

    Index selectively: high-cardinality columns (unique IDs) gain most; low-cardinality columns (e.g. boolean flags) rarely justify an index. A query planner estimates the cheapest access path using table statistics; it may choose a full scan over an index if most rows would match anyway.

    Trap — over-indexing

    More indexes are not better. Each slows writes and consumes memory. Index the columns you actually filter, join, or order by — not every column "just in case".

    NoSQL, the CAP theorem, and big data

    NoSQL databases relax the relational model for scale, flexibility, or speed. Four families:

    TypeModelExample use
    DocumentJSON-like documents, schema-flexibleUser profiles, product catalogues
    Key–valueO(1) lookup by keySessions, caches, shopping carts
    Column-familyWide rows of columnsTime-series, event logs
    GraphNodes + edgesSocial networks, recommendations

    The CAP theorem says a distributed data store can guarantee at most two of: Consistency (all reads see the latest write), Availability (every request gets a response), Partition tolerance (it survives network splits). Under a partition you must trade C for A or vice versa. BASE (Basically Available, Soft state, Eventual consistency) describes many NoSQL stores: they accept temporary inconsistency for availability and converge later.

    Big data is characterised by volume, velocity, and variety. It often uses distributed storage (e.g. splitting files across nodes) and parallel processing rather than one big relational server. This is where NoSQL and warehouses meet: relational for trusted transactions, NoSQL/column stores for scale and flexible ingestion.

    Exam tip

    Compare relational vs NoSQL in one sentence each: relational = ACID, fixed schema, SQL, joins, strong consistency; NoSQL = flexible/loose schema, horizontal scale, eventual consistency, specialised access patterns. Pick based on the requirement, not the hype.

    The database design process end to end

    A real design moves through stages; each stage has a deliverable.

    1. Requirements analysis — interview users, list data needed and operations (reports, transactions).
    2. Conceptual design — draw the ER diagram (entities, attributes, relationships, cardinality).
    3. Logical design — map ER to relational tables; assign keys; apply normalisation to 3NF.
    4. Physical design — choose data types, indexes, partitioning, storage.
    5. Implementation & testing — create tables, load data, write queries, verify against requirements.
    6. Operation & maintenance — backups, tuning, schema evolution.

    Views, triggers, and stored procedures

    A view is a saved query appearing as a virtual table. It hides columns/rows, restricts access, and simplifies complex joins. Some views are updatable (single base table, no aggregates); others are read-only.

    CREATE VIEW top_students AS
SELECT name, mark FROM student WHERE mark >= 80;
-- Users query the view; the base table stays protected.

    A trigger is code that runs automatically before or after an INSERT/UPDATE/DELETE. Example: after inserting a sale, update a stock total. A stored procedure is a named, callable routine that can take parameters and bundle several statements — reducing network round-trips and centralising logic.

    Trap — triggers are hidden

    Because triggers fire silently, a chain of triggers can surprise developers and complicate debugging. Document them and keep logic in one place; do not hide critical validation only inside a trigger.

    Backup strategy and cloud databases

    A backup policy balances recovery time objective (RTO — how fast you must be back) and recovery point objective (RPO — how much data loss is tolerable). A plan mixes full weekly backups, differential dailies, and incremental hourly copies, plus transaction-log backups for point-in-time restore. Off-site or cloud copies protect against site disaster; test restores prove the backups work.

    Cloud databases (managed services) handle replication, patching, scaling, and backups for you. Benefits: elasticity (grow storage on demand), high availability (multi-zone copies), and lower admin burden. Trade-offs: ongoing cost, vendor lock-in, and data-residency/legal constraints on where data may be stored. A Database-as-a-Service model fits when the team wants to focus on queries, not servers.

    Exam tip

    On "evaluate cloud vs on-premise", weigh: control & data sovereignty (on-premise wins), cost predictability & scaling & uptime (cloud wins). A balanced answer mentions both RTO/RPO and lock-in — that is what secures the top band.

    Two fully worked SQL examples

    Worked 1 — aggregation with HAVING

    Schema: order(o_id, cust, amount, region). Task: for each region with more than 5 orders, list the region and its total spend, highest first. Answer:

    SELECT region, SUM(amount) AS total, COUNT(*) AS n
FROM order
GROUP BY region
HAVING COUNT(*) > 5
ORDER BY total DESC;

    Why HAVING not WHERE: the "more than 5 orders" test applies after grouping, so it must be HAVING. WHERE filters rows before grouping and cannot reference aggregates. GROUP BY region collapses per region; SUM/COUNT aggregate; ORDER BY total DESC sorts the result. One mark each for GROUP BY, HAVING, aggregate, ORDER BY.

    Worked 2 — join plus subquery

    Schema: student(sid, name, tutor), enrolment(sid, cid, grade), course(cid, title). Task: list the names of students enrolled in 'CS' and their grade. Answer:

    SELECT s.name, e.grade
FROM student s
JOIN enrolment e ON e.sid = s.sid
JOIN course c ON c.cid = e.cid
WHERE c.title = 'CS';

    Check: the join chain links student→enrolment→course; the filter on c.title selects the course; the projection keeps only name and grade. Equivalent subquery form: WHERE s.sid IN (SELECT sid FROM enrolment WHERE cid = (SELECT cid FROM course WHERE title='CS')). Both correct; the join is usually preferred for clarity and speed.

    Trap — cartesian product

    Forgetting the ON condition (or the WHERE in old-style joins) produces a cross join: every row paired with every row. With 1,000 students and 1,000 courses that is 1,000,000 rows of garbage. Always join on a key.

    Slow queries are fixed by understanding the execution plan. Common causes and fixes:

    SymptomLikely causeFix
    Full table scan on lookupNo index on filter columnCreate an index on that column
    Slow joinUnindexed FKIndex the join key
    Huge intermediate resultMissing join condition (cartesian)Add the ON clause
    Recomputed aggregateCorrelated subquery per rowReplace with join or window function
    Redundant columns readSELECT *Project only needed columns

    Denormalisation is a deliberate, limited reversal of normalisation (e.g. storing a count alongside a table) to speed reads at the cost of update anomalies — acceptable only where read performance dominates and the anomaly is managed by triggers or application logic.

    Exam tip

    "How would you improve this query's performance?" — diagnose first: is it scanning (index it), joining on an unindexed key (index it), or doing N subqueries (rewrite as a join). Name the concrete change and the expected effect; vague "make it faster" earns nothing.

    DBMS architecture and the data dictionary

    A DBMS sits between applications and the stored data. Layers: the query processor (parser, optimiser, executor), the storage manager (file/record/Buffer manager), and a data dictionary / system catalogue holding metadata — table names, columns, types, constraints, indexes, users. Applications send SQL; the DBMS checks the dictionary for schema and permissions, builds a plan, executes it, and returns rows.

    The three-schema architecture separates: the external level (user views), the conceptual level (the logical community schema), and the internal level (physical storage). This independence lets you change storage (internal) without rewriting applications (external) — physical data independence — and change views without touching the conceptual schema — logical data independence.

    Note

    Data independence is a key reason organisations choose a DBMS: the same data serves many applications, and storage upgrades do not break them.

    Transactions and isolation levels worked through

    Worked — transfer with ACID

    Task: move 100 from account A to account B atomically. SQL:

    BEGIN TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 'A';
UPDATE account SET balance = balance + 100 WHERE id = 'B';
COMMIT;

    Atomicity: if the second update fails (e.g. B deleted), ROLLBACK undoes the first — money is never lost. Consistency: the total balance is unchanged. Isolation: another transaction sees either both changes or neither, never a half-moved state. Durability: after COMMIT, the move survives a crash (WAL + durable storage). This four-property walk-through is exactly what a 4-mark question asks.

    Isolation levels trade concurrency for correctness:

    LevelPreventsCost
    Read uncommitted—Highest concurrency, dirty reads possible
    Read committedDirty readsMedium
    Repeatable readDirty + non-repeatableLower
    SerializableAll anomaliesLowest concurrency (effectively sequential)

    Higher isolation means fewer anomalies but more locking and less throughput. The DBMS lets you pick the level that fits the workload.

    Trap — lost update without isolation

    Two transactions read balance 500, each adds 50, each writes 550. One update is lost. Fix with a higher isolation level or an atomic UPDATE ... SET balance = balance + 50 (single statement reads-and-writes under lock, no lost update).

    Analytics, reporting, and evaluating a database design

    Once data is trustworthy, value comes from analytics: aggregates, trends, and dashboards over the warehouse. OLAP operations — slice (fix one dimension), dice (subset ranges), roll-up (coarser granularity), drill-down (finer) — let users explore a cube. Keeping these on a separate warehouse protects the OLTP system's speed.

    Evaluating a design

    Judge a schema by: (1) it meets all requirements (every report is expressible); (2) it is in 3NF with no update/insert/delete anomalies; (3) keys and FKs enforce integrity; (4) indexes support the heavy queries without bloating writes; (5) it will scale (partitioning/sharding plan if needed). A good evaluative answer states a criterion, then says whether this design satisfies it.

    Exam tip — full 8-mark design question

    Structure: (i) list entities and attributes; (ii) draw ER with cardinality; (iii) convert to tables with PK/FK; (iv) normalise to 3NF showing each step; (v) add indexes for stated queries; (vi) one sentence on integrity/security. Following this order, every mark band is covered and the examiner can award partial credit at each stage.

    Revision checklist for databases

    • Relational model terms: relation, tuple, attribute, domain, key, cardinality/degree.
    • Keys: candidate, primary, composite, foreign, surrogate, superkey.
    • Normalisation 1NF/2NF/3NF — define each, work a decomposition.
    • SQL: SELECT, WHERE, JOIN (incl. self/outer), GROUP BY/HAVING, subqueries, set ops, window functions, views.
    • Indexing: B-tree, when to index, trade-offs.
    • ACID + transactions + isolation levels + locking/2PL + deadlock.
    • Concurrency anomalies and how locks prevent them.
    • Recovery: WAL, backup types, restore order.
    • NoSQL families + CAP + BASE.
    • Security: injection, least privilege, encryption, audit.

    Full case study: designing and normalising a real schema

    Worked end to end, because this is the single most common exam task. A school asks for a system recording which students take which subjects and their teachers.

    Worked — from unnormalised to 3NF

    Unnormalised source form (one flat table):

    Registration(
  student_id, student_name, form_group,
  subject_code, subject_name, teacher_name, teacher_room, grade
)

    Problems: a student taking three subjects appears three times (update anomaly — change a name, fix three rows; delete anomaly — drop the last subject and the student vanishes; insert anomaly — cannot add a subject with no students yet).

    Step 1 — 1NF: ensure atomic values (already atomic) and a key. Composite key (student_id, subject_code). It is in 1NF.

    Step 2 — 2NF: remove partial dependencies. student_name and form_group depend only on student_id (part of the key); subject_name, teacher_name, teacher_room depend only on subject_code. Decompose:

    Student(student_id, student_name, form_group)
Subject(subject_code, subject_name, teacher_name, teacher_room)
Grade(student_id, subject_code, grade)     -- PK (student_id, subject_code)

    Step 3 — 3NF: remove transitive dependencies. In Subject, teacher_room depends on teacher_name, not directly on the key subject_code. Decompose:

    Subject(subject_code, subject_name, teacher_id)
Teacher(teacher_id, teacher_name, teacher_room)

    Now every non-key attribute depends on the whole key and nothing but the key. All three anomalies are gone. This is the canonical answer structure: show the dependency, show the split, state the form reached.

    Trap — confusing 2NF and 3NF

    2NF is about partial dependency on part of a composite key. If the key is single (e.g. subject_code), 2NF is automatically satisfied and you go straight to checking 3NF (transitive dependency). Students lose marks by "applying 2NF" to a table that has no composite key.

    Choosing keys in practice

    A surrogate key (e.g. an auto-increment id) replaces a natural key when the natural key is wide, changes, or composite. Example: use student_id (surrogate) rather than (first_name, last_name, dob) as the PK, because names change and duplicates exist. The natural candidate key can still carry a UNIQUE constraint to prevent duplicates. Surrogate keys make joins narrower and stable, at the cost of an extra column and a meaningless value.

    When NOT to over-normalise

    Reading many small joined tables for every page view can be slow. Reporting systems sometimes intentionally keep a wide, partially denormalised star schema in the warehouse. Normalise the OLTP core to 3NF for integrity; relax only in the read-optimised analytics layer, and manage the resulting redundancy explicitly.

    Exam tip

    In a normalisation question, always (1) state the key of the current table, (2) name the dependency you are removing ("teacher_room depends on teacher_name, not on subject_code"), (3) write the resulting tables, (4) label the new normal form. That four-step rhythm is what the mark scheme rewards.

    Entity vs attribute vs value

    Decide what is an entity (becomes a table) versus an attribute (a column). Rule of thumb: if it has its own properties or participates in relationships, it is an entity. "A subject has a teacher" — teacher has a room and a name, so Teacher is an entity, not just a column. "A country has a code" — code is an attribute of country. Getting this right shapes the whole ER diagram.

    Data integrity, validation, and the cost of bad data

    Integrity is the guarantee that stored data is accurate and consistent. It is enforced at several layers, and a good database designer uses all of them rather than trusting the application alone. At the type level, declaring a column INT or DATE rejects values of the wrong shape before they ever enter. At the constraint level, NOT NULL forbids missing values, UNIQUE forbids duplicates, CHECK enforces a range such as age BETWEEN 0 AND 150, and a foreign key refuses any reference to a non-existent parent. At the transaction level, ACID properties stop concurrent edits from corrupting each other. At the application level, input validation in the form (e.g. a dropdown instead of free text) prevents bad data at the source.

    The cost of weak integrity is high: a single duplicate customer row double-counts revenue; a null foreign key silently orphans an order; an unconstrained price of minus ten issues a refund by mistake. Defensive design spends a little effort on constraints now to avoid expensive cleanup and wrong reports later. The principle examiners want you to state is that the database, not just the app, should enforce the rules, because many applications may share one database and any one of them could introduce bad data.

    Exam tip

    If asked how to keep data valid, list the layers in order: data type, then constraints (NOT NULL / UNIQUE / CHECK / FK), then transactions, then application validation. Mentioning that the DBMS enforces rules for every user of the data is what earns the top mark.

    NULL handling in aggregates and joins

    Aggregates ignore NULLs: AVG(mark) divides by the count of non-null marks, not the row count, so a class with some missing marks is averaged correctly over those who have one. COUNT(*) counts rows including NULLs; COUNT(mark) excludes them. In outer joins, unmatched rows show NULL in the right-side columns; a later WHERE right.col = 5 would drop them, quietly turning your outer join back into an inner join — a classic trap. Filter on the join condition (ON) if you want to keep unmatched rows.

    Scaling, sharding, and evaluating database technologies

    Databases grow. Vertical scaling (a bigger server: more CPU, RAM, faster disk) is simple but hits a ceiling and creates a single point of failure. Horizontal scaling spreads data across many commodity servers. Two patterns dominate: replication, where every node holds a full copy, improving read throughput and availability but making writes expensive because all copies must stay in sync; and sharding, where each node holds a slice of the rows (e.g. customers whose id hashes to a range), improving both read and write throughput but complicating queries that span shards and making rebalancing hard.

    Consistency models matter here. A strongly consistent store makes every reader see the latest write but may stall during a network partition. An eventually consistent store (common in NoSQL) accepts that replicas may briefly disagree but converge; this trades correctness-in-the-instant for availability and partition tolerance, exactly the CAP trade-off. For a banking ledger you choose consistency; for a "like" counter on a social post you choose availability.

    Worked — picking a technology

    Scenario: a global game stores player scores, needs to scale to millions of writes per second, and can tolerate a score being a second out of date. Choice: a distributed key-value or column-family NoSQL store with eventual consistency, sharded by player region. Reason: the write volume rules out a single relational server; the staleness tolerance makes eventual consistency acceptable; sharding gives the needed throughput. A relational ACID store would be overkill and a bottleneck here.

    Relational algebra, modelling notation, and exam technique

    Relational algebra is the formal foundation beneath SQL; every SQL query is an algebra expression executed by the engine. The core operators:

    OperatorMeaningSQL analogue
    σ (select)Rows where condition holdsWHERE
    π (project)Keep listed columnsSELECT columns
    ⋈ (join)Combine on a matchJOIN ... ON
    ∪, ∩, −Union, intersect, differenceUNION/INTERSECT/EXCEPT

    A query such as "names of students in CS" is π name (σ title='CS' (student ⋈ enrolment ⋈ course)). Understanding algebra helps you see that a join then filter is the same as filtering then joining — and which is cheaper.

    ER notation variants

    Two notations appear: Chen (entities as rectangles, relationships as diamonds, attributes as ovals) and crow's foot (entities as boxes, relationships as lines with endpoints showing cardinality: one, many, optional). Learn to read both; the IB often uses crow's foot. The cardinality marks — | (one), crow's foot (many), circle (zero/optional) — tell you exactly how to build the FK and whether it is nullable.

    Note

    A many-to-many must become a junction table; a one-to-many puts the FK on the many side; a one-to-one can merge or put FK on either side. Reading the cardinality correctly is the difference between a right and wrong schema.

    Quick reference: SQL cheat sheet

    SELECT col1, agg(col2)
FROM t1 JOIN t2 ON t1.id = t2.fid
WHERE condition
GROUP BY col1
HAVING agg(col2) > n
ORDER BY col1 DESC
LIMIT k;

INSERT INTO t (c1, c2) VALUES (v1, v2);
UPDATE t SET c1 = v WHERE condition;
DELETE FROM t WHERE condition;
CREATE INDEX idx ON t (col);

    Memorise this skeleton; almost every exam SQL question is a variation of it. The most-missed clauses are HAVING (for grouped filters) and the ON condition (to avoid a cartesian product).

    One-paragraph mental model

    A database is a structured, shared, persistent collection of data managed by a DBMS that enforces integrity through keys, constraints, and transactions, serves many applications through a query language, and can be scaled by replication or sharding while trading consistency for availability via CAP. Design it by modelling entities and relationships, normalising to remove anomalies, indexing for the hot queries, and protecting it with least privilege and parameterised queries. Keep that sentence in mind and every topic on this page slots into place.

    Exam tip

    You do not need to memorise every SQL dialect quirk. You need: the relational vocabulary, 1NF/2NF/3NF with a worked decomposition, the core SQL skeleton, ACID with an example, indexing trade-offs, normalisation purpose, and a one-line NoSQL comparison. Those cover the vast majority of database marks.

    Audit trails, change data capture, and the human side

    Beyond constraints, organisations often need to know who changed what and when. An audit trail is a log of changes — typically implemented with a trigger that, on every update or delete, writes the old and new row plus the user and timestamp to a history table. This supports accountability, forensic investigation, and regulatory compliance (e.g. finance and health records). Change data capture (CDC) streams those changes to another system (a warehouse or search index) so analytics and caches stay nearly current without re-querying the source.

    The human side matters too: a database is only as good as the discipline of the people using it. Backups that are never tested may fail to restore; a schema change made without review can break three applications; a password reused across admins invites breach. Good practice adds process — code review for schema migrations, least-privilege accounts for each app, and documented recovery drills — on top of the technical controls.

    Exam tip

    If a question mentions accountability or compliance, reach for audit trails and logging; if it mentions keeping a report system fresh, reach for CDC or replication. These are the "real world" extensions examiners use to stretch a strong candidate beyond the textbook definitions.

    Test yourself rapidly: primary key (uniquely identifies a row), foreign key (references a PK elsewhere), 3NF (no transitive dependency), index (speeds lookup, costs writes), transaction (atomic unit of work), ACID (the four guarantees), view (saved query), trigger (auto-action on change), shard (horizontal data split), CAP (consistency/availability/partition trade-off).     Why databases matter: the big picture

    It is worth stepping back. A database is the memory of an organisation. Without one, every program keeps its own copy of data, copies drift apart, and no one trusts the numbers. The relational model's genius is to store data once, in tables, linked by keys, so that a single update propagates everywhere it is needed and a single query can answer questions no one anticipated at design time. Normalisation protects that single source of truth from anomalies; transactions protect it from concurrent corruption; constraints protect it from bad input; backups protect it from disaster; and a well-chosen index keeps it fast. NoSQL relaxes the model when scale or flexibility outrank strict consistency. Understanding this story — not just the definitions — is what turns a list of terms into real database literacy, and it is exactly the perspective examiners reward in evaluation questions.

    If you remember only one sentence: a database stores data once, links it by keys, and uses keys, constraints, transactions, and indexes to keep it correct, consistent, and fast. Everything on this page is a detail of that idea.

    Self-check

    1. Explain the difference between a primary key and a foreign key, and state whether a foreign key must be unique.

      Show answer
      A primary key uniquely identifies each row in its own table and cannot be null. A foreign key holds the primary key of a different table and is the link between them. A foreign key is usually NOT unique — e.g. many enrolment rows share one studentID. Only the PK (and candidate keys) are unique.

    2. A school has students and clubs, where each student joins many clubs and each club has many students. How do you model this, and why?

      Show answer
      It is many-to-many, so you cannot store it in either table with one column. Create a link table Membership(studentID, clubID, joinedDate) with FKs to Student and Club. This resolves the M:N into two one-to-many relations and is the standard design move.

    3. A table has PK (orderID, productID) and also stores productName. Is it in 2NF? What do you do?

      Show answer
      No. productName depends only on productID, part of the composite key — a partial dependency, so it violates 2NF. Move productName into a Product(productID, productName) table and keep only productID (as FK) in the order table. (Assuming 1NF otherwise held.)

    4. Write SQL to find the name of every student with an average grade above 70 across all their modules.

      Show answer 
      SELECT s.name, AVG(e.grade) AS g
FROM Enrol e
JOIN Student s ON e.studentID = s.studentID
GROUP BY s.studentID, s.name
HAVING AVG(e.grade) > 70;
      The average is computed per student with GROUP BY, and HAVING filters the group — WHERE cannot see AVG.

    5. Why does WHERE AVG(grade) > 60 fail, and what is the correct clause?

      Show answer
      AVG is an aggregate that exists only after GROUP BY has run, but WHERE filters raw rows before grouping, so it cannot see AVG — it is a syntax error. The correct clause is HAVING AVG(grade) > 60, which filters groups after they are formed.

    6. Name the four ACID properties and say what atomicity protects against.

      Show answer
      Atomicity (all-or-nothing), Consistency (valid state to valid state), Isolation (concurrent transactions don't see half-done work), Durability (committed changes survive crashes). Atomicity protects against a failure part-way through a multi-step operation — e.g. a crash between debiting and crediting leaves no money lost, because the whole transaction rolls back.

    7. What is a database index, and why would you not index every column?

      Show answer
      An index (usually a B-tree) on a column speeds up lookups and joins from O(n) to O(log n) by letting the engine find rows without a full scan. You would not index every column because each index must be updated on every INSERT/UPDATE/DELETE, slowing writes, and indexes consume storage. Index only columns you search or join on often.

    8. At a general level, contrast a relational (SQL) database with a document-store NoSQL database.

      Show answer
      Relational: fixed schema, tables linked by keys, strong ACID consistency, scales vertically, uses JOINs. Document NoSQL: flexible/variable schema, data stored as nested documents that embed related data instead of joining, often scales horizontally and offers eventual rather than strict consistency. The trade is flexibility/scale vs strong consistency and structure.
