A3 · Databases

A database is not a spreadsheet with extra steps. It is a claim about the world — "every order belongs to exactly one customer", "no two books share an ISBN" — enforced by software so that the claim stays true no matter how many people use the system at once. This topic teaches you to turn a messy real situation into tables that cannot contradict themselves, and then to ask questions of those tables in SQL. Get it right and the exam questions are the most mechanical marks available in Paper 1.

Theme A · examined in Paper 1; SQL may appear in Paper 2 A3.1 Fundamentals · A3.2 Design · A3.3 Programming · A3.4 Alternative databases (HL) HL only: A3.4 Alternative databases and data warehouses

A3.1 · Why databases rather than flat files

A flat file is a single table holding everything — the shape a spreadsheet naturally takes. Suppose a small bookshop keeps this:

OrderIDOrderDateCustomerNameCustomerEmailCityBookTitleAuthorNameAuthorNationalityQtyUnitPrice
10012026-03-02A. Chena.chen@x.comShanghaiDuneF. HerbertAmerican112.99
10012026-03-02A. Chena.chen@x.comShanghaiEmmaJ. AustenBritish28.50
10022026-03-03L. Moreaul.m@x.comLyonDuneF. HerbertAmerican112.99
10032026-03-05A. Chena.chen@x.comShanghaiEmmaJ. AustenBritish18.50

Now exercise it. These five problems are the standard answer, and each has a name.

1 · Redundancy ()

"F. Herbert — American" is stored three times, and A. Chen's address four. The file is bigger than it needs to be, and every duplicate is a copy that can drift out of step with the others.

2 · Update anomaly ()

A. Chen moves to Beijing. You must find and change every row containing her name. Miss one and the database now says she lives in two cities — and nothing in the file can detect the contradiction.

3 · Insertion anomaly ()

You want to add a new book that nobody has ordered yet. There is nowhere to put it, because a row only exists as part of an order. You are forced to invent a fake order, or leave the book out of the system.

4 · Deletion anomaly ()

Order 1001 is the last order containing Dune. Cancel it and you delete the only record that Dune exists, who wrote it, and what it costs — information that had nothing to do with that order.

5 · No integrity and no concurrency

Nothing in a flat file prevents two different spellings of the same author, a quantity of −3, an order with no customer, or two users overwriting each other's edits. A DBMS can enforce all of those.

Plus: no independent access

Every question ("which books has A. Chen bought?") requires a bespoke program. A database offers one declarative language — SQL — that answers any question you can phrase, without writing new code.

Why this is the real motivation, stated precisely

Notice that all four anomalies come from the same root cause: one row mixes facts about several different things (an order, a customer, a book, an author). Because the facts are tangled, you cannot record one of them without the others, change one without hunting the others, or remove one without destroying the others. Normalisation is not a tidying ritual — it is the process of untangling those facts so that each fact lives in exactly one place. Once each fact has one home, update means "change one row", insert means "add the thing you know", and delete means "remove the thing you no longer need". That is the whole payoff.

Keys — the four kinds you must distinguish

Candidate key
Any attribute, or minimal set of attributes, that uniquely identifies a tuple. Minimal matters: if {StudentID} already works, then {StudentID, Name} is a superkey but not a candidate key, because you could drop Name and still be unique.
Primary key
The candidate key chosen to be the official identifier. Must be unique and never null. It may be a surrogate key — an artificial ID invented by the designer (auto-increment integer) — which is usually better than a natural key because real-world identifiers (names, emails, even ISBNs) can change or be mistyped.
Composite (compound) key
A primary key made of two or more attributes because no single one is unique. In an order-line table, {OrderID, BookID} identifies a row: an order can contain many books and a book can appear in many orders, but the pair occurs once.
Foreign key
An attribute in one table that is the primary key in another, creating a link. It is the mechanism by which relations are, well, relational.
Referential integrity
The rule that every foreign key value must either match an existing primary key value in the referenced table or be null. It is what stops the database containing an order for a customer who does not exist.
Trap — "a foreign key is a link" is not enough

An exam answer that says "a foreign key links two tables" earns one mark. The full answer: it is an attribute whose values are drawn from the primary key of another table; it establishes the relationship; and the DBMS enforces referential integrity on it, which prevents (i) inserting a child row whose parent does not exist, (ii) deleting a parent row that still has children, and (iii) changing a primary key value while children still point at the old one. Naming those three behaviours is where the marks are.

A3.2 · Entity–relationship modelling

An entity is a thing the organisation needs to store data about (Customer, Book, Order). An attribute is a property of an entity. A relationship is an association between entities. Three relationship types, and one of them cannot be implemented directly.

TypeMeaningExampleHow it is implemented
One to one (1:1)Each instance of A relates to at most one of B, and vice versaEach employee has one parking spacePut the foreign key in either table; often the two should simply be merged into one table unless there is a reason to separate them (security, optional data)
One to many (1:M)One instance of A relates to many of B; each B relates to one AOne customer places many orders; each order belongs to one customerPut the one side's primary key into the many side's table as a foreign key — i.e. CustomerID goes into Order
Many to many (M:N)Each A relates to many B and each B to many AAn order contains many books; a book appears in many ordersCannot be implemented directly. It must be resolved with a third, link (junction / associative) table
Proof Why a many-to-many relationship cannot be stored in either table
  1. Suppose we try to store the books in an order by adding BookID to the Order table. One order contains three books, so we need three BookID values in one row — that means either repeated columns (BookID1, BookID2, BookID3), which is not first normal form, or three copies of the whole order row, which reintroduces the redundancy we were trying to remove.
  2. Symmetrically, storing OrderID in the Book table needs one value per order that ever contained that book — the same problem in the other direction.
  3. A relational table has a fixed number of columns and each cell holds one atomic value. No arrangement of columns can hold a variable-length set of references.
  4. But a row can hold a pair: (OrderID, BookID). So we create a new table whose rows are exactly those pairs. The many-to-many becomes two one-to-many relationships with the link table in the middle — and the link table is also the natural home for facts about the pair, such as quantity and the price charged.

What it means: the link table is not a workaround or a convention — it is forced by the structure of a relation. When it is the wrong tool: if the relationship genuinely has no attributes and is strictly one-to-many, adding a link table is over-engineering.

Normalisation — 1NF, 2NF, 3NF on the same scenario

Normalisation is a sequence of tests. At each stage you ask one question, and if the answer is "no", you split the table and repeat.

How to use it — the three tests in plain language
  1. 1NF: Is every cell a single, atomic value, and are there no repeating groups of columns? If a row contains several values in one field, or columns like Phone1, Phone2, Phone3, split them out into separate rows or a separate table.
  2. 2NF: Is the table in 1NF, and does every non-key attribute depend on the whole primary key — not just part of it? This question only bites when the key is composite. A partial dependency (depends on part of the key) must be removed into its own table.
  3. 3NF: Is the table in 2NF, and does every non-key attribute depend on the key, the whole key, and nothing but the key? A transitive dependency (A → B → C, so non-key C depends on non-key B) must be removed into its own table.

The mnemonic is real: "the key, the whole key, and nothing but the key, so help me Codd."

Step 0 — the unnormalised file

Start with the flat file from the top of the page, but in its true form: one row per order, with the ordered books crammed into a repeating group. This is not in 1NF.

OrderIDOrderDateCustomerNameCityDeliveryZoneBooks ordered (repeating group)
10012026-03-02A. ChenShanghaiEastDune (×1, 12.99, F. Herbert, American); Emma (×2, 8.50, J. Austen, British)
10022026-03-03L. MoreauLyonWestDune (×1, 12.99, F. Herbert, American)

Step 1 — first normal form

Remove the repeating group: each order–book pair becomes its own row, and every cell holds one atomic value. Choose the composite primary key {OrderID, BookTitle} (we will replace the title with an ID shortly).

OrderIDBookTitleOrderDateCustomerNameCityDeliveryZoneAuthorNameAuthorNationalityQtyUnitPrice
1001Dune2026-03-02A. ChenShanghaiEastF. HerbertAmerican112.99
1001Emma2026-03-02A. ChenShanghaiEastJ. AustenBritish28.50

Now in 1NF. But look at what 1NF has and has not fixed. The anomalies are all still there — A. Chen's city is still repeated, and cancel the last Dune order and Dune disappears.

Step 2 — second normal form

The key is composite, so ask: does each non-key attribute need both parts of the key to be determined?

  • Qty? Yes — the quantity is a fact about (this order, this book). ✓ full dependency.
  • OrderDate, CustomerName? These depend on OrderID alone — a partial dependency. ✗
  • UnitPrice, AuthorName? These depend on BookTitle alone — also partial. ✗

Remove the partial dependencies into their own tables, keyed by the part of the key they depend on.

ORDER

OrderID (PK), OrderDate, CustomerID (FK)
one row per order

BOOK

BookID (PK), Title, UnitPrice, AuthorID (FK)
one row per book

ORDERLINE

OrderID (PK, FK), BookID (PK, FK), Quantity, PriceCharged
one row per book within an order

What 2NF removed: the insertion anomaly for books (a book can now exist with no orders), the deletion anomaly for books (cancelling an order no longer destroys the book), and the redundancy of repeating the book's price and author on every order line. It also fixed the anomaly that you cannot record an order with no lines yet.

Step 3 — third normal form

Now hunt transitive dependencies in the new tables: a non-key attribute determined by another non-key attribute.

  • In BOOK: BookID → AuthorID → AuthorNationality. Nationality is a fact about the author, not about the book. Transitive. ✗
  • In ORDER → CUSTOMER: CustomerID → City → DeliveryZone. The delivery zone is a fact about the city, not about the customer. Transitive. ✗

What 3NF removed: the transitive dependencies. Author nationality is now stored once per author, so correcting an author's details means one row; a delivery zone is stored once per city, so changing the zone for Shanghai means one row. And critically, you can now record a city's zone before any customer lives there.

Exam technique — how to present a normalisation answer

Examiners do not want prose; they want tables. For each form: (1) state the rule; (2) identify the specific dependency that violates it, naming the attributes; (3) draw the resulting table(s) with the primary key underlined or labelled PK and foreign keys labelled FK. A student who writes "there is a partial dependency so we split the table" without saying which attribute depends on which part of the key loses the identification mark every time.

Worked example 1 IB-style · 9 marks · full normalisation from a description

Question. A school records music lessons. The single table below is used. Each pupil has one instrument teacher; each teacher teaches one instrument and charges a fixed hourly rate.

Lesson(PupilName, PupilForm, TeacherName, Instrument, HourlyRate, LessonDate, Room, Grade)

Normalise to 3NF, stating the reason for each step.

  1. Is it in 1NF? Yes — every cell is atomic and there are no repeating groups. (If a pupil could take two instruments, the key would need both and PupilForm would repeat.)
  2. Choose the key. A pupil has one teacher, so one instrument; lessons differ by date. The key is {PupilID, LessonDate} (introduce PupilID — names are not unique).
  3. 2NF — partial dependencies. PupilForm depends on PupilID alone. TeacherName, Instrument, HourlyRate also depend on PupilID alone (because each pupil has one teacher). Grade depends on the whole key (a pupil's grade at a particular date). Room depends on the whole key.
  4. Split for 2NF: PUPIL(PupilID PK, PupilName, PupilForm, TeacherID FK) and LESSON(PupilID PK FK, LessonDate PK, Room, Grade).
  5. 3NF — transitive dependencies. In PUPIL: PupilID → TeacherID → Instrument and HourlyRate. Instrument and HourlyRate are facts about the teacher, not the pupil, so they must move — otherwise changing a teacher's rate means editing every pupil row for that teacher.
  6. Split for 3NF: TEACHER(TeacherID PK, TeacherName, Instrument, HourlyRate) and PUPIL(PupilID PK, PupilName, PupilForm, TeacherID FK). LESSON is already in 3NF (Room and Grade depend on the whole key and on nothing else).
  7. Final answer: PUPIL, TEACHER, LESSON with TeacherID as a foreign key in PUPIL and PupilID as a foreign key in LESSON.
Marks: 1 for stating 1NF is already satisfied (or correcting it if not), 1 for the key, 2 for identifying the partial dependencies by name, 2 for the 2NF tables, 2 for identifying the transitive dependency, 1 for the final 3NF tables. Naming PupilID as a surrogate key is a mark-winner: it shows you know names are not unique.

A3.3 · SQL in depth

SQL is declarative: you say what you want, not how to find it. That is the single most important idea, and it explains why SQL is short compared with the code you would write in B2 to do the same job.

CREATE TABLE — types and constraints

CREATE TABLE Book (
 BookID INTEGER PRIMARY KEY,
 Title VARCHAR(80) NOT NULL,
 UnitPrice DECIMAL(6,2) NOT NULL CHECK (UnitPrice >= 0),
 AuthorID INTEGER NOT NULL,
 FOREIGN KEY (AuthorID) REFERENCES Author(AuthorID)
);

CREATE TABLE OrderLine (
 OrderID INTEGER,
 BookID INTEGER,
 Quantity INTEGER NOT NULL DEFAULT 1 CHECK (Quantity > 0),
 PriceCharged DECIMAL(6,2) NOT NULL,
 PRIMARY KEY (OrderID, BookID), -- composite key
 FOREIGN KEY (OrderID) REFERENCES OrderT(OrderID) ON DELETE CASCADE,
 FOREIGN KEY (BookID) REFERENCES Book(BookID)
);

Constraints are the point, so learn what each earns you: PRIMARY KEY gives uniqueness and non-null; FOREIGN KEY gives referential integrity; NOT NULL forces a value; CHECK restricts the domain; DEFAULT supplies one when none is given; UNIQUE allows nulls but forbids duplicates. ON DELETE CASCADE says: if the parent order is deleted, delete its lines too — otherwise the delete is rejected.

Trap — ORDER is a reserved word

ORDER is an SQL keyword (ORDER BY), so a table called Order must be quoted or renamed — in the examples above I used OrderT. Related traps: VARCHAR without a length is invalid in some dialects; DECIMAL(6,2) means six digits total with two after the point, so it stores up to 9999.99 — money should never be a FLOAT because of the representation error covered on the A1 page; and NULL is not zero or an empty string, it is "unknown", so WHERE price = NULL never matches — you need WHERE price IS NULL.

INSERT, SELECT, and the WHERE clause

INSERT INTO Author (AuthorID, AuthorName, Nationality)
VALUES (1, 'F. Herbert', 'American'),
 (2, 'J. Austen', 'British');

SELECT Title, UnitPrice FROM Book WHERE UnitPrice > 10 ORDER BY UnitPrice DESC;

Comparison operators: =, <> or !=, <, >, <=, >=. Combine with AND, OR, NOT. Pattern matching uses LIKE with % for any run of characters and _ for exactly one.

-- titles beginning with D
SELECT Title FROM Book WHERE Title LIKE 'D%';
-- authors whose name has 'er' anywhere
SELECT AuthorName FROM Author WHERE AuthorName LIKE '%er%';
-- second character is 'u'
SELECT Title FROM Book WHERE Title LIKE '_u%';
Trap — AND binds tighter than OR

WHERE City = 'Shanghai' OR City = 'Lyon' AND Zone = 'East' means "Shanghai (regardless of zone), or Lyon and East". If you meant "either city, but only East", you need parentheses: WHERE (City = 'Shanghai' OR City = 'Lyon') AND Zone = 'East'. Whenever you mix AND and OR, add the brackets even if you think they are unnecessary.

Aggregate functions, GROUP BY and HAVING

SELECT COUNT(*) AS NumBooks,
 SUM(Quantity) AS TotalCopies,
 AVG(PriceCharged) AS AvgPrice,
 MIN(PriceCharged) AS Cheapest,
 MAX(PriceCharged) AS Dearest
FROM OrderLine;

Without GROUP BY, an aggregate collapses the whole table to one row. With it, you get one row per group:

SELECT BookID, SUM(Quantity) AS CopiesSold
FROM OrderLine
GROUP BY BookID;

-- only groups that pass a condition on the aggregate
SELECT BookID, SUM(Quantity) AS CopiesSold
FROM OrderLine
GROUP BY BookID
HAVING SUM(Quantity) > 5;
How to use it — WHERE vs HAVING, the rule you must know cold

WHERE filters rows before grouping; it cannot refer to an aggregate. HAVING filters groups after aggregation; it is almost always used with an aggregate. So: "orders placed in 2026 by customers who spent more than 200" needs WHERE OrderDate >= '2026-01-01' and HAVING SUM(...) > 200 — both, in that order. A question that asks "which books sold more than five copies" is a HAVING question; one that asks "how many copies of book 4 sold" is a WHERE question.

Exam technique — the "list all students and the number of books they borrowed" question

The word all is the tell. If you write SELECT ... FROM Student s, Loan l WHERE s.StudentID = l.StudentID GROUP BY ... you have written an inner join and every student with no loans vanishes — and you lose a mark for the wrong join plus a mark for the missing zero rows. The correct answer is LEFT JOIN with COUNT(l.LoanID), not COUNT(*), because COUNT(*) counts the NULL-padded row and returns 1 instead of 0. That single distinction — COUNT(column) skips nulls, COUNT(*) does not — is examined frequently.

UPDATE, DELETE, ALTER, DROP

UPDATE Book SET UnitPrice = UnitPrice * 1.05 WHERE AuthorID = 1;
DELETE FROM OrderLine WHERE Quantity = 0;
ALTER TABLE Book ADD COLUMN ISBN VARCHAR(13);
DROP TABLE OrderLine;
Trap — UPDATE and DELETE without WHERE

UPDATE Book SET UnitPrice = 9.99; changes every book. DELETE FROM OrderLine; empties the table. In an exam, a question showing a destructive statement without a WHERE is very often asking you to spot exactly that. Also note the hierarchy: DROP removes an entire table (structure and data), DELETE removes rows (structure intact, and it can be rolled back inside a transaction), and TRUNCATE removes all rows quickly but usually cannot be rolled back.

Transactions, concurrency and deadlock

A transaction is a sequence of operations treated as a single unit. It must satisfy ACID:

Atomicity
All of it happens or none of it does. Transferring money is a debit and a credit; if the credit fails after the debit succeeded, the money has vanished.
Consistency
The database moves from one valid state to another; constraints are satisfied before and after.
Isolation
Concurrent transactions do not see each other's partial work, so their effect is as if they had run one at a time — this is serialisability.
Durability
Once committed, the change survives a crash — which is why the DBMS writes to a log before confirming the commit.
Why Why concurrent access needs locking — the lost update problem
  1. Two customers buy the last copy of a book at the same moment. Both transactions read Stock = 1.
  2. Both compute Stock − 1 = 0 and both write 0. Result: one copy sold, stock reduced by one — fine. But now suppose both compute on a shared value and write back: transaction A reads 10, adds 2, writes 12; transaction B reads 10, adds 5, writes 15. A's update is lost.
  3. The general name is the lost update problem, and it exists whenever read-modify-write is interleaved.
  4. The fix is record locking: a transaction takes a lock on the rows it modifies and holds it until it commits, so the second transaction must wait rather than read a stale value.
  5. Shared (read) locks can be held by many readers at once; an exclusive (write) lock excludes everyone. That is the standard compromise: many readers, one writer.

What it means: serialisability is the correctness property, locking is the mechanism, and the cost is reduced concurrency — the more you lock, the more transactions queue.

Why Why deadlock happens and how a DBMS resolves it
  1. Transaction A locks the Customer row and then requests the Order row. Transaction B locks the Order row and then requests the Customer row.
  2. Each now holds a resource the other needs and neither can proceed. This is deadlock.
  3. There are four conditions for deadlock (mutual exclusion, hold-and-wait, no preemption, circular wait); break any one and deadlock becomes impossible.
  4. Real systems usually allow it and detect it: the DBMS builds a wait-for graph, looks for a cycle, and when it finds one aborts one transaction (the victim — usually the younger or cheaper one), rolls it back, releases its locks and lets the other proceed. The victim's application is told to retry.
  5. Prevention alternatives: acquire all locks in a fixed global order (breaks circular wait) or take all locks at transaction start (breaks hold-and-wait) — both reduce concurrency, which is why detection is usually preferred.

What it means: a deadlock is not a bug in your SQL; it is an inherent consequence of locking, so applications must handle a "deadlock victim" error by retrying.

Backup, recovery, integrity and validation

Backup and recovery

A full backup copies everything; an incremental backup copies only what changed since the last backup; a differential copies everything since the last full backup. Combined with the transaction log, a DBMS can restore to a precise moment (point-in-time recovery). Backups must be stored off-site or in another region, and — critically — must be restored regularly in a test, because an untested backup is not a backup.

Integrity vs validation

Validation checks input at entry: a range check, a type check, a presence check, a format check (regular expression), a length check, a check digit. Integrity is a property of the stored data: entity integrity (primary keys unique and not null), referential integrity (foreign keys match), and domain integrity (values within the declared type and constraints). Validation prevents bad data arriving; integrity constraints guarantee the stored data stays coherent even when a bug lets something through.

Database security

Least privilege — each application account gets only the permissions it needs. Views can expose a subset of columns or rows. Parameterised queries prevent SQL injection. Encryption at rest and in TLS in transit. Auditing records who changed what. And physical security of the server room, because an attacker with the disk owns the data.

Why data must be validated twice

Client-side validation improves the user experience but can be bypassed entirely by sending a request directly to the server. Server-side validation is the one that matters. Both should exist; only one is a security control.

Worked example 2 IB-style · 8 marks · write SQL from a scenario

Question. Using the bookshop tables, write SQL to: (a) list the title and unit price of every book by a British author, cheapest first; (b) find how many copies of each book have been sold, including books that have never been sold; (c) find the names of customers who have placed no orders; (d) increase by 10 % the price of every book that has sold fewer than 3 copies in total.

  1. (a) needs Author and Book joined:
SELECT b.Title, b.UnitPrice
FROM Book b
JOIN Author a ON b.AuthorID = a.AuthorID
WHERE a.Nationality = 'British'
ORDER BY b.UnitPrice ASC;

(b) "including books never sold" signals a LEFT JOIN from Book, and must count the joined column so unsold books give 0, not 1:

SELECT b.Title, COALESCE(SUM(o.Quantity), 0) AS CopiesSold
FROM Book b
LEFT JOIN OrderLine o ON b.BookID = o.BookID
GROUP BY b.BookID, b.Title;

(c) "no orders" — a LEFT JOIN and then filter for the NULL, or use NOT IN:

SELECT c.Name
FROM Customer c
LEFT JOIN OrderT o ON c.CustomerID = o.CustomerID
WHERE o.OrderID IS NULL;

(d) needs a subquery, because you cannot mix an aggregate into an UPDATE's WHERE without one:

UPDATE Book
SET UnitPrice = UnitPrice * 1.10
WHERE BookID IN (
 SELECT o.BookID
 FROM OrderLine o
 GROUP BY o.BookID
 HAVING SUM(o.Quantity) < 3
);
Where the marks are: (a) 2 — the JOIN and the ORDER BY; (b) 2 — the LEFT JOIN and the correct handling of zero; (c) 2 — LEFT JOIN plus IS NULL; (d) 2 — the subquery with GROUP BY and HAVING. In (b), COUNT(*) instead of SUM or COALESCE is the single most common lost mark on this question type.

A3.4 · Alternative databases and data warehouses HL only

The relational model assumes structured data with a stable schema, and it enforces consistency strongly. Those assumptions are exactly what some modern applications cannot accept. Non-relational ("NoSQL") stores relax something in exchange for something else.

TypeHow it stores dataRelaxesBest forExample
DocumentRecords as self-describing documents (usually JSON), grouped in collections; each document may have different fields A fixed schema, and joins Content management, catalogues, user profiles — anything whose fields vary between records or change oftenMongoDB, CouchDB

Why NoSQL exists — the CAP trade-off, in plain terms

Once you replicate data across machines in different locations, a network fault can partition the system into two halves that cannot see each other. Then you must choose: keep answering queries in both halves and accept that they may briefly disagree (availability over consistency), or refuse to answer in the minority half until the partition heals (consistency over availability). You cannot have both under partition — that is the CAP theorem. Relational databases traditionally chose consistency; many NoSQL stores choose availability and accept eventual consistency — the copies converge when the network recovers. For a bank balance, eventual consistency is unacceptable. For a social media like counter, it is obviously fine. Choosing a database is therefore choosing where you sit on that trade-off.

Data warehouses

A database is optimised for running the business now: many small, fast, concurrent reads and writes on current data (OLTP — online transaction processing). A data warehouse is optimised for analysing the business over time: huge reads across historical data (OLAP — online analytical processing).

Operational databaseData warehouse
PurposeDay-to-day transactionsAnalysis, reporting, decision support
DataCurrent, detailed, updated constantlyHistorical, aggregated, appended periodically
DesignHighly normalised (3NF) to avoid update anomaliesDeliberately denormalised (star/snowflake schema) to make queries fast and simple
WorkloadMany short reads and writesFew, very large read queries
Update patternINSERT/UPDATE/DELETE all the timeBulk load via ETL (extract, transform, load) on a schedule; data is rarely updated or deleted

Notice the apparent contradiction, because it is a favourite exam point: we normalise the operational database and then denormalise for the warehouse. There is no inconsistency — normalisation optimises for correctness under update, denormalisation optimises for speed of reading, and a warehouse is written once and read a great deal.

In a star schema, a central fact table (one row per sale, say, holding the numeric measures and foreign keys) is surrounded by dimension tables (Customer, Product, Date, Store) holding the descriptive attributes you group and filter by. The shape is the query pattern made physical.

Practice

  1. State three problems caused by storing data in a single flat file, and name each one.

    Show answer

    Any three of: redundancy — the same fact is stored repeatedly, wasting space; update anomaly — changing one fact requires changing many rows, and a missed row leaves contradictory data; insertion anomaly — a fact cannot be recorded because other unrelated facts are missing; deletion anomaly — removing one fact destroys another; plus the absence of enforced integrity and of concurrency control. Names matter: an unnamed problem scores less.

  2. Explain the difference between a primary key, a candidate key and a foreign key.

    Show answer

    A candidate key is any minimal set of attributes that uniquely identifies a row. The primary key is the one candidate key chosen to identify rows officially; it must be unique and not null, and there is exactly one per table. A foreign key is an attribute in one table that holds the primary key value from another table, thereby creating the relationship between them and enabling the DBMS to enforce referential integrity.

  3. Explain why a many-to-many relationship cannot be implemented directly in a relational database, and describe how it is resolved.

    Show answer
    1. A relational table has a fixed number of columns and each cell holds one atomic value, so there is no way to store a variable-length set of references in a row.
    2. Putting the foreign key in either table would require repeating columns (not 1NF) or duplicating the whole row (reintroducing redundancy).
    3. Resolution: create a third link table whose rows are the pairs, with a composite primary key made of the two foreign keys.
    4. That converts one many-to-many into two one-to-many relationships, and the link table is also the natural home for attributes that belong to the pair — quantity, price charged, date borrowed.

  4. The table Employee(EmpID, EmpName, DeptID, DeptName, DeptPhone) is in 1NF. Normalise it to 3NF, stating the reason for each step.

    Show answer
    1. The key is EmpID, which is not composite, so there can be no partial dependency — the table is already in 2NF.
    2. Check 3NF: EmpID → DeptID, and DeptID → DeptName, DeptPhone. So DeptName and DeptPhone depend on a non-key attribute — a transitive dependency.
    3. Split it out: DEPARTMENT(DeptID PK, DeptName, DeptPhone).
    4. Result: EMPLOYEE(EmpID PK, EmpName, DeptID FK) and DEPARTMENT(DeptID PK, DeptName, DeptPhone).
    5. Why it matters: a department's phone number is now stored once, so changing it is one row; and a new department can be created before it has any employees (removing an insertion anomaly).

  5. Write SQL to list each customer's name together with the total value of their orders, for customers who have ordered, highest total first.

    Show answer
    SELECT c.Name, SUM(o.Total) AS TotalSpent
FROM Customer c
JOIN OrderT o ON c.CustomerID = o.CustomerID
GROUP BY c.CustomerID, c.Name
ORDER BY TotalSpent DESC;

    Points: an INNER JOIN is correct here because the question says "who have ordered"; GROUP BY must include every non-aggregated selected column; and you may order by the alias.

  6. Explain the difference between WHERE and HAVING, and give an example of a question that needs each.

    Show answer

    WHERE filters individual rows before any grouping takes place and cannot contain an aggregate. HAVING filters groups after aggregation and is normally used with an aggregate.

    Example needing WHERE: "list the orders placed after 1 March" — WHERE OrderDate > '2026-03-01'.

    Example needing HAVING: "list the books that have sold more than 10 copies" — GROUP BY BookID HAVING SUM(Quantity) > 10.

  7. Explain, using an example, what a lost update is and how record locking prevents it.

    Show answer
    1. Two transactions read the same value (say stock = 10) at the same time.
    2. Transaction A adds 2 and writes 12. Transaction B, working from the value it read earlier, adds 5 and writes 15.
    3. A's update is lost — the correct total, 17, was never reached.
    4. With a record lock, A takes an exclusive lock on the row before its update and holds it until commit, so B must wait until A finishes and then reads the new value 12 before adding 5, giving 17.
    5. The cost is that B is blocked, so throughput falls; and the risk of deadlock appears, which the DBMS resolves by aborting one transaction and forcing a retry.

  8. HL only A hospital wants to keep (i) live patient monitoring readings arriving thousands of times a second, and (ii) ten years of records for research. Discuss the choice of data store for each.

    Show answer
    1. (i) Live readings: extremely high write volume, time-stamped, append-only, queried by patient and time window. A wide-column store (Cassandra) or a dedicated time-series database suits this: it is built for massive sequential writes and range queries on a partition key, and it scales horizontally by adding nodes.
    2. A relational database would struggle with the write rate and would waste effort on features the data does not need (joins, transactions across rows, strong consistency between readings).
    3. (ii) Ten years of records for research: this is analytical — researchers run large, unpredictable queries over historical data. A data warehouse with a star schema is right: a fact table of measurements with dimension tables for patient, ward, device and date, loaded periodically by ETL from the operational systems.
    4. Denormalisation is appropriate here because the data is written once and read many times, so query speed matters more than update efficiency.
    5. Important qualification: patient identity and clinical records should stay in a strongly consistent relational store because correctness there is non-negotiable — the CAP trade-off is acceptable for sensor readings and not for who is allergic to what.
    Marks: one justified recommendation for each workload, one contrast between OLTP and OLAP, and one mark for the qualification that different data in the same organisation warrants different stores. A single recommendation for both halves of the question cannot reach the top band.
